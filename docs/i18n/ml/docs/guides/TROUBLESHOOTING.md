## വിശദമായ പ്രശ്നപരിഹാരം

---

### സൗജന്യ ദാതാക്കളിലെ നിരക്ക് പരിമിതി (429 / 400 / 401)

**ലക്ഷണം**: സൗജന്യ/പ്രാമാണീകരണം ആവശ്യമില്ലാത്ത ദാതാക്കൾക്കൊപ്പം (opencode, auggie മുതലായവ) `model: "auto"` ഉപയോഗിക്കുമ്പോൾ, ഉത്തരങ്ങൾക്ക് പകരം ഇടയ്ക്കിടെ `HTTP 429`, `400`, അല്ലെങ്കിൽ `401` ലഭിക്കുന്നു. ഏതാനും നിമിഷങ്ങൾക്കുശേഷം അതേ പ്രോംപ്റ്റ് വീണ്ടും ശ്രമിക്കുമ്പോൾ അഭ്യർത്ഥനകൾ വിജയിക്കുന്നുണ്ടെങ്കിലും, ആദ്യ പരാജയത്തിൽ ഓട്ടോമേഷൻ (cron ജോലികൾ, ഏജന്റുകൾ, സ്ക്രിപ്റ്റുകൾ) തകരുന്നു.

**അടിസ്ഥാന കാരണം**: സ്വതന്ത്രമായ മൂന്ന് പരാജയ രീതികൾ ഒന്നിനുമേൽ ഒന്നായി സംഭവിക്കുന്നു:

1. **ദാതാവിന്റെ നിരക്ക് പരിധി (`429`)**: സൗജന്യ ടയറുകൾക്ക് ഓരോ സമയജാലകത്തിനും ഒരു ക്വാട്ട നടപ്പിലാക്കാനാകും. സമാന്തര കോളുകളുടെ ഒരു കുതിച്ചുചാട്ടം അത് തീർക്കുന്നതിനാൽ, സമയജാലകം പുനഃസജ്ജമാകുന്നതുവരെ അടുത്ത അഭ്യർത്ഥന നിരസിക്കപ്പെടും.
2. **പാസ്ത്രൂവിലെ പ്രവർത്തനരഹിതമായ മോഡൽ (`400`/`401`)**: കാറ്റലോഗിൽ രജിസ്റ്റർ ചെയ്തിട്ടുണ്ടെങ്കിലും സജീവ ക്രെഡൻഷ്യലുകളില്ലാത്ത `opencode`-ൽ നിന്നുള്ള പാസ്ത്രൂ മോഡലുകൾ `auto/*` പൂളുകളിൽ ഉൾപ്പെടാം (ഉദാ. `oc/north-mini-code-free` → `401`). ഓട്ടോ-റൂട്ടർ ഒരെണ്ണം പരീക്ഷിക്കുകയും പരാജയപ്പെടുകയും ചെയ്യുന്നു; ഫാൾബാക്ക് പ്രാബല്യത്തിൽ വരുന്നതിനുമുമ്പ് പിശക് പുറത്തേക്ക് പ്രചരിക്കുന്നു.
3. **കൺകറൻസി വർധനം (ലോഡിലുള്ളപ്പോൾ `429`)**: ഒന്നിലധികം ഏജന്റ്/cron സെഷനുകൾ ഒരേസമയം `auto` ഉപയോഗിക്കുമ്പോൾ, മൊത്തം അഭ്യർത്ഥന നിരക്ക് സൗജന്യ ദാതാക്കൾക്ക് സഹിക്കാവുന്നതിനെ മറികടക്കുന്നു. അതിനാൽ നിയമാനുസൃതമായ കോളുകൾ പോലും ദുരുപയോഗമായി അടയാളപ്പെടുത്തപ്പെടുന്നു.

**സ്ഥിരീകരിച്ച പരിഹാരം (കമ്മ്യൂണിറ്റി റിപ്പോർട്ട് ചെയ്തത്, 2026-08-10)**: റൊട്ടേഷൻ, കൺകറൻസി, ഫാൾബാക്ക് എന്നിവ സൗജന്യ ടയറിലെ അസ്ഥിരത കാരണം പരാജയപ്പെടുന്നതിനുപകരം അതിനെ കൈകാര്യം ചെയ്യാൻ മൂന്ന് പരിസ്ഥിതി വേരിയബിളുകൾ ക്രമീകരിക്കുക:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ലഭിക്കുമ്പോൾ മറ്റൊരു മോഡൽ/ദാതാവിലേക്ക് മാറുക (പ്രവർത്തനരഹിതമായ പാസ്ത്രൂ മോഡലുകൾ ഒഴിവാക്കുന്നു)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ഹെവിവെയ്റ്റ് അഡ്മിഷനുള്ള വ്യക്തമായ പരമാവധി (സ്ഥിരസ്ഥിതിയായി സജ്ജീകരിച്ചിട്ടില്ല: അഭ്യർത്ഥനകളുടെ എണ്ണത്തിന് പരിധിയില്ല, താഴെയുള്ള കുറിപ്പ് കാണുക)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ഉടനടി വീണ്ടും ശ്രമിക്കാവുന്ന 503 നൽകുന്നതിനുപകരം ഹെവിവെയ്റ്റ് ശേഷിക്കായി കൂടുതൽ ദൈർഘ്യമുള്ള, പരിധിയുള്ള കാത്തിരിപ്പ്
```

OmniRoute പ്രോസസിന്റെ പരിസ്ഥിതിയിൽ (ഡീമണിൽ, ഉദാ. LaunchAgent plist അല്ലെങ്കിൽ `systemctl edit` വഴി) ഇവ സജ്ജീകരിച്ച ശേഷം OmniRoute പുനരാരംഭിക്കുക. റൊട്ടേഷൻ ഫ്ലാഗാണ് ഏറ്റവും കൂടുതൽ പ്രയോജനം നൽകുന്ന ഒറ്റ ക്രമീകരണം: ഇത് ഒരു കടുത്ത പരാജയത്തെ പൂളിലുള്ള ആരോഗ്യകരമായ ദാതാവിനെതിരായ സുതാര്യമായ പുനഃശ്രമമാക്കി മാറ്റുന്നു.

**കുറിപ്പ്**: ഒരേസമയം എത്ര ഹെവിവെയ്റ്റ് — ദൈർഘ്യമേറിയ കോൺടെക്സ്റ്റുള്ള — അഭ്യർത്ഥനകൾ പ്രവർത്തിക്കാമെന്ന് `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` നിയന്ത്രിക്കുന്നു; ഈ പരിധി ഒരു അഡ്മിഷൻ ഗേറ്റാണ്, ദാതാവിന്റെ നിരക്ക് പരിമിതിയല്ല. **#503-fanout അപ്ഡേറ്റ്:** ഈ വേരിയബിൾ ഇനി സ്ഥിരസ്ഥിതിയായി സജ്ജീകരിക്കപ്പെടുന്നില്ല (മുകളിൽ കാണിച്ചതുപോലെ വ്യക്തമായി കോൺഫിഗർ ചെയ്യുമ്പോൾ മാത്രമാണ് ഇപ്പോൾ ഇത് ബാധകമാകുന്നത്) — പകരം, ഹോസ്റ്റിന്റെ യഥാർത്ഥ മെമ്മറി പരിധിക്കനുസരിച്ച് സ്വയം സ്കെയിൽ ചെയ്യുന്ന, സ്വയമേവ നിർണയിക്കപ്പെടുന്ന ഒരു ബൈറ്റ് ബജറ്റ് (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ആണ് ഹെവിവെയ്റ്റ് അഡ്മിഷൻ നിയന്ത്രിക്കുന്നത്. അതിനാൽ ഈ വേരിയബിൾ സജ്ജീകരിക്കാതെതന്നെ പുതിയൊരു ഡിപ്ലോയ്മെന്റിൽ വളരെ കുറച്ച് `503 chat_admission_busy` നിരസിക്കലുകൾ മാത്രമേ ഉണ്ടാകാവൂ; ഇവിടെ ഇത് വ്യക്തമായി സജ്ജീകരിക്കുന്നത് ഡോക്യുമെന്റ് ചെയ്തതുപോലെതന്നെ തുടർന്നും പ്രവർത്തിക്കും. വ്യക്തമായ ബൈറ്റ്-ബജറ്റ് ഓവർറൈഡുകൾ 8 MiB–2 GiB പരിധിയിൽ നിയന്ത്രിക്കപ്പെടുന്നു. ഒരു `413 body_exceeds_budget` താൽക്കാലികമല്ല: ആ ബൈറ്റ് ബജറ്റ് വർധിപ്പിക്കുക, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` കുറയ്ക്കുക, അല്ലെങ്കിൽ പ്രോസസിന്റെ മെമ്മറി പരിധി വർധിപ്പിക്കുക. ഒരു `inflight_bytes_budget` ഷെഡ് താൽക്കാലികമായ വിഭവമത്സരമാണ്, അത് വീണ്ടും ശ്രമിക്കാവുന്നതായി തുടരും. ഓരോ ദാതാവിനുമുള്ള നിരക്ക് പരിമിതി (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, `RATE_LIMIT_AUTO_ENABLE` എന്നിവയാൽ പ്രത്യേകം നിയന്ത്രിക്കപ്പെടുന്നു — `.env.example` കാണുക.

**ഇത് പ്രവർത്തിച്ചെന്ന് സ്ഥിരീകരിക്കുന്ന വിധം**: നിങ്ങളുടെ ഏജന്റ്/cron തുടർച്ചയായി രണ്ടുതവണ പ്രവർത്തിപ്പിച്ച് രണ്ടും വിജയിക്കുന്നുവെന്ന് സ്ഥിരീകരിക്കുക. പരിഹാരത്തിന് മുമ്പ്, രണ്ടാമത്തെ പ്രവർത്തനം സാധാരണയായി `429`/`401` നൽകും. പരിഹാരത്തിന് ശേഷം, പരാജയങ്ങൾ (ഉണ്ടെങ്കിൽ) സുതാര്യമായി വീണ്ടും ശ്രമിക്കപ്പെടുകയും കോൾ പൂർത്തിയാകുകയും ചെയ്യും. നിങ്ങൾക്ക് `curl /monitoring/health` പ്രവർത്തിപ്പിച്ച് ദാതാവിന്റെ കണക്ഷനുകളിലെ `rateLimitedUntil` ഫീൽഡും ബാധിക്കപ്പെട്ട ദാതാക്കൾക്കായുള്ള `circuitBreakers.providerBreakers[].state`-ഉം നിരീക്ഷിക്കാം — സ്റ്റേറ്റ് `CLOSED`, `DEGRADED`, `OPEN`, അല്ലെങ്കിൽ `HALF_OPEN` എന്നിവയിൽ ഒന്നായിരിക്കും (`src/shared/utils/circuitBreaker.ts` കാണുക). തുടർച്ചയായി പരാജയപ്പെടുന്ന ഒരു ദാതാവ്, പുനഃസജ്ജീകരണ സമയജാലകം ഒരു പരിശോധന അനുവദിക്കുന്നതിനുമുമ്പ് (`HALF_OPEN`), `CLOSED → DEGRADED → OPEN` എന്ന ക്രമത്തിൽ മാറും.

**ഇപ്പോഴും 429 കാണുന്നുവെങ്കിൽ**: ആ ദാതാവിനായുള്ള സജീവ അക്കൗണ്ട് അതിന്റെ _ക്വാട്ട_ യഥാർത്ഥത്തിൽ മുഴുവൻ ഉപയോഗിച്ചിരിക്കുന്നു (നിരക്ക് മാത്രമല്ല). OmniRoute ഡാഷ്ബോർഡ് → ദാതാക്കൾ → അക്കൗണ്ടുകൾ എന്നതിൽ അതേ ദാതാവിനായി രണ്ടാമത്തെ അക്കൗണ്ട് ചേർക്കുക, അല്ലെങ്കിൽ മറ്റൊരു സൗജന്യ ദാതാവിനെയും (ഉദാ. `routeway`, `auggie`) ഉൾപ്പെടുത്തുക. താൽക്കാലിക നിരക്ക്/400/401 പ്രശ്നങ്ങളിൽ മാത്രമാണ് റൊട്ടേഷൻ സഹായിക്കുന്നത്; ക്വാട്ട പൂർണമായും തീർന്നാൽ രണ്ടാമത്തെ ക്രെഡൻഷ്യലോ മറ്റൊരു ദാതാവോ ആവശ്യമാണ്.

**വിഷൻ മോഡലുകളിൽ (`auto/vision`, `bazaarlink/*`) 403 കാണുന്നുവെങ്കിൽ**: കണക്റ്റ് ചെയ്ത അക്കൗണ്ടിന് വിഷൻ ഉൾപ്പെടുന്ന ഒരു പണമടച്ച പ്ലാൻ ഇല്ല, അല്ലെങ്കിൽ API കീയ്ക്ക് മതിയായ അനുമതികളില്ല. കീയുടെ സ്കോപ്പിൽ വിഷൻ/മൾട്ടിമോഡൽ ഉൾപ്പെടുന്നുണ്ടെന്ന് ദാതാവിന്റെ ഡാഷ്ബോർഡിൽ സ്ഥിരീകരിക്കുക, അല്ലെങ്കിൽ പണമടച്ച ടയർ അക്കൗണ്ട് കണക്റ്റ് ചെയ്ത് അതിനെ വിഷൻ ടാർഗെറ്റായി നിലനിർത്തുക.

## npm install മുന്നറിയിപ്പുകൾ (ERESOLVE / peer / deprecated)

നിങ്ങൾ `npm install -g omniroute` പ്രവർത്തിപ്പിക്കുമ്പോൾ, `npm warn ERESOLVE`, peer-dependency അറിയിപ്പുകൾ, `deprecated` സന്ദേശങ്ങൾ എന്നിവ പോലുള്ള നിരവധി മുന്നറിയിപ്പുകൾ കണ്ടേക്കാം. **ഇവ പ്രതീക്ഷിക്കാവുന്നതും ദോഷകരമല്ലാത്തതുമാണ്.** ഔട്ട്പുട്ടിൽ `added <N> packages` എന്ന് കാണുന്നുവെങ്കിൽ നിങ്ങളുടെ ഇൻസ്റ്റാളേഷൻ വിജയിച്ചു.

OmniRoute-ന് നിയന്ത്രണമില്ലാത്ത മൂന്നാം കക്ഷി പാക്കേജുകളിലെ കാലഹരണപ്പെട്ട peer-dependency റേഞ്ചുകളിൽ നിന്നാണ് ഈ മുന്നറിയിപ്പുകൾ ഉണ്ടാകുന്നത്:

1. **`marked-terminal`-ന് `marked >=1 <16` ആവശ്യമാണ്, എന്നാൽ `marked@18` കണ്ടെത്തി** — പ്രായോഗികമായി ഇത് പ്രശ്നമില്ലാതെ പ്രവർത്തിക്കുന്നു; upstream peer റേഞ്ച് കാലഹരണപ്പെട്ടതാണ്.
2. **`deprecated prebuild-install@7.1.3`** — ഇത് ഒരു transitive native-binary ഡൗൺലോഡ് സഹായിയാണ്. പിൻ ചെയ്ത `wreq-js` transport binding ഇൻസ്റ്റാൾ ചെയ്യാൻ ഇത്
   ഉപയോഗിക്കുന്നില്ല; കൂടാതെ web-cookie provider transport സജ്ജീകരണം പരാജയപ്പെട്ടുവെന്ന് ഇത് സൂചിപ്പിക്കുന്നുമില്ല.

**നടപടിയൊന്നും ആവശ്യമില്ല** — upstream പാക്കേജുകൾ fork ചെയ്യാതെ ഈ മുന്നറിയിപ്പുകൾ പൂർണ്ണമായി നിശ്ശബ്ദമാക്കാനാകില്ല.

## ആന്റിവൈറസ് തെറ്റായ പോസിറ്റീവുകൾ

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md`-നെ `MD:HttpRequest-inf[Susp]` ആയി ക്വാറന്റൈൻ ചെയ്യുന്നു

**ഇതൊരു തെറ്റായ പോസിറ്റീവാണ്. ഒന്നിലും അണുബാധയില്ല, ഒരു നടപടിയും ആവശ്യമില്ല.**

HTTP അഭ്യർത്ഥനകളെന്ന് തോന്നിക്കുന്ന ധാരാളം ലിങ്കുകൾ അടങ്ങിയ പ്ലെയിൻ-ടെക്സ്റ്റ്/Markdown ഫയലുകളെ
ഫ്ലാഗ് ചെയ്യുന്ന ഒരു ഹ്യൂറിസ്റ്റിക് Avast-ഉം AVG-ഉം പ്രവർത്തിപ്പിക്കുന്നു. OmniRoute-ന്റെ `README.md`,
npm പാക്കേജിനുള്ളിൽ ഉൾപ്പെടുത്തിയിട്ടുള്ളതാണ് (ഇത് `package.json` → `files` എന്നതിൽ
പട്ടികപ്പെടുത്തിയിരിക്കുന്നു), അതിനാൽ ഒരു ഗ്ലോബൽ ഇൻസ്റ്റാളിൽ അത്
`node_modules/omniroute/README.md` എന്നതിൽ എത്തുന്നു — കൂടാതെ അതിൽ ഏകദേശം 15
`http://localhost:20128/...` ഉദാഹരണങ്ങൾ അടങ്ങിയിരിക്കുന്നു (MCP HTTP/SSE എൻഡ്പോയിന്റുകൾ,
A2A `.well-known` URL, `curl` സ്നിപ്പെറ്റുകൾ എന്നിവ). ഈ ലിങ്കുകളുടെ സാന്ദ്രത ഹ്യൂറിസ്റ്റിക്കിനെ
ട്രിഗർ ചെയ്യാൻ മതിയാകും.

ഇത് അടുത്തിടെയാണ് ആരംഭിച്ചതെങ്കിൽ: ഫയലിന്റെ സ്വഭാവത്തിൽ മാറ്റമൊന്നും ഉണ്ടായിട്ടില്ല. README-യിലെ
എൻഡ്പോയിന്റുകളുടെ പട്ടിക വികസിച്ചു (MCP HTTP + SSE + A2A എന്നിവ ചേർത്തു), കൂടാതെ കൂടുതൽ
`curl` ഉദാഹരണങ്ങളും ഉൾപ്പെടുത്തി; ഇതാണ് അതിനെ പരിധിക്കപ്പുറം എത്തിച്ചത്.

എക്സിക്യൂട്ട് ചെയ്യാവുന്ന ഉള്ളടക്കം ഒന്നുമില്ലാത്ത നിർജ്ജീവമായ ഡോക്യുമെന്റേഷനാണ് ഈ ഫയൽ.
ക്വാറന്റൈനിൽ നിന്ന് നിങ്ങൾക്ക് ഇത് സുരക്ഷിതമായി പുനഃസ്ഥാപിക്കാം.

**എന്ത് ചെയ്യണം:**

1. **അറിയിപ്പുകൾ നിർത്തുക** — നിങ്ങളുടെ ആന്റിവൈറസിൽ ഇൻസ്റ്റാൾ ഡയറക്ടറിയെ ഒഴിവാക്കുക
   (Avast: Settings → Exceptions); നിങ്ങളുടെ ഗ്ലോബൽ `node_modules` പാത്തും കൂടാതെ/അല്ലെങ്കിൽ
   OmniRoute ഡാറ്റ ഡയറക്ടറിയും (`~/.omniroute/`) ചേർക്കുക.
2. **തെറ്റായ പോസിറ്റീവ് റിപ്പോർട്ട് ചെയ്യുക** — <https://www.avast.com/false-positive-file-form.php>,
   ക്വാറന്റൈൻ ചെയ്ത `README.md` അറ്റാച്ച് ചെയ്യുക. ഒരു ടെക്സ്റ്റ് ഫയലിനോട് വെൻഡറുടെ ഹ്യൂറിസ്റ്റിക്
   അമിതമായി പ്രതികരിക്കുന്നതാണ് പ്രശ്നം എന്നതിനാൽ, എല്ലാവർക്കും സഹായകരമാകുന്ന പരിഹാരം ഇതാണ്.

**ഞങ്ങളുടെ ഭാഗത്ത് ഇത് "പരിഹരിക്കാത്തത്" എന്തുകൊണ്ട്:** എല്ലാ ഉദാഹരണങ്ങളും
`http://localhost` ആണ്; സ്വയം ഒപ്പിട്ട സർട്ടിഫിക്കറ്റുകളുമായി ബന്ധപ്പെട്ട ബുദ്ധിമുട്ടുകളില്ലാതെ
localhost-ന് `https` ഉപയോഗിക്കാൻ കഴിയില്ല. ഒരു വെൻഡറുടെ ഹ്യൂറിസ്റ്റിക്കിനെ മറികടക്കാനായി
ഡോക്യുമെന്റേഷൻ വികലമാക്കുന്നത്, ഒരു സ്കാനർ ബഗിനെ തൃപ്തിപ്പെടുത്താൻ എല്ലാ വായനക്കാരെയും
ദോഷകരമായി ബാധിക്കും.

### Kaspersky, ഡെസ്ക്ടോപ്പ് ആപ്പിനെ `PDM:Trojan.Win32.Generic` ആയി ഫ്ലാഗ് ചെയ്യുന്നു

**പെരുമാറ്റ ഹ്യൂറിസ്റ്റിക്കിൽ നിന്നുള്ള തെറ്റായ പോസിറ്റീവാണിത്. ഒന്നിലും അണുബാധയില്ല.**
Kaspersky-യുടെ `PDM:` പ്രിഫിക്സ് അർത്ഥമാക്കുന്നത്, അറിയപ്പെടുന്ന മാൽവെയറുമായി പൊരുത്തപ്പെടുത്തുന്നതിനു
പകരം ഇൻസ്റ്റാളർ _എന്ത് ചെയ്യുന്നു_ എന്ന് വിലയിരുത്തുന്ന അതിന്റെ Proactive Defense Module
(System Watcher)-ൽ നിന്നാണ് വിധി വരുന്നത് എന്നാണ്. ഇത് ട്രിഗർ ചെയ്യുമ്പോൾ, Kaspersky മുഴുവൻ
ഇൻസ്റ്റാളേഷനും "റോൾ ബാക്ക്" ചെയ്യുന്നു — ഇതിനകം എഴുതിയ ഫയലുകൾ ഇല്ലാതാക്കുന്നു — അതിനാൽ ആപ്പ്
പ്രവർത്തനരഹിതമാവുകയോ അപ്രത്യക്ഷമാവുകയോ ചെയ്യുന്നു.

ഡെസ്ക്ടോപ്പ് ആപ്പിനൊപ്പം ബണ്ടിൽ ചെയ്തിട്ടുള്ള, പ്രഖ്യാപിതവും ഓപ്പൺ സോഴ്സുമായ ഡിപ്പെൻഡൻസികളുടെ
സാധാരണ ഘടകങ്ങളാണ് ഇത് ഫ്ലാഗ് ചെയ്യുന്ന ഫയലുകൾ. ഉദാഹരണത്തിന്:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js`,
  `workerProcessEntry.js` എന്നിവ — ആപ്പിനുള്ളിലെ പ്രൊവൈഡർ ലോഗിൻ, ബ്രൗസർ അധിഷ്ഠിത ചാറ്റ്
  എന്നിവയ്ക്കായി ഉപയോഗിക്കുന്ന ബ്രൗസർ ഓട്ടോമേഷൻ ലൈബ്രറിയായ
  [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — വെബ്-കുക്കി പ്രൊവൈഡറുകളിൽ ബ്രൗസർ-ഫിംഗർപ്രിന്റ് ചെയ്ത HTTP-ക്കായി ഉപയോഗിക്കുന്ന,
  പിൻ ചെയ്ത `wreq-js` നേറ്റീവ് ബൈൻഡിങ് (`<arch>` എന്നത് `x64` അല്ലെങ്കിൽ `arm64` ആണ്).

**ഇത് ട്രിഗർ ചെയ്യുന്നതിന്റെ കാരണം:** Windows ഇൻസ്റ്റാളർ **ഇതുവരെ കോഡ്-സൈൻ ചെയ്തിട്ടില്ല**,
അതിനാൽ സൈൻ ചെയ്യാത്ത NSIS ഇൻസ്റ്റാളറിന് യാതൊരു പ്രശസ്തിയും ഇല്ല; പെരുമാറ്റ ഹ്യൂറിസ്റ്റിക്കുകൾ
പരമാവധി കർശനമായി പ്രവർത്തിക്കുകയും ചെയ്യുന്നു. ബണ്ടിൽ ചെയ്ത നേറ്റീവ് DLL-ഉം
`%LOCALAPPDATA%\Programs\OmniRoute`-ന് കീഴിൽ എഴുതുന്ന നൂറുകണക്കിന് `.js` ഫയലുകളും
(Next.js സ്റ്റാൻഡ്എലോൺ ബിൽഡിൽ നിന്നുള്ള ഹാഷ്-സഫിക്സ് ചേർത്ത പാക്കേജ് ഡയറക്ടറികൾ ഉൾപ്പെടെ)
ചേരുമ്പോൾ, ഹ്യൂറിസ്റ്റിക് ട്രിഗർ ചെയ്യാൻ അത് മതിയാകും. കോഡ് സൈനിങ് ആസൂത്രണം ചെയ്തിട്ടുണ്ട്;
അത് നടപ്പാകുന്നതുവരെ പുതിയ റിലീസുകളിൽ ഇത് ആവർത്തിക്കാം.

**എന്ത് ചെയ്യണം:**

1. **ആദ്യം നിങ്ങളുടെ ഡൗൺലോഡ് പരിശോധിച്ചുറപ്പിക്കുക** (ഫയലിൽ കൃത്രിമം നടത്തിയിട്ടില്ലെന്ന്
   ഇത് ഉറപ്പാക്കുന്നു). ഓരോ റിലീസും `latest.yml` പ്രസിദ്ധീകരിക്കുന്നു; അതിലെ `sha512`
   ഫീൽഡ് (base64) `OmniRoute.Setup.<version>.exe` ഇൻസ്റ്റാളറെ ഉൾക്കൊള്ളുന്നു. ഇൻസ്റ്റാളർ
   അടങ്ങിയ ഫോൾഡറിൽ നിന്ന് PowerShell-ൽ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ഔട്ട്പുട്ട് `latest.yml` → `sha512`-നോട് പൊരുത്തപ്പെടണം. പൊരുത്തപ്പെടുന്നില്ലെങ്കിൽ,
   ഫയൽ ഇല്ലാതാക്കി [GitHub റിലീസ് പേജിൽ](https://github.com/diegosouzapw/OmniRoute/releases)
   നിന്ന് മാത്രം വീണ്ടും ഡൗൺലോഡ് ചെയ്യുക.
2. **പുനഃസ്ഥാപിക്കുക + ഒഴിവാക്കുക** — റോൾ ബാക്ക് ചെയ്ത ഇനങ്ങൾ ക്വാറന്റൈനിൽ നിന്ന്
   പുനഃസ്ഥാപിക്കുകയും `%LOCALAPPDATA%\Programs\OmniRoute`-ന് ഒരു ഒഴിവാക്കൽ ചേർക്കുകയും
   ചെയ്യുക (Kaspersky → Settings → Threats and Exclusions), തുടർന്ന് വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക.
3. **തെറ്റായ പോസിറ്റീവ് റിപ്പോർട്ട് ചെയ്യുക** — <https://opentip.kaspersky.com/>. ഉപയോക്താക്കൾ
   സമർപ്പിക്കുന്ന തെറ്റായ പോസിറ്റീവ് റിപ്പോർട്ടുകൾ അലൗലിസ്റ്റിങ് യഥാർഥത്തിൽ വേഗത്തിലാക്കുന്നു.

## Node.js അനുയോജ്യത

<a name="nodejs-compatibility"></a>

### ലോഗിൻ പേജ് ക്രാഷാകുന്നു അല്ലെങ്കിൽ "Module self-registration" പിശക് കാണിക്കുന്നു

**കാരണം:** OmniRoute അംഗീകരിച്ചിട്ടുള്ള ഏറ്റവും കുറഞ്ഞ സുരക്ഷിത റൺടൈം പതിപ്പിന് പുറത്തുള്ള ഒരു Node.js പതിപ്പാണ് നിങ്ങൾ പ്രവർത്തിപ്പിക്കുന്നത്. OmniRoute ആവശ്യപ്പെടുന്ന സുരക്ഷാ പാച്ചുകൾ ഉൾപ്പെടുത്തിയിട്ടുള്ള ഏറ്റവും കുറഞ്ഞ പതിപ്പിനേക്കാൾ പഴയ Node 22 അല്ലെങ്കിൽ 24 പാച്ച് പതിപ്പ് പ്രവർത്തിപ്പിക്കുന്നതാണ് ഏറ്റവും സാധാരണമായ സാഹചര്യം.

**ലക്ഷണങ്ങൾ:**

- ലോഗിൻ പേജിൽ ശൂന്യമായ സ്ക്രീനോ സെർവർ പിശകോ കാണിക്കുന്നു
- കൺസോളിൽ `Error: Module did not self-register` അല്ലെങ്കിൽ സമാനമായ നേറ്റീവ് ബൈൻഡിങ് പിശകുകൾ കാണിക്കുന്നു
- റൺടൈം പിന്തുണയ്ക്കുന്ന സുരക്ഷാ നയത്തിന് പുറത്താണെങ്കിൽ, ലോഗിൻ പേജിൽ നിങ്ങളുടെ Node പതിപ്പിനൊപ്പം ഒരു **ഓറഞ്ച് മുന്നറിയിപ്പ് ബാനർ** കാണിക്കുന്നു

**പരിഹാരം:**

1. പിന്തുണയ്ക്കുന്ന ഒരു Node.js LTS റിലീസ് ഇൻസ്റ്റാൾ ചെയ്യുക (ശുപാർശ ചെയ്യുന്നത്: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. നിങ്ങളുടെ പതിപ്പ് പരിശോധിക്കുക: 24.x LTS ശ്രേണിയിൽ `node --version` എന്നത് `v24.0.0` അല്ലെങ്കിൽ അതിലും പുതിയ പതിപ്പ് കാണിക്കണം
3. OmniRoute വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക: `npm install -g omniroute`
4. പുനരാരംഭിക്കുക: `omniroute`

> **പിന്തുണയ്ക്കുന്ന സുരക്ഷിത പതിപ്പുകൾ:** `>=22.22.2 <23` അല്ലെങ്കിൽ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton), Node.js 26 എന്നിവ പൂർണ്ണമായി പിന്തുണയ്ക്കുന്നു.

### npm v11+: `better-sqlite3` ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ല (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**കാരണം:** npm v11 (Node.js 24+-നൊപ്പം ലഭിക്കുന്നത്) ഐച്ഛിക
ഡിപെൻഡൻസികൾക്കായുള്ള ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾ ഡിഫോൾട്ടായി തടയുന്നു. `better-sqlite3` എന്നത് `optionalDependencies`-ൽ ഉൾപ്പെടുത്തിയിട്ടുള്ളതിനാലും
നേറ്റീവ് കംപൈലേഷൻ (`node-gyp rebuild`) ആവശ്യമായതിനാലും npm അറിയിപ്പൊന്നുമില്ലാതെ അത് ഒഴിവാക്കുന്നു.

**ലക്ഷണങ്ങൾ:**

- ആരംഭിക്കുമ്പോൾ `Cannot find module 'better-sqlite3'` എന്ന പിശകോടെ സെർവർ ക്രാഷാകുന്നു
- `ls node_modules/better-sqlite3` എന്നത് "No such file or directory" എന്ന് കാണിക്കുന്നു
- `npm ls better-sqlite3` എന്നത് `(empty)` എന്ന് കാണിക്കുന്നു

**പരിഹാരം:**

1. ഇൻസ്റ്റാൾ സ്ക്രിപ്റ്റുകൾക്ക് അംഗീകാരം നൽകി വീണ്ടും ഇൻസ്റ്റാൾ ചെയ്യുക:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. അല്ലെങ്കിൽ മുൻകൂട്ടി ബിൽഡ് ചെയ്ത പാക്കേജ് മാനുവലായി ഇൻസ്റ്റാൾ ചെയ്യുക:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ഇത് പ്രവർത്തിക്കുന്നുണ്ടെന്ന് പരിശോധിക്കുക: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**കാരണം:** ഗ്ലോബൽ `npm install -g omniroute` നടത്തിയതിന് ശേഷം, പാക്കേജിനുള്ളിലെ `better-sqlite3` നേറ്റീവ് ബൈനറി, പ്രാദേശികമായി പ്രവർത്തിക്കുന്നതിൽനിന്ന് വ്യത്യസ്തമായ ആർക്കിടെക്ചറിനോ Node.js ABI-യ്ക്കോ വേണ്ടി കംപൈൽ ചെയ്തതായിരിക്കാം. മുൻകൂട്ടി ബിൽഡ് ചെയ്ത ബൈനറി നിങ്ങളുടെ എൻവയോൺമെന്റുമായി പൊരുത്തപ്പെടാത്തപ്പോൾ macOS-ൽ (Apple Silicon, Intel എന്നിവയിൽ) ഇത് സാധാരണമാണ്.

**ലക്ഷണങ്ങൾ:**

- ആരംഭിക്കുമ്പോൾ തന്നെ `dlopen` പിശകോടെ സെർവർ പരാജയപ്പെടുന്നു
- പിശകിൽ `slice is not valid mach-o file` ഉൾപ്പെടുന്നു
- പൂർണ്ണമായ ഉദാഹരണം:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**പരിഹാരം — നിങ്ങളുടെ പ്രാദേശിക എൻവയോൺമെന്റിനായി വീണ്ടും ബിൽഡ് ചെയ്യുക (Node.js പതിപ്പ് താഴ്ത്തേണ്ടതില്ല):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **കുറിപ്പ്:** ഇത് നിങ്ങളുടെ പ്രാദേശിക Node.js പതിപ്പിനും CPU ആർക്കിടെക്ചറിനും അനുയോജ്യമായി നേറ്റീവ് ബൈൻഡിങ് വീണ്ടും കംപൈൽ ചെയ്ത് ബൈനറി പൊരുത്തക്കേട് പരിഹരിക്കുന്നു. ഔദ്യോഗികമായി പിന്തുണയ്ക്കുന്ന റൺടൈം ശ്രേണി **`>=22.22.2 <23` അല്ലെങ്കിൽ `>=24.0.0 <27`** ആണ് (`src/shared/utils/nodeRuntimeSupport.ts`-ലെ `SUPPORTED_NODE_RANGE`, `package.json`-ലെ `engines` ഫീൽഡുമായി വിന്യസിച്ചിരിക്കുന്നു). Node.js 24.x LTS (Krypton), Node.js 26 എന്നിവ `better-sqlite3` v12.x-നൊപ്പം പൂർണ്ണമായി പിന്തുണയ്ക്കുന്നു.

## പ്രോക്സി പ്രശ്നങ്ങൾ

<a name="proxy-issues"></a>

### പ്രൊവൈഡർ സാധൂകരണത്തിൽ "fetch failed" കാണിക്കുന്നു

**കാരണം:** API കീ സാധൂകരണ എൻഡ്പോയിന്റ് (`POST /api/providers/validate`) മുമ്പ് പ്രോക്സി കോൺഫിഗറേഷൻ മറികടന്നിരുന്നതിനാൽ, പ്രോക്സി റൂട്ടിംഗ് ആവശ്യമായ പരിതസ്ഥിതികളിൽ പരാജയങ്ങൾ സംഭവിച്ചിരുന്നു.

**പരിഹാരം (v3.5.5+):** ഇത് ഇപ്പോൾ പരിഹരിച്ചിട്ടുണ്ട്. പ്രൊവൈഡർ-തലത്തിലുള്ളതും ആഗോളവുമായ പ്രോക്സി ക്രമീകരണങ്ങൾ സ്വയമേവ പാലിച്ചുകൊണ്ട്, പ്രൊവൈഡർ സാധൂകരണ അഭ്യർത്ഥനകൾ ഇപ്പോൾ `runWithProxyContext` വഴി റൂട്ട് ചെയ്യപ്പെടുന്നു.

### ടോക്കൺ ആരോഗ്യപരിശോധന "fetch failed" എന്ന പിശകോടെ പരാജയപ്പെടുന്നു

**കാരണം:** പശ്ചാത്തല OAuth ടോക്കൺ പുതുക്കൽ ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ നിർണ്ണയിച്ചിരുന്നില്ല.

**പരിഹാരം (v3.5.5+):** പുതുക്കാൻ ശ്രമിക്കുന്നതിന് മുമ്പ് ടോക്കൺ ആരോഗ്യപരിശോധന ഷെഡ്യൂളർ ഇപ്പോൾ ഓരോ കണക്ഷനുമുള്ള പ്രോക്സി കോൺഫിഗറേഷൻ നിർണ്ണയിക്കുന്നു. v3.5.5+ ലേക്ക് അപ്ഡേറ്റ് ചെയ്യുക.

### SOCKS5 പ്രോക്സി "invalid onRequestStart method" എന്ന പിശക് നൽകുന്നു

**കാരണം:** Node.js 22-ൽ, undici@8 ഡിസ്പാച്ചർ Node-ന്റെ അന്തർനിർമ്മിത `fetch()` നടപ്പാക്കലുമായി പൊരുത്തപ്പെടുന്നില്ല.

**പരിഹാരം (v3.5.5+):** ഒരു പ്രോക്സി ഡിസ്പാച്ചർ സജീവമായിരിക്കുമ്പോൾ OmniRoute ഇപ്പോൾ undici-യുടെ സ്വന്തം `fetch()` ഫങ്ഷൻ ഉപയോഗിക്കുന്നു; ഇത് സ്ഥിരതയുള്ള പ്രവർത്തനം ഉറപ്പാക്കുന്നു. v3.5.5+ ലേക്ക് അപ്ഡേറ്റ് ചെയ്യുക.

### WSL-ന് കീഴിലുള്ള MITM പ്രോക്സി: Windows ഹോസ്റ്റിലെ ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ ഇന്റർസെപ്റ്റ് ചെയ്യപ്പെടുന്നില്ല

**കാരണം:** MITM പ്രോക്സിയും അതിന്റെ CA സർട്ടിഫിക്കറ്റും OmniRoute പ്രവർത്തിക്കുന്ന പരിതസ്ഥിതിയിലാണ് ഇൻസ്റ്റാൾ ചെയ്യപ്പെടുന്നത്. WSL-ന് കീഴിൽ ആ പരിതസ്ഥിതി Linux ഗസ്റ്റ് ആണ്, അതേസമയം AI ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ (Kiro, Trae, Copilot, Zed, …) Windows ഹോസ്റ്റിലാണ് പ്രവർത്തിക്കുന്നത്. ഹോസ്റ്റ് ആപ്പുകൾ ഗസ്റ്റിന്റെ സർട്ടിഫിക്കറ്റ് സ്റ്റോറിനെ വിശ്വസിക്കുകയോ ഗസ്റ്റിന്റെ സിസ്റ്റം പ്രോക്സിയിലൂടെ റൂട്ട് ചെയ്യുകയോ ചെയ്യുന്നില്ല; അതിനാൽ അവിടെ ഡെസ്ക്ടോപ്പ് ഇന്റർസെപ്ഷൻ പ്രവർത്തിക്കില്ല.

**ശുപാർശ:** നിങ്ങൾ ഇന്റർസെപ്റ്റ് ചെയ്യാൻ ആഗ്രഹിക്കുന്ന ഡെസ്ക്ടോപ്പ് ആപ്പുകൾ പ്രവർത്തിക്കുന്ന അതേ OS-ൽ OmniRoute നേറ്റീവ് ആയി പ്രവർത്തിപ്പിക്കുക (Windows ആപ്പുകൾക്ക് Windows; macOS/Linux-നും അതുപോലെ). ഹോസ്റ്റ് ആപ്പുകളെ ലക്ഷ്യമിടുമ്പോൾ OmniRoute WSL-നുള്ളിൽ തന്നെ നിലനിർത്തുന്നതിന്, സൃഷ്ടിച്ച CA സർട്ടിഫിക്കറ്റിനെ Windows ഹോസ്റ്റിൽ മാനുവലായി വിശ്വസനീയമാക്കുകയും ഓരോ ഹോസ്റ്റ് ആപ്പിന്റെയും നെറ്റ്വർക്ക്/പ്രോക്സി ക്രമീകരണങ്ങൾ WSL പ്രോക്സി എൻഡ്പോയിന്റിലേക്ക് ചൂണ്ടുകയും വേണം — ഇത് പിന്തുണയ്ക്കാത്തതും എളുപ്പത്തിൽ തകരാവുന്നതുമായ സജ്ജീകരണമാണ്.

OmniRoute ടോക്കണുകൾ സ്വയമേവ പുതുക്കുന്നു. പ്രശ്നങ്ങൾ തുടരുകയാണെങ്കിൽ:

1. ഡാഷ്ബോർഡ് → പ്രൊവൈഡർ → വീണ്ടും കണക്റ്റ് ചെയ്യുക

### Kiro മൾട്ടി-അക്കൗണ്ട്: രണ്ടാമത്തെ അക്കൗണ്ട് ആദ്യത്തേതിനെ അസാധുവാക്കുന്നു

**കാരണം:** ഓരോ OIDC ക്ലയന്റ് രജിസ്ട്രേഷനും ഒരൊറ്റ സജീവ സെഷൻ മാത്രമേ അനുവദിക്കൂ എന്ന നിബന്ധന Kiro-യുടെ ബാക്ക്എൻഡ് നടപ്പാക്കുന്നു.
രണ്ട് അക്കൗണ്ടുകൾ ഒരേ രജിസ്റ്റർ ചെയ്ത ക്ലയന്റ് പങ്കിടുമ്പോൾ (v3.8.0-ന് മുമ്പ് ഇംപോർട്ട് ചെയ്ത കണക്ഷനുകൾ),
ഒരു അക്കൗണ്ടിന്റെ ടോക്കൺ പുതുക്കുന്നത് മറ്റേ അക്കൗണ്ടിന്റെ റിഫ്രഷ് ടോക്കൺ അസാധുവാക്കുന്നു.

**പരിഹാരം (v3.8.0+):** ബാധിച്ച കണക്ഷനുകൾ വീണ്ടും ഇംപോർട്ട് ചെയ്യുക.
v3.8.0 മുതൽ, **Import Token**,
**Google/GitHub social login**, അല്ലെങ്കിൽ **Auto-Import** വഴി സൃഷ്ടിക്കുന്ന ഓരോ പുതിയ Kiro കണക്ഷനും അതിന് മാത്രമായുള്ള
ഒരു പ്രത്യേക OIDC ക്ലയന്റ് സ്വയമേവ രജിസ്റ്റർ ചെയ്യുന്നു. അതിനാൽ കണക്ഷൻ പൂർണ്ണമായി വേർതിരിക്കപ്പെടുകയും ഒരു
അക്കൗണ്ട് പുതുക്കുന്നത് മറ്റൊരു അക്കൗണ്ടിനെയും ബാധിക്കാതിരിക്കുകയും ചെയ്യുന്നു.

v3.8.0-ന് _മുമ്പ്_ ഇംപോർട്ട് ചെയ്ത കണക്ഷനുകളിൽ ഓരോ കണക്ഷനുമുള്ള പ്രത്യേക ക്ലയന്റ്
രജിസ്ട്രേഷൻ ഉണ്ടായിരിക്കില്ല. ആ കണക്ഷനുകൾ പങ്കിട്ട സോഷ്യൽ-ഓത്ത് റിഫ്രഷ് എൻഡ്പോയിന്റ് തുടർന്നും ഉപയോഗിക്കും.
വേർതിരിവ് ലഭിക്കാൻ, ഡാഷ്ബോർഡ് → പ്രൊവൈഡറുകൾ എന്നതിൽ നിന്ന് പഴയ കണക്ഷൻ ഇല്ലാതാക്കി
മൂന്ന് ഇംപോർട്ട് രീതികളിൽ ഏതെങ്കിലും ഒന്ന് വഴി വീണ്ടും ചേർക്കുക.

## ക്ലൗഡ് പ്രശ്നങ്ങൾ

### ക്ലൗഡ് സമന്വയ പിശകുകൾ

1. `BASE_URL` നിങ്ങളുടെ പ്രവർത്തിക്കുന്ന ഇൻസ്റ്റൻസിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് പരിശോധിക്കുക (ഉദാ., `http://localhost:20128`)
2. `CLOUD_URL` നിങ്ങളുടെ ക്ലൗഡ് എൻഡ്പോയിന്റിലേക്കാണ് വിരൽചൂണ്ടുന്നതെന്ന് പരിശോധിക്കുക (ഉദാ., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` മൂല്യങ്ങൾ സെർവർ-സൈഡ് മൂല്യങ്ങളുമായി പൊരുത്തപ്പെടുത്തി നിലനിർത്തുക

### ക്ലൗഡിൽ `stream=false` ഉപയോഗിക്കുമ്പോൾ 500 ലഭിക്കുന്നു

**ലക്ഷണം:** സ്ട്രീമിംഗ് അല്ലാത്ത കോളുകൾക്കായി ക്ലൗഡ് എൻഡ്പോയിന്റിൽ `Unexpected token 'd'...` ലഭിക്കുന്നു.

**കാരണം:** ക്ലയന്റ് JSON പ്രതീക്ഷിക്കുമ്പോൾ അപ്സ്ട്രീം SSE പേലോഡ് തിരികെ നൽകുന്നു.

**താൽക്കാലിക പരിഹാരം:** ക്ലൗഡിലേക്കുള്ള നേരിട്ടുള്ള കോളുകൾക്ക് `stream=true` ഉപയോഗിക്കുക. ലോക്കൽ റൺടൈമിൽ SSE→JSON ഫാൾബാക്ക് ഉൾപ്പെടുത്തിയിട്ടുണ്ട്.

### ക്ലൗഡ് കണക്റ്റുചെയ്തതായി കാണിക്കുന്നുവെങ്കിലും "അസാധുവായ API കീ" എന്ന് പറയുന്നു

1. ലോക്കൽ ഡാഷ്ബോർഡിൽ നിന്ന് ഒരു പുതിയ കീ സൃഷ്ടിക്കുക (`/api/keys`)
2. ക്ലൗഡ് സമന്വയം പ്രവർത്തിപ്പിക്കുക: ക്ലൗഡ് പ്രവർത്തനക്ഷമമാക്കുക → ഇപ്പോൾ സമന്വയിപ്പിക്കുക
3. പഴയതോ സമന്വയിപ്പിക്കാത്തതോ ആയ കീകൾക്ക് ക്ലൗഡിൽ ഇപ്പോഴും `401` ലഭിക്കാം

## Docker പ്രശ്നങ്ങൾ

### Docker IPv6 / കണക്ഷൻ റീസെറ്റ്

<a name="docker-ipv6"></a>

**ലക്ഷണങ്ങൾ:** `curl http://localhost:20128/v1/models` പ്രവർത്തിപ്പിക്കുമ്പോൾ `curl: (56) Recv failure: Connection reset by peer` ലഭിക്കുന്നു. ഡാഷ്ബോർഡും പ്രാമാണീകരണം ആവശ്യമില്ലാത്ത എൻഡ്പോയിന്റുകളും പ്രവർത്തിക്കുന്നുവെങ്കിലും പ്രാമാണീകരിച്ച എൻഡ്പോയിന്റുകൾ പരാജയപ്പെടുന്നു — ഇത് ഒരു പ്രാമാണീകരണ പ്രശ്നമായി തോന്നുമെങ്കിലും യഥാർത്ഥത്തിൽ അങ്ങനെയല്ല.

**കാരണം:** `docker run -p 20128:20128` എന്നത് `0.0.0.0` (IPv4), `::` (IPv6) എന്നിവ രണ്ടിലും പ്രസിദ്ധീകരിക്കുന്നു, എന്നാൽ കണ്ടെയ്നറിനുള്ളിലെ പ്രോസസ് IPv4-ൽ മാത്രമാണ് ലിസൻ ചെയ്യുന്നത്. `localhost` ആദ്യം `::1` ആയി റിസോൾവ് ചെയ്യുന്ന ഹോസ്റ്റുകളിൽ, കണക്ഷൻ പിന്നിൽ ലിസണർ ഇല്ലാത്ത IPv6 പ്രസിദ്ധീകരിച്ച പോർട്ടിൽ എത്തുന്നു → കണക്ഷൻ റീസെറ്റ്.

**പരിഹാരം:**

1. **ദ്രുത പരിശോധന:** `curl -4 http://localhost:20128/v1/models` പ്രവർത്തിപ്പിക്കുക. `-4` ഉപയോഗിക്കുമ്പോൾ പ്രവർത്തിക്കുകയും അതില്ലാതെ പരാജയപ്പെടുകയും ചെയ്യുന്നുവെങ്കിൽ, നിങ്ങൾക്ക് IPv6 ബൈൻഡ് പൊരുത്തക്കേടുണ്ട്.
2. **സ്ഥിരമായ പരിഹാരം:** നിങ്ങളുടെ `docker run` കമാൻഡിൽ `-p 127.0.0.1:20128:20128` ഉപയോഗിച്ച് IPv4-ലേക്ക് വ്യക്തമായി ബൈൻഡ് ചെയ്യുക:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ഇത് IPv4 ബൈൻഡ് നിർബന്ധമാക്കുകയും എല്ലാ ഹോസ്റ്റ് ഇന്റർഫേസുകളിലും പ്രോക്സി ലഭ്യമാകുന്നത് ഒഴിവാക്കുകയും ചെയ്യുന്നു.

2. പോർട്ടബിൾ മോഡിനായി: `runner-cli` ഇമേജ് ടാർഗറ്റ് ഉപയോഗിക്കുക (CLI-കൾ ഉൾപ്പെടുത്തിയിരിക്കുന്നു)
3. ഹോസ്റ്റ് മൗണ്ട് മോഡിനായി: `CLI_EXTRA_PATHS` സജ്ജമാക്കി ഹോസ്റ്റ് bin ഡയറക്ടറി റീഡ്-ഒൺലി ആയി മൗണ്ട് ചെയ്യുക
4. `installed=true`, `runnable=false` എന്നിങ്ങനെയാണെങ്കിൽ: ബൈനറി കണ്ടെത്തിയെങ്കിലും ഹെൽത്ത്ചെക്ക് പരാജയപ്പെട്ടു

## ഡീബഗ്ഗിംഗ്

### ലോഗ് ഫയലുകൾ പ്രവർത്തനക്ഷമമാക്കുക

നിങ്ങളുടെ `.env` ഫയലിൽ `APP_LOG_TO_FILE=true` സജ്ജമാക്കുക. ആപ്ലിക്കേഷൻ ലോഗുകൾ `logs/`-ന് കീഴിൽ എഴുതപ്പെടുന്നു.
ക്രമീകരണങ്ങളിൽ കോൾ ലോഗ് പൈപ്പ്ലൈൻ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, റിക്വസ്റ്റ് ആർട്ടിഫാക്റ്റുകൾ `${DATA_DIR}/call_logs/`-ന് കീഴിൽ സംഭരിക്കുന്നു.
പൈപ്പ്ലൈൻ ക്യാപ്ചർ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ, സ്ട്രീം ചങ്ക് പേലോഡുകൾ ഒഴിവാക്കാൻ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` സജ്ജമാക്കുക, അല്ലെങ്കിൽ ആർട്ടിഫാക്റ്റിന്റെ KB പരിധി മാറ്റാൻ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ക്രമീകരിക്കുക.

### പ്രൊവൈഡർ ഹെൽത്ത് പരിശോധിക്കുക

```bash
# ഹെൽത്ത് ഡാഷ്ബോർഡ്
http://localhost:20128/dashboard/health

# API ഹെൽത്ത് പരിശോധന
curl http://localhost:20128/api/monitoring/health
```

### റൺടൈം സ്റ്റോറേജ്

- പ്രധാന സ്റ്റേറ്റ്: `${DATA_DIR}/storage.sqlite` (പ്രൊവൈഡറുകൾ, കോംബോകൾ, അപരനാമങ്ങൾ, കീകൾ, ക്രമീകരണങ്ങൾ)
- ഉപയോഗം: `storage.sqlite`-ലെ SQLite ടേബിളുകൾ (`usage_history`, `call_logs`, `proxy_logs`) + ഓപ്ഷണൽ `${DATA_DIR}/call_logs/`
- ആപ്ലിക്കേഷൻ ലോഗുകൾ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ആയിരിക്കുമ്പോൾ)
- കോൾ ലോഗ് ആർട്ടിഫാക്റ്റുകൾ: കോൾ ലോഗ് പൈപ്പ്ലൈൻ പ്രവർത്തനക്ഷമമാക്കിയിരിക്കുമ്പോൾ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

റിക്വസ്റ്റ് ലോഗുകൾ പേജിലെ **ചരിത്രം മായ്ക്കുക** നടപടി `call_logs`, പഴയ
`request_detail_logs`, ലോക്കൽ `${DATA_DIR}/call_logs/` ആർട്ടിഫാക്റ്റ് ഡയറക്ടറി എന്നിവ മായ്ക്കുന്നു.

## സർക്യൂട്ട് ബ്രേക്കർ പ്രശ്നങ്ങൾ

### പ്രൊവൈഡർ OPEN നിലയിൽ കുടുങ്ങിക്കിടക്കുന്നു

ഒരു പ്രൊവൈഡറിന്റെ സർക്യൂട്ട് ബ്രേക്കർ OPEN ആയിരിക്കുമ്പോൾ, കൂൾഡൗൺ കാലാവധി കഴിയുന്നതുവരെ അഭ്യർത്ഥനകൾ തടയപ്പെടും.

**പരിഹാരം:**

1. **ഡാഷ്ബോർഡ് → ക്രമീകരണങ്ങൾ → പ്രതിരോധശേഷി** എന്നതിലേക്ക് പോകുക
2. ബാധിക്കപ്പെട്ട പ്രൊവൈഡറിന്റെ സർക്യൂട്ട് ബ്രേക്കർ കാർഡ് പരിശോധിക്കുക
3. എല്ലാ ബ്രേക്കറുകളും മായ്ക്കാൻ **എല്ലാം റീസെറ്റ് ചെയ്യുക** ക്ലിക്ക് ചെയ്യുക, അല്ലെങ്കിൽ കൂൾഡൗൺ കാലാവധി കഴിയുന്നതുവരെ കാത്തിരിക്കുക
4. റീസെറ്റ് ചെയ്യുന്നതിനുമുമ്പ് പ്രൊവൈഡർ യഥാർത്ഥത്തിൽ ലഭ്യമാണെന്ന് സ്ഥിരീകരിക്കുക

### പ്രൊവൈഡർ സർക്യൂട്ട് ബ്രേക്കർ വീണ്ടും വീണ്ടും ട്രിപ്പ് ചെയ്യുന്നു

ഒരു പ്രൊവൈഡർ ആവർത്തിച്ച് OPEN നിലയിലേക്ക് പ്രവേശിക്കുകയാണെങ്കിൽ:

1. പരാജയങ്ങളുടെ പാറ്റേൺ കണ്ടെത്താൻ **ഡാഷ്ബോർഡ് → ആരോഗ്യനില → പ്രൊവൈഡർ ആരോഗ്യനില** പരിശോധിക്കുക
2. **ക്രമീകരണങ്ങൾ → പ്രതിരോധശേഷി → പ്രൊവൈഡർ പ്രൊഫൈലുകൾ** എന്നതിലേക്ക് പോയി പരാജയ പരിധി വർധിപ്പിക്കുക
3. പ്രൊവൈഡർ API പരിധികൾ മാറ്റിയിട്ടുണ്ടോ അല്ലെങ്കിൽ വീണ്ടും പ്രാമാണീകരണം ആവശ്യമാണോ എന്ന് പരിശോധിക്കുക
4. ലേറ്റൻസി ടെലിമെട്രി പരിശോധിക്കുക — ഉയർന്ന ലേറ്റൻസി ടൈംഔട്ട് അടിസ്ഥാനമാക്കിയുള്ള പരാജയങ്ങൾക്ക് കാരണമാകാം

## ഓഡിയോ ട്രാൻസ്ക്രിപ്ഷൻ പ്രശ്നങ്ങൾ

### "പിന്തുണയ്ക്കാത്ത മോഡൽ" പിശക്

- **ഡാഷ്ബോർഡ് → പ്രൊവൈഡർമാർ** എന്നതിൽ പ്രൊവൈഡർ കണക്റ്റ് ചെയ്തിട്ടുണ്ടെന്ന് സ്ഥിരീകരിക്കുക

### ട്രാൻസ്ക്രിപ്ഷൻ ശൂന്യമായി ലഭിക്കുന്നു അല്ലെങ്കിൽ പരാജയപ്പെടുന്നു

- പിന്തുണയ്ക്കുന്ന ഓഡിയോ ഫോർമാറ്റുകൾ പരിശോധിക്കുക: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ഫയൽ വലുപ്പം പ്രൊവൈഡറുടെ പരിധിക്കുള്ളിലാണെന്ന് സ്ഥിരീകരിക്കുക (സാധാരണയായി < 25MB)
- പ്രൊവൈഡർ കാർഡിലെ API കീ സാധുവാണോ എന്ന് പരിശോധിക്കുക

### സാധാരണ ഫോർമാറ്റ് പ്രശ്നങ്ങൾ

- **തിങ്കിങ് ടാഗുകൾ ദൃശ്യമാകുന്നില്ല** — ലക്ഷ്യ പ്രൊവൈഡർ തിങ്കിങ് പിന്തുണയ്ക്കുന്നുണ്ടോ എന്നും തിങ്കിങ് ബജറ്റ് ക്രമീകരണവും പരിശോധിക്കുക
- **ടൂൾ കോളുകൾ ഒഴിവാകുന്നു** — ചില ഫോർമാറ്റ് പരിവർത്തനങ്ങൾ പിന്തുണയ്ക്കാത്ത ഫീൽഡുകൾ നീക്കം ചെയ്തേക്കാം; പ്ലേഗ്രൗണ്ട് മോഡിൽ സ്ഥിരീകരിക്കുക
- **സിസ്റ്റം പ്രോംപ്റ്റ് കാണുന്നില്ല** — Claude, Gemini എന്നിവ സിസ്റ്റം പ്രോംപ്റ്റുകൾ വ്യത്യസ്തമായി കൈകാര്യം ചെയ്യുന്നു; പരിവർത്തന ഔട്ട്പുട്ട് പരിശോധിക്കുക
- **SDK ഒബ്ജക്റ്റിന് പകരം റോ സ്ട്രിങ് നൽകുന്നു** — v1.x-ൽ പരിഹരിച്ചു; OpenAI SDK Pydantic വാലിഡേഷൻ പരാജയങ്ങൾക്ക് കാരണമാകുന്ന നിലവാരമില്ലാത്ത ഫീൽഡുകൾ (`x_groq`, `usage_breakdown` മുതലായവ) റെസ്പോൺസ് സാനിറ്റൈസർ നീക്കം ചെയ്യുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **GLM/ERNIE `system` റോൾ നിരസിക്കുന്നു** — v1.x-ൽ പരിഹരിച്ചു; പൊരുത്തപ്പെടാത്ത മോഡലുകൾക്കായി റോൾ നോർമലൈസർ സിസ്റ്റം സന്ദേശങ്ങളെ സ്വയമേവ ഉപയോക്തൃ സന്ദേശങ്ങളുമായി ലയിപ്പിക്കുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **`developer` റോൾ തിരിച്ചറിയുന്നില്ല** — v1.x-ൽ പരിഹരിച്ചു; OpenAI ഇതര പ്രൊവൈഡർമാർക്കായി ഇത് സ്വയമേവ `system` ആയി പരിവർത്തനം ചെയ്യുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.
- **Gemini-യോടൊപ്പം `json_schema` പ്രവർത്തിക്കുന്നില്ല** — v1.x-ൽ പരിഹരിച്ചു; `response_format` ഇപ്പോൾ Gemini-യുടെ `responseMimeType` + `responseSchema` എന്നതിലേക്ക് പരിവർത്തനം ചെയ്യുന്നു. v3.x+-ലും ഇത് കാണുന്നുണ്ടെങ്കിൽ, ദയവായി ഒരു ഇഷ്യൂ ഫയൽ ചെയ്യുക.

## പ്രതിരോധശേഷി ക്രമീകരണങ്ങൾ

### സ്വയമേവയുള്ള നിരക്ക്-പരിധി പ്രവർത്തനക്ഷമമാകുന്നില്ല

- സ്വയമേവയുള്ള നിരക്ക്-പരിധി API കീ ദാതാക്കൾക്ക് മാത്രമേ ബാധകമാകൂ (OAuth/സബ്സ്ക്രിപ്ഷന് ബാധകമല്ല)
- **Settings → Resilience → Provider Profiles** എന്നതിൽ സ്വയമേവയുള്ള നിരക്ക്-പരിധി പ്രവർത്തനക്ഷമമാക്കിയിട്ടുണ്ടെന്ന് സ്ഥിരീകരിക്കുക
- ദാതാവ് `429` സ്റ്റാറ്റസ് കോഡുകളോ `Retry-After` ഹെഡറുകളോ നൽകുന്നുണ്ടോയെന്ന് പരിശോധിക്കുക

### എക്സ്പോണൻഷ്യൽ ബാക്ക്ഓഫ് ക്രമീകരിക്കൽ

ദാതൃ പ്രൊഫൈലുകൾ ഈ ക്രമീകരണങ്ങളെ പിന്തുണയ്ക്കുന്നു:

- **അടിസ്ഥാന കാലതാമസം** — ആദ്യ പരാജയത്തിനു ശേഷമുള്ള പ്രാരംഭ കാത്തിരിപ്പ് സമയം (സ്ഥിരസ്ഥിതി: 1s)
- **പരമാവധി കാലതാമസം** — കാത്തിരിപ്പ് സമയത്തിന്റെ പരമാവധി പരിധി (സ്ഥിരസ്ഥിതി: 30s)
- **ഗുണകം** — തുടർച്ചയായ ഓരോ പരാജയത്തിലും കാലതാമസം എത്രത്തോളം വർധിപ്പിക്കണം (സ്ഥിരസ്ഥിതി: 2x)

### തണ്ടറിങ് ഹെർഡ് പ്രതിരോധം

ഒരേസമയം നിരവധി അഭ്യർത്ഥനകൾ നിരക്ക്-പരിമിതപ്പെടുത്തിയ ഒരു ദാതാവിലേക്ക് എത്തുമ്പോൾ, അഭ്യർത്ഥനകളെ ക്രമാനുഗതമാക്കാനും തുടർച്ചയായ പരാജയങ്ങൾ തടയാനും OmniRoute മ്യൂട്ടെക്സും സ്വയമേവയുള്ള നിരക്ക്-പരിധിയും ഉപയോഗിക്കുന്നു. API കീ ദാതാക്കൾക്ക് ഇത് സ്വയമേവ സംഭവിക്കുന്നു.

### ചാറ്റ് അഭ്യർത്ഥനകൾ 503 / chat_admission_busy ഉപയോഗിച്ച് പരാജയപ്പെടുന്നു

**ലക്ഷണങ്ങൾ:**

- ചാറ്റ് പൂർത്തീകരണ എൻഡ്പോയിന്റ്, `chat_admission_busy` എന്ന പിശക് കോഡുള്ള വീണ്ടും ശ്രമിക്കാവുന്ന
  `503` പ്രതികരണം നൽകുന്നു.
- പ്രതികരണത്തിൽ `Retry-After` ഉൾപ്പെടുന്നു. #12135 മുതൽ, നിരീക്ഷിച്ച ഉപയോഗനിലയിൽ നിന്നാണ് അതിന്റെ മൂല്യം
  നിർണ്ണയിക്കുന്നത് — അഭ്യർത്ഥന ഇതിനകം കാത്തിരുന്ന `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ജാലകത്തിന്റെയും
  നിലവിലെ ഭാരമേറിയ ലീസുകൾ കൈവശം വച്ചിരിക്കുന്ന സമയത്തിന്റെയും വലിയ മൂല്യം — പൂർണ്ണ
  സെക്കൻഡുകളിലേക്ക് ഉയർത്തി റൗണ്ട് ചെയ്യുകയും പരമാവധി 60 ആയി പരിമിതപ്പെടുത്തുകയും ചെയ്യുന്നു. നിഷ്ക്രിയമായ ഒരു ഗേറ്റിൽ ഇത്
  ചരിത്രപരമായ കുറഞ്ഞ പരിധികൾ നിലനിർത്തുന്നു: ബൈറ്റ് അടിസ്ഥാനമാക്കിയുള്ള പാതയിൽ 2 സെക്കൻഡ്,
  ഘടന അടിസ്ഥാനമാക്കിയുള്ള പാതയിൽ 1 സെക്കൻഡ് (ഇതിൽ
  `reason: "structure_limit"` എന്നതും ഉൾപ്പെടുന്നു).
- മറ്റൊരു ഭാരമേറിയ ചാറ്റോ ദീർഘനേരം പ്രവർത്തിക്കുന്ന സ്ട്രീമിങ് പ്രതികരണമോ ഇപ്പോഴും
  പുരോഗതിയിലായിരിക്കുമ്പോൾ ഇത് സംഭവിക്കാം.

ബൈറ്റ് അടിസ്ഥാനമാക്കിയുള്ള പ്രതികരണ ബോഡി:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ഘടന അടിസ്ഥാനമാക്കിയുള്ള പ്രതികരണം അതേ ടൈപ്പും കോഡും ഉപയോഗിക്കുന്നു, സന്ദേശം
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
എന്നതും `reason: "structure_limit"` എന്നതുമാണ്.
സ്ഥിരസ്ഥിതി പരിധികളിൽ, ഒരു അഭ്യർത്ഥനയിൽ കുറഞ്ഞത് `200` സന്ദേശങ്ങളോ,
കുറഞ്ഞത് `64` ടൂളുകളോ, കുറഞ്ഞത് `32,000` കണക്കാക്കിയ ടോക്കണുകളോ ഉണ്ടെങ്കിൽ, അല്ലെങ്കിൽ പരിമിതപ്പെടുത്തിയ ഘടനാ കണക്കുകൂട്ടൽ
സന്ദർശിച്ച `10,000` നോഡുകളുടെ പരിധിയോ `12` ആഴമോ പൂർണ്ണമായി ഉപയോഗിച്ചാൽ, അത് ഘടനാപരമായി ഭാരമേറിയതാണ്.

**കാരണം:** ഇത് OmniRoute-നുള്ളിലെ മനഃപൂർവമായ ലോഡ് ഷെഡ്ഡിങ്ങാണ്, അപ്സ്ട്രീം ദാതാവിന്റെ പരാജയമല്ല.
ഒരു വലിയ അഭ്യർത്ഥനാ ബോഡി നിലനിർത്തി പാർസ് ചെയ്യുന്നതിനു മുമ്പ് പരിമിതമായ ഭാരമേറിയ ശേഷി റിസർവ് ചെയ്യാൻ
ഓരോ പ്രോസസ്സും പ്രോസസ്-ലോക്കൽ ഗാർഡ് ഉപയോഗിക്കുന്നു. ഒരു SSE പ്രതികരണത്തിന്റെ ആയുഷ്കാലം മുഴുവൻ
ഭാരമേറിയ ലീസ് കൈവശം തുടരും.

**#503-ഫാൻ-ഔട്ട്:** ഈ പരിഹാരത്തിനു മുമ്പ്, ഹോസ്റ്റ് മെമ്മറി പരിഗണിക്കാതെ ഗാർഡ് കൺകറൻസി ഒരു നിശ്ചിത അഭ്യർത്ഥനാ എണ്ണത്തിൽ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, സ്ഥിരസ്ഥിതി `1`) പരിമിതപ്പെടുത്തിയിരുന്നു. അതിനാൽ കോഡിങ്-ഏജന്റ്
ഫാൻ-ഔട്ട് (ഒന്നിലധികം സബ്ഏജന്റുകൾ/CLI-കൾ, പതിവായി 256 KB-യിൽ കൂടുതലുള്ള ബോഡികൾ) ഫലപ്രദമായ
കൺകറൻസി ~1 ആയി ചുരുക്കുകയും പൂർണ്ണമായും സാധാരണ ലോഡിൽ 503 പിശകുകൾ ഉണ്ടാക്കുകയും ചെയ്തു. ഇപ്പോൾ ഗാർഡ് സ്വയം ക്രമീകരിക്കുന്നു:
പ്രോസസ്സിന്റെ യഥാർഥ മെമ്മറി പരിധിയിൽ നിന്ന് വലുപ്പം നിർണ്ണയിക്കുന്ന, സ്വയമേവ രൂപപ്പെടുത്തുന്ന ഇൻജെസ്റ്റ് ബൈറ്റ് ബജറ്റ്
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ആണ് അതിനെ നിയന്ത്രിക്കുന്നത്. കൂടാതെ അത് തത്സമയ റിസോഴ്സ്-പ്രഷർ
സിഗ്നലും പരിശോധിക്കുന്നു — അതിനാൽ ഒരേ സമയം ഒന്നിലധികം ഭാരമേറിയ അഭ്യർത്ഥനകൾ എത്തിയെന്ന കാരണത്താൽ മാത്രമല്ല,
ഹോസ്റ്റ് യഥാർഥത്തിൽ മെമ്മറി സമ്മർദ്ദത്തിലായിരിക്കുമ്പോൾ മാത്രമേ അത് ലോഡ് കുറയ്ക്കൂ. പഴയ എണ്ണം-പരിധി
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ഇപ്പോഴും മാനിക്കപ്പെടുന്നു, എന്നാൽ നിങ്ങൾ അത് വ്യക്തമായി സജ്ജീകരിച്ചാൽ മാത്രം.

ശേഷി തിരക്കിലായിരിക്കുമ്പോൾ, വീണ്ടും ശ്രമിക്കാവുന്ന `503` മറുപടി നൽകുന്നതിനു മുമ്പ് ഒരു സ്ലോട്ട് ഒഴിവാകാൻ
ഭാരമേറിയ അഭ്യർത്ഥന ആദ്യം `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` വരെ (സ്ഥിരസ്ഥിതി `2000`, `0` കാത്തിരിപ്പ് പ്രവർത്തനരഹിതമാക്കുന്നു)
കാത്തിരിക്കും. ഭാരമേറിയ ഉപ-അഭ്യർത്ഥനകൾ ഒരേസമയം ഫാൻ-ഔട്ട് ചെയ്യുന്ന ഏജന്റ്-ശൈലി ക്ലയന്റുകൾ
(OpenCode, Claude Code, Cursor), ഉടനടിയുള്ള നിരസിക്കലുകളിൽ അവരുടെ മുഴുവൻ പുനഃശ്രമ ബജറ്റും ചെലവഴിച്ച്
ടാസ്ക്കിന്റെ മധ്യേ പരാജയപ്പെടുന്നതിനു പകരം, അഭ്യർത്ഥനാ തിരക്ക് ക്രമാനുഗതമാക്കുന്നതിനാണ് ഈ പരിമിത കാത്തിരിപ്പ്.
നിലവിലെ ഭാരമേറിയ ലീസ് ഉപയോഗനില, നിർണ്ണയിച്ച ബൈറ്റ് ബജറ്റ്, തത്സമയ സമ്മർദ്ദത്തിന്റെ തീവ്രത എന്നിവ
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) എന്നതിൽ ലഭ്യമാണ് — ഏതെങ്കിലും env var മാറ്റുന്നതിനു മുമ്പ് ഇവ പരിശോധിക്കുക.
Settings → Resilience → Request Queue → Concurrent Requests ഇതിനെ നിയന്ത്രിക്കുന്നില്ല; ആ ക്രമീകരണം
വ്യത്യസ്തമായൊരു ദാതൃ അഭ്യർത്ഥനാ-ക്യൂ സംവിധാനം നിയന്ത്രിക്കുന്നു.

**പരിഹാരം:**

1. ആദ്യം വീണ്ടും ശ്രമിക്കുക. അഭ്യർത്ഥന ഉടൻ ആവർത്തിക്കുന്നതിനു പകരം ക്ലയന്റുകൾ `Retry-After` മാനിക്കുകയും
   ബാക്ക്ഓഫ് ഉപയോഗിക്കുകയും വേണം.
2. എന്തെങ്കിലും ക്രമീകരിക്കുന്നതിനു മുമ്പ് `/api/monitoring/health` → `chatAdmission` പരിശോധിക്കുക. `countCapEnabled:
false` എന്നതും മതിയായ `maxInflightBytes` എന്നതും സ്വയമേവ രൂപപ്പെടുത്തിയ ബജറ്റ് ഇതിനകം തന്നെ അതിന്റെ
   ജോലി ചെയ്യുന്നുവെന്ന് അർത്ഥമാക്കുന്നു; `high`/`critical` എന്ന `pressureSeverity`, ഹോസ്റ്റിൽ യഥാർഥത്തിൽ മെമ്മറി കുറവാണെന്ന് സൂചിപ്പിക്കുന്നു —
   അത് ഒരു അഡ്മിഷൻ env var ഉപയോഗിച്ച് പരിഹരിക്കാനാവില്ല; അതിന് കൂടുതൽ RAM അല്ലെങ്കിൽ ചെറിയൊരു വർക്ക്ലോഡ് ആവശ്യമാണ്.
3. `/api/monitoring/health`, സ്വയമേവ രൂപപ്പെടുത്തിയ ബജറ്റ് നിങ്ങളുടെ ഹോസ്റ്റിന് യഥാർഥത്തിൽ വളരെ ചെറുതാണെന്ന്
   കാണിക്കുന്നുവെങ്കിൽ മാത്രം (അപൂർവം — ഇത് ഇതിനകം തന്നെ കണ്ടെയ്നറിൽ നിന്ന് ബെയർ-മെറ്റൽ വരെ സ്കെയിൽ ചെയ്യുന്നു), പഴയ അഭ്യർത്ഥനാ-എണ്ണ പരിധിയിലേക്ക്
   മടങ്ങുന്നതിനു പകരം `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ഉപയോഗിച്ച് അതിനെ നേരിട്ട് ഓവർറൈഡ് ചെയ്യുക.

ആധികാരിക അഡ്മിഷൻ ക്രമീകരണങ്ങൾക്കായി [പരിസ്ഥിതി-വേരിയബിൾ റഫറൻസ്](../reference/ENVIRONMENT.md#4-security--authentication)
കാണുക.

## ഐച്ഛിക RAG / LLM പരാജയ വർഗ്ഗീകരണം (16 പ്രശ്നങ്ങൾ)

ചില OmniRoute ഉപയോക്താക്കൾ RAG അല്ലെങ്കിൽ ഏജന്റ് സ്റ്റാക്കുകൾക്ക് മുന്നിൽ ഗേറ്റ്വേ സ്ഥാപിക്കുന്നു. അത്തരം സജ്ജീകരണങ്ങളിൽ അസാധാരണമായ ഒരു രീതി കാണുന്നത് സാധാരണമാണ്: OmniRoute ആരോഗ്യകരമായി കാണപ്പെടുന്നു (ദാതാക്കൾ പ്രവർത്തനക്ഷമമാണ്, റൂട്ടിംഗ് പ്രൊഫൈലുകൾ ശരിയാണ്, നിരക്ക് പരിധി മുന്നറിയിപ്പുകളില്ല), എന്നിട്ടും അന്തിമ ഉത്തരം തെറ്റായിരിക്കും.

പ്രായോഗികമായി, ഈ സംഭവങ്ങൾ സാധാരണയായി ഗേറ്റ്വേയിൽ നിന്നല്ല, പകരം ഡൗൺസ്ട്രീം RAG പൈപ്പ്ലൈനിൽ നിന്നാണ് ഉണ്ടാകുന്നത്.

ആ പരാജയങ്ങൾ വിവരിക്കാൻ പൊതുവായ ഒരു പദാവലി വേണമെങ്കിൽ, ആവർത്തിച്ച് സംഭവിക്കുന്ന പതിനാറ് RAG / LLM പരാജയ രീതികൾ നിർവചിക്കുന്ന, MIT ലൈസൻസുള്ള ഒരു ബാഹ്യ ടെക്സ്റ്റ് വിഭവമായ WFGY ProblemMap ഉപയോഗിക്കാം. ഉയർന്ന തലത്തിൽ ഇത് ഇനിപ്പറയുന്നവ ഉൾക്കൊള്ളുന്നു:

- റിട്രീവൽ വ്യതിചലനവും തകർന്ന കോൺടെക്സ്റ്റ് അതിരുകളും
- ശൂന്യമായതോ പഴകിയതോ ആയ ഇൻഡെക്സുകളും വെക്റ്റർ സ്റ്റോറുകളും
- എംബെഡിംഗും സെമാന്റിക് അർത്ഥവും തമ്മിലുള്ള പൊരുത്തക്കേട്
- പ്രോംപ്റ്റ് അസംബ്ലിയും കോൺടെക്സ്റ്റ് വിൻഡോയുമായി ബന്ധപ്പെട്ട പ്രശ്നങ്ങളും
- ലോജിക് തകർച്ചയും അമിത ആത്മവിശ്വാസത്തോടെയുള്ള ഉത്തരങ്ങളും
- ദൈർഘ്യമേറിയ ചെയിനുകളുടെയും ഏജന്റ് ഏകോപനത്തിന്റെയും പരാജയങ്ങൾ
- മൾട്ടി-ഏജന്റ് മെമ്മറിയുടെയും റോളുകളുടെയും വ്യതിചലനം
- ഡിപ്ലോയ്മെന്റിലെയും ബൂട്ട്സ്ട്രാപ്പ് ക്രമീകരണത്തിലെയും പ്രശ്നങ്ങൾ

ആശയം ലളിതമാണ്:

1. ഒരു മോശം പ്രതികരണം അന്വേഷിക്കുമ്പോൾ, ഇനിപ്പറയുന്നവ രേഖപ്പെടുത്തുക:
   - ഉപയോക്തൃ ടാസ്കും അഭ്യർത്ഥനയും
   - OmniRoute-ലെ റൂട്ട് അല്ലെങ്കിൽ പ്രൊവൈഡർ കോംബോ
   - ഡൗൺസ്ട്രീമിൽ ഉപയോഗിച്ച ഏതെങ്കിലും RAG കോൺടെക്സ്റ്റ് (റിട്രീവ് ചെയ്ത ഡോക്യുമെന്റുകൾ, ടൂൾ കോളുകൾ തുടങ്ങിയവ)
2. സംഭവത്തെ ഒന്നോ രണ്ടോ WFGY ProblemMap നമ്പറുകളിലേക്ക് (`No.1` … `No.16`) മാപ്പ് ചെയ്യുക.
3. OmniRoute ലോഗുകൾക്ക് സമീപം നിങ്ങളുടെ സ്വന്തം ഡാഷ്ബോർഡിലോ റൺബുക്കിലോ ഇൻസിഡന്റ് ട്രാക്കറിലോ ആ നമ്പർ സംഭരിക്കുക.
4. നിങ്ങളുടെ RAG സ്റ്റാക്ക്, റിട്രീവർ, അല്ലെങ്കിൽ റൂട്ടിംഗ് തന്ത്രം മാറ്റേണ്ടതുണ്ടോ എന്ന് തീരുമാനിക്കാൻ അനുബന്ധ WFGY പേജ് ഉപയോഗിക്കുക.

പൂർണ്ണമായ ടെക്സ്റ്റും പ്രായോഗിക നടപടിക്രമങ്ങളും ഇവിടെ ലഭ്യമാണ് (MIT ലൈസൻസ്, ടെക്സ്റ്റ് മാത്രം):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute-ന് പിന്നിൽ നിങ്ങൾ RAG അല്ലെങ്കിൽ ഏജന്റ് പൈപ്പ്ലൈനുകൾ പ്രവർത്തിപ്പിക്കുന്നില്ലെങ്കിൽ ഈ വിഭാഗം അവഗണിക്കാം.

## v3.8.0-ലെ അറിയപ്പെടുന്ന പ്രശ്നങ്ങൾ

v3.8.0 റിലീസിന് മാത്രമുള്ള പ്രശ്നങ്ങളും അവയ്ക്കുള്ള നിലവിലെ പരിഹാര മാർഗങ്ങളും. പിന്നീടുള്ള ഒരു പാച്ചിൽ പരിഹാരം ലഭിച്ചാൽ, ഈ എൻട്രി അപ്ഡേറ്റ് ചെയ്യുകയോ നീക്കം ചെയ്യുകയോ ചെയ്യും.

### Devin CLI ഓതന്റിക്കേഷൻ പരാജയങ്ങൾ

**ലക്ഷണങ്ങൾ:**

- Devin പിന്തുണയുള്ള ടൂളുകൾ പ്രവർത്തിപ്പിക്കുമ്പോൾ "Devin CLI കണ്ടെത്തിയില്ല" അല്ലെങ്കിൽ "ഓതന്റിക്കേഷൻ പരാജയപ്പെട്ടു" എന്ന് കാണിക്കുന്നു
- CLI റൺടൈം പരിശോധന `installed=false` എന്ന് റിപ്പോർട്ട് ചെയ്യുന്നു

**കാരണങ്ങൾ:**

- `CLI_DEVIN_BIN` നിലവിലില്ലാത്ത ഒരു പാതയിലേക്ക് ചൂണ്ടുന്നു
- ഹോസ്റ്റിൽ Devin CLI ഇൻസ്റ്റാൾ ചെയ്തിട്ടില്ല

**പരിഹാരം:**

1. നിങ്ങളുടെ പ്ലാറ്റ്ഫോമിനായുള്ള Devin CLI ഇൻസ്റ്റാൾ ചെയ്യുക
2. `.env`-ൽ `CLI_DEVIN_BIN=/usr/local/bin/devin` (അല്ലെങ്കിൽ യഥാർത്ഥ പാത) സജ്ജീകരിക്കുക
3. OmniRoute പുനരാരംഭിച്ച് **Dashboard → CLI Tools**-ൽ നിന്ന് വീണ്ടും പരിശോധിക്കുക

### മോഡൽ കൂൾഡൗൺ അവസാനിക്കുന്നില്ല (മാനുവൽ റീസെറ്റ്)

**ലക്ഷണങ്ങൾ:**

- കാലാവധി കഴിഞ്ഞ ശേഷവും ഒരു മോഡൽ കൂൾഡൗണിൽ ഉള്ളതായി പട്ടികയിൽ തുടരുന്നു
- ടൈംസ്റ്റാമ്പ് കഴിഞ്ഞ സമയത്തേതായിട്ടും കോംബോ റൂട്ടിംഗിലെ അഭ്യർത്ഥനകൾ ഇപ്പോഴും ആ മോഡൽ ഒഴിവാക്കുന്നു

**മാനുവൽ റീസെറ്റ്:**

- **Dashboard:** **Settings → Model Cooldowns** → ബാധിച്ച കാർഡിലെ **Re-enable** ക്ലിക്ക് ചെയ്യുക
- **API:** മാനേജ്മെന്റ് ഓതന്റിക്കേഷൻ ഹെഡറുകൾക്കൊപ്പം `DELETE /api/resilience/model-cooldowns`

### Command Code പ്രൊവൈഡർ കണക്ഷൻ 403 നൽകി പരാജയപ്പെടുന്നു

**ലക്ഷണങ്ങൾ:**

- Command Code പ്രൊവൈഡർ കണക്ഷൻ പരിശോധിക്കുമ്പോൾ 403 ലഭിക്കുന്നു
- പുതുതായി ചേർത്തതിന് ശേഷം പ്രൊവൈഡർ കാർഡ് "അനുമതിയില്ല" എന്ന് കാണിക്കുന്നു

**കാരണം:** OAuth ഫ്ലോ പൂർത്തിയായില്ല (കോൾബാക്ക് ലഭിച്ചില്ല അല്ലെങ്കിൽ ടോക്കൺ സ്ഥിരമായി സംഭരിച്ചില്ല).

**പരിഹാരം:**

- OAuth ഫ്ലോ വീണ്ടും ട്രിഗർ ചെയ്യാൻ CLI-യിൽ നിന്ന് `omniroute providers` പ്രവർത്തിപ്പിക്കുക, അല്ലെങ്കിൽ
- **Dashboard → Providers → Command Code → Reconnect**-ൽ നിന്ന് OAuth വീണ്ടും പ്രവർത്തിപ്പിക്കുക

### ModelScope അമിതമായ 429 കൂൾഡൗണുകൾ നൽകുന്നു

**ലക്ഷണങ്ങൾ:**

- ചെറിയൊരു അഭ്യർത്ഥനാ ബർസ്റ്റിന് ശേഷം ModelScope-ൽ വളരെ ചെറിയതോ ഉടനടിയുള്ളതോ ആയ കൂൾഡൗണുകൾ
- പ്രതീക്ഷിച്ചതിനേക്കാൾ നേരത്തേ കോംബോ റൂട്ടിംഗ് ModelScope ഒഴിവാക്കുന്നു

**കാരണം:** ModelScope പ്രൊവൈഡർ-നിർദ്ദിഷ്ട `Retry-After` ഹെഡറുകൾ നൽകുന്നു. ആ ഹെഡറുകൾക്കായുള്ള പ്രത്യേക കൈകാര്യം v3.8.0-ൽ ഉൾപ്പെടുത്തിയിട്ടുണ്ട്; അതിനാൽ പഴയ പതിപ്പുകൾ അവയെ പൊതുവായ നിരക്ക്-പരിധി സൂചനകളായി തെറ്റായി വായിക്കുന്നു.

**പരിഹാരം:**

- നിങ്ങൾ v3.8.0 അല്ലെങ്കിൽ അതിന് ശേഷമുള്ള പതിപ്പിലാണ് ഉപയോഗിക്കുന്നതെന്ന് ഉറപ്പാക്കുക
- **Settings → Resilience**-ന് കീഴിൽ `useUpstream429BreakerHints` ടോഗിൾ പ്രവർത്തനക്ഷമമാക്കിയിട്ടുണ്ടെന്ന് പരിശോധിക്കുക

### പ്രൊഡക്ഷനിൽ OMNIROUTE_WS_BRIDGE_SECRET ഇല്ല

**ലക്ഷണങ്ങൾ:**

- റിമോട്ട് പ്രൊഡക്ഷൻ ഹോസ്റ്റിൽ പ്രവർത്തിക്കുമ്പോൾ ഓരോ Codex/Responses WebSocket ബ്രിഡ്ജ് അഭ്യർത്ഥനയ്ക്കും 401 ലഭിക്കുന്നു
- കണക്റ്റ് ചെയ്ത ഉടൻ WebSocket ബ്രിഡ്ജ് ഹാൻഡ്ഷേക്ക് അവസാനിക്കുന്നു

**കാരണം:** പ്രൊഡക്ഷൻ എൻവയോൺമെന്റിൽ `OMNIROUTE_WS_BRIDGE_SECRET` എൻവയോൺമെന്റ് വേരിയബിൾ ഇല്ല.

**പരിഹാരം:**

1. ക്രമരഹിതമായ ഒരു സീക്രട്ട് സൃഷ്ടിക്കുക: `openssl rand -hex 32`
2. പ്രൊഡക്ഷൻ സെർവർ എൻവയോൺമെന്റിൽ (ബ്രിഡ്ജുമായി ആശയവിനിമയം നടത്തുന്ന ഏതൊരു ക്ലയന്റിലും) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` സജ്ജീകരിക്കുക
3. OmniRoute പുനരാരംഭിക്കുക

### Responses API: ബാക്ക്ഗ്രൗണ്ട് മോഡ് സിൻക്രണസ് മോഡിലേക്ക് താഴ്ത്തിയിരിക്കുന്നു

**ലക്ഷണങ്ങൾ:**

- ലോഗ് ചെയ്ത മുന്നറിയിപ്പ്: `background mode degraded to synchronous`
- ഒരു ബാക്ക്ഗ്രൗണ്ട് ജോബ് ഹാൻഡിലിന് പകരം `background: true` അഭ്യർത്ഥന സാധാരണ സിൻക്രണസ് പ്രതികരണം നൽകുന്നു

**കാരണം:** ഒരു മുന്നറിയിപ്പ് നൽകിക്കൊണ്ട് Responses API-യിലെ `background: true`-നെ v3.8.0 മനഃപൂർവം സിൻക്രണസ് എക്സിക്യൂഷനിലേക്ക് താഴ്ത്തുന്നു. പൂർണ്ണമായ അസിൻക്രണസ് ബാക്ക്ഗ്രൗണ്ട് എക്സിക്യൂഷൻ ഭാവിയിൽ ലഭ്യമാക്കാനിരിക്കുന്നതാണ്.

**പരിഹാരം:**

- `background` ഇല്ലാതെ കോൾ ചെയ്യുന്നതിന് ക്ലയന്റ് ക്രമീകരിക്കുക, അല്ലെങ്കിൽ
- പൂർണ്ണമായ അസിൻക്രണസ് ബാക്ക്ഗ്രൗണ്ട് മോഡ് ഉൾപ്പെടുന്ന പിന്നീടുള്ള റിലീസിനായി കാത്തിരിക്കുക (ചേഞ്ച്ലോഗ് പിന്തുടരുക)
