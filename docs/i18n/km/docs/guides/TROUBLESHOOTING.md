## ឯកសារយោងរហ័ស

**ទើបតែចាប់ផ្តើមប្រើ OmniRoute មែនទេ?** ចាប់ផ្តើមត្រង់នេះ — ដំណោះស្រាយទាំងនេះអាចដោះស្រាយបញ្ហាបាន 90%៖

| ខ្ញុំឃើញសារនេះ          | អត្ថន័យរបស់វា                                    | អ្វីដែលត្រូវធ្វើ                                                                                              |
| ----------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| "Can't connect"         | OmniRoute មិនកំពុងដំណើរការ                       | ដំណើរការ `omniroute` ឬ `docker restart omniroute`                                                             |
| "Invalid API key"       | សោរបស់អ្នកមិនត្រឹមត្រូវ ឬបានផុតកំណត់             | ចម្លងសោម្ដងទៀតពីគេហទំព័ររបស់អ្នកផ្តល់សេវា                                                                     |
| "Rate limit exceeded"   | អ្នកកំពុងផ្ញើសំណើច្រើនពេក                        | រង់ចាំ 1 នាទី ឬប្រើ `model: "auto"` ដើម្បីប្តូរទៅជម្រើសបម្រុងដោយស្វ័យប្រវត្តិ                                 |
| "Quota exceeded"        | អ្នកបានប្រើកូតាឥតគិតថ្លៃ/បង់ប្រាក់របស់អ្នកអស់ហើយ | ភ្ជាប់អ្នកផ្តល់សេវាបន្ថែម ឬប្រើអ្នកផ្តល់សេវាឥតគិតថ្លៃ (Kiro, Pollinations)                                    |
| "Slow responses"        | អ្នកផ្តល់សេវាកំពុងរវល់ ឬស្ថិតនៅឆ្ងាយ             | ប្រើ `model: "auto/fast"` ឬភ្ជាប់អ្នកផ្តល់សេវាដែលលឿនជាង (Groq, Cerebras)                                      |
| "Wrong provider used"   | `auto` បានជ្រើសអ្នកផ្តល់សេវាផ្សេង                | នេះជារឿងធម្មតា! `auto` ជ្រើសជម្រើសល្អបំផុត។ បង្ខំឱ្យប្រើអ្នកផ្តល់សេវាជាក់លាក់ដោយប្រើ `model: "openai/gpt-4o"` |
| "502 Bad Gateway"       | អ្នកផ្តល់សេវាមិនដំណើរការ                         | រង់ចាំ ហើយព្យាយាមម្តងទៀត ឬប្រើ `model: "auto"` ដើម្បីប្តូរអ្នកផ្តល់សេវា                                       |
| "401 Unauthorized"      | ព័ត៌មានសម្គាល់អត្តសញ្ញាណរបស់អ្នកមិនត្រឹមត្រូវ    | ពិនិត្យសោ API របស់អ្នក ឬផ្ទៀងផ្ទាត់អត្តសញ្ញាណម្តងទៀតតាម OAuth                                                 |
| "429 Too Many Requests" | ត្រូវបានកំណត់អត្រាសំណើ                           | រង់ចាំ 1 នាទី ឬភ្ជាប់អ្នកផ្តល់សេវាបន្ថែម                                                                      |

### ការកំណត់អត្រាសំណើលើអ្នកផ្តល់សេវាឥតគិតថ្លៃ (429 / 400 / 401)

**រោគសញ្ញា**៖ នៅពេលប្រើ `model: "auto"` ជាមួយអ្នកផ្តល់សេវាឥតគិតថ្លៃ/មិនទាមទារការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ (opencode, auggie ជាដើម) អ្នកទទួលបាន `HTTP 429`, `400` ឬ `401` ជាបន្តបន្ទាប់មិនទៀងទាត់ ជំនួសឱ្យចម្លើយ។ សំណើទាំងនោះជោគជ័យ នៅពេលព្យាយាម prompt ដដែលម្តងទៀតបន្តិចក្រោយមក ប៉ុន្តែស្វ័យប្រវត្តិកម្ម (cron jobs, agents, scripts) នឹងឈប់ដំណើរការនៅពេលបរាជ័យលើកដំបូង។

**មូលហេតុដើម**៖ របៀបបរាជ័យឯករាជ្យចំនួនបីកើតឡើងត្រួតគ្នា៖

1. **ការកំណត់អត្រារបស់អ្នកផ្តល់សេវា (`429`)**៖ កម្រិតឥតគិតថ្លៃអាចកំណត់កូតាសម្រាប់ចន្លោះពេលនីមួយៗ។ ការផ្ញើការហៅស្របគ្នាជាច្រើនភ្លាមៗធ្វើឱ្យកូតានោះអស់ ដូច្នេះសំណើបន្ទាប់នឹងត្រូវបដិសេធ រហូតដល់ចន្លោះពេលត្រូវបានកំណត់ឡើងវិញ។
2. **ម៉ូដែលខូចក្នុង passthrough (`400`/`401`)**៖ ក្រុម `auto/*` អាចរួមបញ្ចូលម៉ូដែល passthrough ពី `opencode` ដែលបានចុះបញ្ជីក្នុងកាតាឡុក ប៉ុន្តែមិនមានព័ត៌មានសម្គាល់អត្តសញ្ញាណដែលដំណើរការ (ឧ. `oc/north-mini-code-free` → `401`)។ auto-router ព្យាយាមប្រើម៉ូដែលមួយ បរាជ័យ ហើយកំហុសត្រូវបានបញ្ជូនបន្ត មុនពេលការប្តូរទៅជម្រើសបម្រុងចាប់ផ្តើម។
3. **ការពង្រីកផលប៉ះពាល់ដោយសារភាពស្របគ្នា (`429` ក្រោមបន្ទុក)**៖ នៅពេលសម័យ agent/cron ច្រើនប្រើ `auto` ក្នុងពេលតែមួយ អត្រាសំណើសរុបលើសពីកម្រិតដែលអ្នកផ្តល់សេវាឥតគិតថ្លៃអាចទទួលយកបាន ដូច្នេះការហៅស្របច្បាប់ត្រូវបានសម្គាល់ថាជាការប្រើប្រាស់បំពាន។

**ដំណោះស្រាយដែលបានផ្ទៀងផ្ទាត់ (រាយការណ៍ដោយសហគមន៍, 2026-08-10)**៖ កែតម្រូវអថេរបរិស្ថានចំនួនបី ដើម្បីឱ្យការបង្វិល ភាពស្របគ្នា និងការប្តូរទៅជម្រើសបម្រុងស្រូបយកភាពមិនទៀងទាត់របស់កម្រិតឥតគិតថ្លៃ ជំនួសឱ្យបរាជ័យដោយសារវា៖

```bash
export OMNIROUTE_ROTATE_ON_400=true           # ប្តូរទៅម៉ូដែល/អ្នកផ្តល់សេវាផ្សេងនៅពេលមាន 400/401 (រំលងម៉ូដែល passthrough ដែលខូច)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # កម្រិតទទួលយកការងារធ្ងន់អតិបរមាដែលកំណត់ជាក់លាក់ (មិនកំណត់តាមលំនាំដើម៖ គ្មានកម្រិតចំនួនសំណើ សូមមើលកំណត់សម្គាល់ខាងក្រោម)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # រង់ចាំក្នុងរយៈពេលកំណត់យូរជាងមុន ដើម្បីទទួលបានសមត្ថភាពសម្រាប់ការងារធ្ងន់ ជំនួសឱ្យ 503 ដែលអាចព្យាយាមម្តងទៀតភ្លាមៗ
```

កំណត់តម្លៃទាំងនេះក្នុងបរិស្ថានដំណើរការរបស់ OmniRoute (daemon ឧ. តាមរយៈ LaunchAgent plist ឬ `systemctl edit`) បន្ទាប់មកចាប់ផ្តើម OmniRoute ឡើងវិញ។ ទង់ការបង្វិលគឺជាចំណុចដែលមានឥទ្ធិពលខ្ពស់បំផុតតែមួយ៖ វាបម្លែងការបរាជ័យទាំងស្រុងទៅជាការព្យាយាមម្តងទៀតដោយតម្លាភាពជាមួយអ្នកផ្តល់សេវាដែលដំណើរការល្អនៅក្នុងក្រុម។

**កំណត់សម្គាល់**៖ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` កំណត់ចំនួនសំណើធ្ងន់ — ដែលមានបរិបទវែង — អតិបរមាដែលអាចដំណើរការក្នុងពេលតែមួយ។ កម្រិតនេះគឺជាច្រកទទួលយក មិនមែនជាឧបករណ៍កំណត់អត្រារបស់អ្នកផ្តល់សេវាទេ។ **បច្ចុប្បន្នភាព #503-fanout៖** អថេរនេះលែងត្រូវបានកំណត់តាមលំនាំដើមទៀតហើយ (ឥឡូវនេះវាមានប្រសិទ្ធភាពតែនៅពេលកំណត់ជាក់លាក់ ដូចខាងលើ) — ផ្ទុយទៅវិញ ការទទួលយកសំណើធ្ងន់ត្រូវបានគ្រប់គ្រងដោយថវិកាបៃដែលទាញយកដោយស្វ័យប្រវត្តិ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ដែលធ្វើមាត្រដ្ឋានខ្លួនឯងដោយផ្អែកលើកម្រិតអង្គចងចាំពិតប្រាកដរបស់ម៉ាស៊ីន ដូច្នេះការដាក់ឱ្យប្រើប្រាស់ថ្មីគួរតែឃើញការបដិសេធ `503 chat_admission_busy` តិចជាងមុនច្រើន ដោយមិនចាំបាច់កំណត់អថេរនេះទាល់តែសោះ។ ការកំណត់វាជាក់លាក់នៅទីនេះនៅតែដំណើរការត្រឹមត្រូវដូចដែលបានចងក្រងឯកសារ។ ការកំណត់ជំនួសថវិកាបៃជាក់លាក់ត្រូវបានកម្រិតក្នុងចន្លោះ 8 MiB–2 GiB។ `413 body_exceeds_budget` មិនមែនជាបញ្ហាបណ្តោះអាសន្នទេ៖ បង្កើនថវិកាបៃនោះ បន្ថយ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ឬបង្កើនកម្រិតអង្គចងចាំរបស់ដំណើរការ។ ការកាត់បន្ថយបន្ទុក `inflight_bytes_budget` គឺជាការប្រជែងធនធានបណ្តោះអាសន្ន ហើយនៅតែអាចព្យាយាមម្តងទៀតបាន។ ការកំណត់អត្រាសម្រាប់អ្នកផ្តល់សេវានីមួយៗ (`open-sse/services/rateLimitManager.ts`) ត្រូវបានគ្រប់គ្រងដោយឡែកតាមរយៈ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` និង `RATE_LIMIT_AUTO_ENABLE` — សូមមើល `.env.example`។

**របៀបផ្ទៀងផ្ទាត់ថាវាដំណើរការ**៖ ដំណើរការ agent/cron របស់អ្នកពីរដងជាប់ៗគ្នា ហើយបញ្ជាក់ថាទាំងពីរជោគជ័យ។ មុនពេលអនុវត្តដំណោះស្រាយ ការដំណើរការលើកទីពីរជាទូទៅបញ្ចេញ `429`/`401`។ បន្ទាប់ពីអនុវត្តដំណោះស្រាយ ការបរាជ័យ (ប្រសិនបើមាន) នឹងត្រូវបានព្យាយាមម្តងទៀតដោយតម្លាភាព ហើយការហៅនឹងបញ្ចប់។ អ្នកក៏អាចប្រើ `curl /monitoring/health` ហើយតាមដានវាល `rateLimitedUntil` នៅលើការតភ្ជាប់របស់អ្នកផ្តល់សេវា និង `circuitBreakers.providerBreakers[].state` សម្រាប់អ្នកផ្តល់សេវាដែលរងផលប៉ះពាល់ — ស្ថានភាពគឺមួយក្នុងចំណោម `CLOSED`, `DEGRADED`, `OPEN` ឬ `HALF_OPEN` (សូមមើល `src/shared/utils/circuitBreaker.ts`) ហើយអ្នកផ្តល់សេវាដែលបន្តបរាជ័យនឹងប្តូរ `CLOSED → DEGRADED → OPEN` មុនពេលចន្លោះពេលកំណត់ឡើងវិញអនុញ្ញាតឱ្យសំណើសាកល្បងឆ្លងកាត់ (`HALF_OPEN`)។

**ប្រសិនបើអ្នកនៅតែឃើញ 429**៖ គណនីសកម្មសម្រាប់អ្នកផ្តល់សេវានោះពិតជាបានប្រើអស់ _កូតា_ របស់វា (មិនមែនត្រឹមតែដែនកំណត់អត្រាប៉ុណ្ណោះទេ)។ បន្ថែមគណនីទីពីរសម្រាប់អ្នកផ្តល់សេវាដដែលនៅក្នុងផ្ទាំងគ្រប់គ្រង OmniRoute → អ្នកផ្តល់សេវា → គណនី ឬប្រើអ្នកផ្តល់សេវាឥតគិតថ្លៃមួយផ្សេងទៀតរួមគ្នា (ឧ. `routeway`, `auggie`)។ ការប្ដូរវេនជួយបានតែចំពោះបញ្ហាអត្រាបណ្ដោះអាសន្ន/400/401 ប៉ុណ្ណោះ។ ការប្រើអស់កូតាទាំងស្រុងតម្រូវឱ្យមានព័ត៌មានសម្គាល់អត្តសញ្ញាណទីពីរ ឬអ្នកផ្តល់សេវាផ្សេង។

**ប្រសិនបើអ្នកឃើញ 403 លើម៉ូដែលចក្ខុវិស័យ (`auto/vision`, `bazaarlink/*`)**៖ គណនីដែលបានភ្ជាប់មិនមានគម្រោងបង់ប្រាក់ដែលរួមបញ្ចូលមុខងារចក្ខុវិស័យ ឬ API key មានសិទ្ធិមិនគ្រប់គ្រាន់។ ផ្ទៀងផ្ទាត់នៅក្នុងផ្ទាំងគ្រប់គ្រងរបស់អ្នកផ្តល់សេវាថា វិសាលភាពរបស់ key រួមបញ្ចូលចក្ខុវិស័យ/ពហុមធ្យោបាយ ឬភ្ជាប់គណនីកម្រិតបង់ប្រាក់ ហើយរក្សាទុកវាជាគោលដៅចក្ខុវិស័យ។

## ការព្រមានពេល npm install (ERESOLVE / peer / deprecated)

នៅពេលអ្នកដំណើរការ `npm install -g omniroute` អ្នកអាចឃើញសារព្រមានជាច្រើនដូចជា `npm warn ERESOLVE` សេចក្តីជូនដំណឹងអំពី peer dependency និងសារ `deprecated`។ **សារទាំងនេះត្រូវបានរំពឹងទុក ហើយមិនបង្កគ្រោះថ្នាក់ទេ។** ការដំឡើងរបស់អ្នកបានជោគជ័យ ប្រសិនបើអ្នកឃើញ `added <N> packages` នៅក្នុងលទ្ធផល។

សារព្រមានទាំងនេះកើតចេញពីចន្លោះកំណែ peer dependency ដែលហួសសម័យ នៅក្នុងកញ្ចប់របស់ភាគីទីបីដែល OmniRoute មិនអាចគ្រប់គ្រងបាន៖

1. **`marked-terminal` ទាមទារ `marked >=1 <16` ប៉ុន្តែរកឃើញ `marked@18`** — នៅក្នុងការប្រើប្រាស់ជាក់ស្តែង វាដំណើរការបានល្អធម្មតា; ចន្លោះកំណែ peer របស់គម្រោងដើមគ្រាន់តែហួសសម័យប៉ុណ្ណោះ។

## ភាពឆបគ្នាជាមួយ Node.js

<a name="nodejs-compatibility"></a>

### ទំព័រចូលប្រើគាំង ឬបង្ហាញកំហុស "Module self-registration"

**មូលហេតុ៖** អ្នកកំពុងដំណើរការកំណែ Node.js ដែលនៅក្រៅកម្រិត Runtime សុវត្ថិភាពដែល OmniRoute បានអនុម័ត។ ករណីដែលជួបញឹកញាប់បំផុតគឺការដំណើរការកំណែ Patch ចាស់ជាងនៃ Node 22 ឬ 24 ដែលទាបជាងកម្រិតសុវត្ថិភាពដែលបាន Patch ហើយដែល OmniRoute តម្រូវ។

**រោគសញ្ញា៖**

- ទំព័រចូលប្រើបង្ហាញអេក្រង់ទទេ ឬកំហុសម៉ាស៊ីនមេ
- Console បង្ហាញ `Error: Module did not self-register` ឬកំហុស Native Binding ស្រដៀងគ្នា
- ទំព័រចូលប្រើបង្ហាញ **បដាព្រមានពណ៌ទឹកក្រូច** ដែលមានកំណែ Node របស់អ្នក ប្រសិនបើ Runtime ស្ថិតនៅក្រៅគោលការណ៍សុវត្ថិភាពដែលបានគាំទ្រ

**ដំណោះស្រាយ៖**

1. ដំឡើងកំណែ Node.js LTS ដែលបានគាំទ្រ (បានណែនាំ៖ Node.js 24.x)៖
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ផ្ទៀងផ្ទាត់កំណែរបស់អ្នក៖ `node --version` គួរតែបង្ហាញ `v24.0.0` ឬថ្មីជាងនេះនៅលើស៊េរី 24.x LTS
3. ដំឡើង OmniRoute ឡើងវិញ៖ `npm install -g omniroute`
4. ចាប់ផ្ដើមឡើងវិញ៖ `omniroute`

> **កំណែសុវត្ថិភាពដែលបានគាំទ្រ៖** `>=22.22.2 <23` ឬ `>=24.0.0 <27`។ Node.js 24.x LTS (Krypton) និង Node.js 26 ត្រូវបានគាំទ្រយ៉ាងពេញលេញ។

### npm v11+៖ `better-sqlite3` មិនត្រូវបានដំឡើង (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**មូលហេតុ៖** npm v11 (ដែលភ្ជាប់មកជាមួយ Node.js 24+) រារាំងស្គ្រីបដំឡើងសម្រាប់
Dependency ជាជម្រើសតាមលំនាំដើម។ ដោយសារ `better-sqlite3` ត្រូវបានរាយក្នុង `optionalDependencies`
ហើយតម្រូវឱ្យ Compile ជា Native (`node-gyp rebuild`) ដូច្នេះ npm រំលងវាដោយមិនបង្ហាញដំណឹង។

**រោគសញ្ញា៖**

- ម៉ាស៊ីនមេគាំងនៅពេលចាប់ផ្ដើម ដោយមាន `Cannot find module 'better-sqlite3'`
- `ls node_modules/better-sqlite3` បង្ហាញ "No such file or directory"
- `npm ls better-sqlite3` បង្ហាញ `(empty)`

**ដំណោះស្រាយ៖**

1. អនុម័តស្គ្រីបដំឡើង ហើយដំឡើងឡើងវិញ៖
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ឬដំឡើងឯកសារដែលបាន Build ជាមុនដោយដៃ៖
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ផ្ទៀងផ្ទាត់ថាវាដំណើរការ៖ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

**ដំណោះស្រាយ — Build ឡើងវិញសម្រាប់បរិស្ថានមូលដ្ឋានរបស់អ្នក (មិនចាំបាច់បន្ទាបកំណែ Node.js)៖**

## បញ្ហា Proxy

<a name="proxy-issues"></a>

### ការផ្ទៀងផ្ទាត់ Provider បង្ហាញ "fetch failed"

**មូលហេតុ៖** ពីមុន endpoint សម្រាប់ផ្ទៀងផ្ទាត់ API key (`POST /api/providers/validate`) បានរំលងការកំណត់រចនាសម្ព័ន្ធ proxy ដែលបណ្តាលឱ្យមានបញ្ហានៅក្នុងបរិស្ថានដែលតម្រូវឱ្យបញ្ជូនទិន្នន័យតាម proxy។

**ដំណោះស្រាយ (v3.5.5+)៖** បញ្ហានេះត្រូវបានដោះស្រាយហើយ។ ឥឡូវនេះ ការផ្ទៀងផ្ទាត់ Provider ត្រូវបានបញ្ជូនតាម `runWithProxyContext` ដោយគោរពតាមការកំណត់ proxy កម្រិត Provider និងកម្រិតសកលដោយស្វ័យប្រវត្តិ។

### ការត្រួតពិនិត្យស្ថានភាព Token បរាជ័យជាមួយ "fetch failed"

**មូលហេតុ៖** ដំណើរការធ្វើឱ្យ OAuth token ស្រស់ឡើងវិញនៅផ្ទៃខាងក្រោយ មិនបានដោះស្រាយការកំណត់រចនាសម្ព័ន្ធ proxy សម្រាប់ connection នីមួយៗទេ។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះ scheduler សម្រាប់ត្រួតពិនិត្យស្ថានភាព token នឹងដោះស្រាយការកំណត់ proxy សម្រាប់ connection នីមួយៗ មុនពេលព្យាយាមធ្វើឱ្យស្រស់ឡើងវិញ។ សូមធ្វើបច្ចុប្បន្នភាពទៅ v3.5.5+។

### SOCKS5 proxy ត្រឡប់ "invalid onRequestStart method"

**មូលហេតុ៖** នៅលើ Node.js 22 dispatcher របស់ undici@8 មិនត្រូវគ្នាជាមួយការអនុវត្ត `fetch()` ដែលភ្ជាប់មកជាមួយ Node ទេ។

**ដំណោះស្រាយ (v3.5.5+)៖** ឥឡូវនេះ OmniRoute ប្រើមុខងារ `fetch()` ផ្ទាល់របស់ undici នៅពេល proxy dispatcher សកម្ម ដើម្បីធានាឱ្យមានឥរិយាបថស្របគ្នា។ សូមធ្វើបច្ចុប្បន្នភាពទៅ v3.5.5+។

### MITM proxy នៅក្រោម WSL៖ កម្មវិធី desktop នៅលើ Windows host មិនត្រូវបានស្ទាក់ចាប់

**មូលហេតុ៖** MITM proxy និងវិញ្ញាបនបត្រ CA របស់វា ត្រូវបានដំឡើងក្នុងបរិស្ថានដែល OmniRoute ដំណើរការ។ នៅក្រោម WSL បរិស្ថាននោះគឺជា Linux guest ខណៈដែលកម្មវិធី AI desktop (Kiro, Trae, Copilot, Zed, …) ដំណើរការនៅលើ Windows host។ កម្មវិធីនៅលើ host មិនទុកចិត្ត certificate store របស់ guest និងមិនបញ្ជូនទិន្នន័យតាម system proxy របស់ guest ទេ ដូច្នេះការស្ទាក់ចាប់ចរាចរណ៍របស់កម្មវិធី desktop មិនដំណើរការនៅទីនោះទេ។

**អនុសាសន៍៖** ដំណើរការ OmniRoute ដោយផ្ទាល់លើ OS ដូចគ្នានឹងកម្មវិធី desktop ដែលអ្នកចង់ស្ទាក់ចាប់ (Windows សម្រាប់កម្មវិធី Windows; macOS/Linux ក៏ដូចគ្នា)។ ការរក្សា OmniRoute នៅក្នុង WSL ខណៈពេលកំណត់គោលដៅទៅកាន់កម្មវិធីនៅលើ host តម្រូវឱ្យអ្នកទុកចិត្តវិញ្ញាបនបត្រ CA ដែលបានបង្កើតដោយដៃនៅលើ Windows host និងកំណត់ network/proxy settings របស់កម្មវិធីនីមួយៗនៅលើ host ឱ្យចង្អុលទៅកាន់ WSL proxy endpoint — នេះជាការរៀបចំដែលមិនត្រូវបានគាំទ្រ និងងាយមានបញ្ហា។

## បញ្ហា Cloud

### កំហុស Cloud Sync

1. ផ្ទៀងផ្ទាត់ថា `BASE_URL` ចង្អុលទៅ instance ដែលកំពុងដំណើរការរបស់អ្នក (ឧ. `http://localhost:20128`)
2. ផ្ទៀងផ្ទាត់ថា `CLOUD_URL` ចង្អុលទៅ cloud endpoint របស់អ្នក (ឧ. `https://omniroute.dev`)
3. រក្សាតម្លៃ `NEXT_PUBLIC_*` ឱ្យស្របគ្នាជាមួយតម្លៃនៅផ្នែក server

### Cloud `stream=false` ត្រឡប់ 500

**រោគសញ្ញា៖** `Unexpected token 'd'...` នៅលើ cloud endpoint សម្រាប់ការហៅដែលមិនប្រើ streaming។

**មូលហេតុ៖** Upstream ត្រឡប់ SSE payload ខណៈដែល client រំពឹងទុក JSON។

**ដំណោះស្រាយបណ្ដោះអាសន្ន៖** ប្រើ `stream=true` សម្រាប់ការហៅដោយផ្ទាល់ទៅ cloud។ Local runtime រួមបញ្ចូល fallback ពី SSE→JSON។

### Cloud បង្ហាញថាបានភ្ជាប់ ប៉ុន្តែបង្ហាញ "Invalid API key"

1. បង្កើត key ថ្មីពី local dashboard (`/api/keys`)
2. ដំណើរការ cloud sync៖ Enable Cloud → Sync Now
3. Key ចាស់ ឬមិនទាន់បាន sync នៅតែអាចត្រឡប់ `401` នៅលើ cloud

## បញ្ហា Docker

### Docker IPv6 / ការតភ្ជាប់ត្រូវបានកំណត់ឡើងវិញ

<a name="docker-ipv6"></a>

**រោគសញ្ញា៖** `curl http://localhost:20128/v1/models` ត្រឡប់ `curl: (56) Recv failure: Connection reset by peer`។ Dashboard និង endpoint ដែលមិនតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណដំណើរការ ប៉ុន្តែ endpoint ដែលតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណបរាជ័យ — វាហាក់ដូចជាបញ្ហា auth ប៉ុន្តែមិនមែនទេ។

**មូលហេតុ៖** `docker run -p 20128:20128` បើកផ្សាយទាំងនៅលើ `0.0.0.0` (IPv4) និង `::` (IPv6) ប៉ុន្តែ process នៅក្នុង container ស្តាប់តែលើ IPv4 ប៉ុណ្ណោះ។ នៅលើ host ដែល `localhost` ត្រូវបានដោះស្រាយទៅជា `::1` មុន ការតភ្ជាប់នឹងទៅដល់ port IPv6 ដែលបានបើកផ្សាយ ដោយគ្មាន listener នៅពីក្រោយវា → ការតភ្ជាប់ត្រូវបានកំណត់ឡើងវិញ។

**ការកែតម្រូវ៖**

1. **ការធ្វើរោគវិនិច្ឆ័យរហ័ស៖** ដំណើរការ `curl -4 http://localhost:20128/v1/models`។ ប្រសិនបើវាដំណើរការជាមួយ `-4` ប៉ុន្តែបរាជ័យបើគ្មានវា នោះអ្នកមាន bind mismatch របស់ IPv6។
2. **ការកែតម្រូវអចិន្ត្រៃយ៍៖** Bind ទៅ IPv4 ដោយច្បាស់លាស់ដោយប្រើ `-p 127.0.0.1:20128:20128` នៅក្នុង command `docker run` របស់អ្នក៖
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   វាបង្ខំឱ្យ bind ទៅ IPv4 ហើយក៏ជៀសវាងការបើក proxy ឱ្យប្រើបានលើ interface ទាំងអស់របស់ host ផងដែរ។

## បញ្ហាឧបករណ៍កាត់សៀគ្វី

### អ្នកផ្តល់សេវាជាប់គាំងក្នុងស្ថានភាព OPEN

នៅពេលឧបករណ៍កាត់សៀគ្វីរបស់អ្នកផ្តល់សេវាស្ថិតក្នុងស្ថានភាព OPEN សំណើនឹងត្រូវបានរារាំងរហូតដល់រយៈពេលសម្រាកផុតកំណត់។

**ដំណោះស្រាយ៖**

1. ចូលទៅកាន់ **ផ្ទាំងគ្រប់គ្រង → ការកំណត់ → ភាពធន់**
2. ពិនិត្យកាតឧបករណ៍កាត់សៀគ្វីសម្រាប់អ្នកផ្តល់សេវាដែលរងផលប៉ះពាល់
3. ចុច **កំណត់ឡើងវិញទាំងអស់** ដើម្បីសម្អាតឧបករណ៍កាត់សៀគ្វីទាំងអស់ ឬរង់ចាំឱ្យរយៈពេលសម្រាកផុតកំណត់
4. ផ្ទៀងផ្ទាត់ថាអ្នកផ្តល់សេវាពិតជាអាចប្រើបាន មុនពេលកំណត់ឡើងវិញ

### អ្នកផ្តល់សេវាបន្តបង្កឱ្យឧបករណ៍កាត់សៀគ្វីដំណើរការ

ប្រសិនបើអ្នកផ្តល់សេវាចូលក្នុងស្ថានភាព OPEN ម្តងហើយម្តងទៀត៖

1. ពិនិត្យមើលលំនាំបរាជ័យនៅ **ផ្ទាំងគ្រប់គ្រង → ស្ថានភាពប្រព័ន្ធ → ស្ថានភាពអ្នកផ្តល់សេវា**
2. ចូលទៅកាន់ **ការកំណត់ → ភាពធន់ → កម្រងព័ត៌មានអ្នកផ្តល់សេវា** ហើយបង្កើនកម្រិតកំណត់នៃការបរាជ័យ
3. ពិនិត្យមើលថាតើអ្នកផ្តល់សេវាបានផ្លាស់ប្តូរដែនកំណត់ API ឬតម្រូវឱ្យផ្ទៀងផ្ទាត់អត្តសញ្ញាណឡើងវិញឬអត់
4. ពិនិត្យទិន្នន័យតេឡេមេទ្រីនៃភាពយឺត — ភាពយឺតខ្ពស់អាចបង្កឱ្យមានការបរាជ័យដោយសារអស់ពេលកំណត់

## ការកំណត់ភាពធន់

### ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិមិនដំណើរការ

- ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិអនុវត្តតែចំពោះអ្នកផ្ដល់សេវាដែលប្រើ API key ប៉ុណ្ណោះ (មិនអនុវត្តចំពោះ OAuth/ការជាវទេ)
- ផ្ទៀងផ្ទាត់ថា **Settings → Resilience → Provider Profiles** បានបើកការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ
- ពិនិត្យមើលថាតើអ្នកផ្ដល់សេវាត្រឡប់កូដស្ថានភាព `429` ឬ header `Retry-After` ដែរឬទេ

### ការកែសម្រួល exponential backoff

ប្រវត្តិរូបអ្នកផ្ដល់សេវាគាំទ្រការកំណត់ទាំងនេះ៖

- **ការពន្យារពេលគោល** — រយៈពេលរង់ចាំដំបូងបន្ទាប់ពីបរាជ័យលើកទីមួយ (លំនាំដើម៖ 1s)
- **ការពន្យារពេលអតិបរមា** — កម្រិតអតិបរមានៃរយៈពេលរង់ចាំ (លំនាំដើម៖ 30s)
- **មេគុណ** — កម្រិតបង្កើនការពន្យារពេលសម្រាប់រាល់ការបរាជ័យជាប់ៗគ្នា (លំនាំដើម៖ 2x)

### ការទប់ស្កាត់ thundering herd

នៅពេលសំណើស្របពេលជាច្រើនបញ្ជូនទៅអ្នកផ្ដល់សេវាដែលត្រូវបានកំណត់កម្រិតអត្រា OmniRoute ប្រើ mutex + ការកំណត់កម្រិតអត្រាដោយស្វ័យប្រវត្តិ ដើម្បីរៀបសំណើឱ្យដំណើរការតាមលំដាប់ និងទប់ស្កាត់ការបរាជ័យបន្តបន្ទាប់។ វាដំណើរការដោយស្វ័យប្រវត្តិសម្រាប់អ្នកផ្ដល់សេវាដែលប្រើ API key។

### សំណើជជែកបរាជ័យជាមួយ 503 / chat_admission_busy

  `chat_admission_busy`។

## វចនានុក្រមកំហុស RAG / LLM ជាជម្រើស (បញ្ហា 16 ប្រភេទ)

អ្នកប្រើ OmniRoute មួយចំនួនដាក់ gateway នៅពីមុខស្រទាប់ RAG ឬ agent។ នៅក្នុងការរៀបចំទាំងនោះ គេជាញឹកញាប់ឃើញលំនាំចម្លែកមួយ៖ OmniRoute មើលទៅដំណើរការល្អ (providers ដំណើរការ, routing profiles ត្រឹមត្រូវ, គ្មានការជូនដំណឹងអំពី rate limit) ប៉ុន្តែចម្លើយចុងក្រោយនៅតែខុស។

ជាក់ស្តែង ឧបទ្ទវហេតុទាំងនេះជាធម្មតាកើតចេញពី RAG pipeline ផ្នែកខាងក្រោម មិនមែនពី gateway ខ្លួនឯងទេ។

ប្រសិនបើអ្នកចង់បានវាក្យសព្ទរួមសម្រាប់ពិពណ៌នាអំពីកំហុសទាំងនោះ អ្នកអាចប្រើ WFGY ProblemMap ដែលជាធនធានអត្ថបទខាងក្រៅក្រោមអាជ្ញាបណ្ណ MIT ដែលកំណត់លំនាំកំហុស RAG / LLM ដែលកើតឡើងដដែលៗចំនួនដប់ប្រាំមួយ។ ក្នុងកម្រិតទូទៅ វាគ្របដណ្ដប់លើ៖

- indexes និង vector stores ដែលទទេ ឬហួសសម័យ
- ភាពមិនស៊ីគ្នារវាង embedding និងអត្ថន័យ
- បញ្ហាក្នុងការផ្គុំ prompt និង context window
- ការដួលរលំនៃតក្កវិជ្ជា និងចម្លើយដែលមានទំនុកចិត្តហួសហេតុ
- កំហុសក្នុងខ្សែប្រតិបត្តិការវែង និងការសម្របសម្រួល agent

4. ប្រើទំព័រ WFGY ដែលត្រូវគ្នា ដើម្បីសម្រេចថាតើអ្នកត្រូវផ្លាស់ប្ដូរ RAG stack, retriever ឬយុទ្ធសាស្ត្រ routing របស់អ្នកឬអត់។

## បញ្ហាដែលបានដឹងនៅក្នុង v3.8.0

បញ្ហាជាក់លាក់ចំពោះការចេញផ្សាយ v3.8.0 និងដំណោះស្រាយបណ្ដោះអាសន្នបច្ចុប្បន្នរបស់វា។ ប្រសិនបើការកែតម្រូវត្រូវបានដាក់បញ្ចូលក្នុង patch ជំនាន់ក្រោយ ធាតុនេះនឹងត្រូវបានធ្វើបច្ចុប្បន្នភាព ឬដកចេញ។

### កំហុសក្នុងការផ្ទៀងផ្ទាត់អត្តសញ្ញាណ Devin CLI

**រោគសញ្ញា៖**

- "រកមិនឃើញ Devin CLI" ឬ "ការផ្ទៀងផ្ទាត់អត្តសញ្ញាណបានបរាជ័យ" នៅពេលហៅប្រើឧបករណ៍ដែលគាំទ្រដោយ Devin
- ការត្រួតពិនិត្យ CLI runtime រាយការណ៍ថា `installed=false`

**មូលហេតុ៖**

- `CLI_DEVIN_BIN` ចង្អុលទៅកាន់ path ដែលមិនមាន
- Devin CLI មិនត្រូវបានដំឡើងនៅលើ host

**ដំណោះស្រាយ៖**

1. ដំឡើង Devin CLI សម្រាប់ platform របស់អ្នក
2. កំណត់ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ឬ path ពិតប្រាកដ) នៅក្នុង `.env`
3. ចាប់ផ្ដើម OmniRoute ឡើងវិញ ហើយសាកល្បងម្ដងទៀតពី **Dashboard → CLI Tools**

### Model cooldown ជាប់គាំង (កំណត់ឡើងវិញដោយដៃ)

**រោគសញ្ញា៖**

- model មួយនៅតែបង្ហាញក្នុង cooldown សូម្បីតែបន្ទាប់ពីពេលផុតកំណត់បានកន្លងផុតទៅ
- សំណើនៅតែរំលង model នោះក្នុង combo routing ទោះបី timestamp ស្ថិតនៅក្នុងអតីតកាលក៏ដោយ

**ការកំណត់ឡើងវិញដោយដៃ៖**

- **Dashboard:** **Settings → Model Cooldowns** → ចុច **Re-enable** នៅលើ card ដែលរងផលប៉ះពាល់
- **API:** `DELETE /api/resilience/model-cooldowns` ជាមួយ management auth headers

### ការតភ្ជាប់ Command Code provider បរាជ័យដោយមាន 403

**រោគសញ្ញា៖**

- ទទួលបាន 403 នៅពេលសាកល្បងការតភ្ជាប់ Command Code provider
- provider card បង្ហាញ "គ្មានសិទ្ធិ" បន្ទាប់ពីបន្ថែមថ្មី

**មូលហេតុ៖** ដំណើរការ OAuth មិនបានបញ្ចប់ (មិនបានទទួល callback ឬ token មិនត្រូវបានរក្សាទុក)។

**ដំណោះស្រាយ៖**

- ដំណើរការ `omniroute providers` ពី CLI ដើម្បីបង្កដំណើរការ OAuth ឡើងវិញ ឬ
- ដំណើរការ OAuth ឡើងវិញពី **Dashboard → Providers → Command Code → Reconnect**

### ModelScope ផ្ដល់ cooldown 429 ខ្លាំងពេក

**រោគសញ្ញា៖**

- cooldown ខ្លីខ្លាំង ឬភ្លាមៗនៅលើ ModelScope បន្ទាប់ពីសំណើជាបន្តបន្ទាប់ចំនួនតិច
- Combo routing រំលង ModelScope លឿនជាងការរំពឹងទុក

**មូលហេតុ៖** ModelScope បញ្ចេញ headers `Retry-After` ជាក់លាក់របស់ provider។ v3.8.0 មានការគ្រប់គ្រងពិសេសសម្រាប់ headers ទាំងនោះ ដូច្នេះកំណែចាស់ៗបានបកស្រាយពួកវាខុសថាជាសញ្ញា rate-limit ទូទៅ។

**ដំណោះស្រាយ៖**

- ត្រូវប្រាកដថាអ្នកកំពុងប្រើ v3.8.0 ឬជំនាន់ក្រោយ
- ផ្ទៀងផ្ទាត់ថា toggle `useUpstream429BreakerHints` ត្រូវបានបើកនៅក្រោម **Settings → Resilience**

### បាត់ OMNIROUTE_WS_BRIDGE_SECRET នៅក្នុង production

**រោគសញ្ញា៖**

- ទទួលបាន 401 លើគ្រប់សំណើ Codex/Responses WebSocket bridge នៅពេលដំណើរការលើ remote production host
- WebSocket bridge handshake បិទភ្លាមៗបន្ទាប់ពីតភ្ជាប់

**មូលហេតុ៖** env var `OMNIROUTE_WS_BRIDGE_SECRET` បាត់ពី production environment។

**ដំណោះស្រាយ៖**

1. បង្កើត secret ចៃដន្យ៖ `openssl rand -hex 32`
2. កំណត់ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` នៅក្នុង env របស់ production server (និង client ណាមួយដែលទាក់ទងជាមួយ bridge)
3. ចាប់ផ្ដើម OmniRoute ឡើងវិញ

### Responses API៖ background mode ត្រូវបានបន្ថយមកជា synchronous

**រោគសញ្ញា៖**

- បានកត់ត្រាការព្រមាន៖ `background mode degraded to synchronous`
- សំណើ `background: true` ត្រឡប់ synchronous response ធម្មតា ជំនួសឱ្យ background job handle

**មូលហេតុ៖** v3.8.0 មានចេតនាបន្ថយ `background: true` នៅលើ Responses API ទៅជា synchronous execution ខណៈពេលបញ្ចេញការព្រមាន។ ការ execution ជា async background ពេញលេញ គឺជាមុខងារដែលនឹងផ្ដល់ជូននៅពេលអនាគត។

**ដំណោះស្រាយ៖**

- កែតម្រូវ client ឱ្យហៅដោយគ្មាន `background` ឬ
- រង់ចាំការចេញផ្សាយជំនាន់ក្រោយដែលមាន async background mode ពេញលេញ (តាមដាន changelog)
