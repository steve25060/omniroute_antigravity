### အခမဲ့ Provider များတွင် Rate Limiting ဖြစ်ခြင်း (429 / 400 / 401)

**လက္ခဏာ**- free/no-auth provider များ (opencode, auggie စသည်) နှင့်အတူ `model: "auto"` ကို အသုံးပြုသောအခါ အဖြေရမည့်အစား `HTTP 429`, `400` သို့မဟုတ် `401` ကို ရံဖန်ရံခါ ရရှိပါသည်။ ခဏအကြာတွင် တူညီသော prompt ကို ထပ်မံကြိုးစားသည့်အခါ request များ အောင်မြင်သော်လည်း automation (cron job များ၊ agent များ၊ script များ) သည် ပထမဆုံး failure တွင်ပင် ပျက်သွားပါသည်။

**အရင်းခံအကြောင်းရင်း**- သီးခြား failure mode သုံးမျိုး တစ်ပြိုင်နက် ဖြစ်ပေါ်လာခြင်းကြောင့် ဖြစ်ပါသည်-

1. **Provider rate-limit (`429`)**- Free tier များသည် သတ်မှတ်ထားသော အချိန်ကာလတစ်ခုလျှင် quota ကို ကန့်သတ်ထားနိုင်ပါသည်။ Parallel call များ တစ်ပြိုင်နက် များပြားလာခြင်းက quota ကို ကုန်ဆုံးစေသောကြောင့် window reset မဖြစ်မချင်း နောက် request ကို ငြင်းပယ်ပါသည်။
2. **Passthrough ရှိ ပျက်နေသော model (`400`/`401`)**- `auto/*` pool များတွင် catalog ၌ register လုပ်ထားသော်လည်း လက်ရှိအသုံးပြုနိုင်သော credential မရှိသည့် `opencode` မှ passthrough model များ ပါဝင်နိုင်ပါသည် (ဥပမာ `oc/north-mini-code-free` → `401`)။ Auto-router က တစ်ခုကို စမ်းကြည့်ပြီး မအောင်မြင်သည့်အခါ fallback မစတင်မီ error က ရှေ့ဆက်ပျံ့နှံ့သွားပါသည်။
3. **Concurrency ကြောင့် ပိုမိုဆိုးရွားလာခြင်း (load အောက်ရှိ `429`)**- Agent/cron session များစွာက `auto` ကို တစ်ပြိုင်နက် အသုံးပြုသည့်အခါ စုစုပေါင်း request rate သည် free provider များ လက်ခံနိုင်သည့်နှုန်းထက် ကျော်လွန်သွားသောကြောင့် တရားဝင် call များကိုပါ အလွဲသုံးစားလုပ်မှုအဖြစ် သတ်မှတ်ခံရပါသည်။

**အတည်ပြုထားသော ဖြေရှင်းနည်း (community မှ တင်ပြထားသည်၊ 2026-08-10)**- free-tier ၏ အပြောင်းအလဲများကြောင့် ပျက်သွားမည့်အစား rotation, concurrency နှင့် fallback တို့က ထိန်းညှိပေးနိုင်ရန် environment variable သုံးခုကို အောက်ပါအတိုင်း ချိန်ညှိပါ-

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ဖြစ်ပါက အခြား model/provider သို့ ပြောင်းပါ (ပျက်နေသော passthrough model များကို ကျော်သွားသည်)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight admission အများဆုံးပမာဏကို အတိအကျသတ်မှတ်သည် (မူလအတိုင်းဆို မသတ်မှတ်ထားပါ- request အရေအတွက် ကန့်သတ်ချက်မရှိပါ၊ အောက်ပါမှတ်ချက်ကို ကြည့်ပါ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ချက်ချင်း retry လုပ်နိုင်သော 503 ပြန်ပေးမည့်အစား heavyweight capacity ရရှိရန် ကန့်သတ်ထားသောအချိန် ပိုကြာကြာစောင့်သည်
```

၎င်းတို့ကို OmniRoute process environment (daemon၊ ဥပမာ LaunchAgent plist သို့မဟုတ် `systemctl edit` မှတစ်ဆင့်) တွင် သတ်မှတ်ပြီးနောက် OmniRoute ကို restart လုပ်ပါ။ Rotation flag သည် အထိရောက်ဆုံးသော အဓိက setting တစ်ခုဖြစ်ပါသည်။ ၎င်းက hard failure ကို pool အတွင်းရှိ ကောင်းမွန်စွာအလုပ်လုပ်သော provider တစ်ခုနှင့် မမြင်သာဘဲ ထပ်မံကြိုးစားသည့် လုပ်ဆောင်မှုအဖြစ် ပြောင်းလဲပေးပါသည်။

**မှတ်ချက်**- `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` သည် heavyweight — long-context — request များ တစ်ပြိုင်နက် run နိုင်သည့် အရေအတွက်ကို ကန့်သတ်ပါသည်။ ဤကန့်သတ်ချက်သည် admission gate ဖြစ်ပြီး provider rate limiter မဟုတ်ပါ။ **#503-fanout အပ်ဒိတ်-** ဤ var ကို မူလအတိုင်း သတ်မှတ်ပေးထားတော့မည် မဟုတ်ပါ (ယခုအခါ အထက်ပါအတိုင်း အတိအလင်း configure လုပ်ထားမှသာ သက်ရောက်ပါသည်) — ထိုအစား heavyweight admission ကို host ၏ အမှန်တကယ် memory ceiling အပေါ် အခြေခံ၍ အလိုအလျောက် ချိန်ညှိပေးသော auto-derived byte budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ဖြင့် gate လုပ်ထားပါသည်။ ထို့ကြောင့် အသစ် deploy လုပ်ထားသော instance တစ်ခုတွင် ဤ var ကို လုံးဝမသတ်မှတ်ဘဲ `503 chat_admission_busy` reject ဖြစ်မှု သိသိသာသာ လျော့နည်းသင့်ပါသည်။ သို့သော် ဤနေရာတွင် အတိအလင်း သတ်မှတ်ခြင်းသည် ဖော်ပြထားသည့်အတိုင်း ဆက်လက်အလုပ်လုပ်ပါသည်။ Byte-budget override များကို အတိအလင်းသတ်မှတ်ပါက 8 MiB–2 GiB အတွင်း ကန့်သတ်ပါသည်။ `413 body_exceeds_budget` သည် ယာယီမဟုတ်ပါ။ ထို byte budget ကို တိုးပါ၊ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ကို လျှော့ပါ၊ သို့မဟုတ် process memory ceiling ကို တိုးပါ။ `inflight_bytes_budget` shed သည် ယာယီ contention ဖြစ်ပြီး retry လုပ်နိုင်ဆဲဖြစ်ပါသည်။ Provider တစ်ခုချင်းစီအလိုက် rate limiting (`open-sse/services/rateLimitManager.ts`) ကို `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH` နှင့် `RATE_LIMIT_AUTO_ENABLE` တို့ဖြင့် သီးခြားထိန်းချုပ်ပါသည် — `.env.example` ကို ကြည့်ပါ။

**အလုပ်ဖြစ်ကြောင်း စစ်ဆေးနည်း**- သင့် agent/cron ကို အချိန်တိုအတွင်း နှစ်ကြိမ် run ပြီး နှစ်ကြိမ်လုံး အောင်မြင်ကြောင်း အတည်ပြုပါ။ ဖြေရှင်းမှုမပြုမီ ဒုတိယအကြိမ် run သည် ပုံမှန်အားဖြင့် `429`/`401` ကို throw လုပ်ပါသည်။ ဖြေရှင်းပြီးနောက် failure များရှိပါက မမြင်သာဘဲ အလိုအလျောက် retry လုပ်ပြီး call ပြီးမြောက်သွားပါမည်။ ထို့အပြင် `curl /monitoring/health` ကို အသုံးပြုပြီး provider connection များရှိ `rateLimitedUntil` field နှင့် သက်ရောက်မှုရှိသော provider များအတွက် `circuitBreakers.providerBreakers[].state` ကို စောင့်ကြည့်နိုင်ပါသည် — state သည် `CLOSED`, `DEGRADED`, `OPEN` သို့မဟုတ် `HALF_OPEN` တစ်ခုခု ဖြစ်ပါသည် (`src/shared/utils/circuitBreaker.ts` ကို ကြည့်ပါ)။ ဆက်တိုက်မအောင်မြင်သော provider တစ်ခုသည် reset window က probe တစ်ခုကို ဖြတ်သန်းခွင့်မပေးမီ `CLOSED → DEGRADED → OPEN` သို့ ပြောင်းသွားပြီးနောက် (`HALF_OPEN`) ဖြစ်လာပါမည်။

**429 ကို ဆက်လက်တွေ့နေရသေးပါက**: ထို provider အတွက် လက်ရှိအသုံးပြုနေသော account သည် ၎င်း၏ _quota_ ကို အမှန်တကယ် ကုန်ဆုံးသုံးစွဲပြီးဖြစ်သည် (rate သာမဟုတ်ပါ)။ OmniRoute dashboard → Providers → Accounts တွင် တူညီသော provider အတွက် ဒုတိယ account တစ်ခု ထည့်ပါ၊ သို့မဟုတ် အခြားအခမဲ့ provider တစ်ခု (ဥပမာ `routeway`, `auggie`) ကို ရောနှောအသုံးပြုပါ။ Rotation သည် ယာယီ rate/400/401 ပြဿနာများအတွက်သာ အထောက်အကူပြုသည်။ quota အပြည့်အဝ ကုန်ဆုံးသွားပါက ဒုတိယ credential တစ်ခု သို့မဟုတ် အခြား provider တစ်ခု လိုအပ်သည်။

**vision model များ (`auto/vision`, `bazaarlink/*`) တွင် 403 တွေ့ပါက**: ချိတ်ဆက်ထားသော account တွင် vision ပါဝင်သည့် အခပေး plan မရှိခြင်း သို့မဟုတ် API key တွင် လုံလောက်သော permission မရှိခြင်း ဖြစ်သည်။ Key scope တွင် vision/multimodal ပါဝင်ကြောင်း provider dashboard ၌ စစ်ဆေးပါ၊ သို့မဟုတ် အခပေး tier account တစ်ခုကို ချိတ်ဆက်ပြီး ၎င်းကို vision target အဖြစ် ဆက်လက်သတ်မှတ်ထားပါ။

## npm install သတိပေးချက်များ (ERESOLVE / peer / deprecated)

`npm install -g omniroute` ကို အသုံးပြုသည့်အခါ `npm warn ERESOLVE`၊ peer-dependency အသိပေးချက်များနှင့် `deprecated` မက်ဆေ့ချ်များကဲ့သို့ သတိပေးချက်အများအပြားကို မြင်တွေ့ရနိုင်ပါသည်။ **ဤသတိပေးချက်များသည် မျှော်လင့်ထားသည့်အရာများဖြစ်ပြီး အန္တရာယ်မရှိပါ။** output တွင် `added <N> packages` ကို မြင်ရပါက ထည့်သွင်းမှု အောင်မြင်ပါသည်။

အဆိုပါသတိပေးချက်များသည် OmniRoute မှ ထိန်းချုပ်ထားခြင်းမရှိသော ပြင်ပ package များရှိ ခေတ်မမီတော့သည့် peer-dependency range များကြောင့် ဖြစ်ပေါ်ခြင်းဖြစ်သည်-

1. **`marked-terminal` သည် `marked >=1 <16` ကို လိုအပ်သော်လည်း `marked@18` ကို တွေ့ရှိထားသည်** — လက်တွေ့အသုံးပြုရာတွင် ကောင်းမွန်စွာ အလုပ်လုပ်ပါသည်။ upstream peer range သည် ခေတ်မမီတော့ခြင်းသာ ဖြစ်သည်။
2. **`deprecated prebuild-install@7.1.3`** — ဆင့်ပွားမှီခိုထားသော native-binary ရယူရေး အကူကိရိယာတစ်ခုဖြစ်သည်။ ၎င်းကို
   သတ်မှတ်ထားသော `wreq-js` transport binding ကို ထည့်သွင်းရန် အသုံးမပြုသည့်အပြင် web-cookie
   provider transport စီစဉ်သတ်မှတ်မှု မအောင်မြင်ခဲ့ကြောင်းကိုလည်း မဖော်ပြပါ။

**မည်သည့်လုပ်ဆောင်ချက်မျှ မလိုအပ်ပါ** — upstream package များကို fork မလုပ်ဘဲ ဤသတိပေးချက်များကို လုံးဝပိတ်ထား၍ မရနိုင်ပါ။

### Avast/AVG က `README.md` ကို `MD:HttpRequest-inf[Susp]` ဖြင့် quarantine လုပ်ခြင်း

**၎င်းသည် မှားယွင်းသတိပေးချက်တစ်ခုသာ ဖြစ်သည်။ မည်သည့်အရာမျှ ကူးစက်ခံထားရခြင်းမရှိသည့်အပြင် မည်သည့်လုပ်ဆောင်ချက်မျှ ပြုလုပ်ရန်မလိုအပ်ပါ။**

Avast နှင့် AVG တို့သည် HTTP request များနှင့်တူသော link အများအပြား ပါဝင်သည့် plain-text/Markdown ဖိုင်များကို အန္တရာယ်ရှိနိုင်သည်ဟု သတ်မှတ်သည့် heuristic စနစ်ကို အသုံးပြုပါသည်။ OmniRoute ၏ `README.md` ကို npm package ထဲတွင် ထည့်သွင်းဖြန့်ချိထားသည် (`package.json` → `files` တွင် စာရင်းသွင်းထားသည်) ဖြစ်သောကြောင့် global install ပြုလုပ်သောအခါ `node_modules/omniroute/README.md` တွင် ရောက်ရှိနေပါသည် — ထို့အပြင် ၎င်းတွင် `http://localhost:20128/...` နမူနာ ~15 ခု (MCP HTTP/SSE endpoint များ၊ A2A `.well-known` URL နှင့် `curl` နမူနာများ) ပါဝင်ပါသည်။ ထို link သိပ်သည်းဆသည် heuristic စနစ်ကို သတိပေးချက်ထုတ်စေရန် လုံလောက်ပါသည်။

၎င်းသည် မကြာသေးမီကမှ စတင်ဖြစ်ပေါ်ခဲ့ပါက ဖိုင်၏အမျိုးအစား သို့မဟုတ် သဘောသဘာဝ ပြောင်းလဲခဲ့ခြင်းမရှိပါ။ README ၏ endpoint ဇယားတွင် endpoint များ တိုးလာပြီး (MCP HTTP + SSE + A2A တို့ကို ထည့်သွင်းခဲ့သည်) `curl` နမူနာများလည်း ပိုများလာသောကြောင့် သတ်မှတ်ထားသည့် အဆင့်ကို ကျော်လွန်သွားခြင်းဖြစ်သည်။

ဤဖိုင်သည် executable content လုံးဝမပါဝင်သည့် အသုံးပြု၍မရသော documentation ဖိုင်တစ်ခုသာ ဖြစ်ပါသည်။ ၎င်းကို quarantine မှ ဘေးကင်းစွာ restore ပြုလုပ်နိုင်ပါသည်။

**လုပ်ဆောင်ရမည့်အရာများ:**

1. **အသိပေးချက်များကို ရပ်တန့်ပါ** — သင့် antivirus တွင် install directory ကို exclude လုပ်ပါ
   (Avast: Settings → Exceptions)၊ သင့် global `node_modules` path နှင့်/သို့မဟုတ်
   OmniRoute data directory (`~/.omniroute/`) ကို ထည့်သွင်းပါ။
2. **မှားယွင်းသတိပေးချက်ကို report လုပ်ပါ** — <https://www.avast.com/false-positive-file-form.php> တွင်
   quarantine လုပ်ထားသော `README.md` ကို ပူးတွဲတင်ပြပါ။ ၎င်းသည် လူတိုင်းအတွက် အထောက်အကူဖြစ်စေမည့် ဖြေရှင်းချက်ဖြစ်သည်၊ အဘယ်ကြောင့်ဆိုသော် vendor ၏ heuristic က text file တစ်ခုအပေါ် လွန်ကဲစွာ တုံ့ပြန်နေခြင်းကြောင့် ဖြစ်သည်။

**ကျွန်ုပ်တို့ဘက်မှ ဤပြဿနာကို "မဖြေရှင်း" ရသည့်အကြောင်းရင်း:** နမူနာများအားလုံးသည် `http://localhost` ဖြစ်ပြီး self-signed certificate နှင့်ပတ်သက်သည့် အဆင်မပြေမှုများမရှိဘဲ localhost ကို `https` အဖြစ် အသုံးပြု၍မရပါ။ Vendor တစ်ခု၏ heuristic ကို ရှောင်ရှားရန် documentation ကို ပုံပျက်အောင်ပြင်ဆင်ခြင်းသည် scanner bug တစ်ခုကို ကျေနပ်စေရန် ဖတ်ရှုသူတိုင်းကို အဆင်မပြေဖြစ်စေမည်ဖြစ်သည်။

### Kaspersky က Desktop app ကို `PDM:Trojan.Win32.Generic` ဟု သတ်မှတ်ခြင်း

**၎င်းသည် behavioral heuristic ကြောင့် ဖြစ်ပေါ်လာသော မှားယွင်းသတိပေးချက်တစ်ခုသာ ဖြစ်သည်။ မည်သည့်အရာမျှ ကူးစက်ခံထားရခြင်းမရှိပါ။** Kaspersky ၏ `PDM:` prefix သည် သိရှိပြီးသား malware နှင့် တိုက်ဆိုင်စစ်ဆေးခြင်းမဟုတ်ဘဲ installer က _လုပ်ဆောင်သည့်အရာ_ ကို အကဲဖြတ်သော ၎င်း၏ Proactive Defense Module (System Watcher) မှ ဆုံးဖြတ်ချက်ချခြင်းဖြစ်ကြောင်း ဆိုလိုသည်။ သတိပေးချက်ထွက်ပေါ်သောအခါ Kaspersky သည် installation တစ်ခုလုံးကို "roll back" လုပ်ပြီး ရေးသားထားပြီးဖြစ်သည့်ဖိုင်များကိုပါ ဖျက်ပစ်သဖြင့် app သည် နောက်ဆုံးတွင် ပျက်စီးသွားခြင်း သို့မဟုတ် ပျောက်ဆုံးသွားခြင်း ဖြစ်ပေါ်ပါသည်။

၎င်းက အန္တရာယ်ရှိသည်ဟု သတ်မှတ်သောဖိုင်များသည် desktop app နှင့်အတူ ထည့်သွင်းထားသည့် ကြေညာထားပြီး open-source ဖြစ်သော dependency များ၏ ပုံမှန်အစိတ်အပိုင်းများသာ ဖြစ်သည်၊ ဥပမာ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` နှင့်
  `workerProcessEntry.js` — app အတွင်း provider login ပြုလုပ်ရန်နှင့် browser-backed chat အတွက် အသုံးပြုသည့် browser automation
  library ဖြစ်သော [Playwright](https://playwright.dev)။
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — web-cookie provider များတွင် browser-fingerprinted HTTP အတွက် အသုံးပြုသော version သတ်မှတ်ထားသည့် `wreq-js` native binding
  (`<arch>` သည် `x64` သို့မဟုတ် `arm64` ဖြစ်သည်)။

**သတိပေးချက်ထွက်ရသည့်အကြောင်းရင်း:** Windows installer ကို **code-sign မလုပ်ရသေးပါ**၊ ထို့ကြောင့် sign မလုပ်ထားသော NSIS installer တွင် reputation လုံးဝမရှိဘဲ behavioral heuristic များက အပြင်းထန်ဆုံးအဆင့်ဖြင့် စစ်ဆေးပါသည်။ Bundled native DLL တစ်ခုနှင့် `%LOCALAPPDATA%\Programs\OmniRoute` အောက်တွင် ရေးသားထားသည့် `.js` ဖိုင် ရာပေါင်းများစွာ (Next.js standalone build မှ hash suffix ပါသော package directory များ အပါအဝင်) ပေါင်းစပ်လိုက်သောအခါ heuristic ကို သတိပေးချက်ထုတ်စေရန် လုံလောက်ပါသည်။ Code signing ပြုလုပ်ရန် စီစဉ်ထားပါသည်၊ သို့သော် မပြီးမြောက်မီအချိန်အထိ release အသစ်များတွင် ဤပြဿနာ ထပ်မံဖြစ်ပေါ်နိုင်ပါသည်။

**လုပ်ဆောင်ရမည့်အရာများ:**

1. **သင် download လုပ်ထားသောဖိုင်ကို ဦးစွာ verify လုပ်ပါ** (ဖိုင်အား အန္တရာယ်ရှိအောင် ပြုပြင်ထားခြင်းရှိမရှိ ဖယ်ရှားစစ်ဆေးရန်)။ Release တိုင်းတွင်
   `latest.yml` ကို ထုတ်ပြန်ပြီး ၎င်း၏ `sha512` field (base64) သည် `OmniRoute.Setup.<version>.exe`
   installer ကို လွှမ်းခြုံစစ်ဆေးပါသည်။ PowerShell တွင် installer ပါဝင်သော folder မှ အောက်ပါတို့ကို လုပ်ဆောင်ပါ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   Output သည် `latest.yml` → `sha512` နှင့် ကိုက်ညီရပါမည်။ မကိုက်ညီပါက ဖိုင်ကိုဖျက်ပြီး
   [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases) မှသာ ပြန်လည် download လုပ်ပါ။
2. **Restore + exclude လုပ်ပါ** — roll back လုပ်ထားသော item များကို quarantine မှ restore လုပ်ပြီး
   `%LOCALAPPDATA%\Programs\OmniRoute` အတွက် exclusion တစ်ခု ထည့်ပါ (Kaspersky → Settings → Threats and Exclusions)၊
   ထို့နောက် ပြန်လည် install လုပ်ပါ။
3. **မှားယွင်းသတိပေးချက်ကို report လုပ်ပါ** — <https://opentip.kaspersky.com/>။ အသုံးပြုသူများ တင်ပြသော မှားယွင်းသတိပေးချက် report များသည် allowlisting လုပ်ငန်းစဉ်ကို အမှန်တကယ် ပိုမိုမြန်ဆန်စေပါသည်။

## Node.js လိုက်ဖက်ညီမှု

<a name="nodejs-compatibility"></a>

### လော့ဂ်အင်စာမျက်နှာ ပျက်သွားခြင်း သို့မဟုတ် "Module self-registration" အမှားပြခြင်း

**အကြောင်းရင်း:** OmniRoute က အတည်ပြုထားသော လုံခြုံသည့် runtime အနိမ့်ဆုံးသတ်မှတ်ချက်၏ ပြင်ပတွင်ရှိသည့် Node.js ဗားရှင်းကို သင်အသုံးပြုနေပါသည်။ အဖြစ်အများဆုံးအခြေအနေမှာ OmniRoute လိုအပ်သည့် လုံခြုံရေးပြင်ဆင်ချက်ပါဝင်သော အနိမ့်ဆုံးဗားရှင်းထက် နိမ့်သည့် Node 22 သို့မဟုတ် 24 patch အဆင့်အဟောင်းကို အသုံးပြုနေခြင်းဖြစ်သည်။

**လက္ခဏာများ:**

- လော့ဂ်အင်စာမျက်နှာတွင် မျက်နှာပြင်အလွတ် သို့မဟုတ် ဆာဗာအမှားကို ပြသသည်
- Console တွင် `Error: Module did not self-register` သို့မဟုတ် အလားတူ native binding အမှားများကို ပြသသည်
- Runtime သည် ပံ့ပိုးထားသော လုံခြုံရေးမူဝါဒ၏ ပြင်ပတွင်ရှိပါက လော့ဂ်အင်စာမျက်နှာတွင် သင့် Node ဗားရှင်းနှင့်အတူ **လိမ္မော်ရောင် သတိပေးဘန်နာ** ကို ပြသသည်

**ဖြေရှင်းနည်း:**

1. ပံ့ပိုးထားသော Node.js LTS ဖြန့်ချိဗားရှင်းတစ်ခုကို ထည့်သွင်းပါ (အကြံပြုချက်- Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. သင့်ဗားရှင်းကို စစ်ဆေးပါ- `node --version` သည် 24.x LTS လိုင်းတွင် `v24.0.0` သို့မဟုတ် ၎င်းထက်အသစ်ကို ပြသသင့်သည်
3. OmniRoute ကို ပြန်လည်ထည့်သွင်းပါ- `npm install -g omniroute`
4. ပြန်လည်စတင်ပါ- `omniroute`

> **ပံ့ပိုးထားသော လုံခြုံသည့်ဗားရှင်းများ:** `>=22.22.2 <23` သို့မဟုတ် `>=24.0.0 <27`။ Node.js 24.x LTS (Krypton) နှင့် Node.js 26 ကို အပြည့်အဝ ပံ့ပိုးထားသည်။

### npm v11+: `better-sqlite3` ကို ထည့်သွင်းမထားခြင်း (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**အကြောင်းရင်း:** Node.js 24+ နှင့်အတူ ပါဝင်လာသော npm v11 သည် optional
dependencies များအတွက် install scripts များကို မူလသတ်မှတ်ချက်အရ ပိတ်ဆို့ထားသည်။ `better-sqlite3` ကို `optionalDependencies`
တွင် စာရင်းသွင်းထားပြီး native compilation (`node-gyp rebuild`) လိုအပ်သောကြောင့် npm သည် ၎င်းကို အသိပေးခြင်းမရှိဘဲ ကျော်သွားသည်။

**လက္ခဏာများ:**

- ဆာဗာစတင်ချိန်တွင် `Cannot find module 'better-sqlite3'` ဖြင့် ပျက်သွားသည်
- `ls node_modules/better-sqlite3` သည် "No such file or directory" ကို ပြသသည်
- `npm ls better-sqlite3` သည် `(empty)` ကို ပြသသည်

**ဖြေရှင်းနည်း:**

1. Install scripts များကို ခွင့်ပြုပြီး ပြန်လည်ထည့်သွင်းပါ-
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. သို့မဟုတ် ကြိုတင်တည်ဆောက်ထားသည့် package ကို ကိုယ်တိုင်ထည့်သွင်းပါ-
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. အလုပ်လုပ်ကြောင်း စစ်ဆေးပါ- `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**အကြောင်းရင်း:** Global `npm install -g omniroute` ပြုလုပ်ပြီးနောက် package အတွင်းရှိ `better-sqlite3` native binary ကို စက်တွင် လက်ရှိအသုံးပြုနေသည့် architecture သို့မဟုတ် Node.js ABI နှင့်မတူသော ပတ်ဝန်းကျင်အတွက် compile ပြုလုပ်ထားနိုင်သည်။ ကြိုတင်တည်ဆောက်ထားသည့် binary သည် သင့်ပတ်ဝန်းကျင်နှင့် မကိုက်ညီသောအခါ macOS (Apple Silicon နှင့် Intel နှစ်မျိုးလုံး) တွင် ဤပြဿနာ အဖြစ်များသည်။

**လက္ခဏာများ:**

- ဆာဗာစတင်ချိန်တွင် `dlopen` အမှားဖြင့် ချက်ချင်း မအောင်မြင်ဖြစ်သွားသည်
- အမှားတွင် `slice is not valid mach-o file` ပါဝင်သည်
- နမူနာအပြည့်အစုံ-

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ဖြေရှင်းနည်း — သင့်စက်၏ ပတ်ဝန်းကျင်အတွက် ပြန်လည်တည်ဆောက်ပါ (Node.js ဗားရှင်းလျှော့ချရန် မလိုအပ်ပါ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **မှတ်ချက်:** ဤလုပ်ဆောင်ချက်သည် သင့်စက်ရှိ Node.js ဗားရှင်းနှင့် CPU architecture အတွက် native binding ကို ပြန်လည် compile ပြုလုပ်ပြီး binary မကိုက်ညီမှုကို ဖြေရှင်းပေးသည်။ တရားဝင်ပံ့ပိုးထားသော runtime အပိုင်းအခြားမှာ **`>=22.22.2 <23` သို့မဟုတ် `>=24.0.0 <27`** ဖြစ်သည် (`src/shared/utils/nodeRuntimeSupport.ts` ရှိ `SUPPORTED_NODE_RANGE`၊ `package.json` ရှိ `engines` field နှင့် ကိုက်ညီသည်)။ Node.js 24.x LTS (Krypton) နှင့် Node.js 26 ကို `better-sqlite3` v12.x နှင့်အတူ အပြည့်အဝ ပံ့ပိုးထားသည်။

## Proxy ပြဿနာများ

<a name="proxy-issues"></a>

### Provider အတည်ပြုခြင်းတွင် "fetch failed" ဟု ပြသခြင်း

**အကြောင်းရင်း:** API key အတည်ပြုသည့် endpoint (`POST /api/providers/validate`) သည် ယခင်က proxy configuration ကို ကျော်လွှားနေခဲ့သဖြင့် proxy မှတစ်ဆင့် လမ်းကြောင်းပို့ရန် လိုအပ်သော environment များတွင် မအောင်မြင်မှုများ ဖြစ်ပေါ်ခဲ့သည်။

**ဖြေရှင်းချက် (v3.5.5+):** ယခု ပြင်ဆင်ပြီးဖြစ်သည်။ Provider အတည်ပြုခြင်းကို `runWithProxyContext` မှတစ်ဆင့် လမ်းကြောင်းပို့ထားပြီး provider-level နှင့် global proxy setting များကို အလိုအလျောက် လိုက်နာသည်။

### Token အခြေအနေ စစ်ဆေးမှုတွင် "fetch failed" ဟု ပြသခြင်း

**အကြောင်းရင်း:** နောက်ခံ OAuth token refresh လုပ်ငန်းစဉ်သည် connection တစ်ခုချင်းစီအလိုက် proxy configuration ကို ဖြေရှင်းသတ်မှတ်ခြင်း မပြုခဲ့ပါ။

**ဖြေရှင်းချက် (v3.5.5+):** Token အခြေအနေ စစ်ဆေးမှု scheduler သည် refresh ပြုလုပ်ရန် မကြိုးစားမီ connection တစ်ခုချင်းစီအလိုက် proxy config ကို ယခု ဖြေရှင်းသတ်မှတ်ပေးသည်။ v3.5.5+ သို့ အပ်ဒိတ်လုပ်ပါ။

### SOCKS5 proxy တွင် "invalid onRequestStart method" ဟု ပြသခြင်း

**အကြောင်းရင်း:** Node.js 22 တွင် undici@8 dispatcher သည် Node ၏ built-in `fetch()` implementation နှင့် ကိုက်ညီမှုမရှိပါ။

**ဖြေရှင်းချက် (v3.5.5+):** Proxy dispatcher အသုံးပြုနေချိန်တွင် OmniRoute သည် တသမတ်တည်း အလုပ်လုပ်စေရန် undici ၏ ကိုယ်ပိုင် `fetch()` function ကို ယခု အသုံးပြုသည်။ v3.5.5+ သို့ အပ်ဒိတ်လုပ်ပါ။

### WSL အောက်ရှိ MITM proxy: Windows host ပေါ်ရှိ desktop app များကို ကြားဖြတ်ဖမ်းယူခြင်း မပြုနိုင်ပါ

**အကြောင်းရင်း:** MITM proxy နှင့် ၎င်း၏ CA certificate ကို OmniRoute လည်ပတ်နေသည့် environment ထဲတွင် ထည့်သွင်းထားသည်။ WSL အောက်တွင် အဆိုပါ environment သည် Linux guest ဖြစ်ပြီး AI desktop app များ (Kiro, Trae, Copilot, Zed, …) က Windows host ပေါ်တွင် လည်ပတ်သည်။ Host app များသည် guest ၏ certificate store ကို မယုံကြည်သည့်အပြင် guest ၏ system proxy မှတစ်ဆင့်လည်း လမ်းကြောင်းမပို့သောကြောင့် desktop ကြားဖြတ်ဖမ်းယူမှုသည် ထိုနေရာတွင် အလုပ်မလုပ်ပါ။

**အကြံပြုချက်:** ကြားဖြတ်ဖမ်းယူလိုသည့် desktop app များနှင့် တူညီသော OS ပေါ်တွင် OmniRoute ကို မူလစနစ်အတိုင်း တိုက်ရိုက်လည်ပတ်ပါ (Windows app များအတွက် Windows; macOS/Linux အတွက်လည်း အလားတူဖြစ်သည်)။ Host app များကို ပစ်မှတ်ထားစဉ် OmniRoute ကို WSL ထဲတွင် ဆက်ထားလိုပါက ထုတ်ပေးထားသော CA certificate ကို Windows host ပေါ်တွင် ကိုယ်တိုင် ယုံကြည်ခွင့်ပေးပြီး host app တစ်ခုချင်းစီ၏ network/proxy setting များကို WSL proxy endpoint သို့ ညွှန်ပြရန် လိုအပ်သည် — ၎င်းသည် တရားဝင်ပံ့ပိုးမထားသည့်အပြင် ပျက်လွယ်သော setup ဖြစ်သည်။

**Google/GitHub social login** သို့မဟုတ် **Auto-Import** မှတစ်ဆင့် ဖန်တီးသည့် Kiro connection အသစ်တိုင်းသည် ၎င်း၏ကိုယ်ပိုင်

refresh လုပ်ခြင်းက အခြားမည်သည့် account ကိုမျှ သက်ရောက်မှုမရှိပါ။

## Cloud ပြဿနာများ

### Cloud Sync အမှားများ

1. `BASE_URL` သည် သင်လက်ရှိအသုံးပြုနေသော instance ကို ညွှန်ပြထားကြောင်း စစ်ဆေးပါ (ဥပမာ၊ `http://localhost:20128`)
2. `CLOUD_URL` သည် သင်၏ cloud endpoint ကို ညွှန်ပြထားကြောင်း စစ်ဆေးပါ (ဥပမာ၊ `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` တန်ဖိုးများကို server-side တန်ဖိုးများနှင့် ကိုက်ညီအောင် ထားပါ

### Cloud တွင် `stream=false` က 500 ပြန်ပေးခြင်း

**လက္ခဏာ:** Streaming မဟုတ်သော ခေါ်ဆိုမှုများအတွက် cloud endpoint တွင် `Unexpected token 'd'...` ပေါ်လာသည်။

**အကြောင်းရင်း:** Client က JSON ကို မျှော်လင့်နေသော်လည်း upstream က SSE payload ကို ပြန်ပေးသည်။

**ယာယီဖြေရှင်းနည်း:** Cloud ကို တိုက်ရိုက်ခေါ်ဆိုရာတွင် `stream=true` ကို အသုံးပြုပါ။ Local runtime တွင် SSE→JSON fallback ပါဝင်သည်။

### Cloud က ချိတ်ဆက်ပြီးဟု ပြသသော်လည်း "Invalid API key" ပေါ်ခြင်း

1. Local dashboard (`/api/keys`) မှ key အသစ်တစ်ခု ဖန်တီးပါ
2. Cloud sync ကို လုပ်ဆောင်ပါ: Enable Cloud → Sync Now
3. Key အဟောင်းများ သို့မဟုတ် sync မလုပ်ရသေးသော key များသည် cloud တွင် `401` ကို ဆက်လက်ပြန်ပေးနိုင်သည်

## Docker ပြဿနာများ

### Docker IPv6 / Connection Reset

<a name="docker-ipv6"></a>

**လက္ခဏာများ:** `curl http://localhost:20128/v1/models` က `curl: (56) Recv failure: Connection reset by peer` ကို ပြန်ပေးသည်။ Dashboard နှင့် authentication မလိုအပ်သော endpoint များ အလုပ်လုပ်သော်လည်း authenticated endpoint များ မအောင်မြင်ပါ — auth ပြဿနာတစ်ခုကဲ့သို့ ထင်ရသော်လည်း အမှန်တကယ် မဟုတ်ပါ။

**အကြောင်းရင်း:** `docker run -p 20128:20128` သည် `0.0.0.0` (IPv4) နှင့် `::` (IPv6) နှစ်ခုစလုံးတွင် publish လုပ်သော်လည်း container အတွင်းရှိ process က IPv4 တွင်သာ listen လုပ်သည်။ `localhost` က `::1` ကို ဦးစွာ resolve လုပ်သော host များတွင် connection သည် နောက်ကွယ်၌ listener မရှိသော IPv6 published port သို့ ရောက်သွားသဖြင့် → connection reset ဖြစ်သည်။

**ဖြေရှင်းနည်း:**

1. **အမြန်စစ်ဆေးနည်း:** `curl -4 http://localhost:20128/v1/models` ကို run ပါ။ `-4` ဖြင့် အလုပ်လုပ်သော်လည်း ၎င်းမပါဘဲ မအောင်မြင်ပါက သင့်တွင် IPv6 bind မကိုက်ညီမှုရှိနေသည်။
2. **အမြဲတမ်းဖြေရှင်းနည်း:** သင်၏ `docker run` command တွင် `-p 127.0.0.1:20128:20128` ကို အသုံးပြု၍ IPv4 သို့ အတိအကျ bind လုပ်ပါ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ဤနည်းက IPv4 bind ကို မဖြစ်မနေ အသုံးပြုစေပြီး host interface အားလုံးတွင် proxy ကို ဖွင့်ထားခြင်းမှလည်း ရှောင်ရှားပေးသည်။

## Debugging

### Log File များကို ဖွင့်ခြင်း

သင်၏ `.env` file တွင် `APP_LOG_TO_FILE=true` ကို သတ်မှတ်ပါ။ Application log များကို `logs/` အောက်တွင် ရေးသားသိမ်းဆည်းပါသည်။
Setting များတွင် call log pipeline ကို ဖွင့်ထားသောအခါ request artifact များကို `${DATA_DIR}/call_logs/` အောက်တွင် သိမ်းဆည်းပါသည်။
Pipeline capture ကို ဖွင့်ထားသောအခါ stream chunk payload များကို ချန်လှပ်ရန် `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ကို သတ်မှတ်ပါ၊ သို့မဟုတ် artifact အရွယ်အစားကန့်သတ်ချက်ကို KB ဖြင့် ပြောင်းလဲရန် `CALL_LOG_PIPELINE_MAX_SIZE_KB` ကို ချိန်ညှိပါ။

### Provider အခြေအနေကို စစ်ဆေးခြင်း

# အခြေအနေ dashboard
http://localhost:20128/dashboard/health

# API အခြေအနေ စစ်ဆေးခြင်း

### Runtime Storage

- အဓိက state: `${DATA_DIR}/storage.sqlite` (provider များ၊ combo များ၊ alias များ၊ key များ၊ setting များ)
- အသုံးပြုမှု: `storage.sqlite` ရှိ SQLite table များ (`usage_history`, `call_logs`, `proxy_logs`) + ရွေးချယ်နိုင်သော `${DATA_DIR}/call_logs/`
- Application log များ: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ဖြစ်သောအခါ)
- Call log artifact များ: call log pipeline ကို ဖွင့်ထားသောအခါ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs စာမျက်နှာရှိ **Clean history** လုပ်ဆောင်ချက်သည် `call_logs`၊ legacy
`request_detail_logs` နှင့် local `${DATA_DIR}/call_logs/` artifact directory ကို ရှင်းလင်းပေးသည်။

## Circuit Breaker ပြဿနာများ

### Provider သည် OPEN အခြေအနေတွင် ရပ်တန့်နေခြင်း

Provider တစ်ခု၏ circuit breaker သည် OPEN ဖြစ်နေသောအခါ cooldown ကာလကုန်ဆုံးသည်အထိ request များကို ပိတ်ဆို့ထားမည်ဖြစ်သည်။

**ဖြေရှင်းနည်း:**

1. **Dashboard → Settings → Resilience** သို့ သွားပါ
2. ပြဿနာဖြစ်နေသော provider အတွက် circuit breaker card ကို စစ်ဆေးပါ
3. Breaker အားလုံးကို ရှင်းလင်းရန် **Reset All** ကို နှိပ်ပါ၊ သို့မဟုတ် cooldown ကာလကုန်ဆုံးသည်အထိ စောင့်ပါ
4. Reset မလုပ်မီ provider ကို အမှန်တကယ် အသုံးပြုနိုင်ကြောင်း အတည်ပြုပါ

### Provider က circuit breaker ကို ထပ်ခါတလဲလဲ အလုပ်လုပ်စေခြင်း

Provider တစ်ခုသည် OPEN အခြေအနေသို့ ထပ်ခါတလဲလဲ ဝင်ရောက်နေပါက-

1. Failure ပုံစံကို သိရှိရန် **Dashboard → Health → Provider Health** ကို စစ်ဆေးပါ
2. **Settings → Resilience → Provider Profiles** သို့ သွားပြီး failure threshold ကို တိုးမြှင့်ပါ
3. Provider က API limit များကို ပြောင်းလဲထားခြင်းရှိ၊ သို့မဟုတ် ပြန်လည် authentication ပြုလုပ်ရန် လိုအပ်ခြင်းရှိမရှိ စစ်ဆေးပါ
4. Latency telemetry ကို ပြန်လည်သုံးသပ်ပါ — latency မြင့်မားခြင်းကြောင့် timeout အခြေခံ failure များ ဖြစ်ပေါ်နိုင်သည်

## အသံမှ စာသားကူးပြောင်းခြင်းဆိုင်ရာ ပြဿနာများ

### "Unsupported model" error

- ပထမ segment သည် သင့်တွင် credential ရှိသည့် provider ဖြစ်သော model id (`openai/whisper-1`, `openrouter/deepgram/nova-3`) ကို အသုံးပြုပါ။ `deepgram/nova-3` ကို တိုက်ရိုက်အသုံးပြုရန် မူရင်း Deepgram key လိုအပ်သည်။
- Provider ကို **Dashboard → Providers** တွင် ချိတ်ဆက်ထားကြောင်း အတည်ပြုပါ

### Transcription သည် ဗလာဖြစ်နေခြင်း သို့မဟုတ် မအောင်မြင်ခြင်း

- ပံ့ပိုးထားသော အသံဖိုင် format များကို စစ်ဆေးပါ- `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ဖိုင်အရွယ်အစားသည် provider ၏ ကန့်သတ်ချက်အတွင်းရှိကြောင်း အတည်ပြုပါ (ပုံမှန်အားဖြင့် < 25MB)
- Provider card တွင် provider API key မှန်ကန်မှုကို စစ်ဆေးပါ

## Translator ပြဿနာရှာဖွေခြင်း

Format ဘာသာပြန်ပြောင်းလဲမှုဆိုင်ရာ ပြဿနာများကို ရှာဖွေရန် **Dashboard → Translator** ကို အသုံးပြုပါ-

| Mode             | အသုံးပြုသင့်သည့်အချိန်                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Playground**   | Input/output format များကို ဘေးချင်းယှဉ် နှိုင်းယှဉ်ပါ — ဘာသာပြန်ပြောင်းလဲပုံကို ကြည့်ရန် မအောင်မြင်သော request ကို ကူးထည့်ပါ |
| **Chat Tester**  | တိုက်ရိုက် message များ ပေးပို့ပြီး header များအပါအဝင် request/response payload အပြည့်အစုံကို စစ်ဆေးပါ                        |
| **Test Bench**   | မည်သည့် ဘာသာပြန်ပြောင်းလဲမှုများ ပျက်နေကြောင်း ရှာဖွေရန် format ပေါင်းစပ်မှုများတစ်လျှောက် batch test များ လုပ်ဆောင်ပါ        |
| **Live Monitor** | ရံဖန်ရံခါ ဖြစ်ပေါ်သော ဘာသာပြန်ပြောင်းလဲမှု ပြဿနာများကို ဖမ်းယူရန် အချိန်နှင့်တစ်ပြေးညီ request စီးဆင်းမှုကို စောင့်ကြည့်ပါ    |

### အဖြစ်များသော format ပြဿနာများ

- **Thinking tag များ မပေါ်လာခြင်း** — ပစ်မှတ် provider က thinking ကို ပံ့ပိုးခြင်းရှိမရှိနှင့် thinking budget setting ကို စစ်ဆေးပါ
- **Tool call များ ပျောက်ဆုံးခြင်း** — အချို့သော format ဘာသာပြန်ပြောင်းလဲမှုများသည် မပံ့ပိုးထားသော field များကို ဖယ်ရှားနိုင်သည်၊ Playground mode တွင် အတည်ပြုပါ
- **System prompt ပျောက်ဆုံးခြင်း** — Claude နှင့် Gemini တို့သည် system prompt များကို မတူညီစွာ ကိုင်တွယ်သည်၊ ဘာသာပြန်ပြောင်းလဲမှု output ကို စစ်ဆေးပါ
- **SDK က object အစား raw string ပြန်ပေးခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ response sanitizer က OpenAI SDK Pydantic validation မအောင်မြင်မှုများ ဖြစ်စေသော စံမဟုတ်သည့် field များ (`x_groq`, `usage_breakdown` စသည်တို့) ကို ဖယ်ရှားပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။
- **GLM/ERNIE က `system` role ကို ငြင်းပယ်ခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ role normalizer က ကိုက်ညီမှုမရှိသော model များအတွက် system message များကို user message များထဲသို့ အလိုအလျောက် ပေါင်းစည်းပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။
- **`developer` role ကို မမှတ်မိခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ OpenAI မဟုတ်သော provider များအတွက် `system` သို့ အလိုအလျောက် ပြောင်းလဲပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။
- **`json_schema` က Gemini နှင့် အလုပ်မလုပ်ခြင်း** — v1.x တွင် ဖြေရှင်းပြီးဖြစ်သည်၊ ယခုအခါ `response_format` ကို Gemini ၏ `responseMimeType` + `responseSchema` သို့ ပြောင်းလဲပေးသည်။ v3.x+ တွင် ဤပြဿနာကို တွေ့နေရဆဲဖြစ်ပါက issue တစ်ခု တင်ပြပေးပါ။

## ပြန်လည်ခံနိုင်ရည် ဆက်တင်များ

### အလိုအလျောက် နှုန်းကန့်သတ်ခြင်း အလုပ်မလုပ်ခြင်း

- အလိုအလျောက် နှုန်းကန့်သတ်ခြင်းသည် API key provider များအတွက်သာ သက်ရောက်သည် (OAuth/subscription များအတွက် မဟုတ်ပါ)
- **Settings → Resilience → Provider Profiles** တွင် အလိုအလျောက် နှုန်းကန့်သတ်ခြင်းကို ဖွင့်ထားကြောင်း အတည်ပြုပါ
- Provider က `429` status code များ သို့မဟုတ် `Retry-After` header များ ပြန်ပေးခြင်းရှိမရှိ စစ်ဆေးပါ

### Exponential backoff ကို ချိန်ညှိခြင်း

Provider profile များတွင် ဤဆက်တင်များကို ပံ့ပိုးထားသည်-

- **အခြေခံ နှောင့်နှေးချိန်** — ပထမအကြိမ် မအောင်မြင်ပြီးနောက် ကနဦးစောင့်ဆိုင်းချိန် (မူလသတ်မှတ်ချက်- 1s)
- **အများဆုံး နှောင့်နှေးချိန်** — စောင့်ဆိုင်းချိန်၏ အများဆုံးကန့်သတ်ချက် (မူလသတ်မှတ်ချက်- 30s)
- **မြှောက်ကိန်း** — ဆက်တိုက် မအောင်မြင်မှုတစ်ကြိမ်စီအတွက် နှောင့်နှေးချိန် မည်မျှတိုးမည်ကို သတ်မှတ်သည် (မူလသတ်မှတ်ချက်- 2x)

### Thundering herd ကို တားဆီးခြင်း

တစ်ပြိုင်နက်တည်း request များစွာက နှုန်းကန့်သတ်ခံထားရသော provider တစ်ခုထံ ရောက်လာသည့်အခါ OmniRoute သည် request များကို အစဉ်လိုက်လုပ်ဆောင်ရန်နှင့် ဆင့်ကဲမအောင်မြင်မှုများကို တားဆီးရန် mutex + အလိုအလျောက် နှုန်းကန့်သတ်ခြင်းကို အသုံးပြုသည်။ API key provider များအတွက် ၎င်းသည် အလိုအလျောက် လုပ်ဆောင်သည်။

### Chat request များသည် 503 / chat_admission_busy ဖြင့် မအောင်မြင်ခြင်း

**လက္ခဏာများ-**

- Chat completions endpoint က ထပ်မံကြိုးစားနိုင်သော `503` response တစ်ခုကို ပြန်ပေးပြီး ၎င်း၏ error code သည်
  `chat_admission_busy` ဖြစ်သည်။
- Response တွင် `Retry-After` ပါဝင်သည်။ #12135 မှစ၍ ၎င်း၏တန်ဖိုးကို တွေ့ရှိထားသော
  occupancy မှ ဆင်းသက်သတ်မှတ်သည် — request က စောင့်ဆိုင်းပြီးဖြစ်သော `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` window
  နှင့် လက်ရှိ heavyweight lease များကို ထိန်းထားပြီးဖြစ်သော အချိန်တို့အနက် ပိုကြီးသည့်တန်ဖိုးကို ယူကာ စက္ကန့်ပြည့်သို့
  အထက်ဘက်ပတ်လည်ကိန်းယူပြီး အများဆုံး 60 ဖြင့် ကန့်သတ်ထားသည်။ Idle gate တွင်မူ ယခင်ကတည်းကရှိသော အနိမ့်ဆုံးတန်ဖိုးများကို ဆက်လက်ထားရှိသည်-
  byte အခြေပြု path တွင် 2 စက္ကန့်၊ structure အခြေပြု path တွင် 1 စက္ကန့်ဖြစ်သည် (နောက်တစ်ခုတွင်
  `reason: "structure_limit"` လည်း ပါဝင်သည်)။
- အခြား heavyweight chat တစ်ခု သို့မဟုတ် ကြာရှည်စွာ လုပ်ဆောင်နေသော streaming response တစ်ခု
  လုပ်ဆောင်ဆဲဖြစ်နေချိန်တွင် ဤသို့ဖြစ်နိုင်သည်။

Byte အခြေပြု response body မှာ-

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

Structure အခြေပြု response သည် တူညီသော type နှင့် code ကို အသုံးပြုပြီး message မှာ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ဖြစ်ကာ `reason: "structure_limit"` လည်း ပါဝင်သည်။
မူလ threshold များအရ request တစ်ခုတွင် message အနည်းဆုံး `200` ခု၊
tool အနည်းဆုံး `64` ခု သို့မဟုတ် ခန့်မှန်း token အနည်းဆုံး `32,000` ခု ပါဝင်သည့်အခါ၊ သို့မဟုတ် ကန့်သတ်ထားသော structure estimation က
ဝင်ရောက်ကြည့်ရှုသည့် node `10,000` ခု သို့မဟုတ် depth `12` ဟူသော ကန့်သတ်ချက်များကို ကုန်ဆုံးစေသည့်အခါ ထို request ကို structurally heavy ဟု သတ်မှတ်သည်။

**အကြောင်းရင်း-** ဤသည်မှာ upstream provider ပျက်ကွက်ခြင်း မဟုတ်ဘဲ OmniRoute အတွင်း ရည်ရွယ်ချက်ရှိရှိ load လျှော့ချခြင်းဖြစ်သည်။
Process တစ်ခုစီသည် ကြီးမားသော request body တစ်ခုကို ထိန်းသိမ်းပြီး parse မလုပ်မီ ကန့်သတ်ထားသော heavyweight capacity ကို ကြိုတင်သီးသန့်ထားရန်
process-local guard တစ်ခုကို အသုံးပြုသည်။ Heavyweight lease တစ်ခုကို SSE
response ၏ သက်တမ်းတစ်လျှောက်လုံး ဆက်လက်ထိန်းထားသည်။

**#503 ဖြန့်ကျက်မှု-** ဤပြင်ဆင်ချက်မတိုင်မီ guard သည် host memory ကို ထည့်မစဉ်းစားဘဲ တစ်ပြိုင်နက်လုပ်ဆောင်နိုင်မှုကို သတ်မှတ်ထားသော request အရေအတွက်
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`၊ မူလသတ်မှတ်ချက် `1`) ဖြင့် ကန့်သတ်ထားသောကြောင့် coding-agent
ဖြန့်ကျက်မှု (subagent/CLI များစွာ၊ ပုံမှန်အားဖြင့် body များ > 256 KB) သည် အမှန်တကယ်
တစ်ပြိုင်နက်လုပ်ဆောင်နိုင်မှု ~1 အထိ ကျဆင်းပြီး လုံးဝပုံမှန် load အောက်တွင်ပင် 503 ဖြစ်စေခဲ့သည်။ ယခု guard သည် မိမိဘာသာ ချိန်ညှိသည်- ၎င်းကို
process ၏ အမှန်တကယ် memory အမြင့်ဆုံးကန့်သတ်ချက်မှ အရွယ်အစားတွက်ချက်ထားသော အလိုအလျောက်ရရှိသည့် ingest BYTE budget (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ဖြင့်
ထိန်းချုပ်ထားပြီး လက်ရှိ resource-pressure signal ကိုလည်း စစ်ဆေးသည် — ထို့ကြောင့် heavy request တစ်ခုထက်ပို၍
တစ်ပြိုင်နက် ရောက်လာရုံမျှဖြင့် မဟုတ်ဘဲ host သည် အမှန်တကယ် memory ဖိအားအောက်တွင် ရှိသည့်အခါမှသာ
load ကို လျှော့ချသည်။ ယခင် count cap (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ကို
သင်က တိတိကျကျ သတ်မှတ်ထားသည့်အခါတွင် ဆက်လက်လိုက်နာသော်လည်း ထိုအခါမှသာ ဖြစ်သည်။

Capacity မအားလပ်သောအခါ heavyweight request တစ်ခုသည် ထပ်မံကြိုးစားနိုင်သော `503` ကို မပြန်မီ
slot တစ်ခု လွတ်လာရန် `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` အထိ (မူလသတ်မှတ်ချက် `2000`၊ `0` က စောင့်ဆိုင်းမှုကို ပိတ်သည်) ဦးစွာ စောင့်ဆိုင်းသည်။
ဤကန့်သတ်စောင့်ဆိုင်းမှုမှာ heavy sub-request များကို တစ်ပြိုင်နက် ဖြန့်ကျက်သည့် agent ပုံစံ client များ
(OpenCode, Claude Code, Cursor) က ချက်ချင်းငြင်းပယ်မှုများကြောင့် ၎င်းတို့၏ retry budget အားလုံးကို ကုန်ဆုံးစေပြီး
လုပ်ငန်းတစ်ဝက်တစ်ပျက်တွင် ရပ်တန့်သွားမည့်အစား request အစုလိုက်ရောက်ရှိမှုကို အစဉ်လိုက်လုပ်ဆောင်နိုင်စေရန် ဖြစ်သည်။
လက်ရှိ heavyweight lease occupancy၊ သတ်မှတ်ပြီးသော byte budget နှင့် လက်ရှိ pressure severity ကို
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) တွင် ဖော်ပြထားသည် — မည်သည့် env var ကိုမျှ မပြင်မီ ၎င်းတို့ကို စစ်ဆေးပါ။
Settings → Resilience → Request Queue → Concurrent Requests က ဤအရာကို မထိန်းချုပ်ပါ။ ထိုဆက်တင်သည်
သီးခြား provider request-queue ယန္တရားတစ်ခုကို ထိန်းချုပ်သည်။

**ဖြေရှင်းနည်း-**

1. ဦးစွာ ပြန်လည်ကြိုးစားပါ။ Client များသည် request ကို ချက်ချင်း
   ထပ်ခါတလဲလဲ ပြုလုပ်မည့်အစား `Retry-After` ကို လိုက်နာပြီး backoff ကို အသုံးပြုသင့်သည်။
2. မည်သည့်အရာကိုမျှ မချိန်ညှိမီ `/api/monitoring/health` → `chatAdmission` ကို စစ်ဆေးပါ။ `countCapEnabled:
false` နှင့် လုံလောက်ကျယ်ပြန့်သော `maxInflightBytes` တို့သည် အလိုအလျောက်ရရှိသည့် budget က ၎င်း၏
   တာဝန်ကို လုပ်ဆောင်နေပြီးဖြစ်ကြောင်း ဆိုလိုသည်။ `pressureSeverity` က `high`/`critical` ဖြစ်ပါက host တွင် memory အမှန်တကယ် နည်းပါးနေသည် —
   ၎င်းကို admission env var ဖြင့် ဖြေရှင်း၍မရဘဲ RAM ပိုများရန် သို့မဟုတ် workload ပိုသေးရန် လိုအပ်သည်။
3. `/api/monitoring/health` တွင် အလိုအလျောက်ရရှိသည့် budget က သင့် host အတွက် အမှန်တကယ် သေးလွန်းကြောင်း
   ပြသမှသာ (ရှားပါးသည် — container မှ bare-metal အထိ ချဲ့ထွင်နိုင်ရန် ၎င်းက သတ်မှတ်ပြီးဖြစ်သည်) legacy request-count cap ကို ပြန်လည်အသုံးပြုမည့်အစား
   `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ဖြင့် တိုက်ရိုက် override လုပ်ပါ။

တရားဝင် admission ဆက်တင်များအတွက် [environment-variable ရည်ညွှန်းချက်](../reference/ENVIRONMENT.md#4-security--authentication)
ကို ကြည့်ပါ။

## ရွေးချယ်အသုံးပြုနိုင်သော RAG / LLM ချို့ယွင်းမှု အမျိုးအစားခွဲခြားခြင်း (ပြဿနာ ၁၆ မျိုး)

OmniRoute အသုံးပြုသူအချို့သည် gateway ကို RAG သို့မဟုတ် agent stack များ၏ ရှေ့တွင် ထားရှိကြသည်။ ထိုကဲ့သို့ စီစဉ်ထားမှုများတွင် ထူးဆန်းသော ပုံစံတစ်ခုကို မကြာခဏ တွေ့ရတတ်သည်- OmniRoute သည် ပုံမှန်ကောင်းမွန်နေပုံရသော်လည်း (provider များ အလုပ်လုပ်နေခြင်း၊ routing profile များ မှန်ကန်ခြင်း၊ rate limit သတိပေးချက်များ မရှိခြင်း) နောက်ဆုံးအဖြေမှာ မှားယွင်းနေဆဲဖြစ်သည်။

လက်တွေ့တွင် ဤပြဿနာများသည် gateway ကိုယ်တိုင်ကြောင့် မဟုတ်ဘဲ downstream RAG pipeline ကြောင့် ဖြစ်လေ့ရှိသည်။

ထိုချို့ယွင်းမှုများကို ဖော်ပြရန် အားလုံးမျှဝေအသုံးပြုနိုင်သည့် ဝေါဟာရအစုတစ်ခု လိုအပ်ပါက WFGY ProblemMap ကို အသုံးပြုနိုင်သည်။ ၎င်းသည် ထပ်ခါတလဲလဲ ဖြစ်ပေါ်တတ်သော RAG / LLM ချို့ယွင်းမှုပုံစံ ၁၆ မျိုးကို သတ်မှတ်ဖော်ပြထားသည့် ပြင်ပ MIT license စာသားအရင်းအမြစ်တစ်ခု ဖြစ်သည်။ အကျဉ်းချုပ်အားဖြင့် ၎င်းတွင် အောက်ပါတို့ ပါဝင်သည်-

- retrieval လွဲချော်မှုနှင့် ပျက်စီးနေသော context နယ်နိမိတ်များ
- အလွတ်ဖြစ်နေသော သို့မဟုတ် ခေတ်မမီတော့သော index နှင့် vector store များ
- embedding နှင့် semantic အဓိပ္ပာယ် မကိုက်ညီမှု
- prompt တည်ဆောက်ခြင်းနှင့် context window ပြဿနာများ
- logic ပြိုလဲမှုနှင့် ယုံကြည်မှုလွန်ကဲသော အဖြေများ
- ရှည်လျားသော chain နှင့် agent ညှိနှိုင်းမှု ချို့ယွင်းချက်များ
- multi agent memory နှင့် role လွဲချော်မှု
- deployment နှင့် bootstrap အစီအစဉ်ဆိုင်ရာ ပြဿနာများ

အယူအဆမှာ ရိုးရှင်းသည်-

1. မှားယွင်းသော response တစ်ခုကို စုံစမ်းစစ်ဆေးသည့်အခါ အောက်ပါတို့ကို မှတ်တမ်းတင်ပါ-
   - အသုံးပြုသူ၏ task နှင့် request
   - OmniRoute ရှိ route သို့မဟုတ် provider combo
   - downstream တွင် အသုံးပြုထားသော RAG context များ (ရယူထားသော document များ၊ tool call များ စသည်)
2. ဖြစ်ရပ်ကို WFGY ProblemMap နံပါတ် တစ်ခု သို့မဟုတ် နှစ်ခုနှင့် ချိတ်ဆက်သတ်မှတ်ပါ (`No.1` … `No.16`)။
3. ထိုနံပါတ်ကို OmniRoute log များနှင့်အတူ သင့်ကိုယ်ပိုင် dashboard၊ runbook သို့မဟုတ် incident tracker တွင် သိမ်းဆည်းပါ။
4. သင့် RAG stack၊ retriever သို့မဟုတ် routing strategy ကို ပြောင်းလဲရန် လိုအပ်ခြင်း ရှိ၊ မရှိ ဆုံးဖြတ်ရန် သက်ဆိုင်ရာ WFGY စာမျက်နှာကို အသုံးပြုပါ။

စာသားအပြည့်အစုံနှင့် လက်တွေ့အသုံးချနိုင်သော နည်းလမ်းများကို ဤနေရာတွင် ရရှိနိုင်သည် (MIT license၊ စာသားသီးသန့်)-

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRoute ၏ နောက်ကွယ်တွင် RAG သို့မဟုတ် agent pipeline များကို အသုံးမပြုပါက ဤအပိုင်းကို လျစ်လျူရှုနိုင်သည်။

## v3.8.0 တွင် သိရှိထားသော ပြဿနာများ

v3.8.0 release နှင့် သက်ဆိုင်သော ပြဿနာများနှင့် ၎င်းတို့အတွက် လက်ရှိဖြေရှင်းနည်းများ။ နောက်ပိုင်း patch တစ်ခုတွင် ပြင်ဆင်ချက် ထည့်သွင်းပြီးပါက သက်ဆိုင်ရာအကြောင်းအရာကို အပ်ဒိတ်လုပ်မည် သို့မဟုတ် ဖယ်ရှားမည်။

### Devin CLI auth ချို့ယွင်းမှုများ

**လက္ခဏာများ-**

- Devin အခြေပြု tool များကို ခေါ်ယူသည့်အခါ "Devin CLI ကို ရှာမတွေ့ပါ" သို့မဟုတ် "auth မအောင်မြင်ပါ" ဟု ပြသခြင်း
- CLI runtime စစ်ဆေးမှုက `installed=false` ဟု အစီရင်ခံခြင်း

**အကြောင်းရင်းများ-**

- `CLI_DEVIN_BIN` က မရှိသော path တစ်ခုကို ညွှန်ပြနေခြင်း
- host ပေါ်တွင် Devin CLI ကို install မလုပ်ထားခြင်း

**ဖြေရှင်းနည်း-**

1. သင့် platform အတွက် Devin CLI ကို install လုပ်ပါ
2. `.env` တွင် `CLI_DEVIN_BIN=/usr/local/bin/devin` (သို့မဟုတ် အမှန်တကယ်ရှိသော path) ကို သတ်မှတ်ပါ
3. OmniRoute ကို restart လုပ်ပြီး **Dashboard → CLI Tools** မှ ပြန်လည်စမ်းသပ်ပါ

### Model cooldown ပိတ်မိနေခြင်း (ကိုယ်တိုင် reset လုပ်ရန်)

**လက္ခဏာများ-**

- သက်တမ်းကုန်ဆုံးချိန် ကျော်လွန်သွားသော်လည်း model တစ်ခုသည် cooldown စာရင်းထဲတွင် ဆက်လက်ရှိနေခြင်း
- timestamp သည် အတိတ်သို့ ရောက်နေသော်လည်း combo routing က ထို model ကို ဆက်လက်ကျော်သွားခြင်း

**ကိုယ်တိုင် reset လုပ်နည်း-**

- **Dashboard:** **Settings → Model Cooldowns** → သက်ရောက်မှုရှိသော card ပေါ်ရှိ **Re-enable** ကို နှိပ်ပါ
- **API:** management auth header များနှင့်အတူ `DELETE /api/resilience/model-cooldowns`

### Command Code provider ချိတ်ဆက်မှုသည် 403 ဖြင့် မအောင်မြင်ခြင်း

**လက္ခဏာများ-**

- Command Code provider ချိတ်ဆက်မှုကို စမ်းသပ်သည့်အခါ 403 ပြန်လာခြင်း
- အသစ်ထည့်သွင်းပြီးနောက် provider card တွင် "ခွင့်ပြုချက်မရှိပါ" ဟု ပြသခြင်း

**အကြောင်းရင်း-** OAuth လုပ်ငန်းစဉ် မပြီးမြောက်ခဲ့ခြင်း (callback ကို မရရှိခြင်း သို့မဟုတ် token ကို အမြဲတမ်းသိမ်းဆည်းထားခြင်း မရှိခြင်း)။

**ဖြေရှင်းနည်း-**

- OAuth လုပ်ငန်းစဉ်ကို ပြန်လည်အစပျိုးရန် CLI မှ `omniroute providers` ကို run ပါ၊ သို့မဟုတ်
- **Dashboard → Providers → Command Code → Reconnect** မှ OAuth ကို ပြန်လည်လုပ်ဆောင်ပါ

### ModelScope သည် ပြင်းထန်သော 429 cooldown များကို ပြန်ပေးခြင်း

**လက္ခဏာများ-**

- request အနည်းငယ်ကို တစ်ပြိုင်နက်တည်း ပေးပို့ပြီးနောက် ModelScope တွင် အလွန်တိုတောင်းသော သို့မဟုတ် ချက်ချင်းသက်ရောက်သည့် cooldown များ ဖြစ်ပေါ်ခြင်း
- combo routing က ModelScope ကို မျှော်လင့်ထားသည်ထက် စော၍ ကျော်သွားခြင်း

**အကြောင်းရင်း-** ModelScope သည် provider အလိုက် သီးသန့်ဖြစ်သော `Retry-After` header များကို ထုတ်ပေးသည်။ v3.8.0 တွင် ထို header များအတွက် သီးသန့်ကိုင်တွယ်မှု ပါဝင်လာသောကြောင့် ဗားရှင်းအဟောင်းများက ၎င်းတို့ကို ယေဘုယျ rate-limit အရိပ်အမြွက်များအဖြစ် မှားယွင်းဖတ်ရှုသည်။

**ဖြေရှင်းနည်း-**

- v3.8.0 သို့မဟုတ် ၎င်းထက် နောက်ကျသော ဗားရှင်းကို အသုံးပြုနေကြောင်း သေချာပါစေ
- **Settings → Resilience** အောက်ရှိ `useUpstream429BreakerHints` toggle ကို ဖွင့်ထားကြောင်း စစ်ဆေးပါ

### Production တွင် OMNIROUTE_WS_BRIDGE_SECRET မရှိခြင်း

**လက္ခဏာများ-**

- remote production host တစ်ခုပေါ်တွင် အသုံးပြုနေစဉ် Codex/Responses WebSocket bridge request တိုင်း၌ 401 ပြန်လာခြင်း
- ချိတ်ဆက်ပြီးသည်နှင့် WebSocket bridge handshake ချက်ချင်းပိတ်သွားခြင်း

**အကြောင်းရင်း-** production environment တွင် `OMNIROUTE_WS_BRIDGE_SECRET` env var မရှိခြင်း။

**ဖြေရှင်းနည်း-**

1. ကျပန်း secret တစ်ခု ထုတ်လုပ်ပါ- `openssl rand -hex 32`
2. production server env (နှင့် bridge နှင့် ဆက်သွယ်သော client တိုင်း) တွင် `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ကို သတ်မှတ်ပါ
3. OmniRoute ကို restart လုပ်ပါ

### Responses API: background mode ကို synchronous အဖြစ် အဆင့်လျှော့ထားခြင်း

**လက္ခဏာများ-**

- မှတ်တမ်းတင်ထားသော သတိပေးချက်- `background mode degraded to synchronous`
- `background: true` request တစ်ခုက background job handle အစား ပုံမှန် synchronous response ကို ပြန်ပေးခြင်း

**အကြောင်းရင်း-** v3.8.0 တွင် Responses API ရှိ `background: true` ကို synchronous execution အဖြစ် ရည်ရွယ်ချက်ရှိရှိ အဆင့်လျှော့ပြီး သတိပေးချက်တစ်ခု ထုတ်ပေးသည်။ async background execution အပြည့်အစုံသည် အနာဂတ်တွင် ပေးအပ်မည့် လုပ်ဆောင်ချက်ဖြစ်သည်။

**ဖြေရှင်းနည်း-**

- `background` မပါဘဲ ခေါ်ဆိုရန် client ကို ပြင်ဆင်ပါ၊ သို့မဟုတ်
- async background mode အပြည့်အစုံ ပါဝင်လာမည့် နောက်ပိုင်း release ကို စောင့်ပါ (changelog ကို စောင့်ကြည့်ပါ)
