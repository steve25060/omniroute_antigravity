### නොමිලේ සපයන්නන් මත අනුපාත සීමා කිරීම (429 / 400 / 401)

**රෝග ලක්ෂණය**: නොමිලේ/සත්යාපනය අවශ්ය නොවන සපයන්නන් (opencode, auggie, ආදිය) සමඟ `model: "auto"` භාවිත කරන විට, පිළිතුරු වෙනුවට විටින් විට `HTTP 429`, `400`, හෝ `401` ලැබේ. සුළු මොහොතකට පසුව එම ප්රේරණයම නැවත උත්සාහ කළ විට ඉල්ලීම් සාර්ථක වන නමුත්, ස්වයංක්රීයකරණය (cron කාර්ය, නියෝජිතයන්, ස්ක්රිප්ට්) පළමු අසාර්ථකත්වයේදීම බිඳ වැටේ.

**මූලික හේතුව**: ස්වාධීන අසාර්ථකත්ව ආකාර තුනක් එකිනෙක මත ගොඩගැසේ:

1. **සපයන්නාගේ අනුපාත සීමාව (`429`)**: නොමිලේ ස්තරවලට කාල කවුළුවක් සඳහා කෝටාවක් බලාත්මක කළ හැක. සමාන්තර ඇමතුම් සමූහයක් එය අවසන් කරන බැවින්, කවුළුව යළි සැකසෙන තෙක් ඊළඟ ඉල්ලීම ප්රතික්ෂේප වේ.
2. **Passthrough තුළ බිඳුණු ආකෘතිය (`400`/`401`)**: `auto/*` සංචිතවල නාමාවලියේ ලියාපදිංචි වී ඇති නමුත් සක්රිය අක්තපත්ර නොමැති `opencode` වෙතින් passthrough ආකෘති ඇතුළත් විය හැක (උදා. `oc/north-mini-code-free` → `401`). ස්වයංක්රීය රවුටරය එකක් උත්සාහ කර අසාර්ථක වන අතර, පසුබැසීම ක්රියාත්මක වීමට පෙර දෝෂය ඉදිරියට පැතිරේ.
3. **සමකාලීනත්ව විස්තාරණය (බර යටතේ `429`)**: නියෝජිත/cron සැසි කිහිපයක් එකවර `auto` වෙත ප්රවේශ වන විට, සමස්ත ඉල්ලීම් අනුපාතය නොමිලේ සපයන්නන්ට දරාගත හැකි ප්රමාණය ඉක්මවන බැවින්, වලංගු ඇමතුම් අපයෝජන ලෙස සලකුණු වේ.

**සත්යාපිත විසඳුම (ප්රජාව විසින් වාර්තා කරන ලදී, 2026-08-10)**: නොමිලේ ස්තරයේ අස්ථාවරත්වය හේතුවෙන් ක්රියාවලිය නතර වීම වෙනුවට, භ්රමණය, සමකාලීනත්වය සහ පසුබැසීම මඟින් එය අවශෝෂණය කරගැනීමට පරිසර විචල්ය තුනක් සීරුමාරු කරන්න:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ලැබුණු විට වෙනත් ආකෘතියකට/සපයන්නෙකුට මාරු වන්න (බිඳුණු passthrough ආකෘති මඟ හරියි)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # heavyweight ඇතුළත් කිරීමේ උපරිමය පැහැදිලිව සකසයි (පෙරනිමියෙන් සකසා නැත: ඉල්ලීම්-ගණන සීමාවක් නැත, පහත සටහන බලන්න)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ක්ෂණිකව නැවත උත්සාහ කළ හැකි 503ක් ලබාදීම වෙනුවට heavyweight ධාරිතාව සඳහා වඩා දිගු සීමා කළ රැඳීමක්
```

මේවා OmniRoute ක්රියාවලියේ පරිසරය තුළ සකසන්න (daemon එක, උදා. LaunchAgent plist හෝ `systemctl edit` හරහා), ඉන්පසු OmniRoute නැවත ආරම්භ කරන්න. භ්රමණ ධජය තනි වශයෙන් වැඩිම බලපෑමක් ඇති පාලකයයි: එය දැඩි අසාර්ථකත්වයක්, සංචිතයේ සෞඛ්ය සම්පන්න සපයන්නෙකුට එරෙහිව විනිවිද පෙනෙන ලෙස නැවත උත්සාහ කිරීමක් බවට පරිවර්තනය කරයි.

**සටහන**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` මඟින් එකවර ධාවනය වන heavyweight — දිගු-සන්දර්භ — ඉල්ලීම් ගණන සීමා කරයි; මෙම සීමාව ඇතුළත් කිරීමේ දොරටුවක් මිස සපයන්නාගේ අනුපාත සීමාකාරකයක් නොවේ. **#503-fanout යාවත්කාලීනය:** මෙම විචල්යය තවදුරටත් පෙරනිමියෙන් සකසා නැත (දැන් එය බැඳෙන්නේ ඉහත ආකාරයට පැහැදිලිව වින්යාස කළ විට පමණි) — ඒ වෙනුවට heavyweight ඇතුළත් කිරීම, ධාරකයේ සැබෑ මතක සීමාව අනුව ස්වයංක්රීයව පරිමාණය වන ස්වයං-ව්යුත්පන්න බයිට් අයවැයකින් (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) පාලනය වේ. එබැවින් අලුත් යෙදවීමකදී මෙම විචල්යය කිසිසේත් නොසකසා වුවද `503 chat_admission_busy` ප්රතික්ෂේප කිරීම් බොහෝ අඩුවෙන් දැකිය යුතුය; මෙහිදී එය පැහැදිලිව සැකසීම තවමත් ලේඛනගත කළ ආකාරයටම ක්රියා කරයි. පැහැදිලි බයිට්-අයවැය අතික්රමණ 8 MiB–2 GiB අතරට සීමා වේ. `413 body_exceeds_budget` යනු තාවකාලික දෙයක් නොවේ: එම බයිට් අයවැය වැඩි කරන්න, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` අඩු කරන්න, හෝ ක්රියාවලියේ මතක සීමාව වැඩි කරන්න. `inflight_bytes_budget` හේතුවෙන් බර අඩු කිරීම තාවකාලික සම්පත් තරගයක් වන අතර නැවත උත්සාහ කළ හැක. එක් එක් සපයන්නා සඳහා වන අනුපාත සීමා කිරීම (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, සහ `RATE_LIMIT_AUTO_ENABLE` මඟින් වෙනම පාලනය වේ — `.env.example` බලන්න.

**එය ක්රියා කළ බව සත්යාපනය කරන්නේ කෙසේද**: ඔබේ නියෝජිතයා/cron කාර්යය ඉක්මන් අනුක්රමයකින් දෙවරක් ධාවනය කර දෙකම සාර්ථක වන බව තහවුරු කරන්න. විසඳුම යෙදීමට පෙර, දෙවන ධාවනය සාමාන්යයෙන් `429`/`401` දෝෂයක් නිකුත් කරයි. විසඳුමෙන් පසුව, අසාර්ථකත්වයන් (තිබේ නම්) විනිවිද පෙනෙන ලෙස නැවත උත්සාහ කරන අතර ඇමතුම සම්පූර්ණ වේ. ඔබට `curl /monitoring/health` ධාවනය කර, සපයන්නාගේ සම්බන්ධතාවල `rateLimitedUntil` ක්ෂේත්රය සහ බලපෑමට ලක් වූ සපයන්නන් සඳහා `circuitBreakers.providerBreakers[].state` නිරීක්ෂණය කළ හැක — තත්ත්වය `CLOSED`, `DEGRADED`, `OPEN`, හෝ `HALF_OPEN` අතරින් එකකි (`src/shared/utils/circuitBreaker.ts` බලන්න), දිගින් දිගටම අසාර්ථක වන සපයන්නෙකු, යළි සැකසීමේ කාල කවුළුව හරහා පරීක්ෂණ ඉල්ලීමකට ඉඩ ලැබීමට (`HALF_OPEN`) පෙර `CLOSED → DEGRADED → OPEN` ලෙස මාරු වේ.

**ඔබට තවමත් 429 දක්නට ලැබේ නම්**: එම සැපයුම්කරු සඳහා සක්රිය ගිණුමේ _quota_ සැබවින්ම අවසන් වී ඇත (rate එක පමණක් නොවේ). OmniRoute උපකරණ පුවරුවේ → Providers → Accounts වෙත ගොස් එම සැපයුම්කරු සඳහා දෙවන ගිණුමක් එක් කරන්න, නැතහොත් වෙනත් නොමිලේ සැපයුම්කරුවෙකු (උදා. `routeway`, `auggie`) සමඟ මිශ්රව භාවිත කරන්න. මාරුවෙන් මාරුවට භාවිත කිරීම උපකාරී වන්නේ තාවකාලික rate/400/401 දෝෂ සඳහා පමණි; quota එක සම්පූර්ණයෙන් අවසන් වී ඇත්නම් දෙවන අක්තපත්රයක් හෝ වෙනත් සැපයුම්කරුවෙකු අවශ්ය වේ.

**vision models (`auto/vision`, `bazaarlink/*`) මත 403 දක්නට ලැබේ නම්**: සම්බන්ධිත ගිණුමට vision ඇතුළත් ගෙවීම් සැලැස්මක් නොමැති අතර, හෝ API key එකට ප්රමාණවත් අවසර නොමැත. key scope එකට vision/multimodal ඇතුළත් බව සැපයුම්කරුගේ උපකරණ පුවරුවෙන් තහවුරු කරන්න, නැතහොත් ගෙවීම් මට්ටමේ ගිණුමක් සම්බන්ධ කර එය vision ඉලක්කය ලෙස තබා ගන්න.

## npm install අනතුරු ඇඟවීම් (ERESOLVE / peer / deprecated)

ඔබ `npm install -g omniroute` ධාවනය කරන විට, `npm warn ERESOLVE`, peer-dependency දැනුම්දීම් සහ `deprecated` පණිවිඩ වැනි අනතුරු ඇඟවීම් රාශියක් ඔබට දැකිය හැක. **මේවා බලාපොරොත්තු විය හැකි අතර හානිකර නොවේ.** ප්රතිදානයේ `added <N> packages` දිස්වන්නේ නම්, ඔබේ ස්ථාපනය සාර්ථක වී ඇත.

මෙම අනතුරු ඇඟවීම් පැමිණෙන්නේ OmniRoute විසින් පාලනය නොකරන තෙවන පාර්ශ්වීය පැකේජවල යල්පැන ගිය peer-dependency පරාසවලිනි:

1. **`marked-terminal` සඳහා `marked >=1 <16` අවශ්ය නමුත් `marked@18` හමු වී ඇත** — ප්රායෝගිකව මෙය හොඳින් ක්රියා කරයි; upstream peer පරාසය යල්පැන ගොස් ඇත.
2. **`deprecated prebuild-install@7.1.3`** — සංක්රාමික native-binary ලබාගැනීමේ සහායකයකි. එය pin කර ඇති `wreq-js` transport binding ස්ථාපනය කිරීමට
   භාවිත නොකරන අතර, web-cookie provider transport පිහිටුවීම අසාර්ථක වූ බවක් ද නොපෙන්වයි.

**කිසිදු ක්රියාමාර්ගයක් අවශ්ය නොවේ** — upstream පැකේජ fork කිරීමකින් තොරව මෙම අනතුරු ඇඟවීම් සම්පූර්ණයෙන්ම නිහඬ කළ නොහැක.

### Avast/AVG විසින් `README.md`, `MD:HttpRequest-inf[Susp]` ලෙස නිරෝධායනය කිරීම

**මෙය වැරදි ධනාත්මක හඳුනාගැනීමකි. කිසිවක් ආසාදනය වී නොමැති අතර, කිසිදු ක්රියාමාර්ගයක් අවශ්ය නොවේ.**

## ක්ලවුඩ් ගැටලු

### ක්ලවුඩ් සමමුහුර්ත කිරීමේ දෝෂ

1. `BASE_URL` ඔබගේ ක්රියාත්මක වන instance එක වෙත යොමු වන බව තහවුරු කරන්න (උදා., `http://localhost:20128`)
2. `CLOUD_URL` ඔබගේ ක්ලවුඩ් endpoint එක වෙත යොමු වන බව තහවුරු කරන්න (උදා., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` අගයන් server-side අගයන් සමඟ ගැළපෙන ලෙස තබා ගන්න

### ක්ලවුඩ් `stream=false` මඟින් 500 ලැබීම

**ලක්ෂණය:** streaming නොවන calls සඳහා ක්ලවුඩ් endpoint එකේ `Unexpected token 'd'...` දිස් වේ.

**හේතුව:** client එක JSON අපේක්ෂා කරන අතර upstream එක SSE payload එකක් ආපසු ලබා දෙයි.

**තාවකාලික විසඳුම:** ක්ලවුඩ් වෙත සෘජු calls සඳහා `stream=true` භාවිත කරන්න. දේශීය runtime එකේ SSE→JSON fallback එකක් ඇතුළත් වේ.

### ක්ලවුඩ් එක සම්බන්ධ වී ඇති බව පෙන්වන නමුත් "වලංගු නොවන API යතුර" යැයි පවසයි

1. දේශීය dashboard එකෙන් (`/api/keys`) නව යතුරක් සාදන්න
2. ක්ලවුඩ් සමමුහුර්ත කිරීම ක්රියාත්මක කරන්න: Enable Cloud → Sync Now
3. පැරණි/සමමුහුර්ත නොකළ යතුරු සඳහා තවමත් ක්ලවුඩ් එකෙන් `401` ලැබිය හැක

## Docker ගැටලු

### Docker IPv6 / සම්බන්ධතාව යළි පිහිටුවීම

<a name="docker-ipv6"></a>

**ලක්ෂණ:** `curl http://localhost:20128/v1/models` මඟින් `curl: (56) Recv failure: Connection reset by peer` ආපසු ලැබේ. Dashboard එක සහ සත්යාපනය නොකළ endpoints ක්රියා කරන නමුත් සත්යාපනය කළ endpoints අසාර්ථක වේ — මෙය සත්යාපන ගැටලුවක් සේ පෙනුණද එසේ නොවේ.

**හේතුව:** `docker run -p 20128:20128` මඟින් `0.0.0.0` (IPv4) සහ `::` (IPv6) යන දෙකෙහිම පළ කරන නමුත්, container එක තුළ ඇති process එක සවන් දෙන්නේ IPv4 සඳහා පමණි. `localhost` පළමුව `::1` වෙත resolve වන hosts වලදී, සම්බන්ධතාව එය පිටුපස listener එකක් නොමැති IPv6 published port එක වෙත පැමිණේ → සම්බන්ධතාව යළි පිහිටුවේ.

**විසඳුම:**

1. **ඉක්මන් රෝග විනිශ්චය:** `curl -4 http://localhost:20128/v1/models` ධාවනය කරන්න. එය `-4` සමඟ ක්රියා කර එය නොමැතිව අසාර්ථක වේ නම්, ඔබට IPv6 bind නොගැළපීමක් ඇත.
2. **ස්ථිර විසඳුම:** ඔබගේ `docker run` විධානයේ `-p 127.0.0.1:20128:20128` භාවිත කිරීමෙන් IPv4 වෙත පැහැදිලිව bind කරන්න:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   මෙය IPv4 bind කිරීම අනිවාර්ය කරන අතර සියලුම host interfaces මත proxy එක නිරාවරණය වීමද වළක්වයි.

### Log ගොනු සක්රිය කිරීම

ඔබගේ `.env` ගොනුවේ `APP_LOG_TO_FILE=true` සකසන්න. යෙදුම් logs `logs/` යටතේ ලියනු ලැබේ.
සැකසුම් තුළ call log pipeline එක සක්රිය කර ඇති විට request artifacts `${DATA_DIR}/call_logs/` යටතේ ගබඩා වේ.
pipeline capture සක්රිය කර ඇති විට, stream chunk payloads ඉවත් කිරීමට `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` සකසන්න, නැතහොත් artifact සීමාව KB වලින් වෙනස් කිරීමට `CALL_LOG_PIPELINE_MAX_SIZE_KB` සීරුමාරු කරන්න.

http://localhost:20128/dashboard/health

# API සෞඛ්ය පරීක්ෂාව

### Runtime ආචයනය

- ප්රධාන තත්ත්වය: `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)
- භාවිතය: `storage.sqlite` තුළ SQLite වගු (`usage_history`, `call_logs`, `proxy_logs`) + විකල්ප `${DATA_DIR}/call_logs/`
- යෙදුම් logs: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` විට)
- Call log artifacts: call log pipeline එක සක්රිය කර ඇති විට `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

Request Logs පිටුවේ **Clean history** ක්රියාව මඟින් `call_logs`, පැරණි
`request_detail_logs`, සහ දේශීය `${DATA_DIR}/call_logs/` artifact directory එක හිස් කරයි.

### පොදු ආකෘති ගැටලු

- **සිතීමේ ටැග නොපෙන්වීම** — ඉලක්ක සපයන්නා සිතීමට සහාය දක්වන්නේද සහ සිතීමේ අයවැය සැකසුම නිවැරදිද යන්න පරීක්ෂා කරන්න
- **මෙවලම් ඇමතුම් අතහැරීම** — ඇතැම් ආකෘති පරිවර්තන සහාය නොදක්වන ක්ෂේත්ර ඉවත් කළ හැක; අත්හදා බැලීමේ පරිසර ප්රකාරයේදී තහවුරු කරන්න
- **පද්ධති ප්රේරකය නොමැති වීම** — Claude සහ Gemini පද්ධති ප්රේරක වෙනස් ආකාරයෙන් හසුරුවයි; පරිවර්තන ප්රතිදානය පරීක්ෂා කරන්න
- **SDK එක වස්තුවක් වෙනුවට අමු තන්තුවක් ලබා දෙයි** — v1.x තුළ විසඳා ඇත; ප්රතිචාර පිරිසිදුකාරකය OpenAI SDK Pydantic වලංගුකරණ අසාර්ථක වීම් ඇති කරන සම්මත නොවන ක්ෂේත්ර (`x_groq`, `usage_breakdown`, ආදිය) ඉවත් කරයි. ඔබ මෙය තවමත් v3.x+ මත දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.
- **GLM/ERNIE විසින් `system` භූමිකාව ප්රතික්ෂේප කරයි** — v1.x තුළ විසඳා ඇත; භූමිකා සාමාන්යකාරකය නොගැළපෙන ආකෘති සඳහා පද්ධති පණිවිඩ ස්වයංක්රීයව පරිශීලක පණිවිඩ සමඟ ඒකාබද්ධ කරයි. ඔබ මෙය තවමත් v3.x+ මත දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.
- **`developer` භූමිකාව හඳුනා නොගැනීම** — v1.x තුළ විසඳා ඇත; OpenAI නොවන සපයන්නන් සඳහා ස්වයංක්රීයව `system` බවට පරිවර්තනය කෙරේ. ඔබ මෙය තවමත් v3.x+ මත දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.
- **`json_schema` Gemini සමඟ ක්රියා නොකිරීම** — v1.x තුළ විසඳා ඇත; `response_format` දැන් Gemini හි `responseMimeType` + `responseSchema` බවට පරිවර්තනය කෙරේ. ඔබ මෙය තවමත් v3.x+ මත දකින්නේ නම්, කරුණාකර ගැටලුවක් ගොනු කරන්න.

## විකල්ප RAG / LLM අසාර්ථකතා වර්ගීකරණය (ගැටලු 16ක්)

සමහර OmniRoute පරිශීලකයෝ RAG හෝ නියෝජිත ස්ටැක්වලට ඉදිරියෙන් ගේට්වේ එක ස්ථානගත කරති. එවැනි සැකසුම්වල අසාමාන්ය රටාවක් දැකීම සාමාන්ය දෙයකි: OmniRoute සෞඛ්ය සම්පන්න බව පෙනේ (සපයන්නන් ක්රියාත්මකයි, රවුටින් පැතිකඩ නිවැරදියි, අනුපාත සීමා ඇඟවීම් නැත), නමුත් අවසාන පිළිතුර තවමත් වැරදියි.

ප්රායෝගිකව, මෙම සිදුවීම් සාමාන්යයෙන් හටගන්නේ ගේට්වේ එකෙන් නොව, ඉන් පසු ඇති RAG නලමාර්ගයෙනි.

එම අසාර්ථකතා විස්තර කිරීමට ඔබට හවුල් වචන මාලාවක් අවශ්ය නම්, නැවත නැවත ඇතිවන RAG / LLM අසාර්ථකතා රටා දහසයක් අර්ථ දක්වන බාහිර MIT බලපත්රලාභී පෙළ සම්පතක් වන WFGY ProblemMap භාවිත කළ හැක. ඉහළ මට්ටමකින් එය පහත දෑ ආවරණය කරයි:

- ලබාගැනීමේ විස්ථාපනය සහ බිඳුණු සන්දර්භ සීමා
- හිස් හෝ යල්පැන ගිය දර්ශක සහ දෛශික ගබඩා
- embedding සහ අර්ථමය ගැළපීම අතර නොගැළපීම
- ප්රේරක එකලස් කිරීමේ සහ සන්දර්භ කවුළුවේ ගැටලු
- තාර්කික බිඳවැටීම් සහ අධික විශ්වාසයකින් යුතු පිළිතුරු
- දිගු දාම සහ නියෝජිත සම්බන්ධීකරණ අසාර්ථකතා
- බහු-නියෝජිත මතකය සහ භූමිකා විස්ථාපනය
- යෙදවීමේ සහ ආරම්භක අනුපිළිවෙළේ ගැටලු

අදහස සරලයි:

1. වැරදි ප්රතිචාරයක් විමර්ශනය කරන විට, පහත දෑ සටහන් කරගන්න:
   - පරිශීලක කාර්යය සහ ඉල්ලීම
   - OmniRoute හි රූට් එක හෝ සපයන්නන්ගේ සංයෝජනය
   - ඉන් පසු භාවිත කළ ඕනෑම RAG සන්දර්භයක් (ලබාගත් ලේඛන, මෙවලම් ඇමතුම් ආදිය)
2. සිදුවීම WFGY ProblemMap අංක එකකට හෝ දෙකකට (`No.1` … `No.16`) සිතියම්ගත කරන්න.
3. OmniRoute ලොග් අසල, එම අංකය ඔබේම උපකරණ පුවරුවේ, ධාවන මාර්ගෝපදේශයේ හෝ සිදුවීම් ලුහුබැඳීමේ පද්ධතියේ ගබඩා කරන්න.
4. ඔබේ RAG ස්ටැක් එක, ලබාගැනීමේ පද්ධතිය හෝ රවුටින් උපායමාර්ගය වෙනස් කිරීමට අවශ්යද යන්න තීරණය කිරීමට අදාළ WFGY පිටුව භාවිත කරන්න.

- CLI ධාවනකාල පරීක්ෂාව `installed=false` ලෙස වාර්තා කිරීම

**හේතු:**

- `CLI_DEVIN_BIN` නොපවතින මාර්ගයක් වෙත යොමු වේ
- ධාරකයේ Devin CLI ස්ථාපනය කර නැත

**විසඳුම:**

1. ඔබේ වේදිකාව සඳහා Devin CLI ස්ථාපනය කරන්න
2. `.env` තුළ `CLI_DEVIN_BIN=/usr/local/bin/devin` (හෝ සැබෑ මාර්ගය) සකසන්න
3. OmniRoute නැවත ආරම්භ කර **උපකරණ පුවරුව → CLI මෙවලම්** වෙතින් නැවත පරීක්ෂා කරන්න

### ආකෘති cooldown තත්ත්වය සිරවීම (අතින් යළි සැකසීම)

**රෝග ලක්ෂණ:**

- කල් ඉකුත්වීමේ වේලාව පසු වූ පසුවත් ආකෘතියක් cooldown තත්ත්වයේ ලැයිස්තුගතව පවතී
- කාල මුද්රාව අතීතයේ තිබුණත් සංයෝජන රවුටින්හිදී ඉල්ලීම් තවමත් එම ආකෘතිය මඟ හරියි

**අතින් යළි සැකසීම:**

- **උපකරණ පුවරුව:** **සැකසුම් → ආකෘති Cooldown** → බලපෑමට ලක් වූ කාඩ්පතේ **යළි සක්රිය කරන්න** ක්ලික් කරන්න
- **API:** කළමනාකරණ සත්යාපන ශීර්ෂ සමඟ `DELETE /api/resilience/model-cooldowns`

### Command Code සපයන්නාගේ සම්බන්ධතාව 403 සමඟ අසාර්ථක වේ

**රෝග ලක්ෂණ:**

- Command Code සපයන්නාගේ සම්බන්ධතාව පරීක්ෂා කිරීමේදී 403 ලැබීම
- අලුතින් එක් කළ පසුව සපයන්නාගේ කාඩ්පත "unauthorized" ලෙස පෙන්වීම

**හේතුව:** OAuth ප්රවාහය සම්පූර්ණ වී නැත (callback ලැබී නැත හෝ token එක ස්ථිරව ගබඩා වී නැත).

**විසඳුම:**

- OAuth ප්රවාහය නැවත ආරම්භ කිරීමට CLI වෙතින් `omniroute providers` ධාවනය කරන්න, හෝ
- **උපකරණ පුවරුව → සපයන්නන් → Command Code → නැවත සම්බන්ධ කරන්න** වෙතින් OAuth නැවත ධාවනය කරන්න
