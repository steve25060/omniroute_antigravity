### በነፃ አቅራቢዎች ላይ የጥያቄ መጠን ገደብ (429 / 400 / 401)

**ምልክት**፦ `model: "auto"`ን ከነፃ/ማረጋገጫ ከማይፈልጉ አቅራቢዎች (opencode, auggie, ወዘተ) ጋር ሲጠቀሙ፣ አንዳንድ ጊዜ ከመልሶች ይልቅ `HTTP 429`፣ `400` ወይም `401` ያገኛሉ። ተመሳሳዩን ጥያቄ ከጥቂት ጊዜ በኋላ እንደገና ሲሞክሩ ጥያቄዎቹ ይሳካሉ፣ ነገር ግን ራስ-ሰር ሂደቶች (cron jobs, agents, scripts) በመጀመሪያው ውድቀት ላይ ይቋረጣሉ።

**ዋና ምክንያት**፦ ሦስት እርስ በርስ ነፃ የሆኑ የውድቀት ሁኔታዎች ይደራረባሉ፦

1. **የአቅራቢ የጥያቄ መጠን ገደብ (`429`)**፦ ነፃ ደረጃዎች በእያንዳንዱ የጊዜ መስኮት ኮታ ሊያስፈጽሙ ይችላሉ። በአንድ ጊዜ የሚላኩ ብዙ ትይዩ ጥሪዎች ኮታውን ያሟጥጣሉ፣ ስለዚህ የጊዜ መስኮቱ ዳግም እስኪጀመር ድረስ ቀጣዩ ጥያቄ ውድቅ ይደረጋል።
2. **በቀጥታ ማስተላለፊያ ውስጥ የተበላሸ ሞዴል (`400`/`401`)**፦ የ`auto/*` ስብስቦች በካታሎጉ ውስጥ የተመዘገቡ ነገር ግን ንቁ የማረጋገጫ መረጃ የሌላቸውን ከ`opencode` የመጡ ቀጥታ-ማስተላለፊያ ሞዴሎችን ሊያካትቱ ይችላሉ (ለምሳሌ `oc/north-mini-code-free` → `401`)። ራስ-ሰር ራውተሩ አንዱን ይሞክራል፣ ይወድቃል፣ እና ወደ መጠባበቂያው መቀየር ከመጀመሩ በፊት ስህተቱ ወደ ውጭ ይተላለፋል።
3. **የትይዩነት ማጉላት (ጫና ሲኖር `429`)**፦ ብዙ የagent/cron ክፍለ-ጊዜዎች `auto`ን በአንድ ጊዜ ሲጠቀሙ፣ አጠቃላይ የጥያቄ ፍጥነቱ ነፃ አቅራቢዎች ሊቋቋሙት ከሚችሉት በላይ ይሆናል፣ በዚህም ህጋዊ ጥሪዎች እንደ አላግባብ አጠቃቀም ምልክት ይደረግባቸዋል።

**የተረጋገጠ መፍትሔ (በማህበረሰቡ የተዘገበ፣ 2026-08-10)**፦ መዞር፣ ትይዩነት እና መጠባበቂያ ወደ ሌላ አማራጭ መቀየር የነፃ ደረጃውን መለዋወጥ ተቋቁመው እንዲያስተናግዱት ሦስት የአካባቢ ተለዋዋጮችን ያስተካክሉ፦

```bash
export OMNIROUTE_ROTATE_ON_400=true           # በ400/401 ላይ ወደ ሌላ ሞዴል/አቅራቢ ዝለል (የተበላሹ ቀጥታ-ማስተላለፊያ ሞዴሎችን ይዘላል)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ግልጽ የከባድ ሥራ መቀበያ ከፍተኛ ገደብ (በነባሪ አልተዋቀረም፦ የጥያቄ ብዛት ገደብ የለም፣ ከታች ያለውን ማስታወሻ ይመልከቱ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ወዲያውኑ እንደገና ሊሞከር የሚችል 503 ከመስጠት ይልቅ ለከባድ ሥራ አቅም ረዘም ያለ የተወሰነ ጥበቃ
```

እነዚህን በOmniRoute ሂደት አካባቢ (daemonው፣ ለምሳሌ በLaunchAgent plist ወይም `systemctl edit`) ውስጥ ያዘጋጁ፣ ከዚያ OmniRouteን እንደገና ያስጀምሩ። የመዞሪያ ጠቋሚው ብቻውን ከፍተኛውን ውጤት የሚያስገኝ መቆጣጠሪያ ነው፦ ከባድ ውድቀትን በስብስቡ ውስጥ ባለ ጤናማ አቅራቢ ላይ ግልጽ በሆነ መንገድ ወደሚደረግ ዳግም ሙከራ ይቀይረዋል።

**ማስታወሻ**፦ `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` በአንድ ጊዜ የሚሰሩ ከባድ — ረጅም-ዐውድ — ጥያቄዎችን ብዛት ይገድባል፤ ገደቡ የመቀበያ በር እንጂ የአቅራቢ የጥያቄ መጠን ገዳቢ አይደለም። **#503-fanout ማሻሻያ፦** ይህ var ከእንግዲህ በነባሪ አይዘጋጅም (አሁን የሚተገበረው ከላይ እንደተገለጸው በግልጽ ሲዋቀር ብቻ ነው) — በምትኩ የከባድ ሥራ መቀበያ ከhostው ትክክለኛ የማህደረ ትውስታ ጣሪያ ጋር ራሱን በሚመጥን በራስ-ሰር በሚወሰን የባይት በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይገደባል፣ ስለዚህ አዲስ deployment ይህን var ጨርሶ ሳያዘጋጅ እጅግ ያነሱ `503 chat_admission_busy` ውድቅ ማድረጎችን ማየት አለበት፤ እዚህ በግልጽ ማዋቀሩ አሁንም በሰነዱ እንደተገለጸው በትክክል ይሰራል። ግልጽ የባይት-በጀት overrides ከ8 MiB–2 GiB ውስጥ ይገደባሉ። `413 body_exceeds_budget` ጊዜያዊ አይደለም፦ ያንን የባይት በጀት ይጨምሩ፣ `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES`ን ይቀንሱ፣ ወይም የሂደቱን የማህደረ ትውስታ ጣሪያ ይጨምሩ። `inflight_bytes_budget` shed ጊዜያዊ የሀብት ፉክክር ሲሆን እንደገና ሊሞከር ይችላል። የእያንዳንዱ አቅራቢ የጥያቄ መጠን ገደብ (`open-sse/services/rateLimitManager.ts`) በ`RATE_LIMIT_MAX_WAIT_MS`፣ `RATE_LIMIT_MAX_QUEUE_DEPTH` እና `RATE_LIMIT_AUTO_ENABLE` ለየብቻ ይተዳደራል — `.env.example`ን ይመልከቱ።

**መፍትሔው መስራቱን እንዴት ማረጋገጥ እንደሚቻል**፦ agent/cronዎን በተከታታይ ሁለት ጊዜ ያስኪዱ እና ሁለቱም መሳካታቸውን ያረጋግጡ። ከመፍትሔው በፊት፣ ሁለተኛው አሰራር በተለምዶ `429`/`401` ይመልሳል። ከመፍትሔው በኋላ፣ ውድቀቶች (ካሉ) ግልጽ በሆነ መንገድ እንደገና ይሞከራሉ እና ጥሪው ይጠናቀቃል። እንዲሁም `curl /monitoring/health`ን ማስኬድ እና በአቅራቢ ግንኙነቶቹ ላይ ያለውን `rateLimitedUntil` መስክ እንዲሁም ለተጎዱት አቅራቢዎች `circuitBreakers.providerBreakers[].state`ን መከታተል ይችላሉ — ሁኔታው `CLOSED`፣ `DEGRADED`፣ `OPEN` ወይም `HALF_OPEN` ከሚሉት አንዱ ነው (`src/shared/utils/circuitBreaker.ts`ን ይመልከቱ)፣ እና በተደጋጋሚ የሚወድቅ አቅራቢ የዳግም ማስጀመሪያ መስኮቱ ለሙከራ ጥሪ እስኪፈቅድ ድረስ (`HALF_OPEN`) `CLOSED → DEGRADED → OPEN` በሚለው ቅደም ተከተል ይቀየራል።

**አሁንም 429 ካዩ**፦ ለዚያ provider ንቁ የሆነው account የራሱን _quota_ በእርግጥ ጨርሷል (rate ብቻ አይደለም)። በOmniRoute dashboard → Providers → Accounts ውስጥ ለተመሳሳዩ provider ሁለተኛ account ያክሉ፣ ወይም ሌላ ነፃ provider (ለምሳሌ `routeway`፣ `auggie`) ያቀላቅሉ። Rotation የሚረዳው ጊዜያዊ rate/400/401 ስህተቶችን ብቻ ነው፤ ሙሉ የquota መሟጠጥ ሁለተኛ credential ወይም የተለየ provider ይፈልጋል።

**በvision models (`auto/vision`፣ `bazaarlink/*`) ላይ 403 ካዩ**፦ የተገናኘው account visionን የሚያካትት የሚከፈልበት plan የለውም፣ ወይም API keyው በቂ permissions የሉትም። በprovider dashboard ውስጥ የkeyው scope vision/multimodalን እንደሚያካትት ያረጋግጡ፣ ወይም የሚከፈልበት tier account ያገናኙና እንደ vision target ያቆዩት።

## የ npm install ማስጠንቀቂያዎች (ERESOLVE / peer / deprecated)

`npm install -g omniroute` ሲያስኬዱ፣ እንደ `npm warn ERESOLVE`፣ የ peer-dependency ማሳወቂያዎች እና `deprecated` መልዕክቶች ያሉ በርካታ ማስጠንቀቂያዎችን ሊያዩ ይችላሉ። **እነዚህ የሚጠበቁ እና ጉዳት የሌላቸው ናቸው።** በውጤቱ ውስጥ `added <N> packages` ካዩ ጭነቱ ተሳክቷል።

ማስጠንቀቂያዎቹ OmniRoute ሊቆጣጠራቸው በማይችላቸው የሶስተኛ ወገን ጥቅሎች ውስጥ ካሉ ጊዜ ያለፈባቸው የ peer-dependency ክልሎች የሚመጡ ናቸው፦

1. **`marked-terminal` `marked >=1 <16`ን ይፈልጋል፣ `marked@18` ግን ተገኝቷል** — በተግባር ያለችግኝ ይሰራል፤ የ upstream peer ክልሉ ጊዜ ያለፈበት ብቻ ነው።
2. **`deprecated prebuild-install@7.1.3`** — በተዘዋዋሪ የሚካተት የ native-binary ማውረጃ ረዳት ነው። ይህ በተወሰነው ስሪት የተቆለፈውን
   `wreq-js` transport binding ለመጫን አይጠቀምም፣ እንዲሁም የ web-cookie
   provider transport ማዋቀሩ እንዳልተሳካ አያመለክትም።

**ምንም እርምጃ አያስፈልግም** — upstream ጥቅሎችን fork ሳያደርጉ ማስጠንቀቂያዎቹን ሙሉ በሙሉ ማጥፋት አይቻልም።

## የጸረ-ቫይረስ የተሳሳቱ ማንቂያዎች

### Avast/AVG `README.md`ን በ`MD:HttpRequest-inf[Susp]` ወደ ማግለያ ያስገባል

**ይህ የተሳሳተ ማንቂያ ነው። ምንም ነገር በቫይረስ አልተበከለም፣ እና ምንም እርምጃ አያስፈልግም።**

Avast እና AVG ብዙ HTTP ጥያቄ የሚመስሉ አገናኞችን የያዙ ተራ-ጽሑፍ/Markdown ፋይሎችን ምልክት የሚያደርግ ግምታዊ ዘዴ ይጠቀማሉ። የOmniRoute `README.md` በnpm package ውስጥ ተካትቶ ይላካል (`package.json` → `files` ውስጥ ተዘርዝሯል)፤ ስለዚህ በግሎባል ጭነት ጊዜ `node_modules/omniroute/README.md` ላይ ይቀመጣል — እና ~15 የ`http://localhost:20128/...` ምሳሌዎችን (የMCP HTTP/SSE endpoints፣ የA2A `.well-known` URL እና የ`curl` ቅንጥቦችን) ይዟል። ይህ የአገናኞች ብዛት ግምታዊ ማጣሪያውን ለማስነሳት በቂ ነው።

ይህ በቅርቡ ብቻ ከጀመረ፦ የፋይሉ ዓይነት አልተለወጠም። README የendpoints ሰንጠረዡን አስፋፍቷል (MCP HTTP + SSE + A2A ተጨምረዋል)፣ ተጨማሪ የ`curl` ምሳሌዎችም ተጨምረዋል፤ ይህም ከገደቡ እንዲያልፍ አድርጎታል።

ፋይሉ ምንም ሊፈጸም የሚችል ይዘት የሌለው፣ ምንም የማይሠራ ሰነድ ነው። ከማግለያው በደህና መልሰው ማስቀመጥ ይችላሉ።

**ማድረግ ያለብዎት፦**

1. **ማሳወቂያዎቹን ያቁሙ** — የጭነት ማውጫውን በጸረ-ቫይረስዎ ውስጥ ከማጣሪያ ነጻ ያድርጉት
   (Avast፦ Settings → Exceptions)፤ የግሎባል `node_modules` ዱካዎን እና/ወይም
   የOmniRoute ውሂብ ማውጫን (`~/.omniroute/`) ያክሉ።
2. **የተሳሳተውን ማንቂያ ሪፖርት ያድርጉ** — <https://www.avast.com/false-positive-file-form.php>፣
   ወደ ማግለያ የገባውን `README.md` አያይዘው ይላኩ። የአቅራቢው ግምታዊ ማጣሪያ በጽሑፍ ፋይል ላይ ከመጠን በላይ ምላሽ እየሰጠ ስለሆነ፣ ለሁሉም ሰው የሚጠቅመው መፍትሔ ይህ ነው።

**ይህን በእኛ በኩል ለምን "አናስተካክለውም"፦** ሁሉም ምሳሌዎች `http://localhost` ናቸው፣ እና localhost በራስ የተፈረመ ሰርቲፊኬት የሚያስከትለው ችግር ሳይኖር `https` መሆን አይችልም። የአንድን አቅራቢ ግምታዊ ማጣሪያ ለማለፍ ሰነዶቹን ማበላሸት፣ የስካነሩን ሳንካ ለማርካት ሲባል እያንዳንዱን አንባቢ ይጎዳል።

### Kaspersky የDesktop መተግበሪያውን `PDM:Trojan.Win32.Generic` ብሎ ምልክት ያደርጋል

**ይህ ከባህሪ ላይ ከተመሠረተ ግምታዊ ማጣሪያ የመጣ የተሳሳተ ማንቂያ ነው። ምንም ነገር በቫይረስ አልተበከለም።** የKaspersky `PDM:` ቅድመ ቅጥያ ውሳኔው ከProactive Defense Module (System Watcher) እንደመጣ ያመለክታል፤ ይህም ጫኚውን ከሚታወቅ ማልዌር ጋር ከማዛመድ ይልቅ ጫኚው _የሚያደርገውን_ ይገመግማል። ማንቂያው ሲነሳ Kaspersky መላውን ጭነት "ወደ ኋላ ይመልሳል" — ቀደም ብሎ የጻፋቸውን ፋይሎች ይሰርዛል — ስለዚህ መተግበሪያው ተበላሽቶ ወይም ጠፍቶ ይቀራል።

ምልክት የሚያደርግባቸው ፋይሎች ከDesktop መተግበሪያው ጋር የታሸጉ በይፋ የተገለጹ ክፍት-ምንጭ dependencies መደበኛ ክፍሎች ናቸው፣ ለምሳሌ፦

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` እና

  library።

### የመግቢያ ገጹ ይበላሻል ወይም የ"Module self-registration" ስህተት ያሳያል

**ምክንያት:** ከOmniRoute የጸደቀው ደህንነቱ የተጠበቀ የማስኬጃ ዝቅተኛ ወሰን ውጪ የሆነ የNode.js ስሪት እያስኬዱ ነው። በጣም የተለመደው ሁኔታ OmniRoute ከሚጠይቀው የታረመ የደህንነት ዝቅተኛ ወሰን በታች የሆነ አሮጌ የNode 22 ወይም 24 የማሻሻያ ደረጃ ማስኬድ ነው።

**ምልክቶች:**

- የመግቢያ ገጹ ባዶ ማያ ገጽ ወይም የአገልጋይ ስህተት ያሳያል
- ኮንሶሉ `Error: Module did not self-register` ወይም ተመሳሳይ የnative binding ስህተቶችን ያሳያል
- ማስኬጃው ከሚደገፈው ደህንነቱ የተጠበቀ ፖሊሲ ውጪ ከሆነ፣ የመግቢያ ገጹ የNode ስሪትዎን የያዘ **ብርቱካናማ የማስጠንቀቂያ ሰንደቅ** ያሳያል

**መፍትሔ:**

1. የሚደገፍ የNode.js LTS ልቀት ይጫኑ (የሚመከረው፦ Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ስሪትዎን ያረጋግጡ፦ `node --version` በ24.x LTS መስመር ላይ `v24.0.0` ወይም ከዚያ አዲስ ስሪት ማሳየት አለበት
3. OmniRouteን እንደገና ይጫኑ፦ `npm install -g omniroute`
4. እንደገና ያስጀምሩ፦ `omniroute`

> **የሚደገፉ ደህንነታቸው የተጠበቀ ስሪቶች:** `>=22.22.2 <23` ወይም `>=24.0.0 <27`። Node.js 24.x LTS (Krypton) እና Node.js 26 ሙሉ በሙሉ ይደገፋሉ።

### npm v11+፦ `better-sqlite3` አልተጫነም (Cannot find module)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ምክንያት:** npm v11 (ከNode.js 24+ ጋር የሚቀርብ) በነባሪነት ለአማራጭ
ጥገኞች የመጫኛ ስክሪፕቶችን ያግዳል። `better-sqlite3` በ`optionalDependencies`
ውስጥ ስለተዘረዘረ እና native compilation (`node-gyp rebuild`) ስለሚያስፈልገው፣ npm ያለማሳወቅ ይዘለዋል።

**ምልክቶች:**

- አገልጋዩ ሲጀምር `Cannot find module 'better-sqlite3'` በሚል ስህተት ይበላሻል
- `ls node_modules/better-sqlite3` `"No such file or directory"` ያሳያል
- `npm ls better-sqlite3` `(empty)` ያሳያል

**መፍትሔ:**

1. የመጫኛ ስክሪፕቶቹን ያጽድቁ እና እንደገና ይጫኑ፦
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ወይም አስቀድሞ የተገነባውን በእጅ ይጫኑ፦
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. እንደሚሠራ ያረጋግጡ፦ `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS፦ `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ምክንያት:** ዓለም አቀፍ `npm install -g omniroute` ከተከናወነ በኋላ፣ በጥቅሉ ውስጥ ያለው የ`better-sqlite3` native binary በአካባቢው እየሠራ ካለው የተለየ architecture ወይም Node.js ABI ሊገነባ ይችላል። አስቀድሞ የተገነባው binary ከአካባቢዎ ጋር በማይዛመድበት ጊዜ፣ ይህ በmacOS (በApple Silicon እና Intel ላይ) የተለመደ ነው።

**ምልክቶች:**

- አገልጋዩ ሲጀምር ወዲያውኑ በ`dlopen` ስህተት ይበላሻል
- ስህተቱ `slice is not valid mach-o file` የሚለውን ይዟል
- ሙሉ ምሳሌ፦

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**መፍትሔ — ለአካባቢያዊ አካባቢዎ እንደገና ይገንቡ (የNode.js ስሪትን ዝቅ ማድረግ አያስፈልግም):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ማስታወሻ:** ይህ native bindingን ከአካባቢያዊ የNode.js ስሪትዎ እና ከCPU architecture ጋር እንደገና በማጠናቀር የbinary አለመዛመዱን ይፈታል። በይፋ የሚደገፈው የማስኬጃ ክልል **`>=22.22.2 <23` ወይም `>=24.0.0 <27`** ነው (`SUPPORTED_NODE_RANGE` በ`src/shared/utils/nodeRuntimeSupport.ts` ውስጥ፣ ከ`package.json` `engines` መስክ ጋር የተጣጣመ)። Node.js 24.x LTS (Krypton) እና Node.js 26 ከ`better-sqlite3` v12.x ጋር ሙሉ በሙሉ ይደገፋሉ።

### የአቅራቢ ማረጋገጫ "fetch failed" ያሳያል

**ምክንያት፦** የAPI ቁልፍ ማረጋገጫ መገናኛ ነጥብ (`POST /api/providers/validate`) ከዚህ ቀደም የፕሮክሲ ውቅረትን ያልፍ ስለነበር፣ የፕሮክሲ ማዘዋወር በሚያስፈልጋቸው አካባቢዎች ውድቀቶችን ያስከትል ነበር።

**መፍትሔ (v3.5.5+)፦** ይህ አሁን ተስተካክሏል። የአቅራቢ ማረጋገጫ `runWithProxyContext`ን በመጠቀም ይተላለፋል፤ የአቅራቢ ደረጃ እና ዓለም አቀፍ የፕሮክሲ ቅንብሮችንም በራስ-ሰር ያከብራል።

### የቶከን ጤና ምርመራ "fetch failed" በሚል ይወድቃል

**ምክንያት፦** በዳራ የሚከናወነው የOAuth ቶከን እድሳት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን አይፈታም ነበር።

**መፍትሔ (v3.5.5+)፦** የቶከን ጤና ምርመራ መርሐግብር አውጪው አሁን እድሳትን ከመሞከሩ በፊት ለእያንዳንዱ ግንኙነት የፕሮክሲ ውቅረትን ይፈታል። ወደ v3.5.5+ ያዘምኑ።

### SOCKS5 ፕሮክሲ "invalid onRequestStart method" ይመልሳል

**ምክንያት፦** በNode.js 22 ላይ፣ የundici@8 dispatcher ከNode አብሮገነብ `fetch()` አተገባበር ጋር ተኳሃኝ አይደለም።

**መፍትሔ (v3.5.5+)፦** የፕሮክሲ dispatcher ገቢር ሲሆን OmniRoute ወጥ ባህሪን ለማረጋገጥ አሁን የundiciን የራሱን `fetch()` ተግባር ይጠቀማል። ወደ v3.5.5+ ያዘምኑ።

### በWSL ስር ያለ MITM ፕሮክሲ፦ በWindows አስተናጋጅ ላይ ያሉ የዴስክቶፕ መተግበሪያዎች አይጠለፉም

## የCloud ችግሮች

### የCloud Sync ስህተቶች

1. `BASE_URL` እየሰራ ወዳለው instanceዎ መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `http://localhost:20128`)
2. `CLOUD_URL` ወደ cloud endpointዎ መጠቆሙን ያረጋግጡ (ለምሳሌ፣ `https://omniroute.dev`)
3. የ`NEXT_PUBLIC_*` እሴቶችን ከserver-side እሴቶች ጋር እንዲጣጣሙ ያድርጉ

### የCloud `stream=false` 500 ይመልሳል

**ምልክት:** streaming ለማያደርጉ ጥሪዎች በcloud endpoint ላይ `Unexpected token 'd'...` ይታያል።

**ምክንያት:** clientው JSON ሲጠብቅ upstream SSE payload ይመልሳል።

**ጊዜያዊ መፍትሔ:** ለቀጥታ የcloud ጥሪዎች `stream=true` ይጠቀሙ። local runtime የSSE→JSON fallbackን ያካትታል።

### Cloud እንደተገናኘ ይገልጻል፣ ነገር ግን "ልክ ያልሆነ API key" ይላል

1. ከlocal dashboard (`/api/keys`) አዲስ key ይፍጠሩ
2. የcloud syncን ያስኪዱ፦ Cloudን ያንቁ → አሁን Sync ያድርጉ
3. የቆዩ/ያልተመሳሰሉ keys በcloud ላይ አሁንም `401` ሊመልሱ ይችላሉ

## የDocker ችግሮች

### Docker IPv6 / የግንኙነት ዳግም ማስጀመር

<a name="docker-ipv6"></a>

**ምልክቶች:** `curl http://localhost:20128/v1/models` የሚለው `curl: (56) Recv failure: Connection reset by peer` ይመልሳል። Dashboard እና authentication የማይፈልጉ endpoints ይሰራሉ፣ authentication የሚፈልጉ endpoints ግን አይሰሩም — የauth ችግር ይመስላል፣ ግን አይደለም።

**ምክንያት:** `docker run -p 20128:20128` በሁለቱም `0.0.0.0` (IPv4) እና `::` (IPv6) ላይ ያትማል፣ ነገር ግን containerው ውስጥ ያለው process IPv4ን ብቻ ያዳምጣል። `localhost` መጀመሪያ ወደ `::1` በሚፈታባቸው hosts ላይ ግንኙነቱ ከኋላው listener በሌለው የታተመ IPv6 port ላይ ያርፋል → ግንኙነቱ ዳግም ይጀመራል።

**መፍትሔ:**

1. **ፈጣን ምርመራ:** `curl -4 http://localhost:20128/v1/models` ያስኪዱ። ከ`-4` ጋር ቢሰራ ነገር ግን ያለሱ ቢከሽፍ፣ የIPv6 bind አለመጣጣም አለብዎት።
2. **ቋሚ መፍትሔ:** በ`docker run` commandዎ ውስጥ `-p 127.0.0.1:20128:20128`ን በመጠቀም በግልጽ ወደ IPv4 bind ያድርጉ፦
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ይህ IPv4 bindን ያስገድዳል፣ እንዲሁም proxyው በሁሉም የhost interfaces ላይ እንዳይጋለጥ ያደርጋል።

### የRuntime ማከማቻ

- ዋና ሁኔታ፦ `${DATA_DIR}/storage.sqlite` (providers, combos, aliases, keys, settings)

## የCircuit Breaker ችግሮች

### Provider በOPEN ሁኔታ ላይ ተጣብቆ ቀርቷል

የprovider circuit breaker OPEN በሚሆንበት ጊዜ፣ የእረፍት ጊዜው እስኪያበቃ ድረስ ጥያቄዎች ይታገዳሉ።

**መፍትሔ፦**

1. ወደ **ዳሽቦርድ → ቅንብሮች → የመቋቋም ችሎታ** ይሂዱ
2. ለተጎዳው provider የcircuit breaker ካርዱን ያረጋግጡ
3. ሁሉንም breaker-ዎች ለማጽዳት **ሁሉንም ዳግም አስጀምር**ን ጠቅ ያድርጉ፣ ወይም የእረፍት ጊዜው እስኪያበቃ ይጠብቁ
4. ዳግም ከማስጀመርዎ በፊት provider-ው በእርግጥ መገኘቱን ያረጋግጡ

### Provider በተደጋጋሚ circuit breaker-ን ያስነሳል

አንድ provider በተደጋጋሚ ወደ OPEN ሁኔታ ከገባ፦

1. የብልሽት ንድፉን ለማየት **ዳሽቦርድ → ጤና → የProvider ጤና**ን ይመልከቱ
2. ወደ **ቅንብሮች → የመቋቋም ችሎታ → የProvider መገለጫዎች** ይሂዱና የብልሽት ገደቡን ይጨምሩ
3. Provider-ው የAPI ገደቦቹን እንደቀየረ ወይም እንደገና ማረጋገጥ እንደሚያስፈልገው ያረጋግጡ
4. የlatency telemetry ይገምግሙ — ከፍተኛ latency በtimeout ላይ የተመሠረቱ ብልሽቶችን ሊያስከትል ይችላል

## የድምፅ ጽሑፍ ቅጂ ችግሮች

### "ያልተደገፈ model" ስህተት

- የመጀመሪያው ክፍል ማረጋገጫ ያለዎት provider የሆነ model id ይጠቀሙ (`openai/whisper-1`፣ `openrouter/deepgram/nova-3`)። `deepgram/nova-3`ን ብቻውን መጠቀም ቤተኛ Deepgram key ያስፈልገዋል።
- Provider-ው በ**ዳሽቦርድ → Providers** ውስጥ መገናኘቱን ያረጋግጡ

### የጽሑፍ ቅጂው ባዶ ይመለሳል ወይም አይሳካም

- የሚደገፉ የድምፅ ቅርጸቶችን ያረጋግጡ፦ `mp3`፣ `wav`፣ `m4a`፣ `flac`፣ `ogg`፣ `webm`
- የፋይሉ መጠን በprovider-ው ገደቦች ውስጥ መሆኑን ያረጋግጡ (በተለምዶ < 25MB)
- በprovider ካርዱ ውስጥ የprovider API key ትክክለኛነትን ያረጋግጡ

- **SDK ከobject ይልቅ raw string ይመልሳል** — በv1.x ተፈትቷል፤ response sanitizer የOpenAI SDK Pydantic ማረጋገጫ ብልሽቶችን የሚያስከትሉ መደበኛ ያልሆኑ መስኮችን (`x_groq`፣ `usage_breakdown`፣ ወዘተ) ያስወግዳል። ይህን አሁንም በv3.x+ ላይ ካዩ፣ እባክዎ issue ያቅርቡ።

- **የ`developer` role አይታወቅም** — በv1.x ተፈትቷል፤ OpenAI ላልሆኑ providers በራስ-ሰር ወደ `system` ይቀየራል። ይህን አሁንም በv3.x+ ላይ ካዩ፣ እባክዎ issue ያቅርቡ።
- **`json_schema` ከGemini ጋር አይሠራም** — በv1.x ተፈትቷል፤ `response_format` አሁን ወደ Gemini `responseMimeType` + `responseSchema` ይቀየራል። ይህን አሁንም በv3.x+ ላይ ካዩ፣ እባክዎ issue ያቅርቡ።

## የጽናት ቅንብሮች

### ራስ-ሰር የፍጥነት ገደብ አለመጀመር

- ራስ-ሰር የፍጥነት ገደብ የሚተገበረው በAPI ቁልፍ አቅራቢዎች ላይ ብቻ ነው (በOAuth/ደንበኝነት ምዝገባ ላይ አይደለም)
- **ቅንብሮች → ጽናት → የአቅራቢ መገለጫዎች** ውስጥ ራስ-ሰር የፍጥነት ገደብ መንቃቱን ያረጋግጡ
- አቅራቢው `429` የሁኔታ ኮዶችን ወይም `Retry-After` ራስጌዎችን እየመለሰ መሆኑን ያረጋግጡ

### የኤክስፖነንሻል የድጋሚ ሙከራ መዘግየትን ማስተካከል

የአቅራቢ መገለጫዎች እነዚህን ቅንብሮች ይደግፋሉ፦

- **መሠረታዊ መዘግየት** — ከመጀመሪያው ውድቀት በኋላ ያለው የመጀመሪያ መጠበቂያ ጊዜ (ነባሪ፦ 1s)
- **ከፍተኛ መዘግየት** — የመጠበቂያ ጊዜው ከፍተኛ ገደብ (ነባሪ፦ 30s)
- **አባዥ** — በእያንዳንዱ ተከታታይ ውድቀት መዘግየቱ ምን ያህል እንደሚጨምር (ነባሪ፦ 2x)

### የተቀናጀ ድንገተኛ ጭነትን መከላከል

ብዙ በአንድ ጊዜ የሚከናወኑ ጥያቄዎች የፍጥነት ገደብ ያለበትን አቅራቢ ሲደርሱ፣ OmniRoute ጥያቄዎችን በቅደም ተከተል ለማስኬድ እና ተከታታይ ውድቀቶችን ለመከላከል mutex + ራስ-ሰር የፍጥነት ገደብን ይጠቀማል። ይህ ለAPI ቁልፍ አቅራቢዎች በራስ-ሰር ይከናወናል።

### የውይይት ጥያቄዎች በ503 / chat_admission_busy ይወድቃሉ

**ምልክቶች፦**

- የውይይት ማጠናቀቂያዎች መጨረሻ ነጥብ የስህተት ኮዱ
  `chat_admission_busy` የሆነ እንደገና ሊሞከር የሚችል `503` ምላሽ ይመልሳል።
- ምላሹ `Retry-After`ን ያካትታል። ከ#12135 ጀምሮ እሴቱ ከታየው
  የአቅም አጠቃቀም የሚመነጭ ነው — ጥያቄው አስቀድሞ ከጠበቀው የ`OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` መስኮት
  እና አሁን ያሉት ከባድ የሊዝ ፈቃዶች ከተያዙበት ጊዜ መካከል ትልቁን ይወስዳል — ወደ ሙሉ
  ሰከንዶች ወደ ላይ ተጠጋግቶ በ60 ይገደባል። በሥራ ፈት በር ላይ ታሪካዊዎቹን ዝቅተኛ ገደቦች ይጠብቃል፦ በ
  ባይት-ተኮር መንገድ 2 ሰከንድ፣ በመዋቅር-ተኮር መንገድ 1 ሰከንድ (ይህም
  `reason: "structure_limit"`ን ያካትታል)።
- ይህ ሌላ ከባድ የውይይት ጥያቄ ወይም ለረጅም ጊዜ የሚሄድ የዥረት ምላሽ አሁንም
  በሂደት ላይ እያለ ሊከሰት ይችላል።

ባይት-ተኮር የምላሽ አካል ይህ ነው፦

```json

    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

መዋቅር-ተኮር ምላሹ ተመሳሳይ ዓይነትና ኮድ ይጠቀማል፣ መልዕክቱም
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
እና `reason: "structure_limit"` ነው።
በነባሪ ገደቦች፣ አንድ ጥያቄ ቢያንስ `200` መልዕክቶች፣
ቢያንስ `64` መሣሪያዎች፣ ወይም ቢያንስ `32,000` የተገመቱ ቶከኖች ካሉት፣ ወይም የተገደበ የመዋቅር ግምቱ
የ`10,000` የተጎበኙ ኖዶች ወይም የ`12` ጥልቀት ገደቦቹን ካሟጠጠ በመዋቅራዊ ሁኔታ ከባድ ነው።

**ምክንያት፦** ይህ በOmniRoute ውስጥ ሆን ተብሎ የሚደረግ የጭነት ቅነሳ እንጂ የላይኛው-ደረጃ አቅራቢ ውድቀት አይደለም።
እያንዳንዱ ሂደት ትልቅ የጥያቄ አካልን ከማቆየቱና
ከመተንተኑ በፊት የተገደበ ከባድ የሥራ አቅምን ለመያዝ ሂደት-አካባቢያዊ ጠባቂ ይጠቀማል። ከባድ የሊዝ ፈቃድ ለSSE
ምላሽ የሕይወት ዘመን ሙሉ ተይዞ ይቆያል።

**#503-ስርጭት፦** ከዚህ ማስተካከያ በፊት፣ ጠባቂው የአስተናጋጁን ማህደረ ትውስታ ሳያገናዝብ በቋሚ የጥያቄ ብዛት
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`፣ ነባሪ `1`) የበአንድ ጊዜ ሂደትን ይገድብ ነበር፤ ስለዚህ የኮድ ወኪል
ስርጭት (በርካታ ንዑስ ወኪሎች/CLIዎች፣ በተለምዶ > 256 KB የሆኑ አካላት) ውጤታማውን
የበአንድ ጊዜ ሂደት ወደ ~1 ዝቅ አድርጎ በፍጹም መደበኛ ጭነት ስር 503 ስህተት ያስከትል ነበር። ጠባቂው አሁን ራሱን
ያስተካክላል፦ ከሂደቱ ትክክለኛ የማህደረ ትውስታ ጣሪያ መጠኑ በሚወሰን በራስ-ሰር የተመነጨ የግቤት ባይት በጀት (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ይቆጣጠራል፣ እንዲሁም
ቀጥታ የሀብት-ጫና ምልክትን ይመለከታል — ስለዚህ አስተናጋጁ በእውነት በማህደረ ትውስታ ጫና ስር ሲሆን ብቻ
ጭነትን ይቀንሳል፤ ከአንድ በላይ ከባድ ጥያቄዎች በአንድ ጊዜ ስለደረሱ ብቻ አይደለም። የቀድሞው የብዛት ገደብ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`)
አሁንም ይከበራል፣ ግን በግልጽ እርስዎ ካዘጋጁት ብቻ ነው።

አቅሙ ሥራ ላይ ሲሆን፣ ከባድ ጥያቄ እንደገና ሊሞከር የሚችለውን `503` ከመመለሱ በፊት
ቦታ እስኪለቀቅ ድረስ በመጀመሪያ እስከ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ነባሪ `2000`፣ `0` መጠበቁን ያሰናክላል) ይጠብቃል።
የተገደበው መጠበቅ ያለው፣ ከባድ ንዑስ-ጥያቄዎችን በአንድ ጊዜ የሚያሰራጩ የወኪል-ቅጥ ደንበኞች
(OpenCode, Claude Code, Cursor) ወዲያውኑ በሚደረጉ ውድቅ ማድረጎች የድጋሚ ሙከራ በጀታቸውን በሙሉ አቃጥለው በሥራ መካከል ከመቋረጥ ይልቅ ድንገተኛውን ጭነት
በቅደም ተከተል እንዲያስኬዱ ነው።
አሁን ያለው የከባድ ሊዝ አቅም አጠቃቀም፣ የተወሰነው የባይት በጀት፣ እና የቀጥታ ጫና ክብደት
በ`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ላይ ይታያሉ — ማንኛውንም env var ከመቀየርዎ በፊት እነዚህን ያረጋግጡ።
ቅንብሮች → ጽናት → የጥያቄ ወረፋ → በአንድ ጊዜ የሚከናወኑ ጥያቄዎች ይህን አይቆጣጠርም፤ ያ ቅንብር
የተለየ የአቅራቢ ጥያቄ-ወረፋ ዘዴን ይቆጣጠራል።

1. መጀመሪያ እንደገና ይሞክሩ። ደንበኞች ጥያቄውን ወዲያውኑ
   ከመድገም ይልቅ `Retry-After`ን ማክበር እና የድጋሚ ሙከራ መዘግየትን መጠቀም አለባቸው።
2. ማንኛውንም ነገር ከማስተካከልዎ በፊት `/api/monitoring/health` → `chatAdmission`ን ያረጋግጡ። `countCapEnabled:
false` እና ሰፊ `maxInflightBytes` ማለት በራስ-ሰር የተመነጨው በጀት አስቀድሞ ሥራውን
   እየሠራ ነው ማለት ነው፤ `high`/`critical` የሆነ `pressureSeverity` አስተናጋጁ በእውነት የማህደረ ትውስታ እጥረት እንዳለበት ያመለክታል —
   ይህ በadmission env var ሊስተካከል አይችልም፤ ተጨማሪ RAM ወይም አነስተኛ የሥራ ጫና ያስፈልገዋል።
3. `/api/monitoring/health` በራስ-ሰር የተመነጨው በጀት ለአስተናጋጅዎ በእውነት በጣም አነስተኛ መሆኑን
   ካሳየ ብቻ (ይህ አልፎ አልፎ ነው — ከኮንቴይነር እስከ bare-metal ድረስ አስቀድሞ መጠኑን ያስተካክላል)፣ ወደ ቀድሞው የጥያቄ-ብዛት ገደብ ከመመለስ ይልቅ
   በ`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` በቀጥታ ይሽሩት።

ለትክክለኛዎቹ የመግቢያ ቅንብሮች [የአካባቢ-ተለዋዋጭ ማጣቀሻውን](../reference/ENVIRONMENT.md#4-security--authentication)
ይመልከቱ።

## አማራጭ RAG / LLM የውድቀት ምደባ (16 ችግሮች)

አንዳንድ OmniRoute ተጠቃሚዎች gatewayን በRAG ወይም agent stacks ፊት ያስቀምጣሉ። በእነዚህ ውቅሮች ውስጥ አንድ እንግዳ ሁኔታ ማየት የተለመደ ነው፦ OmniRoute ጤናማ ይመስላል (providers እየሠሩ ናቸው፣ routing profiles ደህና ናቸው፣ ምንም የrate limit ማንቂያዎች የሉም) ነገር ግን የመጨረሻው መልስ አሁንም የተሳሳተ ነው።

በተግባር እነዚህ ክስተቶች ብዙውን ጊዜ የሚመጡት ከgateway ራሱ ሳይሆን ከ downstream RAG pipeline ነው።

እነዚያን ውድቀቶች ለመግለጽ የጋራ ቃላትን መጠቀም ከፈለጉ፣ WFGY ProblemMapን መጠቀም ይችላሉ፤ ይህም አሥራ ስድስት ተደጋጋሚ የRAG / LLM ውድቀት ቅጦችን የሚገልጽ ውጫዊ የMIT license የጽሑፍ ምንጭ ነው። በአጠቃላይ የሚከተሉትን ይሸፍናል፦

- የretrieval መዛባት እና የተበላሹ የcontext ወሰኖች
- ባዶ ወይም ጊዜ ያለፈባቸው indexes እና vector stores
- በembedding እና semantic መካከል ያለ አለመዛመድ
- የprompt ስብስብ እና የcontext window ችግሮች
- የሎጂክ መፍረስ እና ከመጠን በላይ እርግጠኛ የሆኑ መልሶች
- የረጅም chain እና የagent ቅንጅት ውድቀቶች
- የmulti agent ማህደረ ትውስታ እና የሚና መዛባት
- የdeployment እና bootstrap ቅደም ተከተል ችግሮች

ሐሳቡ ቀላል ነው፦

1. መጥፎ ምላሽን ሲመረምሩ፣ የሚከተሉትን ይመዝግቡ፦
   - የተጠቃሚውን ተግባር እና ጥያቄ
   - በOmniRoute ውስጥ ያለውን የroute ወይም provider combo
   - downstream ላይ ጥቅም ላይ የዋለ ማንኛውንም የRAG context (የተገኙ ሰነዶች፣ tool calls፣ ወዘተ)
2. ክስተቱን ከአንድ ወይም ከሁለት WFGY ProblemMap ቁጥሮች (`No.1` … `No.16`) ጋር ያዛምዱ።
3. ቁጥሩን ከOmniRoute logs አጠገብ በራስዎ dashboard፣ runbook ወይም incident tracker ውስጥ ያስቀምጡ።
4. የእርስዎን RAG stack፣ retriever ወይም routing strategy መቀየር እንዳለብዎት ለመወሰን ተዛማጁን የWFGY ገጽ ይጠቀሙ።

ሙሉው ጽሑፍ እና ተጨባጭ መመሪያዎች እዚህ ይገኛሉ (MIT license፣ ጽሑፍ ብቻ)፦

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ከOmniRoute በስተጀርባ RAG ወይም agent pipelinesን የማያስኬዱ ከሆነ ይህን ክፍል ችላ ማለት ይችላሉ።

## v3.8.0 የሚታወቁ ችግሮች

ለv3.8.0 release የተለዩ ችግሮች እና የአሁን ጊዜ ጊዜያዊ መፍትሔዎቻቸው። መፍትሔ በኋለኛ patch ውስጥ ከተካተተ፣ ግቤቱ ይዘምናል ወይም ይወገዳል።

### የDevin CLI ማረጋገጫ ውድቀቶች

**ምልክቶች፦**

- በDevin የሚደገፉ toolsን ሲጠሩ "Devin CLI not found" ወይም "auth failed"
- የCLI runtime ፍተሻ `installed=false` እንደሆነ ያሳያል

**ምክንያቶች፦**

- `CLI_DEVIN_BIN` ወደሌለ path ይጠቁማል
- Devin CLI በhost ላይ አልተጫነም

**መፍትሔ፦**

1. ለplatformዎ Devin CLIን ይጫኑ
2. በ`.env` ውስጥ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ወይም ትክክለኛውን path) ያዘጋጁ
3. OmniRouteን እንደገና ያስጀምሩ እና ከ**Dashboard → CLI Tools** እንደገና ይፈትሹ

### የModel cooldown ተጣብቆ መቅረት (በእጅ ዳግም ማስጀመር)

**ምልክቶች፦**

- የማብቂያ ጊዜው ካለፈ በኋላም model በcooldown ዝርዝር ውስጥ ይቆያል
- timestampው ያለፈ ቢሆንም requests በcombo routing ውስጥ modelውን አሁንም ይዘላሉ

**በእጅ ዳግም ማስጀመር፦**

- **Dashboard፦** **Settings → Model Cooldowns** → በተጎዳው card ላይ **Re-enable**ን ጠቅ ያድርጉ
- **API፦** ከmanagement auth headers ጋር `DELETE /api/resilience/model-cooldowns`

### የCommand Code provider ግንኙነት በ403 ይወድቃል

**ምልክቶች፦**

- የCommand Code provider ግንኙነትን ሲፈትሹ 403 ይመለሳል
- አዲስ ከታከለ በኋላ provider cardው "unauthorized" ያሳያል

**ምክንያት፦** የOAuth flow አልተጠናቀቀም (callback አልደረሰም ወይም token አልተቀመጠም)።

**መፍትሔ፦**

- የOAuth flowን እንደገና ለማስነሳት ከCLI `omniroute providers`ን ያስኪዱ፣ ወይም
- ከ**Dashboard → Providers → Command Code → Reconnect** OAuthን እንደገና ያስኪዱ

### ModelScope ከመጠን በላይ ኃይለኛ 429 cooldowns ይመልሳል

**ምልክቶች፦**

- ከትንሽ የrequests ፍንዳታ በኋላ በModelScope ላይ በጣም አጭር ወይም ፈጣን cooldowns
- Combo routing ከተጠበቀው ቀደም ብሎ ModelScopeን ይዘላል

**ምክንያት፦** ModelScope ለprovider የተለዩ `Retry-After` headersን ያወጣል። v3.8.0 ለእነዚያ headers የተለየ አያያዝን ይዞ ይመጣል፤ ስለዚህ የቆዩ versions እንደ አጠቃላይ የrate-limit ፍንጮች በተሳሳተ መንገድ ያነቧቸዋል።

**መፍትሔ፦**

- v3.8.0 ወይም ከዚያ በኋላ ባለ version ላይ መሆንዎን ያረጋግጡ
- በ**Settings → Resilience** ስር ያለው `useUpstream429BreakerHints` toggle እንደነቃ ያረጋግጡ

### OMNIROUTE_WS_BRIDGE_SECRET በproduction ውስጥ የለም

**ምልክቶች፦**

- በርቀት production host ላይ ሲያስኬዱ በእያንዳንዱ Codex/Responses WebSocket bridge request ላይ 401
- የWebSocket bridge handshake ከተገናኘ በኋላ ወዲያውኑ ይዘጋል

**ምክንያት፦** `OMNIROUTE_WS_BRIDGE_SECRET` env var ከproduction environment ውስጥ የለም።

**መፍትሔ፦**

1. የዘፈቀደ secret ይፍጠሩ፦ `openssl rand -hex 32`
2. በproduction server env ውስጥ (እና ከbridge ጋር በሚገናኝ ማንኛውም client ውስጥ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>`ን ያዘጋጁ
3. OmniRouteን እንደገና ያስጀምሩ

### Responses API፦ background mode ወደ synchronous ዝቅ ብሏል

**ምልክቶች፦**

- የተመዘገበ ማስጠንቀቂያ፦ `background mode degraded to synchronous`
- `background: true` request ከbackground job handle ይልቅ መደበኛ synchronous response ይመልሳል

**ምክንያት፦** v3.8.0 ማስጠንቀቂያ እያወጣ፣ በResponses API ላይ `background: true`ን ሆን ብሎ ወደ synchronous execution ዝቅ ያደርገዋል። ሙሉ async background execution ወደፊት የሚቀርብ ባህሪ ነው።

**መፍትሔ፦**

- clientን `background` ሳይጠቀም እንዲጠራ ያስተካክሉ፣ ወይም
- ሙሉ async background modeን የሚያቀርብ በኋላ የሚወጣ release ይጠብቁ (changelogን ይከታተሉ)
