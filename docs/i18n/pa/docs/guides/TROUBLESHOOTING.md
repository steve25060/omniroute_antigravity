## ਵਿਸਤ੍ਰਿਤ ਸਮੱਸਿਆ-ਨਿਵਾਰਣ

### ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਿਆਂ ਉੱਤੇ ਦਰ ਸੀਮਾਬੰਦੀ (429 / 400 / 401)

**ਲੱਛਣ**: ਮੁਫ਼ਤ/ਪ੍ਰਮਾਣੀਕਰਨ-ਰਹਿਤ ਪ੍ਰਦਾਤਿਆਂ (opencode, auggie ਆਦਿ) ਨਾਲ `model: "auto"` ਵਰਤਦੇ ਸਮੇਂ, ਤੁਹਾਨੂੰ ਕਦੇ-ਕਦਾਈਂ ਜਵਾਬਾਂ ਦੀ ਬਜਾਏ `HTTP 429`, `400`, ਜਾਂ `401` ਮਿਲਦਾ ਹੈ। ਕੁਝ ਪਲਾਂ ਬਾਅਦ ਉਸੇ ਪ੍ਰੌਂਪਟ ਨਾਲ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ ਕਰਨ ਉੱਤੇ ਬੇਨਤੀਆਂ ਸਫਲ ਹੋ ਜਾਂਦੀਆਂ ਹਨ, ਪਰ ਆਟੋਮੇਸ਼ਨ (cron ਜੌਬਾਂ, ਏਜੰਟ, ਸਕ੍ਰਿਪਟਾਂ) ਪਹਿਲੀ ਅਸਫਲਤਾ ਉੱਤੇ ਹੀ ਰੁਕ ਜਾਂਦੀ ਹੈ।

**ਮੂਲ ਕਾਰਨ**: ਤਿੰਨ ਸੁਤੰਤਰ ਅਸਫਲਤਾ ਢੰਗ ਇਕੱਠੇ ਹੋ ਜਾਂਦੇ ਹਨ:

1. **ਪ੍ਰਦਾਤਾ ਦਰ-ਸੀਮਾ (`429`)**: ਮੁਫ਼ਤ ਟੀਅਰ ਹਰ ਸਮਾਂ-ਵਿੰਡੋ ਲਈ ਕੋਟਾ ਲਾਗੂ ਕਰ ਸਕਦੇ ਹਨ। ਸਮਾਂਤਰ ਕਾਲਾਂ ਦਾ ਅਚਾਨਕ ਵਾਧਾ ਇਸਨੂੰ ਖਤਮ ਕਰ ਦਿੰਦਾ ਹੈ, ਇਸ ਲਈ ਵਿੰਡੋ ਰੀਸੈੱਟ ਹੋਣ ਤੱਕ ਅਗਲੀ ਬੇਨਤੀ ਅਸਵੀਕਾਰ ਕਰ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
2. **ਪਾਸਥਰੂ ਵਿੱਚ ਖਰਾਬ ਮਾਡਲ (`400`/`401`)**: `auto/*` ਪੂਲਾਂ ਵਿੱਚ `opencode` ਦੇ ਅਜਿਹੇ ਪਾਸਥਰੂ ਮਾਡਲ ਸ਼ਾਮਲ ਹੋ ਸਕਦੇ ਹਨ ਜੋ ਕੈਟਾਲਾਗ ਵਿੱਚ ਰਜਿਸਟਰਡ ਹਨ ਪਰ ਉਨ੍ਹਾਂ ਕੋਲ ਕਿਰਿਆਸ਼ੀਲ ਪ੍ਰਮਾਣ-ਪੱਤਰ ਨਹੀਂ ਹਨ (ਉਦਾਹਰਨ ਲਈ `oc/north-mini-code-free` → `401`)। ਆਟੋ-ਰਾਊਟਰ ਇੱਕ ਨੂੰ ਅਜ਼ਮਾਉਂਦਾ ਹੈ, ਅਸਫਲ ਹੁੰਦਾ ਹੈ ਅਤੇ ਫਾਲਬੈਕ ਸ਼ੁਰੂ ਹੋਣ ਤੋਂ ਪਹਿਲਾਂ ਹੀ ਗਲਤੀ ਅੱਗੇ ਭੇਜ ਦਿੱਤੀ ਜਾਂਦੀ ਹੈ।
3. **ਸਮਕਾਲੀਤਾ ਵਾਧਾ (ਲੋਡ ਅਧੀਨ `429`)**: ਜਦੋਂ ਕਈ ਏਜੰਟ/cron ਸੈਸ਼ਨ ਇੱਕੋ ਸਮੇਂ `auto` ਨੂੰ ਬੇਨਤੀਆਂ ਭੇਜਦੇ ਹਨ, ਤਾਂ ਕੁੱਲ ਬੇਨਤੀ ਦਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਿਆਂ ਦੀ ਸਹਿਣਸ਼ੀਲਤਾ ਤੋਂ ਵੱਧ ਜਾਂਦੀ ਹੈ, ਜਿਸ ਕਾਰਨ ਵੈਧ ਕਾਲਾਂ ਨੂੰ ਵੀ ਦੁਰਵਰਤੋਂ ਵਜੋਂ ਚਿੰਨ੍ਹਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ।

**ਪ੍ਰਮਾਣਿਤ ਹੱਲ (ਭਾਈਚਾਰੇ ਵੱਲੋਂ ਰਿਪੋਰਟ ਕੀਤਾ ਗਿਆ, 2026-08-10)**: ਤਿੰਨ ਇਨਵਾਇਰਨਮੈਂਟ ਵੇਰੀਏਬਲ ਇਸ ਤਰ੍ਹਾਂ ਟਿਊਨ ਕਰੋ ਕਿ ਰੋਟੇਸ਼ਨ, ਸਮਕਾਲੀਤਾ ਅਤੇ ਫਾਲਬੈਕ ਮੁਫ਼ਤ ਟੀਅਰ ਦੇ ਉਤਾਰ-ਚੜ੍ਹਾਵ ਨੂੰ ਸੰਭਾਲਣ, ਨਾ ਕਿ ਇਸ ਕਾਰਨ ਬੰਦ ਹੋ ਜਾਣ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ਉੱਤੇ ਕਿਸੇ ਹੋਰ ਮਾਡਲ/ਪ੍ਰਦਾਤੇ ਵੱਲ ਜਾਓ (ਖਰਾਬ ਪਾਸਥਰੂ ਮਾਡਲਾਂ ਨੂੰ ਛੱਡਦਾ ਹੈ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ਹੈਵੀਵੇਟ ਦਾਖਲੇ ਦੀ ਸਪਸ਼ਟ ਅਧਿਕਤਮ ਸੀਮਾ (ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ: ਬੇਨਤੀ-ਗਿਣਤੀ ਦੀ ਕੋਈ ਸੀਮਾ ਨਹੀਂ, ਹੇਠਾਂ ਨੋਟ ਦੇਖੋ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ਤੁਰੰਤ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ਯੋਗ 503 ਦੀ ਬਜਾਏ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਲਈ ਵਧੇਰੇ ਲੰਮੀ ਸੀਮਿਤ ਉਡੀਕ
```

ਇਨ੍ਹਾਂ ਨੂੰ OmniRoute ਪ੍ਰਕਿਰਿਆ ਦੇ ਇਨਵਾਇਰਨਮੈਂਟ ਵਿੱਚ ਸੈੱਟ ਕਰੋ (ਡੈਮਨ, ਉਦਾਹਰਨ ਲਈ LaunchAgent plist ਜਾਂ `systemctl edit` ਰਾਹੀਂ), ਫਿਰ OmniRoute ਨੂੰ ਮੁੜ-ਚਾਲੂ ਕਰੋ। ਰੋਟੇਸ਼ਨ ਫਲੈਗ ਸਭ ਤੋਂ ਵੱਧ ਪ੍ਰਭਾਵਸ਼ਾਲੀ ਸਾਧਨ ਹੈ: ਇਹ ਸਖ਼ਤ ਅਸਫਲਤਾ ਨੂੰ ਪੂਲ ਵਿੱਚ ਕਿਸੇ ਸਿਹਤਮੰਦ ਪ੍ਰਦਾਤੇ ਵਿਰੁੱਧ ਪਾਰਦਰਸ਼ੀ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਵਿੱਚ ਬਦਲ ਦਿੰਦਾ ਹੈ।

**ਨੋਟ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ਇਹ ਸੀਮਿਤ ਕਰਦਾ ਹੈ ਕਿ ਇੱਕੋ ਸਮੇਂ ਕਿੰਨੀਆਂ ਹੈਵੀਵੇਟ — ਲੰਬੇ-ਕੰਟੈਕਸਟ ਵਾਲੀਆਂ — ਬੇਨਤੀਆਂ ਚੱਲ ਸਕਦੀਆਂ ਹਨ; ਇਹ ਸੀਮਾ ਇੱਕ ਦਾਖਲਾ ਗੇਟ ਹੈ, ਪ੍ਰਦਾਤਾ ਦੀ ਦਰ ਸੀਮਾ ਨਹੀਂ। **#503-fanout ਅੱਪਡੇਟ:** ਇਹ ਵੇਰੀਏਬਲ ਹੁਣ ਮੂਲ ਰੂਪ ਵਿੱਚ ਸੈੱਟ ਨਹੀਂ ਹੁੰਦਾ (ਹੁਣ ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਹੀ ਲਾਗੂ ਹੁੰਦਾ ਹੈ ਜਦੋਂ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ ਕੌਂਫਿਗਰ ਕੀਤਾ ਜਾਵੇ, ਜਿਵੇਂ ਉੱਪਰ ਕੀਤਾ ਗਿਆ ਹੈ) — ਇਸਦੀ ਬਜਾਏ ਹੈਵੀਵੇਟ ਦਾਖਲਾ ਇੱਕ ਆਪਣੇ-ਆਪ ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਦੁਆਰਾ ਨਿਯੰਤ੍ਰਿਤ ਹੁੰਦਾ ਹੈ, ਜੋ ਹੋਸਟ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਦੇ ਅਨੁਸਾਰ ਆਪਣੇ ਆਪ ਸਕੇਲ ਹੁੰਦਾ ਹੈ। ਇਸ ਲਈ ਨਵੀਂ ਡਿਪਲੌਇਮੈਂਟ ਵਿੱਚ ਇਸ ਵੇਰੀਏਬਲ ਨੂੰ ਬਿਲਕੁਲ ਵੀ ਸੈੱਟ ਕੀਤੇ ਬਿਨਾਂ ਕਾਫ਼ੀ ਘੱਟ `503 chat_admission_busy` ਅਸਵੀਕਾਰਤਾਵਾਂ ਦਿਖਾਈ ਦੇਣੀਆਂ ਚਾਹੀਦੀਆਂ ਹਨ; ਇਸਨੂੰ ਇੱਥੇ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ ਸੈੱਟ ਕਰਨਾ ਹਾਲੇ ਵੀ ਦਸਤਾਵੇਜ਼ ਵਿੱਚ ਦਿੱਤੇ ਅਨੁਸਾਰ ਹੀ ਕੰਮ ਕਰਦਾ ਹੈ। ਸਪਸ਼ਟ ਬਾਈਟ-ਬਜਟ ਓਵਰਰਾਈਡ 8 MiB–2 GiB ਤੱਕ ਸੀਮਿਤ ਹੁੰਦੇ ਹਨ। `413 body_exceeds_budget` ਅਸਥਾਈ ਨਹੀਂ ਹੁੰਦਾ: ਉਸ ਬਾਈਟ ਬਜਟ ਨੂੰ ਵਧਾਓ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ਘਟਾਓ, ਜਾਂ ਪ੍ਰਕਿਰਿਆ ਦੀ ਮੈਮੋਰੀ ਸੀਮਾ ਵਧਾਓ। `inflight_bytes_budget` ਸ਼ੈਡ ਅਸਥਾਈ ਸਰੋਤ-ਟਕਰਾਅ ਹੈ ਅਤੇ ਇਸ ਉੱਤੇ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾ ਸਕਦੀ ਹੈ। ਪ੍ਰਤੀ-ਪ੍ਰਦਾਤਾ ਦਰ ਸੀਮਾਬੰਦੀ (`open-sse/services/rateLimitManager.ts`) ਵੱਖਰੇ ਤੌਰ ਉੱਤੇ `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ਅਤੇ `RATE_LIMIT_AUTO_ENABLE` ਦੁਆਰਾ ਨਿਯੰਤ੍ਰਿਤ ਹੁੰਦੀ ਹੈ — `.env.example` ਦੇਖੋ।

**ਇਹ ਪੁਸ਼ਟੀ ਕਿਵੇਂ ਕਰਨੀ ਹੈ ਕਿ ਹੱਲ ਕੰਮ ਕਰ ਗਿਆ**: ਆਪਣੇ ਏਜੰਟ/cron ਨੂੰ ਥੋੜ੍ਹੇ ਅੰਤਰ ਵਿੱਚ ਦੋ ਵਾਰ ਚਲਾਓ ਅਤੇ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਦੋਵੇਂ ਵਾਰ ਸਫਲਤਾ ਮਿਲਦੀ ਹੈ। ਹੱਲ ਤੋਂ ਪਹਿਲਾਂ, ਦੂਜੀ ਵਾਰ ਚਲਾਉਣ ਉੱਤੇ ਆਮ ਤੌਰ ਉੱਤੇ `429`/`401` ਆਉਂਦਾ ਹੈ। ਹੱਲ ਤੋਂ ਬਾਅਦ, ਅਸਫਲਤਾਵਾਂ (ਜੇ ਕੋਈ ਹੋਣ) ਉੱਤੇ ਪਾਰਦਰਸ਼ੀ ਢੰਗ ਨਾਲ ਦੁਬਾਰਾ ਕੋਸ਼ਿਸ਼ ਕੀਤੀ ਜਾਂਦੀ ਹੈ ਅਤੇ ਕਾਲ ਪੂਰੀ ਹੋ ਜਾਂਦੀ ਹੈ। ਤੁਸੀਂ `curl /monitoring/health` ਵੀ ਚਲਾ ਸਕਦੇ ਹੋ ਅਤੇ ਪ੍ਰਦਾਤਾ ਕਨੈਕਸ਼ਨਾਂ ਉੱਤੇ `rateLimitedUntil` ਫ਼ੀਲਡ ਅਤੇ ਪ੍ਰਭਾਵਿਤ ਪ੍ਰਦਾਤਿਆਂ ਲਈ `circuitBreakers.providerBreakers[].state` ਨੂੰ ਦੇਖ ਸਕਦੇ ਹੋ — ਸਥਿਤੀ `CLOSED`, `DEGRADED`, `OPEN`, ਜਾਂ `HALF_OPEN` ਵਿੱਚੋਂ ਇੱਕ ਹੁੰਦੀ ਹੈ (`src/shared/utils/circuitBreaker.ts` ਦੇਖੋ), ਅਤੇ ਲਗਾਤਾਰ ਅਸਫਲ ਹੋਣ ਵਾਲਾ ਪ੍ਰਦਾਤਾ ਰੀਸੈੱਟ ਵਿੰਡੋ ਦੁਆਰਾ ਜਾਂਚ ਦੀ ਆਗਿਆ ਦੇਣ ਤੋਂ ਪਹਿਲਾਂ `CLOSED → DEGRADED → OPEN` ਵਿੱਚ ਬਦਲ ਜਾਵੇਗਾ (`HALF_OPEN`)।

**ਜੇ ਤੁਹਾਨੂੰ ਹਾਲੇ ਵੀ 429 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਉਸ ਪ੍ਰਦਾਤਾ ਲਈ ਸਰਗਰਮ ਖਾਤੇ ਦਾ _ਕੋਟਾ_ ਅਸਲ ਵਿੱਚ ਖ਼ਤਮ ਹੋ ਚੁੱਕਾ ਹੈ (ਸਿਰਫ਼ ਦਰ ਸੀਮਾ ਨਹੀਂ)। OmniRoute ਡੈਸ਼ਬੋਰਡ → Providers → Accounts ਵਿੱਚ ਉਸੇ ਪ੍ਰਦਾਤਾ ਲਈ ਦੂਜਾ ਖਾਤਾ ਸ਼ਾਮਲ ਕਰੋ, ਜਾਂ ਕਿਸੇ ਹੋਰ ਮੁਫ਼ਤ ਪ੍ਰਦਾਤਾ ਨੂੰ ਵੀ ਸ਼ਾਮਲ ਕਰੋ (ਉਦਾਹਰਨ ਲਈ `routeway`, `auggie`)। ਰੋਟੇਸ਼ਨ ਸਿਰਫ਼ ਅਸਥਾਈ ਦਰ ਸੀਮਾ/400/401 ਸਮੱਸਿਆਵਾਂ ਵਿੱਚ ਮਦਦ ਕਰਦੀ ਹੈ; ਕੋਟਾ ਪੂਰੀ ਤਰ੍ਹਾਂ ਖ਼ਤਮ ਹੋਣ ਦੀ ਸਥਿਤੀ ਵਿੱਚ ਦੂਜੇ ਕ੍ਰੈਡੈਂਸ਼ੀਅਲ ਜਾਂ ਕਿਸੇ ਵੱਖਰੇ ਪ੍ਰਦਾਤਾ ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ।

**ਜੇ ਤੁਹਾਨੂੰ ਵਿਜ਼ਨ ਮਾਡਲਾਂ (`auto/vision`, `bazaarlink/*`) ਉੱਤੇ 403 ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ**: ਕਨੈਕਟ ਕੀਤੇ ਖਾਤੇ ਕੋਲ ਵਿਜ਼ਨ ਸ਼ਾਮਲ ਕਰਨ ਵਾਲੀ ਭੁਗਤਾਨਸ਼ੁਦਾ ਯੋਜਨਾ ਨਹੀਂ ਹੈ, ਜਾਂ API ਕੁੰਜੀ ਕੋਲ ਲੋੜੀਂਦੀਆਂ ਅਨੁਮਤੀਆਂ ਨਹੀਂ ਹਨ। ਪ੍ਰਦਾਤਾ ਡੈਸ਼ਬੋਰਡ ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਕੁੰਜੀ ਦੇ ਸਕੋਪ ਵਿੱਚ ਵਿਜ਼ਨ/ਮਲਟੀਮੋਡਲ ਸ਼ਾਮਲ ਹੈ, ਜਾਂ ਭੁਗਤਾਨਸ਼ੁਦਾ ਟੀਅਰ ਵਾਲਾ ਖਾਤਾ ਕਨੈਕਟ ਕਰਕੇ ਉਸਨੂੰ ਵਿਜ਼ਨ ਟਾਰਗੇਟ ਵਜੋਂ ਰੱਖੋ।

## npm install ਚੇਤਾਵਨੀਆਂ (ERESOLVE / peer / deprecated)

ਜਦੋਂ ਤੁਸੀਂ `npm install -g omniroute` ਚਲਾਉਂਦੇ ਹੋ, ਤਾਂ ਤੁਹਾਨੂੰ `npm warn ERESOLVE`, peer-dependency ਸੂਚਨਾਵਾਂ ਅਤੇ `deprecated` ਸੁਨੇਹਿਆਂ ਵਰਗੀਆਂ ਬਹੁਤ ਸਾਰੀਆਂ ਚੇਤਾਵਨੀਆਂ ਦਿਖਾਈ ਦੇ ਸਕਦੀਆਂ ਹਨ। **ਇਹ ਉਮੀਦ ਅਨੁਸਾਰ ਹਨ ਅਤੇ ਨੁਕਸਾਨਦੇਹ ਨਹੀਂ ਹਨ।** ਜੇਕਰ ਆਉਟਪੁੱਟ ਵਿੱਚ `added <N> packages` ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੀ ਇੰਸਟਾਲੇਸ਼ਨ ਸਫਲ ਹੋ ਗਈ ਹੈ।

ਇਹ ਚੇਤਾਵਨੀਆਂ ਤੀਜੀ-ਧਿਰ ਦੇ ਉਹਨਾਂ ਪੈਕੇਜਾਂ ਵਿੱਚ ਪੁਰਾਣੀਆਂ peer-dependency ਰੇਂਜਾਂ ਕਾਰਨ ਆਉਂਦੀਆਂ ਹਨ, ਜਿਨ੍ਹਾਂ ਨੂੰ OmniRoute ਕੰਟਰੋਲ ਨਹੀਂ ਕਰਦਾ:

1. **`marked-terminal` ਨੂੰ `marked >=1 <16` ਚਾਹੀਦਾ ਹੈ, ਪਰ `marked@18` ਮਿਲਿਆ** — ਅਮਲ ਵਿੱਚ ਇਹ ਠੀਕ ਕੰਮ ਕਰਦਾ ਹੈ; upstream peer ਰੇਂਜ ਸਿਰਫ਼ ਪੁਰਾਣੀ ਹੈ।
2. **`deprecated prebuild-install@7.1.3`** — ਇਹ ਇੱਕ transitive native-binary ਪ੍ਰਾਪਤੀ ਸਹਾਇਕ ਹੈ। ਇਸਦੀ ਵਰਤੋਂ
   ਪਿੰਨ ਕੀਤੀ `wreq-js` transport binding ਨੂੰ ਇੰਸਟਾਲ ਕਰਨ ਲਈ ਨਹੀਂ ਕੀਤੀ ਜਾਂਦੀ ਅਤੇ ਇਹ ਇਸ ਗੱਲ ਦਾ ਸੰਕੇਤ ਨਹੀਂ ਦਿੰਦਾ ਕਿ web-cookie
   provider transport ਸੈੱਟਅੱਪ ਅਸਫਲ ਹੋ ਗਿਆ ਹੈ।

**ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ** — upstream ਪੈਕੇਜਾਂ ਨੂੰ fork ਕੀਤੇ ਬਿਨਾਂ ਇਨ੍ਹਾਂ ਚੇਤਾਵਨੀਆਂ ਨੂੰ ਪੂਰੀ ਤਰ੍ਹਾਂ ਚੁੱਪ ਨਹੀਂ ਕਰਵਾਇਆ ਜਾ ਸਕਦਾ।

## ਐਂਟੀਵਾਇਰਸ ਦੇ ਗਲਤ ਪਾਜ਼ਿਟਿਵ

<a name="antivirus-false-positives"></a>

### Avast/AVG ਵੱਲੋਂ `README.md` ਨੂੰ `MD:HttpRequest-inf[Susp]` ਦੇ ਤੌਰ 'ਤੇ ਕੁਆਰੰਟੀਨ ਕਰਨਾ

**ਇਹ ਇੱਕ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ ਅਤੇ ਕਿਸੇ ਕਾਰਵਾਈ ਦੀ ਲੋੜ ਨਹੀਂ ਹੈ।**

Avast ਅਤੇ AVG ਇੱਕ ਅਜਿਹੀ ਹਿਊਰਿਸਟਿਕ ਚਲਾਉਂਦੇ ਹਨ ਜੋ ਬਹੁਤ ਸਾਰੇ
HTTP ਬੇਨਤੀਆਂ ਵਰਗੇ ਦਿਖਾਈ ਦੇਣ ਵਾਲੇ ਲਿੰਕਾਂ ਵਾਲੀਆਂ ਸਧਾਰਨ-ਟੈਕਸਟ/Markdown ਫ਼ਾਈਲਾਂ ਨੂੰ ਫਲੈਗ ਕਰਦੀ ਹੈ।
OmniRoute ਦੀ `README.md` npm ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਆਉਂਦੀ ਹੈ (ਇਹ
`package.json` → `files` ਵਿੱਚ ਸੂਚੀਬੱਧ ਹੈ), ਇਸ ਲਈ ਗਲੋਬਲ ਇੰਸਟਾਲੇਸ਼ਨ ਦੌਰਾਨ ਇਹ
`node_modules/omniroute/README.md` ਵਿੱਚ ਪਹੁੰਚਦੀ ਹੈ — ਅਤੇ ਇਸ ਵਿੱਚ ਲਗਭਗ 15
`http://localhost:20128/...` ਉਦਾਹਰਨਾਂ ਹਨ (MCP HTTP/SSE ਐਂਡਪੁਆਇੰਟ, A2A
`.well-known` URL ਅਤੇ `curl` ਸਨਿੱਪਟ)। ਲਿੰਕਾਂ ਦੀ ਇਹ ਘਣਤਾ ਹਿਊਰਿਸਟਿਕ ਨੂੰ ਚਾਲੂ ਕਰਨ ਲਈ
ਕਾਫ਼ੀ ਹੈ।

ਜੇ ਇਹ ਹੁਣੇ ਜਿਹੇ ਹੀ ਸ਼ੁਰੂ ਹੋਇਆ ਹੈ: ਫ਼ਾਈਲ ਦੀ ਕਿਸਮ ਨਹੀਂ ਬਦਲੀ। README ਦੀ
ਐਂਡਪੁਆਇੰਟ ਸਾਰਣੀ ਵਧੀ ਹੈ (MCP HTTP + SSE + A2A ਜੋੜੇ ਗਏ ਸਨ) ਅਤੇ ਹੋਰ `curl`
ਉਦਾਹਰਨਾਂ ਸ਼ਾਮਲ ਹੋਈਆਂ, ਜਿਸ ਕਾਰਨ ਇਹ ਸੀਮਾ ਤੋਂ ਪਾਰ ਹੋ ਗਈ।

ਇਹ ਫ਼ਾਈਲ ਸਿਰਫ਼ ਨਿਸ਼ਕ੍ਰਿਆ ਦਸਤਾਵੇਜ਼ ਹੈ ਅਤੇ ਇਸ ਵਿੱਚ ਕੋਈ ਵੀ ਚਲਾਉਣਯੋਗ ਸਮੱਗਰੀ ਨਹੀਂ ਹੈ।
ਤੁਸੀਂ ਇਸਨੂੰ ਕੁਆਰੰਟੀਨ ਤੋਂ ਸੁਰੱਖਿਅਤ ਢੰਗ ਨਾਲ ਬਹਾਲ ਕਰ ਸਕਦੇ ਹੋ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਸੂਚਨਾਵਾਂ ਬੰਦ ਕਰੋ** — ਆਪਣੇ ਐਂਟੀਵਾਇਰਸ ਵਿੱਚ ਇੰਸਟਾਲੇਸ਼ਨ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਬਾਹਰ ਰੱਖੋ
   (Avast: Settings → Exceptions), ਅਤੇ ਆਪਣਾ ਗਲੋਬਲ `node_modules` ਪਾਥ ਅਤੇ/ਜਾਂ
   OmniRoute ਡਾਟਾ ਡਾਇਰੈਕਟਰੀ (`~/.omniroute/`) ਸ਼ਾਮਲ ਕਰੋ।
2. **ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://www.avast.com/false-positive-file-form.php>,
   ਅਤੇ ਕੁਆਰੰਟੀਨ ਕੀਤੀ `README.md` ਨੱਥੀ ਕਰੋ। ਇਹ ਉਹ ਹੱਲ ਹੈ ਜੋ ਹਰ ਕਿਸੇ ਦੀ ਮਦਦ ਕਰਦਾ ਹੈ,
   ਕਿਉਂਕਿ ਵਿਕਰੇਤਾ ਦੀ ਹਿਊਰਿਸਟਿਕ ਇੱਕ ਟੈਕਸਟ ਫ਼ਾਈਲ ਪ੍ਰਤੀ ਲੋੜ ਤੋਂ ਵੱਧ ਪ੍ਰਤੀਕਿਰਿਆ ਕਰ ਰਹੀ ਹੈ।

**ਅਸੀਂ ਆਪਣੇ ਪਾਸੇ ਇਸਨੂੰ "ਠੀਕ" ਕਿਉਂ ਨਹੀਂ ਕਰਦੇ:** ਸਾਰੀਆਂ ਉਦਾਹਰਨਾਂ `http://localhost` ਹਨ,
ਅਤੇ ਸਵੈ-ਦਸਤਖ਼ਤ ਕੀਤੇ ਸਰਟੀਫਿਕੇਟ ਦੀ ਪਰੇਸ਼ਾਨੀ ਤੋਂ ਬਿਨਾਂ localhost ਨੂੰ `https` ਨਹੀਂ ਬਣਾਇਆ ਜਾ ਸਕਦਾ।
ਇੱਕ ਵਿਕਰੇਤਾ ਦੀ ਹਿਊਰਿਸਟਿਕ ਤੋਂ ਬਚਣ ਲਈ ਦਸਤਾਵੇਜ਼ਾਂ ਨੂੰ ਵਿਗਾੜਨਾ, ਸਕੈਨਰ ਦੇ ਇੱਕ ਬੱਗ ਨੂੰ ਸੰਤੁਸ਼ਟ ਕਰਨ ਵਾਸਤੇ
ਹਰ ਪਾਠਕ ਨੂੰ ਨੁਕਸਾਨ ਪਹੁੰਚਾਏਗਾ।

### Kaspersky ਵੱਲੋਂ Desktop ਐਪ ਨੂੰ `PDM:Trojan.Win32.Generic` ਵਜੋਂ ਫਲੈਗ ਕਰਨਾ

**ਇਹ ਵਿਹਾਰਕ ਹਿਊਰਿਸਟਿਕ ਤੋਂ ਆਇਆ ਇੱਕ ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਹੈ। ਕੁਝ ਵੀ ਸੰਕਰਮਿਤ ਨਹੀਂ ਹੈ।**
Kaspersky ਦਾ `PDM:` ਅਗੇਤਰ ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ ਇਹ ਨਿਰਣਾ ਇਸਦੇ Proactive Defense Module
(System Watcher) ਤੋਂ ਆਇਆ ਹੈ, ਜੋ ਜਾਣੇ-ਪਛਾਣੇ ਮਾਲਵੇਅਰ ਨਾਲ ਮੇਲ ਕਰਨ ਦੀ ਬਜਾਏ ਇਹ ਜਾਂਚਦਾ ਹੈ ਕਿ
ਇੰਸਟਾਲਰ _ਕੀ ਕਰਦਾ ਹੈ_। ਜਦੋਂ ਇਹ ਚਾਲੂ ਹੁੰਦਾ ਹੈ, ਤਾਂ Kaspersky ਪੂਰੀ ਇੰਸਟਾਲੇਸ਼ਨ ਨੂੰ
"ਰੋਲ ਬੈਕ" ਕਰ ਦਿੰਦਾ ਹੈ — ਪਹਿਲਾਂ ਹੀ ਲਿਖੀਆਂ ਫ਼ਾਈਲਾਂ ਨੂੰ ਮਿਟਾ ਕੇ — ਜਿਸ ਕਾਰਨ ਐਪ ਅੰਤ ਵਿੱਚ
ਖਰਾਬ ਹੋ ਜਾਂਦੀ ਹੈ ਜਾਂ ਗਾਇਬ ਹੋ ਜਾਂਦੀ ਹੈ।

ਇਸ ਵੱਲੋਂ ਫਲੈਗ ਕੀਤੀਆਂ ਫ਼ਾਈਲਾਂ Desktop ਐਪ ਨਾਲ ਬੰਡਲ ਕੀਤੀਆਂ, ਘੋਸ਼ਿਤ ਓਪਨ-ਸੋਰਸ
ਨਿਰਭਰਤਾਵਾਂ ਦੇ ਮਿਆਰੀ ਹਿੱਸੇ ਹਨ, ਉਦਾਹਰਨ ਵਜੋਂ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ਅਤੇ
  `workerProcessEntry.js` — [Playwright](https://playwright.dev), ਐਪ ਅੰਦਰ ਪ੍ਰਦਾਤਾ ਲੌਗਇਨ
  ਅਤੇ ਬ੍ਰਾਊਜ਼ਰ-ਸਮਰਥਿਤ ਚੈਟ ਲਈ ਵਰਤੀ ਜਾਂਦੀ ਬ੍ਰਾਊਜ਼ਰ-ਆਟੋਮੇਸ਼ਨ ਲਾਇਬ੍ਰੇਰੀ।
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ਵੈੱਬ-ਕੂਕੀ ਪ੍ਰਦਾਤਾਵਾਂ ਉੱਤੇ ਬ੍ਰਾਊਜ਼ਰ-ਫਿੰਗਰਪ੍ਰਿੰਟ ਕੀਤੇ HTTP ਲਈ ਵਰਤੀ ਜਾਣ ਵਾਲੀ ਪਿੰਨ ਕੀਤੀ
  `wreq-js` ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ (`<arch>` ਦਾ ਮੁੱਲ `x64` ਜਾਂ `arm64` ਹੁੰਦਾ ਹੈ)।

**ਇਹ ਕਿਉਂ ਚਾਲੂ ਹੁੰਦਾ ਹੈ:** Windows ਇੰਸਟਾਲਰ ਹਾਲੇ **ਕੋਡ-ਸਾਈਨ ਨਹੀਂ ਕੀਤਾ ਗਿਆ**, ਇਸ ਲਈ ਇੱਕ
ਬਿਨਾਂ ਦਸਤਖ਼ਤ ਵਾਲੇ NSIS ਇੰਸਟਾਲਰ ਦੀ ਕੋਈ ਸਾਖ ਨਹੀਂ ਹੁੰਦੀ ਅਤੇ ਵਿਹਾਰਕ ਹਿਊਰਿਸਟਿਕ ਸਭ ਤੋਂ ਵੱਧ
ਸਖ਼ਤੀ ਨਾਲ ਚੱਲਦੀ ਹੈ। ਇਸਦੇ ਨਾਲ ਬੰਡਲ ਕੀਤੀ ਨੇਟਿਵ DLL ਅਤੇ
`%LOCALAPPDATA%\Programs\OmniRoute` ਹੇਠ ਲਿਖੀਆਂ ਸੈਂਕੜੇ `.js` ਫ਼ਾਈਲਾਂ (Next.js
ਸਟੈਂਡਅਲੋਨ ਬਿਲਡ ਤੋਂ ਹੈਸ਼-ਪਿਛੇਤਰ ਵਾਲੀਆਂ ਪੈਕੇਜ ਡਾਇਰੈਕਟਰੀਆਂ ਸਮੇਤ), ਹਿਊਰਿਸਟਿਕ ਨੂੰ ਚਾਲੂ ਕਰਨ ਲਈ
ਕਾਫ਼ੀ ਹਨ। ਕੋਡ ਸਾਈਨਿੰਗ ਦੀ ਯੋਜਨਾ ਹੈ; ਇਸਦੇ ਲਾਗੂ ਹੋਣ ਤੱਕ, ਨਵੀਆਂ ਰਿਲੀਜ਼ਾਂ ਨਾਲ ਇਹ ਮੁੜ ਹੋ ਸਕਦਾ ਹੈ।

**ਕੀ ਕਰਨਾ ਹੈ:**

1. **ਪਹਿਲਾਂ ਆਪਣੇ ਡਾਊਨਲੋਡ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ** (ਇਸ ਨਾਲ ਛੇੜਛਾੜ ਕੀਤੀ ਫ਼ਾਈਲ ਦੀ ਸੰਭਾਵਨਾ ਰੱਦ ਹੋ ਜਾਂਦੀ ਹੈ)।
   ਹਰ ਰਿਲੀਜ਼ `latest.yml` ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦੀ ਹੈ, ਜਿਸਦਾ `sha512` ਖੇਤਰ (base64)
   `OmniRoute.Setup.<version>.exe` ਇੰਸਟਾਲਰ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ। PowerShell ਵਿੱਚ,
   ਇੰਸਟਾਲਰ ਵਾਲੇ ਫੋਲਡਰ ਤੋਂ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ਆਉਟਪੁੱਟ ਦਾ `latest.yml` → `sha512` ਨਾਲ ਮੇਲ ਖਾਣਾ ਲਾਜ਼ਮੀ ਹੈ। ਜੇ ਮੇਲ ਨਹੀਂ ਖਾਂਦਾ,
   ਤਾਂ ਫ਼ਾਈਲ ਮਿਟਾਓ ਅਤੇ ਕੇਵਲ [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases)
   ਤੋਂ ਦੁਬਾਰਾ ਡਾਊਨਲੋਡ ਕਰੋ।
2. **ਬਹਾਲ ਕਰੋ + ਬਾਹਰ ਰੱਖੋ** — ਕੁਆਰੰਟੀਨ ਤੋਂ ਰੋਲ-ਬੈਕ ਕੀਤੀਆਂ ਆਈਟਮਾਂ ਬਹਾਲ ਕਰੋ ਅਤੇ
   `%LOCALAPPDATA%\Programs\OmniRoute` ਲਈ ਇੱਕ ਛੋਟ ਜੋੜੋ
   (Kaspersky → Settings → Threats and Exclusions), ਫਿਰ ਦੁਬਾਰਾ ਇੰਸਟਾਲ ਕਰੋ।
3. **ਗਲਤ ਪਾਜ਼ਿਟਿਵ ਦੀ ਰਿਪੋਰਟ ਕਰੋ** — <https://opentip.kaspersky.com/>। ਵਰਤੋਂਕਾਰਾਂ ਵੱਲੋਂ
   ਭੇਜੀਆਂ FP ਰਿਪੋਰਟਾਂ ਵਾਕਈ ਅਨੁਮਤ-ਸੂਚੀਕਰਨ ਨੂੰ ਤੇਜ਼ ਕਰਦੀਆਂ ਹਨ।

## Node.js ਅਨੁਕੂਲਤਾ

<a name="nodejs-compatibility"></a>

### ਲੌਗਇਨ ਪੰਨਾ ਕ੍ਰੈਸ਼ ਹੁੰਦਾ ਹੈ ਜਾਂ "Module self-registration" ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** ਤੁਸੀਂ Node.js ਦਾ ਅਜਿਹਾ ਵਰਜਨ ਚਲਾ ਰਹੇ ਹੋ ਜੋ OmniRoute ਦੀ ਮਨਜ਼ੂਰਸ਼ੁਦਾ ਸੁਰੱਖਿਅਤ ਰਨਟਾਈਮ ਦੀ ਘੱਟੋ-ਘੱਟ ਸੀਮਾ ਤੋਂ ਬਾਹਰ ਹੈ। ਸਭ ਤੋਂ ਆਮ ਮਾਮਲਾ Node 22 ਜਾਂ 24 ਦਾ ਅਜਿਹਾ ਪੁਰਾਣਾ ਪੈਚ ਪੱਧਰ ਚਲਾਉਣਾ ਹੈ ਜੋ OmniRoute ਲਈ ਲੋੜੀਂਦੀ ਪੈਚ ਕੀਤੀ ਸੁਰੱਖਿਆ ਸੀਮਾ ਤੋਂ ਹੇਠਾਂ ਹੈ।

**ਲੱਛਣ:**

- ਲੌਗਇਨ ਪੰਨਾ ਖਾਲੀ ਸਕ੍ਰੀਨ ਜਾਂ ਸਰਵਰ ਗਲਤੀ ਦਿਖਾਉਂਦਾ ਹੈ
- ਕੰਸੋਲ `Error: Module did not self-register` ਜਾਂ ਇਸੇ ਤਰ੍ਹਾਂ ਦੀਆਂ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਗਲਤੀਆਂ ਦਿਖਾਉਂਦਾ ਹੈ
- ਜੇ ਰਨਟਾਈਮ ਸਮਰਥਿਤ ਸੁਰੱਖਿਆ ਨੀਤੀ ਤੋਂ ਬਾਹਰ ਹੈ, ਤਾਂ ਲੌਗਇਨ ਪੰਨਾ ਤੁਹਾਡੇ Node ਵਰਜਨ ਸਮੇਤ ਇੱਕ **ਸੰਤਰੀ ਚੇਤਾਵਨੀ ਬੈਨਰ** ਦਿਖਾਉਂਦਾ ਹੈ

**ਹੱਲ:**

1. ਇੱਕ ਸਮਰਥਿਤ Node.js LTS ਰਿਲੀਜ਼ ਇੰਸਟਾਲ ਕਰੋ (ਸਿਫ਼ਾਰਸ਼ੀ: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ਆਪਣੇ ਵਰਜਨ ਦੀ ਪੁਸ਼ਟੀ ਕਰੋ: `node --version` ਨੂੰ 24.x LTS ਲੜੀ ਵਿੱਚ `v24.0.0` ਜਾਂ ਇਸ ਤੋਂ ਨਵਾਂ ਵਰਜਨ ਦਿਖਾਉਣਾ ਚਾਹੀਦਾ ਹੈ
3. OmniRoute ਨੂੰ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ: `npm install -g omniroute`
4. ਮੁੜ ਸ਼ੁਰੂ ਕਰੋ: `omniroute`

> **ਸਮਰਥਿਤ ਸੁਰੱਖਿਅਤ ਵਰਜਨ:** `>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26 ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

### npm v11+: `better-sqlite3` ਇੰਸਟਾਲ ਨਹੀਂ ਹੋਇਆ (ਮੋਡੀਊਲ ਨਹੀਂ ਲੱਭਿਆ ਜਾ ਸਕਦਾ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ਕਾਰਨ:** npm v11 (ਜੋ Node.js 24+ ਨਾਲ ਮਿਲਦਾ ਹੈ) ਮੂਲ ਰੂਪ ਵਿੱਚ ਵਿਕਲਪਿਕ
ਨਿਰਭਰਤਾਵਾਂ ਲਈ ਇੰਸਟਾਲੇਸ਼ਨ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਬਲੌਕ ਕਰਦਾ ਹੈ। ਕਿਉਂਕਿ `better-sqlite3` ਨੂੰ `optionalDependencies`
ਵਿੱਚ ਸੂਚੀਬੱਧ ਕੀਤਾ ਗਿਆ ਹੈ ਅਤੇ ਇਸ ਲਈ ਨੇਟਿਵ ਕੰਪਾਈਲੇਸ਼ਨ (`node-gyp rebuild`) ਦੀ ਲੋੜ ਹੁੰਦੀ ਹੈ, npm ਇਸਨੂੰ ਬਿਨਾਂ ਕੋਈ ਸੁਨੇਹਾ ਦਿੱਤੇ ਛੱਡ ਦਿੰਦਾ ਹੈ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਸ਼ੁਰੂ ਹੋਣ ਵੇਲੇ `Cannot find module 'better-sqlite3'` ਨਾਲ ਕ੍ਰੈਸ਼ ਹੋ ਜਾਂਦਾ ਹੈ
- `ls node_modules/better-sqlite3` "No such file or directory" ਦਿਖਾਉਂਦਾ ਹੈ
- `npm ls better-sqlite3` `(empty)` ਦਿਖਾਉਂਦਾ ਹੈ

**ਹੱਲ:**

1. ਇੰਸਟਾਲੇਸ਼ਨ ਸਕ੍ਰਿਪਟਾਂ ਨੂੰ ਮਨਜ਼ੂਰੀ ਦਿਓ ਅਤੇ ਮੁੜ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ਜਾਂ ਪਹਿਲਾਂ ਤੋਂ ਬਣਿਆ ਪੈਕੇਜ ਹੱਥੀਂ ਇੰਸਟਾਲ ਕਰੋ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਇਹ ਕੰਮ ਕਰਦਾ ਹੈ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "slice is not valid mach-o file"

<a name="macos-native-module-rebuild"></a>

**ਕਾਰਨ:** ਗਲੋਬਲ `npm install -g omniroute` ਤੋਂ ਬਾਅਦ, ਪੈਕੇਜ ਦੇ ਅੰਦਰ ਮੌਜੂਦ `better-sqlite3` ਨੇਟਿਵ ਬਾਈਨਰੀ ਸ਼ਾਇਦ ਸਥਾਨਕ ਤੌਰ 'ਤੇ ਚੱਲ ਰਹੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ Node.js ABI ਤੋਂ ਵੱਖਰੇ ਆਰਕੀਟੈਕਚਰ ਜਾਂ ABI ਲਈ ਕੰਪਾਇਲ ਕੀਤੀ ਗਈ ਹੋਵੇ। ਇਹ macOS (Apple Silicon ਅਤੇ Intel ਦੋਵਾਂ) ਉੱਤੇ ਆਮ ਹੈ, ਜਦੋਂ ਪਹਿਲਾਂ ਤੋਂ ਬਣੀ ਬਾਈਨਰੀ ਤੁਹਾਡੇ ਵਾਤਾਵਰਣ ਨਾਲ ਮੇਲ ਨਹੀਂ ਖਾਂਦੀ।

**ਲੱਛਣ:**

- ਸਰਵਰ ਸ਼ੁਰੂ ਹੁੰਦਿਆਂ ਹੀ `dlopen` ਗਲਤੀ ਨਾਲ ਅਸਫਲ ਹੋ ਜਾਂਦਾ ਹੈ
- ਗਲਤੀ ਵਿੱਚ `slice is not valid mach-o file` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ
- ਪੂਰੀ ਉਦਾਹਰਨ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ਹੱਲ — ਆਪਣੇ ਸਥਾਨਕ ਵਾਤਾਵਰਣ ਲਈ ਮੁੜ ਬਿਲਡ ਕਰੋ (Node.js ਨੂੰ ਪੁਰਾਣੇ ਵਰਜਨ 'ਤੇ ਲਿਆਉਣ ਦੀ ਲੋੜ ਨਹੀਂ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ਨੋਟ:** ਇਹ ਨੇਟਿਵ ਬਾਈਂਡਿੰਗ ਨੂੰ ਤੁਹਾਡੇ ਸਥਾਨਕ Node.js ਵਰਜਨ ਅਤੇ CPU ਆਰਕੀਟੈਕਚਰ ਦੇ ਅਨੁਸਾਰ ਮੁੜ ਕੰਪਾਇਲ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਬਾਈਨਰੀ ਦਾ ਬੇਮੇਲ ਹੱਲ ਹੋ ਜਾਂਦਾ ਹੈ। ਅਧਿਕਾਰਤ ਤੌਰ 'ਤੇ ਸਮਰਥਿਤ ਰਨਟਾਈਮ ਰੇਂਜ **`>=22.22.2 <23` ਜਾਂ `>=24.0.0 <27`** ਹੈ (`src/shared/utils/nodeRuntimeSupport.ts` ਵਿੱਚ `SUPPORTED_NODE_RANGE`, ਜੋ `package.json` ਦੇ `engines` ਫ਼ੀਲਡ ਨਾਲ ਇਕਸਾਰ ਹੈ)। Node.js 24.x LTS (Krypton) ਅਤੇ Node.js 26, `better-sqlite3` v12.x ਨਾਲ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਮਰਥਿਤ ਹਨ।

## ਪ੍ਰੌਕਸੀ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

<a name="proxy-issues"></a>

### ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣਿਕਤਾ "fetch failed" ਦਿਖਾਉਂਦੀ ਹੈ

**ਕਾਰਨ:** API ਕੁੰਜੀ ਪ੍ਰਮਾਣਿਕਤਾ ਐਂਡਪੌਇੰਟ (`POST /api/providers/validate`) ਪਹਿਲਾਂ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਬਾਈਪਾਸ ਕਰ ਰਿਹਾ ਸੀ, ਜਿਸ ਕਾਰਨ ਪ੍ਰੌਕਸੀ ਰਾਊਟਿੰਗ ਦੀ ਲੋੜ ਵਾਲੇ ਵਾਤਾਵਰਣਾਂ ਵਿੱਚ ਅਸਫਲਤਾਵਾਂ ਆ ਰਹੀਆਂ ਸਨ।

**ਹੱਲ (v3.5.5+):** ਹੁਣ ਇਹ ਠੀਕ ਕਰ ਦਿੱਤਾ ਗਿਆ ਹੈ। ਪ੍ਰਦਾਤਾ ਪ੍ਰਮਾਣਿਕਤਾ `runWithProxyContext` ਰਾਹੀਂ ਰੂਟ ਹੁੰਦੀ ਹੈ ਅਤੇ ਆਪਣੇ ਆਪ ਪ੍ਰਦਾਤਾ-ਪੱਧਰੀ ਅਤੇ ਗਲੋਬਲ ਪ੍ਰੌਕਸੀ ਸੈਟਿੰਗਾਂ ਦੀ ਪਾਲਣਾ ਕਰਦੀ ਹੈ।

### ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ "fetch failed" ਨਾਲ ਅਸਫਲ ਹੁੰਦੀ ਹੈ

**ਕਾਰਨ:** ਬੈਕਗ੍ਰਾਊਂਡ OAuth ਟੋਕਨ ਰਿਫ੍ਰੈਸ਼ ਹਰ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਹੱਲ ਨਹੀਂ ਕਰ ਰਿਹਾ ਸੀ।

**ਹੱਲ (v3.5.5+):** ਟੋਕਨ ਸਿਹਤ ਜਾਂਚ ਸ਼ਡਿਊਲਰ ਹੁਣ ਰਿਫ੍ਰੈਸ਼ ਦੀ ਕੋਸ਼ਿਸ਼ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਹਰ ਕਨੈਕਸ਼ਨ ਲਈ ਪ੍ਰੌਕਸੀ ਸੰਰਚਨਾ ਨੂੰ ਹੱਲ ਕਰਦਾ ਹੈ। v3.5.5+ ’ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### SOCKS5 ਪ੍ਰੌਕਸੀ "invalid onRequestStart method" ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** Node.js 22 ’ਤੇ, undici@8 ਡਿਸਪੈਚਰ Node ਦੇ ਬਿਲਟ-ਇਨ `fetch()` ਕਾਰਜਾਨਵੈਨ ਨਾਲ ਅਨੁਕੂਲ ਨਹੀਂ ਹੈ।

**ਹੱਲ (v3.5.5+):** ਜਦੋਂ ਕੋਈ ਪ੍ਰੌਕਸੀ ਡਿਸਪੈਚਰ ਸਰਗਰਮ ਹੁੰਦਾ ਹੈ, ਤਾਂ OmniRoute ਹੁਣ undici ਦੇ ਆਪਣੇ `fetch()` ਫੰਕਸ਼ਨ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ, ਜਿਸ ਨਾਲ ਇਕਸਾਰ ਵਿਹਾਰ ਯਕੀਨੀ ਬਣਦਾ ਹੈ। v3.5.5+ ’ਤੇ ਅੱਪਡੇਟ ਕਰੋ।

### WSL ਅਧੀਨ MITM ਪ੍ਰੌਕਸੀ: Windows ਹੋਸਟ ਉੱਤੇ ਡੈਸਕਟਾਪ ਐਪਾਂ ਇੰਟਰਸੈਪਟ ਨਹੀਂ ਹੁੰਦੀਆਂ

**ਕਾਰਨ:** MITM ਪ੍ਰੌਕਸੀ ਅਤੇ ਇਸ ਦਾ CA ਸਰਟੀਫਿਕੇਟ ਉਸ ਵਾਤਾਵਰਣ ਵਿੱਚ ਇੰਸਟਾਲ ਹੁੰਦੇ ਹਨ ਜਿੱਥੇ OmniRoute ਚੱਲਦਾ ਹੈ। WSL ਅਧੀਨ ਉਹ ਵਾਤਾਵਰਣ Linux ਗੈਸਟ ਹੁੰਦਾ ਹੈ, ਜਦਕਿ AI ਡੈਸਕਟਾਪ ਐਪਾਂ (Kiro, Trae, Copilot, Zed, …) Windows ਹੋਸਟ ਉੱਤੇ ਚੱਲਦੀਆਂ ਹਨ। ਹੋਸਟ ਐਪਾਂ ਗੈਸਟ ਦੇ ਸਰਟੀਫਿਕੇਟ ਸਟੋਰ ’ਤੇ ਭਰੋਸਾ ਨਹੀਂ ਕਰਦੀਆਂ ਅਤੇ ਗੈਸਟ ਦੀ ਸਿਸਟਮ ਪ੍ਰੌਕਸੀ ਰਾਹੀਂ ਰੂਟ ਨਹੀਂ ਹੁੰਦੀਆਂ, ਇਸ ਲਈ ਉੱਥੇ ਡੈਸਕਟਾਪ ਇੰਟਰਸੈਪਸ਼ਨ ਸਰਗਰਮ ਨਹੀਂ ਹੁੰਦੀ।

**ਸਿਫ਼ਾਰਸ਼:** OmniRoute ਨੂੰ ਮੂਲ ਰੂਪ ਵਿੱਚ ਉਸੇ OS ਉੱਤੇ ਚਲਾਓ ਜਿਸ ਉੱਤੇ ਉਹ ਡੈਸਕਟਾਪ ਐਪਾਂ ਚੱਲਦੀਆਂ ਹਨ ਜਿਨ੍ਹਾਂ ਨੂੰ ਤੁਸੀਂ ਇੰਟਰਸੈਪਟ ਕਰਨਾ ਚਾਹੁੰਦੇ ਹੋ (Windows ਐਪਾਂ ਲਈ Windows; ਇਸੇ ਤਰ੍ਹਾਂ macOS/Linux ਲਈ ਵੀ)। ਹੋਸਟ ਐਪਾਂ ਨੂੰ ਨਿਸ਼ਾਨਾ ਬਣਾਉਂਦੇ ਹੋਏ OmniRoute ਨੂੰ WSL ਦੇ ਅੰਦਰ ਰੱਖਣ ਲਈ Windows ਹੋਸਟ ਉੱਤੇ ਬਣਾਏ ਗਏ CA ਸਰਟੀਫਿਕੇਟ ਨੂੰ ਹੱਥੀਂ ਭਰੋਸੇਯੋਗ ਬਣਾਉਣਾ ਅਤੇ ਹਰ ਹੋਸਟ ਐਪ ਦੀਆਂ ਨੈੱਟਵਰਕ/ਪ੍ਰੌਕਸੀ ਸੈਟਿੰਗਾਂ ਨੂੰ WSL ਪ੍ਰੌਕਸੀ ਐਂਡਪੌਇੰਟ ਵੱਲ ਸੈੱਟ ਕਰਨਾ ਲੋੜੀਂਦਾ ਹੈ — ਇਹ ਇੱਕ ਅਸਮਰਥਿਤ ਅਤੇ ਨਾਜ਼ੁਕ ਸੈਟਅੱਪ ਹੈ।

## ਕਲਾਉਡ ਸਮੱਸਿਆਵਾਂ

### ਕਲਾਉਡ ਸਿੰਕ ਗਲਤੀਆਂ

1. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `BASE_URL` ਤੁਹਾਡੇ ਚੱਲ ਰਹੇ ਇੰਸਟੈਂਸ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `http://localhost:20128`)
2. ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ `CLOUD_URL` ਤੁਹਾਡੇ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ (ਉਦਾਹਰਨ ਲਈ, `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ਮੁੱਲਾਂ ਨੂੰ ਸਰਵਰ-ਸਾਈਡ ਮੁੱਲਾਂ ਨਾਲ ਇਕਸਾਰ ਰੱਖੋ

### ਕਲਾਉਡ `stream=false` 500 ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:** ਗੈਰ-ਸਟ੍ਰੀਮਿੰਗ ਕਾਲਾਂ ਲਈ ਕਲਾਉਡ ਐਂਡਪੌਇੰਟ ਉੱਤੇ `Unexpected token 'd'...`।

**ਕਾਰਨ:** ਅੱਪਸਟ੍ਰੀਮ SSE ਪੇਲੋਡ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਦਕਿ ਕਲਾਇੰਟ JSON ਦੀ ਉਮੀਦ ਕਰਦਾ ਹੈ।

**ਅਸਥਾਈ ਹੱਲ:** ਕਲਾਉਡ ਨੂੰ ਸਿੱਧੀਆਂ ਕਾਲਾਂ ਲਈ `stream=true` ਵਰਤੋ। ਲੋਕਲ ਰਨਟਾਈਮ ਵਿੱਚ SSE→JSON ਫਾਲਬੈਕ ਸ਼ਾਮਲ ਹੈ।

### ਕਲਾਉਡ ਕਨੈਕਟਡ ਦਿਖਾਉਂਦਾ ਹੈ ਪਰ "ਅਵੈਧ API ਕੁੰਜੀ" ਕਹਿੰਦਾ ਹੈ

1. ਲੋਕਲ ਡੈਸ਼ਬੋਰਡ (`/api/keys`) ਤੋਂ ਇੱਕ ਨਵੀਂ ਕੁੰਜੀ ਬਣਾਓ
2. ਕਲਾਉਡ ਸਿੰਕ ਚਲਾਓ: ਕਲਾਉਡ ਸਮਰੱਥ ਕਰੋ → ਹੁਣੇ ਸਿੰਕ ਕਰੋ
3. ਪੁਰਾਣੀਆਂ/ਸਿੰਕ ਨਾ ਕੀਤੀਆਂ ਕੁੰਜੀਆਂ ਹਾਲੇ ਵੀ ਕਲਾਉਡ ਉੱਤੇ `401` ਵਾਪਸ ਕਰ ਸਕਦੀਆਂ ਹਨ

## Docker ਸਮੱਸਿਆਵਾਂ

### Docker IPv6 / ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ

<a name="docker-ipv6"></a>

**ਲੱਛਣ:** `curl http://localhost:20128/v1/models` ਚਲਾਉਣ ਉੱਤੇ `curl: (56) Recv failure: Connection reset by peer` ਵਾਪਸ ਆਉਂਦਾ ਹੈ। ਡੈਸ਼ਬੋਰਡ ਅਤੇ ਬਿਨਾਂ ਪ੍ਰਮਾਣੀਕਰਨ ਵਾਲੇ ਐਂਡਪੌਇੰਟ ਕੰਮ ਕਰਦੇ ਹਨ, ਪਰ ਪ੍ਰਮਾਣੀਕ੍ਰਿਤ ਐਂਡਪੌਇੰਟ ਅਸਫਲ ਹੁੰਦੇ ਹਨ — ਇਹ ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਸਮੱਸਿਆ ਜਾਪਦੀ ਹੈ, ਪਰ ਅਸਲ ਵਿੱਚ ਨਹੀਂ ਹੈ।

**ਕਾਰਨ:** `docker run -p 20128:20128` ਦੋਵਾਂ `0.0.0.0` (IPv4) ਅਤੇ `::` (IPv6) ਉੱਤੇ ਪੋਰਟ ਪ੍ਰਕਾਸ਼ਿਤ ਕਰਦਾ ਹੈ, ਪਰ ਕੰਟੇਨਰ ਦੇ ਅੰਦਰਲੀ ਪ੍ਰਕਿਰਿਆ ਸਿਰਫ਼ IPv4 ਉੱਤੇ ਸੁਣਦੀ ਹੈ। ਉਹਨਾਂ ਹੋਸਟਾਂ ਉੱਤੇ ਜਿੱਥੇ `localhost` ਪਹਿਲਾਂ `::1` ਵਜੋਂ ਰਿਜ਼ਾਲਵ ਹੁੰਦਾ ਹੈ, ਕਨੈਕਸ਼ਨ IPv6 ਦੇ ਪ੍ਰਕਾਸ਼ਿਤ ਪੋਰਟ ਉੱਤੇ ਪਹੁੰਚਦਾ ਹੈ, ਜਿਸ ਦੇ ਪਿੱਛੇ ਕੋਈ ਲਿਸਨਰ ਨਹੀਂ ਹੁੰਦਾ → ਕਨੈਕਸ਼ਨ ਰੀਸੈੱਟ।

**ਹੱਲ:**

1. **ਤੁਰੰਤ ਜਾਂਚ:** `curl -4 http://localhost:20128/v1/models` ਚਲਾਓ। ਜੇ ਇਹ `-4` ਨਾਲ ਕੰਮ ਕਰਦਾ ਹੈ ਪਰ ਇਸ ਤੋਂ ਬਿਨਾਂ ਅਸਫਲ ਹੁੰਦਾ ਹੈ, ਤਾਂ ਤੁਹਾਡੇ ਕੋਲ IPv6 ਬਾਈਂਡ ਬੇਮੇਲਤਾ ਹੈ।
2. **ਸਥਾਈ ਹੱਲ:** ਆਪਣੀ `docker run` ਕਮਾਂਡ ਵਿੱਚ `-p 127.0.0.1:20128:20128` ਵਰਤ ਕੇ ਸਪਸ਼ਟ ਤੌਰ ਉੱਤੇ IPv4 ਨਾਲ ਬਾਈਂਡ ਕਰੋ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ਇਹ IPv4 ਬਾਈਂਡ ਨੂੰ ਲਾਜ਼ਮੀ ਬਣਾਉਂਦਾ ਹੈ ਅਤੇ ਪ੍ਰਾਕਸੀ ਨੂੰ ਹੋਸਟ ਦੇ ਸਾਰੇ ਇੰਟਰਫੇਸਾਂ ਉੱਤੇ ਉਪਲਬਧ ਹੋਣ ਤੋਂ ਵੀ ਰੋਕਦਾ ਹੈ।

## ਡੀਬੱਗਿੰਗ

### ਲਾਗ ਫਾਈਲਾਂ ਸਮਰੱਥ ਕਰੋ

ਆਪਣੀ `.env` ਫਾਈਲ ਵਿੱਚ `APP_LOG_TO_FILE=true` ਸੈੱਟ ਕਰੋ। ਐਪਲੀਕੇਸ਼ਨ ਲਾਗ `logs/` ਦੇ ਅਧੀਨ ਲਿਖੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਸੈਟਿੰਗਾਂ ਵਿੱਚ ਕਾਲ ਲਾਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਬੇਨਤੀ ਆਰਟੀਫੈਕਟ `${DATA_DIR}/call_logs/` ਦੇ ਅਧੀਨ ਸਟੋਰ ਕੀਤੇ ਜਾਂਦੇ ਹਨ।
ਜਦੋਂ ਪਾਈਪਲਾਈਨ ਕੈਪਚਰ ਸਮਰੱਥ ਹੋਵੇ, ਤਾਂ ਸਟ੍ਰੀਮ ਚੰਕ ਪੇਲੋਡਾਂ ਨੂੰ ਛੱਡਣ ਲਈ `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ਸੈੱਟ ਕਰੋ, ਜਾਂ ਆਰਟੀਫੈਕਟ ਦੀ KB ਵਿੱਚ ਸੀਮਾ ਬਦਲਣ ਲਈ `CALL_LOG_PIPELINE_MAX_SIZE_KB` ਨੂੰ ਸਮਾਯੋਜਿਤ ਕਰੋ।

### ਪ੍ਰਦਾਤਾ ਦੀ ਸਿਹਤ ਜਾਂਚੋ

```bash
# ਸਿਹਤ ਡੈਸ਼ਬੋਰਡ
http://localhost:20128/dashboard/health

# API ਸਿਹਤ ਜਾਂਚ
curl http://localhost:20128/api/monitoring/health
```

### ਰਨਟਾਈਮ ਸਟੋਰੇਜ

- ਮੁੱਖ ਸਥਿਤੀ: `${DATA_DIR}/storage.sqlite` (ਪ੍ਰਦਾਤਾ, ਕੰਬੋ, ਉਪਨਾਮ, ਕੁੰਜੀਆਂ, ਸੈਟਿੰਗਾਂ)
- ਵਰਤੋਂ: `storage.sqlite` ਵਿੱਚ SQLite ਟੇਬਲਾਂ (`usage_history`, `call_logs`, `proxy_logs`) + ਵਿਕਲਪਿਕ `${DATA_DIR}/call_logs/`
- ਐਪਲੀਕੇਸ਼ਨ ਲਾਗ: `<repo>/logs/...` (ਜਦੋਂ `APP_LOG_TO_FILE=true`)
- ਕਾਲ ਲਾਗ ਆਰਟੀਫੈਕਟ: ਕਾਲ ਲਾਗ ਪਾਈਪਲਾਈਨ ਸਮਰੱਥ ਹੋਣ ਉੱਤੇ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

ਬੇਨਤੀ ਲਾਗ ਪੰਨੇ ਦੀ **ਇਤਿਹਾਸ ਸਾਫ਼ ਕਰੋ** ਕਾਰਵਾਈ `call_logs`, ਪੁਰਾਣੇ
`request_detail_logs`, ਅਤੇ ਲੋਕਲ `${DATA_DIR}/call_logs/` ਆਰਟੀਫੈਕਟ ਡਾਇਰੈਕਟਰੀ ਨੂੰ ਸਾਫ਼ ਕਰਦੀ ਹੈ।

## ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਸੰਬੰਧੀ ਸਮੱਸਿਆਵਾਂ

### ਪ੍ਰੋਵਾਈਡਰ OPEN ਸਥਿਤੀ ਵਿੱਚ ਅਟਕਿਆ ਹੋਇਆ ਹੈ

ਜਦੋਂ ਕਿਸੇ ਪ੍ਰੋਵਾਈਡਰ ਦਾ ਸਰਕਿਟ ਬ੍ਰੇਕਰ OPEN ਹੁੰਦਾ ਹੈ, ਤਾਂ ਕੂਲਡਾਊਨ ਸਮਾਪਤ ਹੋਣ ਤੱਕ ਬੇਨਤੀਆਂ ਬਲੌਕ ਰਹਿੰਦੀਆਂ ਹਨ।

**ਹੱਲ:**

1. **Dashboard → Settings → Resilience** 'ਤੇ ਜਾਓ
2. ਪ੍ਰਭਾਵਿਤ ਪ੍ਰੋਵਾਈਡਰ ਲਈ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਕਾਰਡ ਦੀ ਜਾਂਚ ਕਰੋ
3. ਸਾਰੇ ਬ੍ਰੇਕਰ ਸਾਫ਼ ਕਰਨ ਲਈ **Reset All** 'ਤੇ ਕਲਿੱਕ ਕਰੋ, ਜਾਂ ਕੂਲਡਾਊਨ ਸਮਾਪਤ ਹੋਣ ਦੀ ਉਡੀਕ ਕਰੋ
4. ਰੀਸੈੱਟ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ ਪ੍ਰੋਵਾਈਡਰ ਅਸਲ ਵਿੱਚ ਉਪਲਬਧ ਹੈ

### ਪ੍ਰੋਵਾਈਡਰ ਵਾਰ-ਵਾਰ ਸਰਕਿਟ ਬ੍ਰੇਕਰ ਨੂੰ ਟ੍ਰਿਪ ਕਰਦਾ ਹੈ

ਜੇ ਕੋਈ ਪ੍ਰੋਵਾਈਡਰ ਵਾਰ-ਵਾਰ OPEN ਸਥਿਤੀ ਵਿੱਚ ਜਾਂਦਾ ਹੈ:

1. ਅਸਫਲਤਾ ਦੇ ਪੈਟਰਨ ਲਈ **Dashboard → Health → Provider Health** ਦੀ ਜਾਂਚ ਕਰੋ
2. **Settings → Resilience → Provider Profiles** 'ਤੇ ਜਾਓ ਅਤੇ ਅਸਫਲਤਾ ਸੀਮਾ ਵਧਾਓ
3. ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰੋਵਾਈਡਰ ਨੇ API ਸੀਮਾਵਾਂ ਬਦਲੀਆਂ ਹਨ ਜਾਂ ਮੁੜ ਪ੍ਰਮਾਣੀਕਰਨ ਦੀ ਲੋੜ ਹੈ

- **ਟੂਲ ਕਾਲਾਂ ਗਾਇਬ ਹੋ ਰਹੀਆਂ ਹਨ** — ਕੁਝ ਫਾਰਮੈਟ ਅਨੁਵਾਦ ਅਸਮਰਥਿਤ ਫ਼ੀਲਡਾਂ ਨੂੰ ਹਟਾ ਸਕਦੇ ਹਨ; Playground ਮੋਡ ਵਿੱਚ ਪੁਸ਼ਟੀ ਕਰੋ
- **ਸਿਸਟਮ ਪ੍ਰੌਮਪਟ ਮੌਜੂਦ ਨਹੀਂ ਹੈ** — Claude ਅਤੇ Gemini ਸਿਸਟਮ ਪ੍ਰੌਮਪਟਾਂ ਨੂੰ ਵੱਖਰੇ ਢੰਗ ਨਾਲ ਸੰਭਾਲਦੇ ਹਨ; ਅਨੁਵਾਦ ਆਉਟਪੁੱਟ ਦੀ ਜਾਂਚ ਕਰੋ
- **SDK ਆਬਜੈਕਟ ਦੀ ਬਜਾਏ ਕੱਚੀ ਸਟਰਿੰਗ ਵਾਪਸ ਕਰਦਾ ਹੈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; ਰਿਸਪਾਂਸ ਸੈਨੀਟਾਈਜ਼ਰ ਗੈਰ-ਮਿਆਰੀ ਫ਼ੀਲਡਾਂ (`x_groq`, `usage_breakdown`, ਆਦਿ) ਨੂੰ ਹਟਾਉਂਦਾ ਹੈ, ਜੋ OpenAI SDK Pydantic ਵੈਲੀਡੇਸ਼ਨ ਅਸਫਲਤਾਵਾਂ ਦਾ ਕਾਰਨ ਬਣਦੀਆਂ ਹਨ। ਜੇ ਤੁਸੀਂ ਅਜੇ ਵੀ ਇਹ ਸਮੱਸਿਆ v3.x+ 'ਤੇ ਦੇਖਦੇ ਹੋ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ ਇਸ਼ੂ ਦਰਜ ਕਰੋ।
- **GLM/ERNIE `system` ਰੋਲ ਨੂੰ ਅਸਵੀਕਾਰ ਕਰਦਾ ਹੈ** — v1.x ਵਿੱਚ ਹੱਲ ਕੀਤਾ ਗਿਆ; ਰੋਲ ਨਾਰਮਲਾਈਜ਼ਰ ਅਸੰਗਤ ਮਾਡਲਾਂ ਲਈ ਸਿਸਟਮ ਸੁਨੇਹਿਆਂ ਨੂੰ ਆਪਣੇ ਆਪ ਯੂਜ਼ਰ ਸੁਨੇਹਿਆਂ ਵਿੱਚ ਮਿਲਾ ਦਿੰਦਾ ਹੈ। ਜੇ ਤੁਸੀਂ ਅਜੇ ਵੀ ਇਹ ਸਮੱਸਿਆ v3.x+ 'ਤੇ ਦੇਖਦੇ ਹੋ, ਤਾਂ ਕਿਰਪਾ ਕਰਕੇ ਇੱਕ ਇਸ਼ੂ ਦਰਜ ਕਰੋ।

## ਲਚੀਲੇਪਣ ਦੀਆਂ ਸੈਟਿੰਗਾਂ

### ਸਵੈਚਾਲਿਤ ਰੇਟ-ਲਿਮਿਟ ਚਾਲੂ ਨਹੀਂ ਹੋ ਰਹੀ

- ਸਵੈਚਾਲਿਤ ਰੇਟ-ਲਿਮਿਟ ਸਿਰਫ਼ API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ 'ਤੇ ਲਾਗੂ ਹੁੰਦੀ ਹੈ (OAuth/ਸਬਸਕ੍ਰਿਪਸ਼ਨ 'ਤੇ ਨਹੀਂ)
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **Settings → Resilience → Provider Profiles** ਵਿੱਚ ਸਵੈਚਾਲਿਤ ਰੇਟ-ਲਿਮਿਟ ਸਮਰੱਥ ਹੈ
- ਜਾਂਚ ਕਰੋ ਕਿ ਕੀ ਪ੍ਰਦਾਤਾ `429` ਸਥਿਤੀ ਕੋਡ ਜਾਂ `Retry-After` ਹੈਡਰ ਵਾਪਸ ਕਰਦਾ ਹੈ

### ਐਕਸਪੋਨੇਨਸ਼ੀਅਲ ਬੈਕਆਫ਼ ਨੂੰ ਟਿਊਨ ਕਰਨਾ

ਪ੍ਰਦਾਤਾ ਪ੍ਰੋਫ਼ਾਈਲ ਇਨ੍ਹਾਂ ਸੈਟਿੰਗਾਂ ਦਾ ਸਮਰਥਨ ਕਰਦੇ ਹਨ:

- **ਮੂਲ ਦੇਰੀ** — ਪਹਿਲੀ ਅਸਫਲਤਾ ਤੋਂ ਬਾਅਦ ਸ਼ੁਰੂਆਤੀ ਉਡੀਕ ਸਮਾਂ (ਡਿਫੌਲਟ: 1s)
- **ਵੱਧ ਤੋਂ ਵੱਧ ਦੇਰੀ** — ਉਡੀਕ ਸਮੇਂ ਦੀ ਅਧਿਕਤਮ ਸੀਮਾ (ਡਿਫੌਲਟ: 30s)
- **ਗੁਣਕ** — ਹਰ ਲਗਾਤਾਰ ਅਸਫਲਤਾ ਨਾਲ ਦੇਰੀ ਕਿੰਨੀ ਵਧਾਉਣੀ ਹੈ (ਡਿਫੌਲਟ: 2x)

### ਥੰਡਰਿੰਗ ਹਰਡ ਤੋਂ ਸੁਰੱਖਿਆ

ਜਦੋਂ ਕਈ ਸਮਕਾਲੀ ਬੇਨਤੀਆਂ ਕਿਸੇ ਰੇਟ-ਲਿਮਿਟ ਕੀਤੇ ਪ੍ਰਦਾਤਾ ਤੱਕ ਪਹੁੰਚਦੀਆਂ ਹਨ, ਤਾਂ OmniRoute ਬੇਨਤੀਆਂ ਨੂੰ ਲੜੀਬੱਧ ਕਰਨ ਅਤੇ ਲੜੀਵਾਰ ਅਸਫਲਤਾਵਾਂ ਨੂੰ ਰੋਕਣ ਲਈ mutex + ਸਵੈਚਾਲਿਤ ਰੇਟ-ਲਿਮਿਟਿੰਗ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। API ਕੁੰਜੀ ਪ੍ਰਦਾਤਾਵਾਂ ਲਈ ਇਹ ਸਵੈਚਾਲਿਤ ਹੈ।

### ਚੈਟ ਬੇਨਤੀਆਂ 503 / chat_admission_busy ਨਾਲ ਅਸਫਲ ਹੁੰਦੀਆਂ ਹਨ

**ਲੱਛਣ:**

- ਚੈਟ ਕੰਪਲੀਸ਼ਨਜ਼ ਐਂਡਪੌਇੰਟ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਜਵਾਬ ਵਾਪਸ ਕਰਦਾ ਹੈ, ਜਿਸਦਾ ਤਰੁੱਟੀ ਕੋਡ
  `chat_admission_busy` ਹੁੰਦਾ ਹੈ।
- ਜਵਾਬ ਵਿੱਚ `Retry-After` ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ। #12135 ਤੋਂ ਇਸਦਾ ਮੁੱਲ ਵੇਖੀ ਗਈ
  ਆਕਿਊਪੈਂਸੀ ਤੋਂ ਲਿਆ ਜਾਂਦਾ ਹੈ — ਬੇਨਤੀ ਵੱਲੋਂ ਪਹਿਲਾਂ ਹੀ ਉਡੀਕੀ ਗਈ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ਵਿੰਡੋ
  ਅਤੇ ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ਾਂ ਦੇ ਹੋਲਡ ਰਹਿਣ ਦੇ ਸਮੇਂ ਵਿੱਚੋਂ ਜੋ ਵੀ ਵੱਡਾ ਹੋਵੇ — ਉਸਨੂੰ ਉੱਪਰ ਵੱਲ ਪੂਰੇ
  ਸਕਿੰਟਾਂ ਵਿੱਚ ਰਾਊਂਡ ਕਰਕੇ 60 ਤੱਕ ਸੀਮਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ। ਨਿਸ਼ਕਿਰਿਆ ਗੇਟ 'ਤੇ ਇਹ ਇਤਿਹਾਸਕ ਨਿਊਨਤਮ ਹੱਦਾਂ ਕਾਇਮ ਰੱਖਦਾ ਹੈ: ਬਾਈਟ-ਅਧਾਰਿਤ
  ਮਾਰਗ 'ਤੇ 2 ਸਕਿੰਟ ਅਤੇ ਸਟਰਕਚਰ-ਅਧਾਰਿਤ ਮਾਰਗ 'ਤੇ 1 ਸਕਿੰਟ (ਜਿਸ ਵਿੱਚ
  `reason: "structure_limit"` ਵੀ ਸ਼ਾਮਲ ਹੁੰਦਾ ਹੈ)।
- ਇਹ ਉਦੋਂ ਹੋ ਸਕਦਾ ਹੈ ਜਦੋਂ ਕੋਈ ਹੋਰ ਹੈਵੀਵੇਟ ਚੈਟ ਜਾਂ ਲੰਬੇ ਸਮੇਂ ਤੋਂ ਚੱਲ ਰਿਹਾ ਸਟ੍ਰੀਮਿੰਗ ਜਵਾਬ ਅਜੇ ਵੀ
  ਪ੍ਰਕਿਰਿਆ ਅਧੀਨ ਹੋਵੇ।

ਬਾਈਟ-ਅਧਾਰਿਤ ਜਵਾਬ ਦੀ ਬਾਡੀ ਇਹ ਹੈ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ਸਟਰਕਚਰ-ਅਧਾਰਿਤ ਜਵਾਬ ਇਹੀ ਕਿਸਮ ਅਤੇ ਕੋਡ ਵਰਤਦਾ ਹੈ, ਜਿਸ ਵਿੱਚ ਸੁਨੇਹਾ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ਅਤੇ `reason: "structure_limit"` ਹੁੰਦਾ ਹੈ।
ਡਿਫੌਲਟ ਥ੍ਰੈਸ਼ਹੋਲਡਾਂ 'ਤੇ, ਕੋਈ ਬੇਨਤੀ ਸਟਰਕਚਰਕ ਤੌਰ 'ਤੇ ਭਾਰੀ ਹੁੰਦੀ ਹੈ ਜਦੋਂ ਉਸ ਵਿੱਚ ਘੱਟੋ-ਘੱਟ `200` ਸੁਨੇਹੇ,
ਘੱਟੋ-ਘੱਟ `64` ਟੂਲ ਜਾਂ ਘੱਟੋ-ਘੱਟ `32,000` ਅਨੁਮਾਨਿਤ ਟੋਕਨ ਹੋਣ, ਜਾਂ ਜਦੋਂ ਸੀਮਾਬੱਧ ਸਟਰਕਚਰ ਅਨੁਮਾਨ
`10,000` ਵਿਜ਼ਿਟ ਕੀਤੇ ਨੋਡਾਂ ਜਾਂ `12` ਦੀ ਡੂੰਘਾਈ ਦੀਆਂ ਆਪਣੀਆਂ ਹੱਦਾਂ ਖ਼ਤਮ ਕਰ ਦੇਵੇ।

**ਕਾਰਨ:** ਇਹ OmniRoute ਦੇ ਅੰਦਰ ਜਾਣਬੁੱਝ ਕੇ ਕੀਤੀ ਗਈ ਲੋਡ ਸ਼ੈਡਿੰਗ ਹੈ, ਅੱਪਸਟ੍ਰੀਮ ਪ੍ਰਦਾਤਾ ਦੀ ਅਸਫਲਤਾ ਨਹੀਂ।
ਹਰੇਕ ਪ੍ਰੋਸੈਸ ਵੱਡੀ ਬੇਨਤੀ ਬਾਡੀ ਨੂੰ ਬਰਕਰਾਰ ਰੱਖਣ ਅਤੇ ਪਾਰਸ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ ਸੀਮਿਤ ਹੈਵੀਵੇਟ ਸਮਰੱਥਾ ਰਾਖਵੀਂ ਕਰਨ ਲਈ
ਇੱਕ ਪ੍ਰੋਸੈਸ-ਲੋਕਲ ਗਾਰਡ ਦੀ ਵਰਤੋਂ ਕਰਦਾ ਹੈ। ਹੈਵੀਵੇਟ ਲੀਜ਼ ਕਿਸੇ SSE
ਜਵਾਬ ਦੇ ਪੂਰੇ ਜੀਵਨਕਾਲ ਦੌਰਾਨ ਹੋਲਡ ਰਹਿੰਦੀ ਹੈ।

**#503-fanout:** ਇਸ ਸੁਧਾਰ ਤੋਂ ਪਹਿਲਾਂ, ਗਾਰਡ ਹੋਸਟ ਮੈਮੋਰੀ ਦੀ ਪਰਵਾਹ ਕੀਤੇ ਬਿਨਾਂ ਸਮਕਾਲਿਕਤਾ ਨੂੰ ਇੱਕ ਨਿਸ਼ਚਿਤ ਬੇਨਤੀ COUNT
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ਡਿਫੌਲਟ `1`) ਤੱਕ ਸੀਮਿਤ ਕਰਦਾ ਸੀ, ਇਸ ਲਈ ਕੋਡਿੰਗ-ਏਜੰਟ
ਫੈਨ-ਆਉਟ (ਕਈ ਸਬ-ਏਜੰਟ/CLI, ਆਮ ਤੌਰ 'ਤੇ > 256 KB ਬਾਡੀਆਂ) ਲਗਭਗ 1 ਦੀ ਪ੍ਰਭਾਵੀ
ਸਮਕਾਲਿਕਤਾ ਤੱਕ ਡਿੱਗ ਜਾਂਦਾ ਸੀ ਅਤੇ ਪੂਰੀ ਤਰ੍ਹਾਂ ਸਧਾਰਨ ਲੋਡ ਹੇਠ 503 ਤਰੁੱਟੀਆਂ ਦੇਣ ਲੱਗਦਾ ਸੀ। ਹੁਣ ਗਾਰਡ ਆਪਣੇ-ਆਪ ਟਿਊਨ ਹੁੰਦਾ ਹੈ: ਇਸਨੂੰ
ਪ੍ਰੋਸੈਸ ਦੀ ਅਸਲ ਮੈਮੋਰੀ ਸੀਮਾ ਤੋਂ ਆਕਾਰ ਲੈਣ ਵਾਲੇ ਸਵੈਚਾਲਿਤ ਤੌਰ 'ਤੇ ਨਿਰਧਾਰਤ ਇੰਜੈਸਟ BYTE ਬਜਟ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ਰਾਹੀਂ ਨਿਯੰਤਰਿਤ ਕੀਤਾ ਜਾਂਦਾ ਹੈ,
ਅਤੇ ਇਹ ਇੱਕ ਲਾਈਵ ਸਰੋਤ-ਦਬਾਅ ਸੰਕੇਤ ਨੂੰ ਵੀ ਧਿਆਨ ਵਿੱਚ ਰੱਖਦਾ ਹੈ — ਇਸ ਲਈ ਇਹ ਸਿਰਫ਼ ਉਦੋਂ ਲੋਡ ਘਟਾਉਂਦਾ ਹੈ
ਜਦੋਂ ਹੋਸਟ ਸੱਚਮੁੱਚ ਮੈਮੋਰੀ ਦਬਾਅ ਹੇਠ ਹੋਵੇ, ਨਾ ਕਿ ਸਿਰਫ਼ ਇਸ ਕਰਕੇ ਕਿ ਇੱਕ ਤੋਂ ਵੱਧ
ਭਾਰੀ ਬੇਨਤੀਆਂ ਇੱਕੋ ਵੇਲੇ ਆ ਗਈਆਂ। ਪੁਰਾਣੀ ਗਿਣਤੀ ਸੀਮਾ (`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ਦਾ
ਹਾਲੇ ਵੀ ਸਨਮਾਨ ਕੀਤਾ ਜਾਂਦਾ ਹੈ, ਪਰ ਸਿਰਫ਼ ਉਦੋਂ ਜਦੋਂ ਤੁਸੀਂ ਇਸਨੂੰ ਸਪਸ਼ਟ ਤੌਰ 'ਤੇ ਸੈੱਟ ਕਰਦੇ ਹੋ।

ਜਦੋਂ ਸਮਰੱਥਾ ਵਿਅਸਤ ਹੁੰਦੀ ਹੈ, ਤਾਂ ਹੈਵੀਵੇਟ ਬੇਨਤੀ ਮੁੜ ਕੋਸ਼ਿਸ਼ਯੋਗ `503` ਜਵਾਬ ਦੇਣ ਤੋਂ ਪਹਿਲਾਂ
ਸਲਾਟ ਖਾਲੀ ਹੋਣ ਲਈ ਵੱਧ ਤੋਂ ਵੱਧ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` (ਡਿਫੌਲਟ `2000`, `0` ਉਡੀਕ ਨੂੰ ਅਸਮਰੱਥ ਕਰਦਾ ਹੈ) ਤੱਕ ਉਡੀਕ ਕਰਦੀ ਹੈ।
ਇਹ ਸੀਮਾਬੱਧ ਉਡੀਕ ਇਸ ਲਈ ਮੌਜੂਦ ਹੈ ਤਾਂ ਜੋ ਭਾਰੀ ਉਪ-ਬੇਨਤੀਆਂ ਨੂੰ ਇੱਕੋ ਵੇਲੇ ਫੈਨ-ਆਉਟ ਕਰਨ ਵਾਲੇ ਏਜੰਟ-ਸ਼ੈਲੀ ਕਲਾਇੰਟ
(OpenCode, Claude Code, Cursor) ਤੁਰੰਤ ਰੱਦੀਆਂ 'ਤੇ ਆਪਣਾ ਪੂਰਾ ਮੁੜ-ਕੋਸ਼ਿਸ਼ ਬਜਟ ਖਰਚ ਕੇ ਕੰਮ ਦੇ ਵਿਚਕਾਰ ਬੰਦ ਹੋਣ ਦੀ ਬਜਾਏ
ਬਰਸਟ ਨੂੰ ਲੜੀਬੱਧ ਕਰਨ।
ਮੌਜੂਦਾ ਹੈਵੀਵੇਟ ਲੀਜ਼ ਆਕਿਊਪੈਂਸੀ, ਨਿਰਧਾਰਤ ਬਾਈਟ ਬਜਟ ਅਤੇ ਲਾਈਵ ਦਬਾਅ ਦੀ ਗੰਭੀਰਤਾ
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) 'ਤੇ ਦਿਖਾਈ ਜਾਂਦੀ ਹੈ — ਕਿਸੇ ਵੀ env var ਨੂੰ ਬਦਲਣ ਤੋਂ ਪਹਿਲਾਂ ਇਨ੍ਹਾਂ ਦੀ ਜਾਂਚ ਕਰੋ।
Settings → Resilience → Request Queue → Concurrent Requests ਇਸਨੂੰ ਨਿਯੰਤਰਿਤ ਨਹੀਂ ਕਰਦਾ; ਉਹ ਸੈਟਿੰਗ
ਇੱਕ ਵੱਖਰੇ ਪ੍ਰਦਾਤਾ ਬੇਨਤੀ-ਕਤਾਰ ਮਕੈਨਿਜ਼ਮ ਨੂੰ ਨਿਯੰਤਰਿਤ ਕਰਦੀ ਹੈ।

**ਹੱਲ:**

1. ਪਹਿਲਾਂ ਮੁੜ ਕੋਸ਼ਿਸ਼ ਕਰੋ। ਕਲਾਇੰਟਾਂ ਨੂੰ ਬੇਨਤੀ ਤੁਰੰਤ ਦੁਹਰਾਉਣ ਦੀ ਬਜਾਏ `Retry-After` ਦੀ ਪਾਲਣਾ
   ਕਰਨੀ ਅਤੇ ਬੈਕਆਫ਼ ਵਰਤਣਾ ਚਾਹੀਦਾ ਹੈ।
2. ਕੁਝ ਵੀ ਟਿਊਨ ਕਰਨ ਤੋਂ ਪਹਿਲਾਂ `/api/monitoring/health` → `chatAdmission` ਦੀ ਜਾਂਚ ਕਰੋ। `countCapEnabled:
false` ਅਤੇ ਖੁੱਲ੍ਹਾ `maxInflightBytes` ਦਰਸਾਉਂਦੇ ਹਨ ਕਿ ਸਵੈਚਾਲਿਤ ਤੌਰ 'ਤੇ ਨਿਰਧਾਰਤ ਬਜਟ ਪਹਿਲਾਂ ਹੀ ਆਪਣਾ
   ਕੰਮ ਕਰ ਰਿਹਾ ਹੈ; `high`/`critical` ਦਾ `pressureSeverity` ਦਰਸਾਉਂਦਾ ਹੈ ਕਿ ਹੋਸਟ 'ਤੇ ਸੱਚਮੁੱਚ ਮੈਮੋਰੀ ਘੱਟ ਹੈ —
   ਇਸਨੂੰ ਐਡਮਿਸ਼ਨ env var ਨਾਲ ਠੀਕ ਨਹੀਂ ਕੀਤਾ ਜਾ ਸਕਦਾ; ਇਸ ਲਈ ਵਧੇਰੇ RAM ਜਾਂ ਛੋਟੇ ਵਰਕਲੋਡ ਦੀ ਲੋੜ ਹੈ।
3. ਸਿਰਫ਼ ਉਦੋਂ, ਜਦੋਂ `/api/monitoring/health` ਦਿਖਾਉਂਦਾ ਹੈ ਕਿ ਸਵੈਚਾਲਿਤ ਤੌਰ 'ਤੇ ਨਿਰਧਾਰਤ ਬਜਟ ਤੁਹਾਡੇ
   ਹੋਸਟ ਲਈ ਸੱਚਮੁੱਚ ਬਹੁਤ ਛੋਟਾ ਹੈ (ਇਹ ਦੁਰਲੱਭ ਹੈ — ਇਹ ਪਹਿਲਾਂ ਹੀ ਕੰਟੇਨਰ ਤੋਂ ਬੇਅਰ-ਮੈਟਲ ਤੱਕ ਸਕੇਲ ਕਰਦਾ ਹੈ), ਪੁਰਾਣੀ ਬੇਨਤੀ-ਗਿਣਤੀ ਸੀਮਾ 'ਤੇ ਵਾਪਸ ਜਾਣ ਦੀ ਬਜਾਏ
   ਇਸਨੂੰ ਸਿੱਧੇ `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ਨਾਲ ਓਵਰਰਾਈਡ ਕਰੋ।

ਅਧਿਕਾਰਤ ਐਡਮਿਸ਼ਨ ਸੈਟਿੰਗਾਂ ਲਈ [ਵਾਤਾਵਰਣ-ਵੇਰੀਏਬਲ ਹਵਾਲਾ](../reference/ENVIRONMENT.md#4-security--authentication)
ਵੇਖੋ।

## ਵਿਕਲਪਿਕ RAG / LLM ਅਸਫਲਤਾ ਵਰਗੀਕਰਨ (16 ਸਮੱਸਿਆਵਾਂ)

ਕੁਝ OmniRoute ਵਰਤੋਂਕਾਰ gateway ਨੂੰ RAG ਜਾਂ agent stacks ਦੇ ਅੱਗੇ ਰੱਖਦੇ ਹਨ। ਅਜਿਹੀਆਂ ਸੰਰਚਨਾਵਾਂ ਵਿੱਚ ਇੱਕ ਅਜੀਬ ਪੈਟਰਨ ਆਮ ਤੌਰ 'ਤੇ ਦੇਖਣ ਨੂੰ ਮਿਲਦਾ ਹੈ: OmniRoute ਠੀਕ ਦਿਖਾਈ ਦਿੰਦਾ ਹੈ (providers ਚਾਲੂ ਹਨ, routing profiles ਠੀਕ ਹਨ, ਕੋਈ rate limit alerts ਨਹੀਂ ਹਨ), ਪਰ ਅੰਤਿਮ ਜਵਾਬ ਫਿਰ ਵੀ ਗਲਤ ਹੁੰਦਾ ਹੈ।

ਅਮਲ ਵਿੱਚ, ਇਹ ਘਟਨਾਵਾਂ ਆਮ ਤੌਰ 'ਤੇ gateway ਦੀ ਬਜਾਏ downstream RAG pipeline ਤੋਂ ਪੈਦਾ ਹੁੰਦੀਆਂ ਹਨ।

ਜੇ ਤੁਸੀਂ ਇਨ੍ਹਾਂ ਅਸਫਲਤਾਵਾਂ ਦਾ ਵਰਣਨ ਕਰਨ ਲਈ ਇੱਕ ਸਾਂਝੀ ਸ਼ਬਦਾਵਲੀ ਚਾਹੁੰਦੇ ਹੋ, ਤਾਂ ਤੁਸੀਂ WFGY ProblemMap ਦੀ ਵਰਤੋਂ ਕਰ ਸਕਦੇ ਹੋ। ਇਹ MIT license ਵਾਲਾ ਇੱਕ ਬਾਹਰੀ ਪਾਠ ਸਰੋਤ ਹੈ ਜੋ RAG / LLM ਦੀਆਂ ਵਾਰ-ਵਾਰ ਆਉਣ ਵਾਲੀਆਂ ਸੋਲ੍ਹਾਂ ਅਸਫਲਤਾ ਕਿਸਮਾਂ ਨੂੰ ਪਰਿਭਾਸ਼ਿਤ ਕਰਦਾ ਹੈ। ਉੱਚ ਪੱਧਰ 'ਤੇ ਇਹ ਹੇਠ ਲਿਖੇ ਵਿਸ਼ਿਆਂ ਨੂੰ ਕਵਰ ਕਰਦਾ ਹੈ:

- retrieval ਵਿੱਚ ਭਟਕਾਅ ਅਤੇ ਟੁੱਟੀਆਂ context ਸੀਮਾਵਾਂ
- ਖਾਲੀ ਜਾਂ ਪੁਰਾਣੇ indexes ਅਤੇ vector stores
- embedding ਅਤੇ semantics ਵਿਚਕਾਰ ਅਸੰਗਤਤਾ
- prompt assembly ਅਤੇ context window ਨਾਲ ਸੰਬੰਧਿਤ ਸਮੱਸਿਆਵਾਂ
- logic ਦਾ ਢਹਿ ਜਾਣਾ ਅਤੇ ਹੱਦੋਂ ਵੱਧ ਭਰੋਸੇ ਵਾਲੇ ਜਵਾਬ
- ਲੰਬੀਆਂ chains ਅਤੇ agent coordination ਦੀਆਂ ਅਸਫਲਤਾਵਾਂ
- multi-agent memory ਅਤੇ role ਵਿੱਚ ਭਟਕਾਅ
- deployment ਅਤੇ bootstrap ਦੇ ਕ੍ਰਮ ਨਾਲ ਸੰਬੰਧਿਤ ਸਮੱਸਿਆਵਾਂ

ਵਿਚਾਰ ਸਧਾਰਨ ਹੈ:

1. ਜਦੋਂ ਤੁਸੀਂ ਕਿਸੇ ਖਰਾਬ ਜਵਾਬ ਦੀ ਜਾਂਚ ਕਰਦੇ ਹੋ, ਤਾਂ ਇਹ ਜਾਣਕਾਰੀ ਇਕੱਠੀ ਕਰੋ:
   - ਵਰਤੋਂਕਾਰ ਦਾ ਕੰਮ ਅਤੇ ਬੇਨਤੀ
   - OmniRoute ਵਿੱਚ route ਜਾਂ provider combo
   - downstream ਵਰਤਿਆ ਗਿਆ ਕੋਈ ਵੀ RAG context (ਪ੍ਰਾਪਤ ਕੀਤੇ ਦਸਤਾਵੇਜ਼, tool calls ਆਦਿ)
2. ਘਟਨਾ ਨੂੰ ਇੱਕ ਜਾਂ ਦੋ WFGY ProblemMap ਨੰਬਰਾਂ (`No.1` … `No.16`) ਨਾਲ ਜੋੜੋ।
3. ਨੰਬਰ ਨੂੰ OmniRoute logs ਦੇ ਨਾਲ ਆਪਣੇ dashboard, runbook ਜਾਂ incident tracker ਵਿੱਚ ਸੰਭਾਲੋ।
4. ਇਹ ਫ਼ੈਸਲਾ ਕਰਨ ਲਈ ਸੰਬੰਧਿਤ WFGY ਪੰਨੇ ਦੀ ਵਰਤੋਂ ਕਰੋ ਕਿ ਕੀ ਤੁਹਾਨੂੰ ਆਪਣਾ RAG stack, retriever ਜਾਂ routing strategy ਬਦਲਣ ਦੀ ਲੋੜ ਹੈ।

ਪੂਰਾ ਪਾਠ ਅਤੇ ਵਿਹਾਰਕ ਨੁਸਖੇ ਇੱਥੇ ਉਪਲਬਧ ਹਨ (MIT license, ਸਿਰਫ਼ ਪਾਠ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

ਜੇ ਤੁਸੀਂ OmniRoute ਦੇ ਪਿੱਛੇ RAG ਜਾਂ agent pipelines ਨਹੀਂ ਚਲਾਉਂਦੇ, ਤਾਂ ਤੁਸੀਂ ਇਸ ਭਾਗ ਨੂੰ ਅਣਡਿੱਠਾ ਕਰ ਸਕਦੇ ਹੋ।

## v3.8.0 ਦੀਆਂ ਜਾਣੀਆਂ-ਪਛਾਣੀਆਂ ਸਮੱਸਿਆਵਾਂ

v3.8.0 release ਨਾਲ ਸੰਬੰਧਿਤ ਖਾਸ ਸਮੱਸਿਆਵਾਂ ਅਤੇ ਉਨ੍ਹਾਂ ਦੇ ਮੌਜੂਦਾ ਹੱਲ। ਜੇ ਕਿਸੇ ਬਾਅਦ ਵਾਲੇ patch ਵਿੱਚ fix ਆ ਜਾਂਦਾ ਹੈ, ਤਾਂ entry ਨੂੰ ਅੱਪਡੇਟ ਜਾਂ ਹਟਾ ਦਿੱਤਾ ਜਾਵੇਗਾ।

### Devin CLI ਪ੍ਰਮਾਣੀਕਰਨ ਅਸਫਲਤਾਵਾਂ

**ਲੱਛਣ:**

- Devin-ਅਧਾਰਿਤ tools ਨੂੰ ਚਲਾਉਂਦੇ ਸਮੇਂ "Devin CLI not found" ਜਾਂ "auth failed"
- CLI runtime ਜਾਂਚ `installed=false` ਰਿਪੋਰਟ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:**

- `CLI_DEVIN_BIN` ਅਜਿਹੇ path ਵੱਲ ਇਸ਼ਾਰਾ ਕਰਦਾ ਹੈ ਜੋ ਮੌਜੂਦ ਨਹੀਂ ਹੈ
- host ਉੱਤੇ Devin CLI ਇੰਸਟਾਲ ਨਹੀਂ ਹੈ

**ਹੱਲ:**

1. ਆਪਣੇ platform ਲਈ Devin CLI ਇੰਸਟਾਲ ਕਰੋ
2. `.env` ਵਿੱਚ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ਜਾਂ ਅਸਲ path) ਸੈੱਟ ਕਰੋ
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ ਅਤੇ **Dashboard → CLI Tools** ਤੋਂ ਦੁਬਾਰਾ ਟੈਸਟ ਕਰੋ

### Model cooldown ਅਟਕਿਆ ਹੋਇਆ ਹੈ (ਹੱਥੀਂ reset)

**ਲੱਛਣ:**

- ਮਿਆਦ ਖ਼ਤਮ ਹੋਣ ਦਾ ਸਮਾਂ ਲੰਘ ਜਾਣ ਤੋਂ ਬਾਅਦ ਵੀ ਇੱਕ model cooldown ਵਿੱਚ ਸੂਚੀਬੱਧ ਰਹਿੰਦਾ ਹੈ
- timestamp ਬੀਤੇ ਸਮੇਂ ਵਿੱਚ ਹੋਣ ਦੇ ਬਾਵਜੂਦ combo routing ਵਿੱਚ ਬੇਨਤੀਆਂ ਅਜੇ ਵੀ model ਨੂੰ ਛੱਡ ਦਿੰਦੀਆਂ ਹਨ

**ਹੱਥੀਂ reset:**

- **Dashboard:** **Settings → Model Cooldowns** → ਪ੍ਰਭਾਵਿਤ card ਉੱਤੇ **Re-enable** ਨੂੰ ਕਲਿੱਕ ਕਰੋ
- **API:** management auth headers ਨਾਲ `DELETE /api/resilience/model-cooldowns`

### Command Code provider connection 403 ਨਾਲ ਅਸਫਲ ਹੁੰਦਾ ਹੈ

**ਲੱਛਣ:**

- Command Code provider connection ਦੀ ਜਾਂਚ ਕਰਦੇ ਸਮੇਂ 403
- ਨਵਾਂ ਜੋੜਨ ਤੋਂ ਬਾਅਦ provider card "unauthorized" ਦਿਖਾਉਂਦਾ ਹੈ

**ਕਾਰਨ:** OAuth flow ਪੂਰਾ ਨਹੀਂ ਹੋਇਆ (callback ਪ੍ਰਾਪਤ ਨਹੀਂ ਹੋਇਆ ਜਾਂ token ਸੰਭਾਲਿਆ ਨਹੀਂ ਗਿਆ)।

**ਹੱਲ:**

- OAuth flow ਨੂੰ ਦੁਬਾਰਾ ਸ਼ੁਰੂ ਕਰਨ ਲਈ CLI ਤੋਂ `omniroute providers` ਚਲਾਓ, ਜਾਂ
- **Dashboard → Providers → Command Code → Reconnect** ਤੋਂ OAuth ਦੁਬਾਰਾ ਚਲਾਓ

### ModelScope ਬਹੁਤ ਆਕਰਮਕ 429 cooldowns ਵਾਪਸ ਕਰਦਾ ਹੈ

**ਲੱਛਣ:**

- ਬੇਨਤੀਆਂ ਦੇ ਇੱਕ ਛੋਟੇ burst ਤੋਂ ਬਾਅਦ ModelScope ਉੱਤੇ ਬਹੁਤ ਛੋਟੇ ਜਾਂ ਤੁਰੰਤ cooldowns
- Combo routing ਉਮੀਦ ਤੋਂ ਪਹਿਲਾਂ ModelScope ਨੂੰ ਛੱਡ ਦਿੰਦੀ ਹੈ

**ਕਾਰਨ:** ModelScope provider-ਵਿਸ਼ੇਸ਼ `Retry-After` headers ਭੇਜਦਾ ਹੈ। v3.8.0 ਵਿੱਚ ਇਨ੍ਹਾਂ headers ਲਈ ਸਮਰਪਿਤ handling ਸ਼ਾਮਲ ਹੈ, ਇਸ ਲਈ ਪੁਰਾਣੇ versions ਇਨ੍ਹਾਂ ਨੂੰ ਆਮ rate-limit hints ਵਜੋਂ ਗਲਤ ਪੜ੍ਹਦੇ ਹਨ।

**ਹੱਲ:**

- ਯਕੀਨੀ ਬਣਾਓ ਕਿ ਤੁਸੀਂ v3.8.0 ਜਾਂ ਇਸ ਤੋਂ ਬਾਅਦ ਵਾਲੇ version ਉੱਤੇ ਹੋ
- ਪੁਸ਼ਟੀ ਕਰੋ ਕਿ **Settings → Resilience** ਹੇਠਾਂ `useUpstream429BreakerHints` toggle ਚਾਲੂ ਹੈ

### production ਵਿੱਚ OMNIROUTE_WS_BRIDGE_SECRET ਮੌਜੂਦ ਨਹੀਂ ਹੈ

**ਲੱਛਣ:**

- remote production host ਉੱਤੇ ਚੱਲਦੇ ਸਮੇਂ ਹਰ Codex/Responses WebSocket bridge ਬੇਨਤੀ ਉੱਤੇ 401
- connect ਹੋਣ ਤੋਂ ਤੁਰੰਤ ਬਾਅਦ WebSocket bridge handshake ਬੰਦ ਹੋ ਜਾਂਦਾ ਹੈ

**ਕਾਰਨ:** production environment ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET` env var ਮੌਜੂਦ ਨਹੀਂ ਹੈ।

**ਹੱਲ:**

1. ਇੱਕ random secret ਬਣਾਓ: `openssl rand -hex 32`
2. production server env ਵਿੱਚ `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ਸੈੱਟ ਕਰੋ (ਅਤੇ bridge ਨਾਲ ਸੰਚਾਰ ਕਰਨ ਵਾਲੇ ਕਿਸੇ ਵੀ client ਵਿੱਚ ਵੀ)
3. OmniRoute ਨੂੰ ਮੁੜ ਚਾਲੂ ਕਰੋ

### Responses API: background mode ਨੂੰ synchronous ਵਿੱਚ ਘਟਾਇਆ ਗਿਆ

**ਲੱਛਣ:**

- log ਕੀਤੀ ਚੇਤਾਵਨੀ: `background mode degraded to synchronous`
- ਇੱਕ `background: true` ਬੇਨਤੀ background job handle ਦੀ ਬਜਾਏ ਇੱਕ ਆਮ synchronous response ਵਾਪਸ ਕਰਦੀ ਹੈ

**ਕਾਰਨ:** v3.8.0 ਜਾਣਬੁੱਝ ਕੇ Responses API ਉੱਤੇ `background: true` ਨੂੰ synchronous execution ਵਿੱਚ ਘਟਾਉਂਦਾ ਹੈ ਅਤੇ ਨਾਲ ਹੀ ਇੱਕ ਚੇਤਾਵਨੀ ਜਾਰੀ ਕਰਦਾ ਹੈ। ਪੂਰਾ async background execution ਭਵਿੱਖ ਵਿੱਚ ਪ੍ਰਦਾਨ ਕੀਤਾ ਜਾਵੇਗਾ।

**ਹੱਲ:**

- client ਨੂੰ `background` ਤੋਂ ਬਿਨਾਂ call ਕਰਨ ਲਈ ਵਿਵਸਥਿਤ ਕਰੋ, ਜਾਂ
- ਪੂਰਾ async background mode ਸ਼ਾਮਲ ਕਰਨ ਵਾਲੀ ਬਾਅਦ ਦੀ release ਦੀ ਉਡੀਕ ਕਰੋ (changelog ਨੂੰ ਟਰੈਕ ਕਰੋ)
