## ವಿವರವಾದ ದೋಷನಿವಾರಣೆ

---

### ಉಚಿತ ಪೂರೈಕೆದಾರರಲ್ಲಿನ ದರ ಮಿತಿ (429 / 400 / 401)

**ಲಕ್ಷಣ**: ಉಚಿತ/ದೃಢೀಕರಣವಿಲ್ಲದ ಪೂರೈಕೆದಾರರೊಂದಿಗೆ (opencode, auggie, ಇತ್ಯಾದಿ) `model: "auto"` ಬಳಸುವಾಗ, ಉತ್ತರಗಳ ಬದಲಿಗೆ ಆಗಾಗ್ಗೆ `HTTP 429`, `400`, ಅಥವಾ `401` ದೊರೆಯುತ್ತದೆ. ಸ್ವಲ್ಪ ಸಮಯದ ನಂತರ ಅದೇ ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ಮರುಪ್ರಯತ್ನಿಸಿದಾಗ ವಿನಂತಿಗಳು ಯಶಸ್ವಿಯಾಗುತ್ತವೆ, ಆದರೆ ಮೊದಲ ವೈಫಲ್ಯದಲ್ಲಿಯೇ ಸ್ವಯಂಚಾಲನೆ (cron ಕೆಲಸಗಳು, ಏಜೆಂಟ್ಗಳು, ಸ್ಕ್ರಿಪ್ಟ್ಗಳು) ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

**ಮೂಲ ಕಾರಣ**: ಮೂರು ಸ್ವತಂತ್ರ ವೈಫಲ್ಯ ವಿಧಾನಗಳು ಒಟ್ಟಾಗಿ ಪರಿಣಾಮ ಬೀರುತ್ತವೆ:

1. **ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿ (`429`)**: ಉಚಿತ ಶ್ರೇಣಿಗಳು ಪ್ರತಿ ಸಮಯಾವಧಿಗೆ ಕೋಟಾವನ್ನು ಜಾರಿಗೊಳಿಸಬಹುದು. ಸಮಾನಾಂತರ ಕರೆಗಳ ಹಠಾತ್ ಹೆಚ್ಚಳವು ಅದನ್ನು ಖಾಲಿಮಾಡುತ್ತದೆ, ಆದ್ದರಿಂದ ಸಮಯಾವಧಿ ಮರುಹೊಂದುವವರೆಗೆ ಮುಂದಿನ ವಿನಂತಿಯನ್ನು ನಿರಾಕರಿಸಲಾಗುತ್ತದೆ.
2. **ನೇರವರ್ಗಾವಣೆಯಲ್ಲಿನ ದೋಷಯುಕ್ತ ಮಾದರಿ (`400`/`401`)**: `auto/*` ಪೂಲ್ಗಳು `opencode` ನಿಂದ ಕ್ಯಾಟಲಾಗ್ನಲ್ಲಿ ನೋಂದಾಯಿಸಲಾದ, ಆದರೆ ಸಕ್ರಿಯ ರುಜುವಾತುಗಳಿಲ್ಲದ ನೇರವರ್ಗಾವಣೆ ಮಾದರಿಗಳನ್ನು ಒಳಗೊಂಡಿರಬಹುದು (ಉದಾ. `oc/north-mini-code-free` → `401`). ಸ್ವಯಂ-ರೂಟರ್ ಒಂದನ್ನು ಪ್ರಯತ್ನಿಸುತ್ತದೆ, ವಿಫಲಗೊಳ್ಳುತ್ತದೆ ಮತ್ತು ಪರ್ಯಾಯವು ಕಾರ್ಯಗತಗೊಳ್ಳುವ ಮೊದಲೇ ದೋಷವನ್ನು ಮುಂದಕ್ಕೆ ರವಾನಿಸಲಾಗುತ್ತದೆ.
3. **ಸಮಕಾಲೀನತೆ ವರ್ಧನೆ (ಲೋಡ್ನಡಿ `429`)**: ಅನೇಕ ಏಜೆಂಟ್/cron ಸೆಷನ್ಗಳು ಒಂದೇ ಸಮಯದಲ್ಲಿ `auto` ಅನ್ನು ಬಳಸಿದಾಗ, ಒಟ್ಟು ವಿನಂತಿ ದರವು ಉಚಿತ ಪೂರೈಕೆದಾರರು ಸಹಿಸಬಲ್ಲ ಮಿತಿಯನ್ನು ಮೀರುತ್ತದೆ, ಆದ್ದರಿಂದ ನ್ಯಾಯಸಮ್ಮತ ಕರೆಗಳನ್ನೂ ದುರುಪಯೋಗವೆಂದು ಗುರುತಿಸಲಾಗುತ್ತದೆ.

**ಪರಿಶೀಲಿಸಲಾದ ಪರಿಹಾರ (ಸಮುದಾಯದಿಂದ ವರದಿಯಾದದ್ದು, 2026-08-10)**: ರೊಟೇಶನ್, ಸಮಕಾಲೀನತೆ ಮತ್ತು ಪರ್ಯಾಯ ಕಾರ್ಯವಿಧಾನಗಳು ಉಚಿತ-ಶ್ರೇಣಿಯ ಏರಿಳಿತದಿಂದ ಸ್ಥಗಿತಗೊಳ್ಳುವ ಬದಲು ಅದನ್ನು ನಿಭಾಯಿಸುವಂತೆ ಮೂರು ಪರಿಸರ ಚರಾಂಶಗಳನ್ನು ಹೊಂದಿಸಿ:

```bash
export OMNIROUTE_ROTATE_ON_400=true           # 400/401 ಬಂದಾಗ ಮತ್ತೊಂದು ಮಾದರಿ/ಪೂರೈಕೆದಾರರಿಗೆ ಹೋಗಿ (ದೋಷಯುಕ್ತ ನೇರವರ್ಗಾವಣೆ ಮಾದರಿಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ)
export OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT=4   # ಭಾರೀ ವಿನಂತಿಗಳ ಪ್ರವೇಶಕ್ಕೆ ಸ್ಪಷ್ಟ ಗರಿಷ್ಠ ಮಿತಿ (ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಹೊಂದಿಸಲಾಗಿಲ್ಲ: ವಿನಂತಿ-ಎಣಿಕೆ ಮಿತಿಯಿಲ್ಲ, ಕೆಳಗಿನ ಟಿಪ್ಪಣಿ ನೋಡಿ)
export OMNIROUTE_CHAT_ADMISSION_QUEUE_MS=5000 # ತಕ್ಷಣದ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ 503 ಬದಲಿಗೆ ಭಾರೀ ಸಾಮರ್ಥ್ಯಕ್ಕಾಗಿ ಹೆಚ್ಚು ಸಮಯದ ಮಿತಿಯೊಳಗಿನ ಕಾಯುವಿಕೆ
```

ಇವುಗಳನ್ನು OmniRoute ಪ್ರಕ್ರಿಯೆಯ ಪರಿಸರದಲ್ಲಿ (ಡೀಮನ್ನಲ್ಲಿ, ಉದಾ. LaunchAgent plist ಅಥವಾ `systemctl edit` ಮೂಲಕ) ಹೊಂದಿಸಿ, ನಂತರ OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ. ರೊಟೇಶನ್ ಧ್ವಜವು ಅತ್ಯಂತ ಹೆಚ್ಚಿನ ಪರಿಣಾಮ ನೀಡುವ ಏಕೈಕ ಸಾಧನವಾಗಿದೆ: ಇದು ಗಂಭೀರ ವೈಫಲ್ಯವನ್ನು ಪೂಲ್ನಲ್ಲಿರುವ ಆರೋಗ್ಯಕರ ಪೂರೈಕೆದಾರರ ವಿರುದ್ಧ ಪಾರದರ್ಶಕ ಮರುಪ್ರಯತ್ನವಾಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ.

**ಟಿಪ್ಪಣಿ**: `OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT` ಒಂದೇ ಸಮಯದಲ್ಲಿ ಎಷ್ಟು ಭಾರೀ — ದೀರ್ಘ-ಸಂದರ್ಭದ — ವಿನಂತಿಗಳು ಚಲಿಸುತ್ತವೆ ಎಂಬುದನ್ನು ಮಿತಿಗೊಳಿಸುತ್ತದೆ; ಈ ಮಿತಿಯು ಪ್ರವೇಶ ದ್ವಾರವೇ ಹೊರತು ಪೂರೈಕೆದಾರರ ದರ ಮಿತಿಗಾರವಲ್ಲ. **#503-fanout ನವೀಕರಣ:** ಈ ಚರಾಂಶವನ್ನು ಇನ್ನು ಮುಂದೆ ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಹೊಂದಿಸಲಾಗುವುದಿಲ್ಲ (ಈಗ ಮೇಲೆ ತೋರಿಸಿದಂತೆ ಸ್ಪಷ್ಟವಾಗಿ ಕಾನ್ಫಿಗರ್ ಮಾಡಿದಾಗ ಮಾತ್ರ ಅದು ಅನ್ವಯಿಸುತ್ತದೆ) — ಬದಲಾಗಿ ಭಾರೀ ವಿನಂತಿಗಳ ಪ್ರವೇಶವನ್ನು ಹೋಸ್ಟ್ನ ನೈಜ ಮೆಮೊರಿ ಮಿತಿಗೆ ಅನುಗುಣವಾಗಿ ಸ್ವತಃ ಹೊಂದಿಕೊಳ್ಳುವ, ಸ್ವಯಂ-ನಿರ್ಧರಿತ ಬೈಟ್ ಬಜೆಟ್ (`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ನಿಯಂತ್ರಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಹೊಸ ನಿಯೋಜನೆಯು ಈ ಚರಾಂಶವನ್ನು ಹೊಂದಿಸದೆಯೇ ಬಹಳ ಕಡಿಮೆ `503 chat_admission_busy` ನಿರಾಕರಣೆಗಳನ್ನು ಕಾಣಬೇಕು; ಇಲ್ಲಿ ಅದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸುವುದು ಇನ್ನೂ ದಾಖಲಿಸಿದಂತೆಯೇ ನಿಖರವಾಗಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ. ಸ್ಪಷ್ಟ ಬೈಟ್-ಬಜೆಟ್ ಅತಿಕ್ರಮಣಗಳನ್ನು 8 MiB–2 GiB ವ್ಯಾಪ್ತಿಗೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ. `413 body_exceeds_budget` ತಾತ್ಕಾಲಿಕವಲ್ಲ: ಆ ಬೈಟ್ ಬಜೆಟ್ ಅನ್ನು ಹೆಚ್ಚಿಸಿ, `OMNIROUTE_CHAT_HARD_MAX_BODY_BYTES` ಅನ್ನು ಕಡಿಮೆ ಮಾಡಿ, ಅಥವಾ ಪ್ರಕ್ರಿಯೆಯ ಮೆಮೊರಿ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ. `inflight_bytes_budget` ಕಾರಣದ ಕೈಬಿಡುವಿಕೆಯು ತಾತ್ಕಾಲಿಕ ಸಂಪನ್ಮೂಲ ಪೈಪೋಟಿಯಾಗಿದ್ದು, ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾಗಿದೆ. ಪ್ರತಿ-ಪೂರೈಕೆದಾರ ದರ ಮಿತಿಯನ್ನು (`open-sse/services/rateLimitManager.ts`) `RATE_LIMIT_MAX_WAIT_MS`, `RATE_LIMIT_MAX_QUEUE_DEPTH`, ಮತ್ತು `RATE_LIMIT_AUTO_ENABLE` ಪ್ರತ್ಯೇಕವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತವೆ — `.env.example` ನೋಡಿ.

**ಇದು ಕೆಲಸ ಮಾಡಿದೆ ಎಂದು ಪರಿಶೀಲಿಸುವ ವಿಧಾನ**: ನಿಮ್ಮ ಏಜೆಂಟ್/cron ಅನ್ನು ತ್ವರಿತ ಅನುಕ್ರಮದಲ್ಲಿ ಎರಡು ಬಾರಿ ಚಲಾಯಿಸಿ ಮತ್ತು ಎರಡೂ ಯಶಸ್ವಿಯಾಗುವುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ. ಪರಿಹಾರಕ್ಕೆ ಮೊದಲು, ಎರಡನೇ ಚಾಲನೆಯು ಸಾಮಾನ್ಯವಾಗಿ `429`/`401` ಎಸೆಯುತ್ತದೆ. ಪರಿಹಾರದ ನಂತರ, ವೈಫಲ್ಯಗಳಿದ್ದರೆ ಅವುಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ ಮರುಪ್ರಯತ್ನಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಕರೆ ಪೂರ್ಣಗೊಳ್ಳುತ್ತದೆ. ನೀವು `curl /monitoring/health` ಅನ್ನು ಬಳಸಿಕೊಂಡು ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕಗಳಲ್ಲಿನ `rateLimitedUntil` ಕ್ಷೇತ್ರ ಮತ್ತು ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಪೂರೈಕೆದಾರರ `circuitBreakers.providerBreakers[].state` ಅನ್ನು ಗಮನಿಸಬಹುದು — ಸ್ಥಿತಿಯು `CLOSED`, `DEGRADED`, `OPEN`, ಅಥವಾ `HALF_OPEN` ಇವುಗಳಲ್ಲಿ ಒಂದಾಗಿರುತ್ತದೆ (`src/shared/utils/circuitBreaker.ts` ನೋಡಿ), ಮತ್ತು ನಿರಂತರವಾಗಿ ವಿಫಲಗೊಳ್ಳುವ ಪೂರೈಕೆದಾರರು ಮರುಹೊಂದಿಸುವ ಸಮಯಾವಧಿಯು ಪರೀಕ್ಷಾ ವಿನಂತಿಯನ್ನು ಅನುಮತಿಸುವ (`HALF_OPEN`) ಮೊದಲು `CLOSED → DEGRADED → OPEN` ಗೆ ಬದಲಾಗುತ್ತಾರೆ.

**ನಿಮಗೆ ಇನ್ನೂ 429 ಕಾಣಿಸಿದರೆ**: ಆ ಪೂರೈಕೆದಾರರ ಸಕ್ರಿಯ ಖಾತೆಯು ನಿಜವಾಗಿಯೂ ತನ್ನ _ಕೋಟಾ_ವನ್ನು (ಕೇವಲ ದರವನ್ನಲ್ಲ) ಸಂಪೂರ್ಣವಾಗಿ ಬಳಸಿದೆ. OmniRoute ಡ್ಯಾಶ್ಬೋರ್ಡ್ → Providers → Accounts ನಲ್ಲಿ ಅದೇ ಪೂರೈಕೆದಾರರಿಗಾಗಿ ಎರಡನೇ ಖಾತೆಯನ್ನು ಸೇರಿಸಿ, ಅಥವಾ ಮತ್ತೊಂದು ಉಚಿತ ಪೂರೈಕೆದಾರರನ್ನು (ಉದಾ. `routeway`, `auggie`) ಸೇರಿಸಿ. ರೊಟೇಶನ್ ತಾತ್ಕಾಲಿಕ ದರ/400/401 ಸಮಸ್ಯೆಗಳಿಗೆ ಮಾತ್ರ ಸಹಾಯ ಮಾಡುತ್ತದೆ; ಕೋಟಾ ಸಂಪೂರ್ಣವಾಗಿ ಖಾಲಿಯಾದರೆ ಎರಡನೇ ರುಜುವಾತು ಅಥವಾ ಬೇರೆ ಪೂರೈಕೆದಾರರು ಅಗತ್ಯವಿರುತ್ತಾರೆ.

**ದೃಶ್ಯ ಮಾದರಿಗಳಲ್ಲಿ (`auto/vision`, `bazaarlink/*`) 403 ಕಂಡುಬಂದರೆ**: ಸಂಪರ್ಕಿತ ಖಾತೆಯು ದೃಶ್ಯ ವೈಶಿಷ್ಟ್ಯವನ್ನು ಒಳಗೊಂಡ ಪಾವತಿಸಿದ ಯೋಜನೆಯನ್ನು ಹೊಂದಿಲ್ಲ, ಅಥವಾ API ಕೀಲಿಗೆ ಸಾಕಷ್ಟು ಅನುಮತಿಗಳಿಲ್ಲ. ಕೀಲಿಯ ವ್ಯಾಪ್ತಿಯು ದೃಶ್ಯ/ಬಹುಮಾಧ್ಯಮವನ್ನು ಒಳಗೊಂಡಿದೆ ಎಂಬುದನ್ನು ಪೂರೈಕೆದಾರರ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಲ್ಲಿ ಪರಿಶೀಲಿಸಿ, ಅಥವಾ ಪಾವತಿಸಿದ ಶ್ರೇಣಿಯ ಖಾತೆಯನ್ನು ಸಂಪರ್ಕಿಸಿ ಮತ್ತು ಅದನ್ನು ದೃಶ್ಯ ಗುರಿಯಾಗಿ ಇರಿಸಿಕೊಳ್ಳಿ.

## npm install ಎಚ್ಚರಿಕೆಗಳು (ERESOLVE / peer / deprecated)

ನೀವು `npm install -g omniroute` ಅನ್ನು ಚಲಾಯಿಸಿದಾಗ, `npm warn ERESOLVE`, peer-dependency ಸೂಚನೆಗಳು ಮತ್ತು `deprecated` ಸಂದೇಶಗಳಂತಹ ಎಚ್ಚರಿಕೆಗಳ ದೊಡ್ಡ ಪಟ್ಟಿಯನ್ನು ನೋಡಬಹುದು. **ಇವು ನಿರೀಕ್ಷಿತವಾಗಿದ್ದು, ಯಾವುದೇ ಹಾನಿಯುಂಟುಮಾಡುವುದಿಲ್ಲ.** ಔಟ್ಪುಟ್ನಲ್ಲಿ `added <N> packages` ಕಂಡುಬಂದರೆ ನಿಮ್ಮ ಇನ್ಸ್ಟಾಲೇಶನ್ ಯಶಸ್ವಿಯಾಗಿದೆ.

OmniRoute ನಿಯಂತ್ರಿಸದ ಮೂರನೇ-ಪಕ್ಷದ ಪ್ಯಾಕೇಜ್ಗಳಲ್ಲಿನ ಹಳತಾದ peer-dependency ಶ್ರೇಣಿಗಳಿಂದ ಈ ಎಚ್ಚರಿಕೆಗಳು ಬರುತ್ತವೆ:

1. **`marked-terminal` ಗೆ `marked >=1 <16` ಬೇಕು, ಆದರೆ `marked@18` ಕಂಡುಬಂದಿದೆ** — ಪ್ರಾಯೋಗಿಕವಾಗಿ ಸರಿಯಾಗಿ ಕೆಲಸ ಮಾಡುತ್ತದೆ; upstream peer ಶ್ರೇಣಿಯು ಕೇವಲ ಹಳತಾಗಿದೆ.
2. **`deprecated prebuild-install@7.1.3`** — ಇದು ಪರೋಕ್ಷ native-binary ಡೌನ್ಲೋಡ್ ಸಹಾಯಕವಾಗಿದೆ. ಪಿನ್ ಮಾಡಲಾದ `wreq-js` ಟ್ರಾನ್ಸ್ಪೋರ್ಟ್ ಬೈಂಡಿಂಗ್ ಅನ್ನು ಇನ್ಸ್ಟಾಲ್ ಮಾಡಲು ಇದನ್ನು
   ಬಳಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು web-cookie ಪೂರೈಕೆದಾರರ ಟ್ರಾನ್ಸ್ಪೋರ್ಟ್ ಸೆಟಪ್ ವಿಫಲವಾಗಿದೆ ಎಂಬುದನ್ನು ಇದು ಸೂಚಿಸುವುದಿಲ್ಲ.

**ಯಾವುದೇ ಕ್ರಮದ ಅಗತ್ಯವಿಲ್ಲ** — upstream ಪ್ಯಾಕೇಜ್ಗಳನ್ನು fork ಮಾಡದೆ ಈ ಎಚ್ಚರಿಕೆಗಳನ್ನು ಸಂಪೂರ್ಣವಾಗಿ ಮೌನಗೊಳಿಸಲು ಸಾಧ್ಯವಿಲ್ಲ.

## ಆಂಟಿವೈರಸ್ನ ತಪ್ಪು ಧನಾತ್ಮಕ ಪತ್ತೆಗಳು

<a name="antivirus-false-positives"></a>

### Avast/AVG, `README.md` ಅನ್ನು `MD:HttpRequest-inf[Susp]` ಎಂದು ಕ್ವಾರಂಟೈನ್ ಮಾಡುತ್ತದೆ

**ಇದು ತಪ್ಪು ಧನಾತ್ಮಕ ಪತ್ತೆ. ಯಾವುದಕ್ಕೂ ಸೋಂಕು ತಗುಲಿಲ್ಲ ಮತ್ತು ಯಾವುದೇ ಕ್ರಮ ಅಗತ್ಯವಿಲ್ಲ.**

ಹಲವಾರು HTTP ವಿನಂತಿಯಂತೆ ಕಾಣುವ ಲಿಂಕ್ಗಳನ್ನು ಹೊಂದಿರುವ ಸರಳ ಪಠ್ಯ/Markdown ಫೈಲ್ಗಳನ್ನು ಗುರುತಿಸುವ
ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು Avast ಮತ್ತು AVG ಬಳಸುತ್ತವೆ. OmniRoute ನ `README.md`, npm ಪ್ಯಾಕೇಜ್ನೊಳಗೆ
ಒಳಗೊಂಡಿರುತ್ತದೆ (ಇದನ್ನು `package.json` → `files` ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಲಾಗಿದೆ), ಆದ್ದರಿಂದ ಜಾಗತಿಕ
ಸ್ಥಾಪನೆಯಾಗುವಾಗ ಅದು `node_modules/omniroute/README.md` ನಲ್ಲಿ ಕಾಣಿಸಿಕೊಳ್ಳುತ್ತದೆ — ಮತ್ತು
ಅದು ಸುಮಾರು 15 `http://localhost:20128/...` ಉದಾಹರಣೆಗಳನ್ನು ಹೊಂದಿದೆ (MCP HTTP/SSE
ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು, A2A `.well-known` URL ಮತ್ತು `curl` ತುಣುಕುಗಳು). ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು
ಪ್ರಚೋದಿಸಲು ಅಷ್ಟೊಂದು ಲಿಂಕ್ ಸಾಂದ್ರತೆಯೇ ಸಾಕಾಗುತ್ತದೆ.

ಇದು ಇತ್ತೀಚೆಗಷ್ಟೇ ಪ್ರಾರಂಭವಾಗಿದ್ದರೆ: ಫೈಲ್ನ ಸ್ವರೂಪ ಬದಲಾಗಿಲ್ಲ. README ಯ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳ
ಕೋಷ್ಟಕ ವಿಸ್ತರಿಸಿದೆ (MCP HTTP + SSE + A2A ಸೇರಿಸಲಾಗಿದೆ) ಮತ್ತು ಇನ್ನಷ್ಟು `curl` ಉದಾಹರಣೆಗಳನ್ನು
ಸೇರಿಸಲಾಗಿದೆ; ಇದರಿಂದ ಅದು ಮಿತಿಯನ್ನು ಮೀರಿದೆ.

ಈ ಫೈಲ್ ಯಾವುದೇ ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದ ವಿಷಯವಿಲ್ಲದ ನಿಷ್ಕ್ರಿಯ ದಸ್ತಾವೇಜಾಗಿದೆ. ನೀವು ಅದನ್ನು
ಕ್ವಾರಂಟೈನ್ನಿಂದ ಸುರಕ್ಷಿತವಾಗಿ ಮರುಸ್ಥಾಪಿಸಬಹುದು.

**ಏನು ಮಾಡಬೇಕು:**

1. **ಅಧಿಸೂಚನೆಗಳನ್ನು ನಿಲ್ಲಿಸಿ** — ನಿಮ್ಮ ಆಂಟಿವೈರಸ್ನಲ್ಲಿ ಸ್ಥಾಪನಾ ಡೈರೆಕ್ಟರಿಯನ್ನು ಹೊರತುಪಡಿಸಿ
   (Avast: Settings → Exceptions), ನಿಮ್ಮ ಜಾಗತಿಕ `node_modules` ಪಥ ಮತ್ತು/ಅಥವಾ
   OmniRoute ಡೇಟಾ ಡೈರೆಕ್ಟರಿಯನ್ನು (`~/.omniroute/`) ಸೇರಿಸಿ.
2. **ತಪ್ಪು ಧನಾತ್ಮಕ ಪತ್ತೆಯನ್ನು ವರದಿ ಮಾಡಿ** — <https://www.avast.com/false-positive-file-form.php>,
   ಕ್ವಾರಂಟೈನ್ ಮಾಡಿದ `README.md` ಅನ್ನು ಲಗತ್ತಿಸಿ. ಪೂರೈಕೆದಾರರ ಹ್ಯೂರಿಸ್ಟಿಕ್ ಒಂದು ಪಠ್ಯ ಫೈಲ್ಗೆ
   ಅತಿಯಾಗಿ ಪ್ರತಿಕ್ರಿಯಿಸುತ್ತಿರುವುದರಿಂದ, ಎಲ್ಲರಿಗೂ ಸಹಾಯ ಮಾಡುವ ಪರಿಹಾರ ಇದಾಗಿದೆ.

**ನಮ್ಮ ಕಡೆಯಿಂದ ಇದನ್ನು ನಾವು ಏಕೆ "ಸರಿಪಡಿಸುವುದಿಲ್ಲ":** ಎಲ್ಲಾ ಉದಾಹರಣೆಗಳೂ `http://localhost`
ಆಗಿವೆ ಮತ್ತು ಸ್ವಯಂ-ಸಹಿ ಮಾಡಿದ ಪ್ರಮಾಣಪತ್ರದ ತೊಡಕು ಇಲ್ಲದೆ localhost ಅನ್ನು `https` ಮಾಡಲು
ಸಾಧ್ಯವಿಲ್ಲ. ಒಬ್ಬ ಪೂರೈಕೆದಾರರ ಹ್ಯೂರಿಸ್ಟಿಕ್ನಿಂದ ತಪ್ಪಿಸಿಕೊಳ್ಳಲು ದಸ್ತಾವೇಜನ್ನು ವಿರೂಪಗೊಳಿಸುವುದು,
ಸ್ಕ್ಯಾನರ್ ದೋಷವನ್ನು ತೃಪ್ತಿಪಡಿಸುವ ಸಲುವಾಗಿ ಪ್ರತಿಯೊಬ್ಬ ಓದುಗರಿಗೂ ತೊಂದರೆ ಉಂಟುಮಾಡುತ್ತದೆ.

### Kaspersky, ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ ಅನ್ನು `PDM:Trojan.Win32.Generic` ಎಂದು ಗುರುತಿಸುತ್ತದೆ

**ಇದು ವರ್ತನಾ ಹ್ಯೂರಿಸ್ಟಿಕ್ನಿಂದ ಉಂಟಾದ ತಪ್ಪು ಧನಾತ್ಮಕ ಪತ್ತೆ. ಯಾವುದಕ್ಕೂ ಸೋಂಕು ತಗುಲಿಲ್ಲ.**
Kaspersky ಯ `PDM:` ಪೂರ್ವಪ್ರತ್ಯಯವು, ತಿಳಿದಿರುವ ಮಾಲ್ವೇರ್ಗೆ ಹೋಲಿಸಿ ಹೊಂದಾಣಿಕೆ ಮಾಡುವ ಬದಲು
ಸ್ಥಾಪಕವು _ಏನು ಮಾಡುತ್ತದೆ_ ಎಂಬುದನ್ನು ನಿರ್ಣಯಿಸುವ ಅದರ Proactive Defense Module (System Watcher)
ನಿಂದ ಈ ತೀರ್ಪು ಬಂದಿದೆ ಎಂದು ಸೂಚಿಸುತ್ತದೆ. ಇದು ಪ್ರಚೋದಿತವಾದಾಗ, Kaspersky ಸಂಪೂರ್ಣ ಸ್ಥಾಪನೆಯನ್ನು
"ಹಿಂದಕ್ಕೆ ತಿರುಗಿಸುತ್ತದೆ" — ಅದು ಈಗಾಗಲೇ ಬರೆದಿದ್ದ ಫೈಲ್ಗಳನ್ನು ಅಳಿಸುತ್ತದೆ — ಆದ್ದರಿಂದ ಆ್ಯಪ್
ದೋಷಪೂರಿತವಾಗುತ್ತದೆ ಅಥವಾ ಕಾಣೆಯಾಗುತ್ತದೆ.

ಇದು ಗುರುತಿಸುವ ಫೈಲ್ಗಳು ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ನೊಂದಿಗೆ ಬಂಡಲ್ ಮಾಡಲಾದ, ಘೋಷಿತ ಮುಕ್ತ-ಮೂಲದ
ಅವಲಂಬನೆಗಳ ಪ್ರಮಾಣಿತ ಭಾಗಗಳಾಗಿವೆ, ಉದಾಹರಣೆಗೆ:

- `resources/app/.build/next/node_modules/playwright-<hash>/lib/…/agentParser.js` ಮತ್ತು
  `workerProcessEntry.js` — ಆ್ಯಪ್ನೊಳಗಿನ ಪೂರೈಕೆದಾರ ಲಾಗಿನ್ ಮತ್ತು ಬ್ರೌಸರ್-ಆಧಾರಿತ ಚಾಟ್ಗಾಗಿ
  ಬಳಸಲಾಗುವ ಬ್ರೌಸರ್-ಸ್ವಯಂಚಾಲನಾ ಲೈಬ್ರರಿಯಾದ [Playwright](https://playwright.dev).
- `resources/app/.build/next/node_modules/@wreq-js/binding-win32-<arch>-msvc-<hash>/wreq-js.win32-<arch>-msvc.node`
  — ವೆಬ್-ಕುಕೀ ಪೂರೈಕೆದಾರರಲ್ಲಿ ಬ್ರೌಸರ್-ಫಿಂಗರ್ಪ್ರಿಂಟ್ ಮಾಡಿದ HTTP ಗಾಗಿ ಬಳಸುವ, ನಿರ್ದಿಷ್ಟ
  ಆವೃತ್ತಿಗೆ ಸ್ಥಿರಗೊಳಿಸಿದ `wreq-js` ನೇಟಿವ್ ಬೈಂಡಿಂಗ್ (`<arch>` ಎಂದರೆ `x64` ಅಥವಾ `arm64`).

**ಇದು ಏಕೆ ಪ್ರಚೋದಿತವಾಗುತ್ತದೆ:** Windows ಸ್ಥಾಪಕಕ್ಕೆ **ಇನ್ನೂ ಕೋಡ್ ಸಹಿ ಮಾಡಿಲ್ಲ**, ಆದ್ದರಿಂದ ಸಹಿ
ಮಾಡದ NSIS ಸ್ಥಾಪಕಕ್ಕೆ ಯಾವುದೇ ಪ್ರತಿಷ್ಠೆ ಇರುವುದಿಲ್ಲ ಮತ್ತು ವರ್ತನಾ ಹ್ಯೂರಿಸ್ಟಿಕ್ಗಳು ಗರಿಷ್ಠ
ಆಕ್ರಮಣಶೀಲತೆಯಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ. ಬಂಡಲ್ ಮಾಡಿದ ನೇಟಿವ್ DLL ಮತ್ತು
`%LOCALAPPDATA%\Programs\OmniRoute` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾದ ನೂರಾರು `.js` ಫೈಲ್ಗಳೊಂದಿಗೆ
(Next.js ಸ್ವತಂತ್ರ ಬಿಲ್ಡ್ನ ಹ್ಯಾಶ್-ಪ್ರತ್ಯಯ ಹೊಂದಿರುವ ಪ್ಯಾಕೇಜ್ ಡೈರೆಕ್ಟರಿಗಳೂ ಸೇರಿ), ಇದು
ಹ್ಯೂರಿಸ್ಟಿಕ್ ಅನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಕಾಗುತ್ತದೆ. ಕೋಡ್ ಸಹಿ ಮಾಡುವುದನ್ನು ಯೋಜಿಸಲಾಗಿದೆ; ಅದು
ಕಾರ್ಯಗತವಾಗುವವರೆಗೆ, ಹೊಸ ಬಿಡುಗಡೆಗಳಲ್ಲಿ ಇದು ಪುನರಾವರ್ತಿಸಬಹುದು.

**ಏನು ಮಾಡಬೇಕು:**

1. **ಮೊದಲು ನಿಮ್ಮ ಡೌನ್ಲೋಡ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ** (ಇದು ಫೈಲ್ನಲ್ಲಿ ಅನಧಿಕೃತ ಬದಲಾವಣೆ ಮಾಡಲಾಗಿದೆ
   ಎಂಬ ಸಾಧ್ಯತೆಯನ್ನು ತಳ್ಳಿಹಾಕುತ್ತದೆ). ಪ್ರತಿಯೊಂದು ಬಿಡುಗಡೆಯೂ `latest.yml` ಅನ್ನು ಪ್ರಕಟಿಸುತ್ತದೆ;
   ಅದರ `sha512` ಕ್ಷೇತ್ರವು (base64) `OmniRoute.Setup.<version>.exe` ಸ್ಥಾಪಕವನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ.
   PowerShell ನಲ್ಲಿ, ಸ್ಥಾಪಕವನ್ನು ಹೊಂದಿರುವ ಫೋಲ್ಡರ್ನಿಂದ:
   ```powershell
   $b = [System.Security.Cryptography.SHA512]::Create().ComputeHash(
     [System.IO.File]::ReadAllBytes("$PWD\OmniRoute.Setup.<version>.exe"))
   [Convert]::ToBase64String($b)
   ```
   ಔಟ್ಪುಟ್ `latest.yml` → `sha512` ಗೆ ಹೊಂದಿಕೆಯಾಗಬೇಕು. ಅದು ಹೊಂದಿಕೆಯಾಗದಿದ್ದರೆ, ಫೈಲ್ ಅನ್ನು
   ಅಳಿಸಿ ಮತ್ತು [GitHub releases page](https://github.com/diegosouzapw/OmniRoute/releases)
   ನಿಂದ ಮಾತ್ರ ಮತ್ತೊಮ್ಮೆ ಡೌನ್ಲೋಡ್ ಮಾಡಿ.
2. **ಮರುಸ್ಥಾಪಿಸಿ + ಹೊರತುಪಡಿಸಿ** — ಹಿಂದಕ್ಕೆ ತಿರುಗಿಸಲಾದ ಐಟಂಗಳನ್ನು ಕ್ವಾರಂಟೈನ್ನಿಂದ ಮರುಸ್ಥಾಪಿಸಿ
   ಮತ್ತು `%LOCALAPPDATA%\Programs\OmniRoute` ಗಾಗಿ ಹೊರತುಪಡಿಸುವಿಕೆಯನ್ನು ಸೇರಿಸಿ

   ಸಲ್ಲಿಸುವ FP ವರದಿಗಳು ಅನುಮತಿಪಟ್ಟಿಗೆ ಸೇರಿಸುವ ಪ್ರಕ್ರಿಯೆಯನ್ನು ನಿಜವಾಗಿಯೂ ವೇಗಗೊಳಿಸುತ್ತವೆ.

## Node.js ಹೊಂದಾಣಿಕೆ

<a name="nodejs-compatibility"></a>

### ಲಾಗಿನ್ ಪುಟ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ ಅಥವಾ "ಮಾಡ್ಯೂಲ್ ಸ್ವಯಂ-ನೋಂದಣಿ" ದೋಷವನ್ನು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** ನೀವು OmniRoute ಅನುಮೋದಿಸಿದ ಸುರಕ್ಷಿತ ರನ್ಟೈಮ್ನ ಕನಿಷ್ಠ ಆವೃತ್ತಿಯ ವ್ಯಾಪ್ತಿಯಿಂದ ಹೊರಗಿರುವ Node.js ಆವೃತ್ತಿಯನ್ನು ಚಲಾಯಿಸುತ್ತಿದ್ದೀರಿ. OmniRoute ಅಗತ್ಯಪಡಿಸುವ ಭದ್ರತಾ ಪ್ಯಾಚ್ನ ಕನಿಷ್ಠ ಆವೃತ್ತಿಗಿಂತ ಹಳೆಯದಾದ Node 22 ಅಥವಾ 24 ಪ್ಯಾಚ್ ಆವೃತ್ತಿಯನ್ನು ಚಲಾಯಿಸುವುದು ಅತ್ಯಂತ ಸಾಮಾನ್ಯ ಸಂದರ್ಭವಾಗಿದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಲಾಗಿನ್ ಪುಟವು ಖಾಲಿ ಪರದೆ ಅಥವಾ ಸರ್ವರ್ ದೋಷವನ್ನು ತೋರಿಸುತ್ತದೆ
- ಕನ್ಸೋಲ್ನಲ್ಲಿ `Error: Module did not self-register` ಅಥವಾ ಅದೇ ರೀತಿಯ ಸ್ಥಳೀಯ ಬೈಂಡಿಂಗ್ ದೋಷಗಳು ಕಾಣಿಸುತ್ತವೆ
- ರನ್ಟೈಮ್ ಬೆಂಬಲಿತ ಸುರಕ್ಷತಾ ನೀತಿಯ ವ್ಯಾಪ್ತಿಯಿಂದ ಹೊರಗಿದ್ದರೆ, ಲಾಗಿನ್ ಪುಟವು ನಿಮ್ಮ Node ಆವೃತ್ತಿಯೊಂದಿಗೆ **ಕಿತ್ತಳೆ ಬಣ್ಣದ ಎಚ್ಚರಿಕೆ ಬ್ಯಾನರ್** ಅನ್ನು ತೋರಿಸುತ್ತದೆ

**ಪರಿಹಾರ:**

1. ಬೆಂಬಲಿತ Node.js LTS ಬಿಡುಗಡೆಯನ್ನು ಸ್ಥಾಪಿಸಿ (ಶಿಫಾರಸು: Node.js 24.x):
   ```bash
   nvm install 24
   nvm use 24
   ```
2. ನಿಮ್ಮ ಆವೃತ್ತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ: `node --version` 24.x LTS ಶ್ರೇಣಿಯಲ್ಲಿ `v24.0.0` ಅಥವಾ ಅದಕ್ಕಿಂತ ಹೊಸ ಆವೃತ್ತಿಯನ್ನು ತೋರಿಸಬೇಕು
3. OmniRoute ಅನ್ನು ಮರುಸ್ಥಾಪಿಸಿ: `npm install -g omniroute`
4. ಮರುಪ್ರಾರಂಭಿಸಿ: `omniroute`

> **ಬೆಂಬಲಿತ ಸುರಕ್ಷಿತ ಆವೃತ್ತಿಗಳು:** `>=22.22.2 <23` ಅಥವಾ `>=24.0.0 <27`. Node.js 24.x LTS (Krypton) ಮತ್ತು Node.js 26 ಸಂಪೂರ್ಣವಾಗಿ ಬೆಂಬಲಿತವಾಗಿವೆ.

### npm v11+: `better-sqlite3` ಸ್ಥಾಪನೆಯಾಗಿಲ್ಲ (ಮಾಡ್ಯೂಲ್ ಕಂಡುಬಂದಿಲ್ಲ)

<a name="npm-v11-better-sqlite3-not-installed-cannot-find-module"></a>

**ಕಾರಣ:** npm v11 (Node.js 24+ ಜೊತೆಗೆ ಒದಗಿಸಲಾಗುತ್ತದೆ) ಐಚ್ಛಿಕ
ಅವಲಂಬನೆಗಳ ಸ್ಥಾಪನಾ ಸ್ಕ್ರಿಪ್ಟ್ಗಳನ್ನು ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ನಿರ್ಬಂಧಿಸುತ್ತದೆ. `better-sqlite3` ಅನ್ನು `optionalDependencies` ನಲ್ಲಿ ಪಟ್ಟಿ ಮಾಡಿರುವುದರಿಂದ
ಮತ್ತು ಅದಕ್ಕೆ ಸ್ಥಳೀಯ ಕಂಪೈಲೇಶನ್ (`node-gyp rebuild`) ಅಗತ್ಯವಿರುವುದರಿಂದ, npm ಯಾವುದೇ ಸೂಚನೆಯಿಲ್ಲದೆ ಅದನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಪ್ರಾರಂಭಿಸುವಾಗ ಸರ್ವರ್ `Cannot find module 'better-sqlite3'` ದೋಷದೊಂದಿಗೆ ಕ್ರ್ಯಾಶ್ ಆಗುತ್ತದೆ
- `ls node_modules/better-sqlite3` "ಅಂತಹ ಫೈಲ್ ಅಥವಾ ಡೈರೆಕ್ಟರಿ ಇಲ್ಲ" ಎಂದು ತೋರಿಸುತ್ತದೆ
- `npm ls better-sqlite3` `(empty)` ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಪರಿಹಾರ:**

1. ಸ್ಥಾಪನಾ ಸ್ಕ್ರಿಪ್ಟ್ಗಳನ್ನು ಅನುಮೋದಿಸಿ ಮತ್ತು ಮರುಸ್ಥಾಪಿಸಿ:
   ```bash
   npm approve-scripts better-sqlite3
   npm install
   ```
2. ಅಥವಾ ಮೊದಲೇ ನಿರ್ಮಿಸಲಾದ ಪ್ಯಾಕೇಜ್ ಅನ್ನು ಕೈಯಾರೆ ಸ್ಥಾಪಿಸಿ:
   ```bash
   npm pack better-sqlite3@13.0.1
   tar -xzf better-sqlite3-*.tgz -C node_modules
   mv node_modules/package node_modules/better-sqlite3
   rm better-sqlite3-*.tgz
   ```
3. ಅದು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ: `node -e "require('better-sqlite3')(':memory:').close(); console.log('OK')"`

### macOS: `dlopen` / "ಸ್ಲೈಸ್ ಮಾನ್ಯವಾದ mach-o ಫೈಲ್ ಅಲ್ಲ"

<a name="macos-native-module-rebuild"></a>

**ಕಾರಣ:** ಜಾಗತಿಕ `npm install -g omniroute` ಸ್ಥಾಪನೆಯ ನಂತರ, ಪ್ಯಾಕೇಜ್ನೊಳಗಿನ `better-sqlite3` ಸ್ಥಳೀಯ ಬೈನರಿಯನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸುತ್ತಿರುವ ಆರ್ಕಿಟೆಕ್ಚರ್ ಅಥವಾ Node.js ABI ಗಿಂತ ಬೇರೆಯದಕ್ಕಾಗಿ ಕಂಪೈಲ್ ಮಾಡಿರಬಹುದು. ಮೊದಲೇ ನಿರ್ಮಿಸಲಾದ ಬೈನರಿ ನಿಮ್ಮ ಪರಿಸರಕ್ಕೆ ಹೊಂದಿಕೆಯಾಗದಿದ್ದಾಗ, macOSನಲ್ಲಿ (Apple Silicon ಮತ್ತು Intel ಎರಡರಲ್ಲೂ) ಇದು ಸಾಮಾನ್ಯವಾಗಿ ಸಂಭವಿಸುತ್ತದೆ.

**ಲಕ್ಷಣಗಳು:**

- ಪ್ರಾರಂಭಿಸುವಾಗ ಸರ್ವರ್ ತಕ್ಷಣವೇ `dlopen` ದೋಷದೊಂದಿಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- ದೋಷವು `slice is not valid mach-o file` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ
- ಸಂಪೂರ್ಣ ಉದಾಹರಣೆ:

```
dlopen(/Users/<user>/.nvm/versions/node/v24.14.1/lib/node_modules/omniroute/app/node_modules/better-sqlite3/build/Release/better_sqlite3.node, 0x0001): tried: '...' (slice is not valid mach-o file)
```

**ಪರಿಹಾರ — ನಿಮ್ಮ ಸ್ಥಳೀಯ ಪರಿಸರಕ್ಕಾಗಿ ಮರುನಿರ್ಮಿಸಿ (Node.js ಆವೃತ್ತಿಯನ್ನು ಕೆಳಗಿಳಿಸುವ ಅಗತ್ಯವಿಲ್ಲ):**

```bash
cd $(npm root -g)/omniroute/app
npm rebuild better-sqlite3
omniroute
```

> **ಗಮನಿಸಿ:** ಇದು ನಿಮ್ಮ ಸ್ಥಳೀಯ Node.js ಆವೃತ್ತಿ ಮತ್ತು CPU ಆರ್ಕಿಟೆಕ್ಚರ್ಗೆ ಅನುಗುಣವಾಗಿ ಸ್ಥಳೀಯ ಬೈಂಡಿಂಗ್ ಅನ್ನು ಮರುಕಂಪೈಲ್ ಮಾಡಿ, ಬೈನರಿ ಅಸಾಮರಸ್ಯವನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. ಅಧಿಕೃತವಾಗಿ ಬೆಂಬಲಿತ ರನ್ಟೈಮ್ ವ್ಯಾಪ್ತಿಯು **`>=22.22.2 <23` ಅಥವಾ `>=24.0.0 <27`** ಆಗಿದೆ (`src/shared/utils/nodeRuntimeSupport.ts` ನಲ್ಲಿರುವ `SUPPORTED_NODE_RANGE`, `package.json` ನ `engines` ಕ್ಷೇತ್ರದೊಂದಿಗೆ ಹೊಂದಿಸಲಾಗಿದೆ). Node.js 24.x LTS (Krypton) ಮತ್ತು Node.js 26 ಅನ್ನು `better-sqlite3` v12.x ಜೊತೆಗೆ ಸಂಪೂರ್ಣವಾಗಿ ಬೆಂಬಲಿಸಲಾಗುತ್ತದೆ.

## ಪ್ರಾಕ್ಸಿ ಸಮಸ್ಯೆಗಳು

<a name="proxy-issues"></a>

### ಪೂರೈಕೆದಾರರ ಮೌಲ್ಯೀಕರಣವು "fetch failed" ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** API ಕೀ ಮೌಲ್ಯೀಕರಣ ಎಂಡ್ಪಾಯಿಂಟ್ (`POST /api/providers/validate`) ಈ ಹಿಂದೆ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಬಿಟ್ಟುಹೋಗುತ್ತಿತ್ತು, ಇದರಿಂದ ಪ್ರಾಕ್ಸಿ ರೂಟಿಂಗ್ ಅಗತ್ಯವಿರುವ ಪರಿಸರಗಳಲ್ಲಿ ವೈಫಲ್ಯಗಳು ಉಂಟಾಗುತ್ತಿದ್ದವು.

**ಪರಿಹಾರ (v3.5.5+):** ಇದನ್ನು ಈಗ ಸರಿಪಡಿಸಲಾಗಿದೆ. ಪೂರೈಕೆದಾರರ ಮೌಲ್ಯೀಕರಣವು `runWithProxyContext` ಮೂಲಕ ರೂಟ್ ಆಗುತ್ತದೆ ಮತ್ತು ಪೂರೈಕೆದಾರ-ಮಟ್ಟದ ಹಾಗೂ ಜಾಗತಿಕ ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಪಾಲಿಸುತ್ತದೆ.

### ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನೆಯು "fetch failed" ದೋಷದೊಂದಿಗೆ ವಿಫಲವಾಗುತ್ತದೆ

**ಕಾರಣ:** ಹಿನ್ನೆಲೆಯ OAuth ಟೋಕನ್ ರಿಫ್ರೆಶ್ ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೂ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸುತ್ತಿರಲಿಲ್ಲ.

**ಪರಿಹಾರ (v3.5.5+):** ಟೋಕನ್ ಆರೋಗ್ಯ ಪರಿಶೀಲನೆ ಶೆಡ್ಯೂಲರ್ ಈಗ ರಿಫ್ರೆಶ್ ಮಾಡಲು ಪ್ರಯತ್ನಿಸುವ ಮೊದಲು ಪ್ರತಿ ಸಂಪರ್ಕಕ್ಕೂ ಪ್ರಾಕ್ಸಿ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸುತ್ತದೆ. v3.5.5+ ಗೆ ನವೀಕರಿಸಿ.

### SOCKS5 ಪ್ರಾಕ್ಸಿಯು "invalid onRequestStart method" ದೋಷವನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ

**ಕಾರಣ:** Node.js 22 ನಲ್ಲಿ, undici@8 ಡಿಸ್ಪ್ಯಾಚರ್ Node ನ ಅಂತರ್ನಿರ್ಮಿತ `fetch()` ಅನುಷ್ಠಾನದೊಂದಿಗೆ ಹೊಂದಿಕೆಯಾಗುವುದಿಲ್ಲ.

**ಪರಿಹಾರ (v3.5.5+):** ಪ್ರಾಕ್ಸಿ ಡಿಸ್ಪ್ಯಾಚರ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ OmniRoute ಈಗ undici ಯ ಸ್ವಂತ `fetch()` ಫಂಕ್ಷನ್ ಅನ್ನು ಬಳಸುತ್ತದೆ, ಇದರಿಂದ ಸ್ಥಿರವಾದ ವರ್ತನೆ ಖಚಿತವಾಗುತ್ತದೆ. v3.5.5+ ಗೆ ನವೀಕರಿಸಿ.

### WSL ಅಡಿಯಲ್ಲಿನ MITM ಪ್ರಾಕ್ಸಿ: Windows ಹೋಸ್ಟ್ನಲ್ಲಿರುವ ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳನ್ನು ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡಲಾಗುವುದಿಲ್ಲ

**ಕಾರಣ:** MITM ಪ್ರಾಕ್ಸಿ ಮತ್ತು ಅದರ CA ಪ್ರಮಾಣಪತ್ರವು OmniRoute ಚಾಲನೆಯಾಗುವ ಪರಿಸರದಲ್ಲಿ ಸ್ಥಾಪನೆಯಾಗುತ್ತವೆ. WSL ಅಡಿಯಲ್ಲಿ ಆ ಪರಿಸರವು Linux ಗೆಸ್ಟ್ ಆಗಿರುತ್ತದೆ, ಆದರೆ AI ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳು (Kiro, Trae, Copilot, Zed, …) Windows ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಾಲನೆಯಾಗುತ್ತವೆ. ಹೋಸ್ಟ್ ಆ್ಯಪ್ಗಳು ಗೆಸ್ಟ್ನ ಪ್ರಮಾಣಪತ್ರ ಸ್ಟೋರ್ ಅನ್ನು ನಂಬುವುದಿಲ್ಲ ಮತ್ತು ಗೆಸ್ಟ್ನ ಸಿಸ್ಟಮ್ ಪ್ರಾಕ್ಸಿ ಮೂಲಕ ರೂಟ್ ಆಗುವುದಿಲ್ಲ, ಆದ್ದರಿಂದ ಅಲ್ಲಿ ಡೆಸ್ಕ್ಟಾಪ್ ಇಂಟರ್ಸೆಪ್ಷನ್ ಸಕ್ರಿಯವಾಗುವುದಿಲ್ಲ.

**ಶಿಫಾರಸು:** ನೀವು ಇಂಟರ್ಸೆಪ್ಟ್ ಮಾಡಲು ಬಯಸುವ ಡೆಸ್ಕ್ಟಾಪ್ ಆ್ಯಪ್ಗಳು ಇರುವ ಅದೇ OS ನಲ್ಲಿ OmniRoute ಅನ್ನು ಸ್ಥಳೀಯವಾಗಿ ಚಲಾಯಿಸಿ (Windows ಆ್ಯಪ್ಗಳಿಗೆ Windows; macOS/Linux ಗೂ ಇದೇ ಅನ್ವಯಿಸುತ್ತದೆ). ಹೋಸ್ಟ್ ಆ್ಯಪ್ಗಳನ್ನು ಗುರಿಯಾಗಿಸಿಕೊಂಡು OmniRoute ಅನ್ನು WSL ಒಳಗೆ ಇಟ್ಟುಕೊಳ್ಳುವುದಕ್ಕೆ, ರಚಿಸಲಾದ CA ಪ್ರಮಾಣಪತ್ರವನ್ನು Windows ಹೋಸ್ಟ್ನಲ್ಲಿ ಕೈಯಾರೆ ವಿಶ್ವಾಸಾರ್ಹಗೊಳಿಸುವುದು ಮತ್ತು ಪ್ರತಿ ಹೋಸ್ಟ್ ಆ್ಯಪ್ನ ನೆಟ್ವರ್ಕ್/ಪ್ರಾಕ್ಸಿ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು WSL ಪ್ರಾಕ್ಸಿ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಸೂಚಿಸುವುದು ಅಗತ್ಯವಿರುತ್ತದೆ — ಇದು ಬೆಂಬಲವಿಲ್ಲದ, ಸುಲಭವಾಗಿ ವಿಫಲವಾಗಬಹುದಾದ ಸೆಟಪ್ ಆಗಿದೆ.

## ಪೂರೈಕೆದಾರರ ಸಮಸ್ಯೆಗಳು

### "Language model did not provide messages"

**ಕಾರಣ:** ಪೂರೈಕೆದಾರರ ಕೋಟಾ ಖಾಲಿಯಾಗಿದೆ.

**ಪರಿಹಾರ:**

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ನ ಕೋಟಾ ಟ್ರ್ಯಾಕರ್ ಪರಿಶೀಲಿಸಿ
2. ಫಾಲ್ಬ್ಯಾಕ್ ಹಂತಗಳನ್ನು ಹೊಂದಿರುವ ಕಾಂಬೊ ಬಳಸಿ
3. ಕಡಿಮೆ ವೆಚ್ಚದ/ಉಚಿತ ಹಂತಕ್ಕೆ ಬದಲಿಸಿ

### ದರ ಮಿತಿಗೊಳಿಸುವಿಕೆ

**ಕಾರಣ:** ಚಂದಾದಾರಿಕೆ ಕೋಟಾ ಖಾಲಿಯಾಗಿದೆ.

**ಪರಿಹಾರ:**

- ಫಾಲ್ಬ್ಯಾಕ್ ಸೇರಿಸಿ: `cc/claude-opus-4-6 → glm/glm-4.7 → if/qwen3.8-max-preview`
- ಕಡಿಮೆ ವೆಚ್ಚದ ಬ್ಯಾಕಪ್ ಆಗಿ GLM/MiniMax ಬಳಸಿ

### OAuth ಟೋಕನ್ ಅವಧಿ ಮುಗಿದಿದೆ

OmniRoute ಟೋಕನ್ಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ರಿಫ್ರೆಶ್ ಮಾಡುತ್ತದೆ. ಸಮಸ್ಯೆಗಳು ಮುಂದುವರಿದರೆ:

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರ → ಮರುಸಂಪರ್ಕಿಸಿ
2. ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವನ್ನು ಅಳಿಸಿ ಮತ್ತು ಮರುಸೇರಿಸಿ

### Kiro ಬಹು-ಖಾತೆ: ಎರಡನೇ ಖಾತೆಯು ಮೊದಲನೆಯದನ್ನು ಅಮಾನ್ಯಗೊಳಿಸುತ್ತದೆ

**ಕಾರಣ:** Kiro ನ ಬ್ಯಾಕೆಂಡ್ ಪ್ರತಿ OIDC ಕ್ಲೈಂಟ್ ನೋಂದಣಿಗೆ ಒಂದೇ ಸಕ್ರಿಯ ಸೆಷನ್ ಅನ್ನು ಕಡ್ಡಾಯಗೊಳಿಸುತ್ತದೆ.
ಎರಡು ಖಾತೆಗಳು ಒಂದೇ ನೋಂದಾಯಿತ ಕ್ಲೈಂಟ್ ಅನ್ನು ಹಂಚಿಕೊಂಡಾಗ (v3.8.0 ಕ್ಕಿಂತ ಮೊದಲು ಆಮದು ಮಾಡಿದ ಸಂಪರ್ಕಗಳು),
ಒಂದು ಖಾತೆಯ ಟೋಕನ್ ಅನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವುದರಿಂದ ಮತ್ತೊಂದು ಖಾತೆಯ ರಿಫ್ರೆಶ್ ಟೋಕನ್ ಅಮಾನ್ಯಗೊಳ್ಳುತ್ತದೆ.

**ಪರಿಹಾರ (v3.8.0+):** ಪರಿಣಾಮಕ್ಕೊಳಗಾದ ಸಂಪರ್ಕಗಳನ್ನು ಮರು-ಆಮದು ಮಾಡಿ.
v3.8.0 ರಿಂದ ಪ್ರಾರಂಭಿಸಿ, **ಟೋಕನ್ ಆಮದು**, **Google/GitHub ಸಾಮಾಜಿಕ ಲಾಗಿನ್**,
ಅಥವಾ **ಸ್ವಯಂ-ಆಮದು** ಮೂಲಕ ರಚಿಸಲಾದ ಪ್ರತಿಯೊಂದು ಹೊಸ Kiro ಸಂಪರ್ಕವೂ ತನ್ನದೇ ಆದ
ಮೀಸಲಾದ OIDC ಕ್ಲೈಂಟ್ ಅನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ನೋಂದಾಯಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಸಂಪರ್ಕವು ಸಂಪೂರ್ಣವಾಗಿ ಪ್ರತ್ಯೇಕವಾಗಿರುತ್ತದೆ ಮತ್ತು ಒಂದು
ಖಾತೆಯನ್ನು ರಿಫ್ರೆಶ್ ಮಾಡುವುದರಿಂದ ಬೇರೆ ಯಾವುದೇ ಖಾತೆಯ ಮೇಲೆ ಪರಿಣಾಮ ಬೀರುವುದಿಲ್ಲ.

v3.8.0 ಕ್ಕಿಂತ _ಮೊದಲು_ ಆಮದು ಮಾಡಿದ ಸಂಪರ್ಕಗಳು ಪ್ರತಿ-ಸಂಪರ್ಕದ ಕ್ಲೈಂಟ್
ನೋಂದಣಿಯನ್ನು ಹೊಂದಿರುವುದಿಲ್ಲ. ಆ ಸಂಪರ್ಕಗಳು ಹಂಚಿಕೆಯ ಸಾಮಾಜಿಕ-ದೃಢೀಕರಣ ರಿಫ್ರೆಶ್ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಳಸುವುದನ್ನು ಮುಂದುವರಿಸುತ್ತವೆ.
ಪ್ರತ್ಯೇಕತೆಯನ್ನು ಪಡೆಯಲು, ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು ವಿಭಾಗದಿಂದ ಹಳೆಯ ಸಂಪರ್ಕವನ್ನು ಅಳಿಸಿ ಮತ್ತು
ಮೂರು ಆಮದು ಪ್ರಕ್ರಿಯೆಗಳಲ್ಲಿ ಯಾವುದಾದರೂ ಒಂದರ ಮೂಲಕ ಅದನ್ನು ಮರುಸೇರಿಸಿ.

ಎರಡು Kiro ಖಾತೆಗಳನ್ನು ಅಕ್ಕಪಕ್ಕದಲ್ಲಿ ಸೇರಿಸುವ ಸಂಪೂರ್ಣ ವಿವರಗಳು ಮತ್ತು ಹಂತ-ಹಂತದ ಸೂಚನೆಗಳಿಗಾಗಿ,
[`docs/guides/KIRO_SETUP.md`](./KIRO_SETUP.md) ನೋಡಿ.

## ಕ್ಲೌಡ್ ಸಮಸ್ಯೆಗಳು

### ಕ್ಲೌಡ್ ಸಿಂಕ್ ದೋಷಗಳು

1. `BASE_URL` ನಿಮ್ಮ ಚಾಲನೆಯಲ್ಲಿರುವ ಇನ್ಸ್ಟೆನ್ಸ್ಗೆ ಸೂಚಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (ಉದಾ., `http://localhost:20128`)
2. `CLOUD_URL` ನಿಮ್ಮ ಕ್ಲೌಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ಗೆ ಸೂಚಿಸುತ್ತಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ (ಉದಾ., `https://omniroute.dev`)
3. `NEXT_PUBLIC_*` ಮೌಲ್ಯಗಳನ್ನು ಸರ್ವರ್-ಸೈಡ್ ಮೌಲ್ಯಗಳೊಂದಿಗೆ ಹೊಂದಾಣಿಕೆಯಲ್ಲಿ ಇರಿಸಿ

### ಕ್ಲೌಡ್ನಲ್ಲಿ `stream=false` ಬಳಸಿದಾಗ 500 ಮರಳುತ್ತದೆ

**ಲಕ್ಷಣ:** ಸ್ಟ್ರೀಮಿಂಗ್ ಅಲ್ಲದ ಕರೆಗಳಿಗೆ ಕ್ಲೌಡ್ ಎಂಡ್ಪಾಯಿಂಟ್ನಲ್ಲಿ `Unexpected token 'd'...` ಕಾಣಿಸುತ್ತದೆ.

**ಕಾರಣ:** ಕ್ಲೈಂಟ್ JSON ನಿರೀಕ್ಷಿಸುತ್ತಿರುವಾಗ ಅಪ್ಸ್ಟ್ರೀಮ್ SSE ಪೇಲೋಡ್ ಅನ್ನು ಮರಳಿಸುತ್ತದೆ.

**ತಾತ್ಕಾಲಿಕ ಪರಿಹಾರ:** ಕ್ಲೌಡ್ಗೆ ನೇರ ಕರೆಗಳಿಗಾಗಿ `stream=true` ಬಳಸಿ. ಸ್ಥಳೀಯ ರನ್ಟೈಮ್ SSE→JSON ಫಾಲ್ಬ್ಯಾಕ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ.

### ಕ್ಲೌಡ್ ಸಂಪರ್ಕಗೊಂಡಿದೆ ಎಂದು ಹೇಳುತ್ತದೆ, ಆದರೆ "ಅಮಾನ್ಯ API ಕೀ" ತೋರಿಸುತ್ತದೆ

1. ಸ್ಥಳೀಯ ಡ್ಯಾಶ್ಬೋರ್ಡ್ನಿಂದ (`/api/keys`) ಹೊಸ ಕೀ ರಚಿಸಿ
2. ಕ್ಲೌಡ್ ಸಿಂಕ್ ಚಲಾಯಿಸಿ: ಕ್ಲೌಡ್ ಸಕ್ರಿಯಗೊಳಿಸಿ → ಈಗ ಸಿಂಕ್ ಮಾಡಿ
3. ಹಳೆಯ/ಸಿಂಕ್ ಮಾಡದ ಕೀಗಳು ಕ್ಲೌಡ್ನಲ್ಲಿ ಇನ್ನೂ `401` ಅನ್ನು ಮರಳಿಸಬಹುದು

## Docker ಸಮಸ್ಯೆಗಳು

### Docker IPv6 / ಸಂಪರ್ಕ ಮರುಹೊಂದಿಕೆ

<a name="docker-ipv6"></a>

**ಲಕ್ಷಣಗಳು:** `curl http://localhost:20128/v1/models` ಅನ್ನು ಚಲಾಯಿಸಿದಾಗ `curl: (56) Recv failure: Connection reset by peer` ಮರಳುತ್ತದೆ. ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಮತ್ತು ದೃಢೀಕರಣ ಅಗತ್ಯವಿಲ್ಲದ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತವೆ, ಆದರೆ ದೃಢೀಕೃತ ಎಂಡ್ಪಾಯಿಂಟ್ಗಳು ವಿಫಲವಾಗುತ್ತವೆ — ಇದು ದೃಢೀಕರಣದ ಸಮಸ್ಯೆಯಂತೆ ಕಾಣಿಸಿದರೂ ವಾಸ್ತವದಲ್ಲಿ ಹಾಗಲ್ಲ.

**ಕಾರಣ:** `docker run -p 20128:20128` ಎರಡೂ `0.0.0.0` (IPv4) ಮತ್ತು `::` (IPv6) ಮೇಲೆ ಪಬ್ಲಿಷ್ ಮಾಡುತ್ತದೆ, ಆದರೆ ಕಂಟೇನರ್ನೊಳಗಿನ ಪ್ರಕ್ರಿಯೆಯು IPv4 ಮೇಲೆ ಮಾತ್ರ ಆಲಿಸುತ್ತದೆ. `localhost` ಮೊದಲು `::1` ಗೆ ರೆಸಾಲ್ವ್ ಆಗುವ ಹೋಸ್ಟ್ಗಳಲ್ಲಿ, ಸಂಪರ್ಕವು ಅದರ ಹಿಂದೆ ಯಾವುದೇ ಲಿಸನರ್ ಇಲ್ಲದ IPv6 ಪಬ್ಲಿಷ್ ಮಾಡಿದ ಪೋರ್ಟ್ಗೆ ತಲುಪುತ್ತದೆ → ಸಂಪರ್ಕ ಮರುಹೊಂದಿಕೆಯಾಗುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. **ತ್ವರಿತ ರೋಗನಿರ್ಣಯ:** `curl -4 http://localhost:20128/v1/models` ಅನ್ನು ಚಲಾಯಿಸಿ. ಇದು `-4` ಜೊತೆಗೆ ಕಾರ್ಯನಿರ್ವಹಿಸಿ, ಅದಿಲ್ಲದೆ ವಿಫಲವಾದರೆ, ನಿಮ್ಮಲ್ಲಿ IPv6 ಬೈಂಡ್ ಅಸಾಮರಸ್ಯವಿದೆ.
2. **ಶಾಶ್ವತ ಪರಿಹಾರ:** ನಿಮ್ಮ `docker run` ಕಮಾಂಡ್ನಲ್ಲಿ `-p 127.0.0.1:20128:20128` ಬಳಸುವ ಮೂಲಕ IPv4 ಗೆ ಸ್ಪಷ್ಟವಾಗಿ ಬೈಂಡ್ ಮಾಡಿ:
   ```bash
   docker run -d --name omniroute --restart unless-stopped --stop-timeout 40 \
     -p 127.0.0.1:20128:20128 -v omniroute-data:/app/data diegosouzapw/omniroute:latest
   ```
   ಇದು IPv4 ಬೈಂಡ್ ಅನ್ನು ಬಲವಂತಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಎಲ್ಲಾ ಹೋಸ್ಟ್ ಇಂಟರ್ಫೇಸ್ಗಳಲ್ಲಿ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದನ್ನೂ ತಪ್ಪಿಸುತ್ತದೆ.

## ವೆಚ್ಚದ ಸಮಸ್ಯೆಗಳು

### ಹೆಚ್ಚಿನ ವೆಚ್ಚಗಳು

1. ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಬಳಕೆ ವಿಭಾಗದಲ್ಲಿ ಬಳಕೆಯ ಅಂಕಿಅಂಶಗಳನ್ನು ಪರಿಶೀಲಿಸಿ
2. ಪ್ರಾಥಮಿಕ ಮಾದರಿಯನ್ನು GLM/MiniMax ಗೆ ಬದಲಿಸಿ
3. ನಿರ್ಣಾಯಕವಲ್ಲದ ಕಾರ್ಯಗಳಿಗೆ ಉಚಿತ ಶ್ರೇಣಿಯನ್ನು (Qoder, Kiro) ಬಳಸಿ
4. ಪ್ರತಿ API ಕೀಗೆ ವೆಚ್ಚದ ಬಜೆಟ್ಗಳನ್ನು ಹೊಂದಿಸಿ: ಡ್ಯಾಶ್ಬೋರ್ಡ್ → API ಕೀಗಳು → ಬಜೆಟ್

## ಡೀಬಗ್ ಮಾಡುವುದು

### ಲಾಗ್ ಫೈಲ್ಗಳನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಿ

ನಿಮ್ಮ `.env` ಫೈಲ್ನಲ್ಲಿ `APP_LOG_TO_FILE=true` ಹೊಂದಿಸಿ. ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್ಗಳನ್ನು `logs/` ಅಡಿಯಲ್ಲಿ ಬರೆಯಲಾಗುತ್ತದೆ.
ಸೆಟ್ಟಿಂಗ್ಗಳಲ್ಲಿ ಕಾಲ್ ಲಾಗ್ ಪೈಪ್ಲೈನ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ, ವಿನಂತಿಯ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳನ್ನು `${DATA_DIR}/call_logs/` ಅಡಿಯಲ್ಲಿ ಸಂಗ್ರಹಿಸಲಾಗುತ್ತದೆ.
ಪೈಪ್ಲೈನ್ ಕ್ಯಾಪ್ಚರ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ, ಸ್ಟ್ರೀಮ್ ಚಂಕ್ ಪೇಲೋಡ್ಗಳನ್ನು ಬಿಟ್ಟುಬಿಡಲು `CALL_LOG_PIPELINE_CAPTURE_STREAM_CHUNKS=false` ಹೊಂದಿಸಿ ಅಥವಾ KBಯಲ್ಲಿ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಮಿತಿಯನ್ನು ಬದಲಾಯಿಸಲು `CALL_LOG_PIPELINE_MAX_SIZE_KB` ಅನ್ನು ಹೊಂದಿಸಿ.

### ಪೂರೈಕೆದಾರರ ಸ್ಥಿತಿಯನ್ನು ಪರಿಶೀಲಿಸಿ

```bash
# ಸ್ಥಿತಿ ಡ್ಯಾಶ್ಬೋರ್ಡ್
http://localhost:20128/dashboard/health

# API ಸ್ಥಿತಿ ಪರಿಶೀಲನೆ
curl http://localhost:20128/api/monitoring/health
```

### ರನ್ಟೈಮ್ ಸಂಗ್ರಹಣೆ

- ಮುಖ್ಯ ಸ್ಥಿತಿ: `${DATA_DIR}/storage.sqlite` (ಪೂರೈಕೆದಾರರು, ಕಾಂಬೊಗಳು, ಅಲಿಯಾಸ್ಗಳು, ಕೀಗಳು, ಸೆಟ್ಟಿಂಗ್ಗಳು)
- ಬಳಕೆ: `storage.sqlite` ನಲ್ಲಿರುವ SQLite ಟೇಬಲ್ಗಳು (`usage_history`, `call_logs`, `proxy_logs`) + ಐಚ್ಛಿಕ `${DATA_DIR}/call_logs/`
- ಅಪ್ಲಿಕೇಶನ್ ಲಾಗ್ಗಳು: `<repo>/logs/...` (`APP_LOG_TO_FILE=true` ಆಗಿರುವಾಗ)
- ಕಾಲ್ ಲಾಗ್ ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ಗಳು: ಕಾಲ್ ಲಾಗ್ ಪೈಪ್ಲೈನ್ ಸಕ್ರಿಯವಾಗಿರುವಾಗ `${DATA_DIR}/call_logs/YYYY-MM-DD/...`

ವಿನಂತಿ ಲಾಗ್ಗಳ ಪುಟದಲ್ಲಿನ **ಇತಿಹಾಸವನ್ನು ಸ್ವಚ್ಛಗೊಳಿಸಿ** ಕ್ರಿಯೆಯು `call_logs`, ಹಳೆಯ
`request_detail_logs`, ಮತ್ತು ಸ್ಥಳೀಯ `${DATA_DIR}/call_logs/` ಆರ್ಟಿಫ್ಯಾಕ್ಟ್ ಡೈರೆಕ್ಟರಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ.

## ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಸಮಸ್ಯೆಗಳು

### ಪೂರೈಕೆದಾರರು OPEN ಸ್ಥಿತಿಯಲ್ಲೇ ಸಿಲುಕಿದ್ದಾರೆ

ಪೂರೈಕೆದಾರರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ OPEN ಆಗಿರುವಾಗ, ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ವಿನಂತಿಗಳನ್ನು ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ.

**ಪರಿಹಾರ:**

1. **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ**ಕ್ಕೆ ಹೋಗಿ
2. ಸಮಸ್ಯೆಗೆ ಒಳಗಾದ ಪೂರೈಕೆದಾರರ ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಕಾರ್ಡ್ ಪರಿಶೀಲಿಸಿ
3. ಎಲ್ಲಾ ಬ್ರೇಕರ್ಗಳನ್ನು ತೆರವುಗೊಳಿಸಲು **ಎಲ್ಲವನ್ನೂ ಮರುಹೊಂದಿಸಿ** ಕ್ಲಿಕ್ ಮಾಡಿ ಅಥವಾ ಕೂಲ್ಡೌನ್ ಅವಧಿ ಮುಗಿಯುವವರೆಗೆ ಕಾಯಿರಿ
4. ಮರುಹೊಂದಿಸುವ ಮೊದಲು ಪೂರೈಕೆದಾರರು ನಿಜವಾಗಿಯೂ ಲಭ್ಯವಿದ್ದಾರೆಯೇ ಎಂದು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ

### ಪೂರೈಕೆದಾರರು ಸರ್ಕ್ಯೂಟ್ ಬ್ರೇಕರ್ ಅನ್ನು ಪದೇಪದೇ ಟ್ರಿಗರ್ ಮಾಡುತ್ತಿದ್ದಾರೆ

ಪೂರೈಕೆದಾರರು ಪದೇಪದೇ OPEN ಸ್ಥಿತಿಯನ್ನು ಪ್ರವೇಶಿಸುತ್ತಿದ್ದರೆ:

1. ವೈಫಲ್ಯದ ಮಾದರಿಗಾಗಿ **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಆರೋಗ್ಯ → ಪೂರೈಕೆದಾರರ ಆರೋಗ್ಯ** ಪರಿಶೀಲಿಸಿ
2. **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು**ಗೆ ಹೋಗಿ ಮತ್ತು ವೈಫಲ್ಯದ ಮಿತಿಯನ್ನು ಹೆಚ್ಚಿಸಿ
3. ಪೂರೈಕೆದಾರರು API ಮಿತಿಗಳನ್ನು ಬದಲಾಯಿಸಿದ್ದಾರೆಯೇ ಅಥವಾ ಮರು-ದೃಢೀಕರಣದ ಅಗತ್ಯವಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ
4. ವಿಳಂಬದ ಟೆಲಿಮೆಟ್ರಿಯನ್ನು ಪರಿಶೀಲಿಸಿ — ಹೆಚ್ಚಿನ ವಿಳಂಬವು ಕಾಲಮಿತಿ ಆಧಾರಿತ ವೈಫಲ್ಯಗಳಿಗೆ ಕಾರಣವಾಗಬಹುದು

## ಆಡಿಯೊ ಲಿಪ್ಯಂತರಣ ಸಮಸ್ಯೆಗಳು

### "ಬೆಂಬಲಿಸದ ಮಾದರಿ" ದೋಷ

- ಮೊದಲ ವಿಭಾಗವು ನೀವು ದೃಢೀಕರಣ ವಿವರಗಳನ್ನು ಹೊಂದಿರುವ ಪೂರೈಕೆದಾರರಾಗಿರುವ model id ಬಳಸಿ (`openai/whisper-1`, `openrouter/deepgram/nova-3`). ಕೇವಲ `deepgram/nova-3` ಬಳಸಲು ಸ್ಥಳೀಯ Deepgram ಕೀ ಅಗತ್ಯವಿದೆ.
- ಪೂರೈಕೆದಾರರು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು** ವಿಭಾಗದಲ್ಲಿ ಸಂಪರ್ಕಗೊಂಡಿರುವುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ

### ಲಿಪ್ಯಂತರಣವು ಖಾಲಿಯಾಗಿ ಮರಳುತ್ತದೆ ಅಥವಾ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

- ಬೆಂಬಲಿತ ಆಡಿಯೊ ಸ್ವರೂಪಗಳನ್ನು ಪರಿಶೀಲಿಸಿ: `mp3`, `wav`, `m4a`, `flac`, `ogg`, `webm`
- ಫೈಲ್ ಗಾತ್ರವು ಪೂರೈಕೆದಾರರ ಮಿತಿಗಳೊಳಗೆ ಇದೆ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ (ಸಾಮಾನ್ಯವಾಗಿ < 25MB)
- ಪೂರೈಕೆದಾರರ ಕಾರ್ಡ್ನಲ್ಲಿ API ಕೀಯ ಸಿಂಧುತ್ವವನ್ನು ಪರಿಶೀಲಿಸಿ

## ಅನುವಾದಕದ ದೋಷನಿವಾರಣೆ

ಸ್ವರೂಪ ಅನುವಾದದ ಸಮಸ್ಯೆಗಳನ್ನು ದೋಷನಿವಾರಣೆ ಮಾಡಲು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಅನುವಾದಕ** ಬಳಸಿ:

| ಮೋಡ್               | ಯಾವಾಗ ಬಳಸಬೇಕು                                                                                                          |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| **ಪ್ಲೇಗ್ರೌಂಡ್**    | ಇನ್ಪುಟ್/ಔಟ್ಪುಟ್ ಸ್ವರೂಪಗಳನ್ನು ಅಕ್ಕಪಕ್ಕದಲ್ಲಿ ಹೋಲಿಸಿ — ಅದು ಹೇಗೆ ಅನುವಾದಗೊಳ್ಳುತ್ತದೆ ಎಂಬುದನ್ನು ನೋಡಲು ವಿಫಲ ವಿನಂತಿಯನ್ನು ಅಂಟಿಸಿ |
| **ಚಾಟ್ ಪರೀಕ್ಷಕ**   | ನೇರ ಸಂದೇಶಗಳನ್ನು ಕಳುಹಿಸಿ ಮತ್ತು ಹೆಡರ್ಗಳನ್ನು ಒಳಗೊಂಡ ಸಂಪೂರ್ಣ ವಿನಂತಿ/ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಪರಿಶೀಲಿಸಿ                           |
| **ಪರೀಕ್ಷಾ ವೇದಿಕೆ** | ಯಾವ ಅನುವಾದಗಳು ದೋಷಪೂರಿತವಾಗಿವೆ ಎಂಬುದನ್ನು ಕಂಡುಹಿಡಿಯಲು ಸ್ವರೂಪ ಸಂಯೋಜನೆಗಳಾದ್ಯಂತ ಬ್ಯಾಚ್ ಪರೀಕ್ಷೆಗಳನ್ನು ಚಲಾಯಿಸಿ                 |
| **ನೇರ ಮಾನಿಟರ್**    | ಮಧ್ಯಂತರವಾಗಿ ಸಂಭವಿಸುವ ಅನುವಾದ ಸಮಸ್ಯೆಗಳನ್ನು ಪತ್ತೆಹಚ್ಚಲು ನೈಜ-ಸಮಯದ ವಿನಂತಿ ಹರಿವನ್ನು ವೀಕ್ಷಿಸಿ                                 |

### ಸಾಮಾನ್ಯ ಸ್ವರೂಪದ ಸಮಸ್ಯೆಗಳು

- **ಆಲೋಚನಾ ಟ್ಯಾಗ್ಗಳು ಕಾಣಿಸುತ್ತಿಲ್ಲ** — ಗುರಿ ಪೂರೈಕೆದಾರರು ಆಲೋಚನೆಯನ್ನು ಬೆಂಬಲಿಸುತ್ತಾರೆಯೇ ಮತ್ತು ಆಲೋಚನಾ ಬಜೆಟ್ ಸೆಟ್ಟಿಂಗ್ ಸರಿಯಾಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ
- **ಟೂಲ್ ಕರೆಗಳು ಕಾಣೆಯಾಗುತ್ತಿವೆ** — ಕೆಲವು ಸ್ವರೂಪ ಅನುವಾದಗಳು ಬೆಂಬಲಿಸದ ಕ್ಷೇತ್ರಗಳನ್ನು ತೆಗೆದುಹಾಕಬಹುದು; ಪ್ಲೇಗ್ರೌಂಡ್ ಮೋಡ್ನಲ್ಲಿ ಪರಿಶೀಲಿಸಿ
- **ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ ಕಾಣೆಯಾಗಿದೆ** — Claude ಮತ್ತು Gemini ಸಿಸ್ಟಮ್ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ವಿಭಿನ್ನವಾಗಿ ನಿರ್ವಹಿಸುತ್ತವೆ; ಅನುವಾದದ ಔಟ್ಪುಟ್ ಪರಿಶೀಲಿಸಿ
- **SDK ಆಬ್ಜೆಕ್ಟ್ ಬದಲಿಗೆ ಕಚ್ಚಾ ಸ್ಟ್ರಿಂಗ್ ಅನ್ನು ಮರಳಿಸುತ್ತದೆ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; OpenAI SDK Pydantic ಮೌಲ್ಯೀಕರಣ ವೈಫಲ್ಯಗಳಿಗೆ ಕಾರಣವಾಗುವ ಪ್ರಮಾಣಿತವಲ್ಲದ ಕ್ಷೇತ್ರಗಳನ್ನು (`x_groq`, `usage_breakdown`, ಇತ್ಯಾದಿ) ಪ್ರತಿಕ್ರಿಯೆ ಸ್ಯಾನಿಟೈಸರ್ ತೆಗೆದುಹಾಕುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯೊಂದನ್ನು ದಾಖಲಿಸಿ.
- **GLM/ERNIE `system` ಪಾತ್ರವನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; ಹೊಂದಾಣಿಕೆಯಾಗದ ಮಾದರಿಗಳಿಗಾಗಿ ಪಾತ್ರ ನಾರ್ಮಲೈಸರ್ ಸಿಸ್ಟಮ್ ಸಂದೇಶಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಬಳಕೆದಾರರ ಸಂದೇಶಗಳೊಂದಿಗೆ ವಿಲೀನಗೊಳಿಸುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯೊಂದನ್ನು ದಾಖಲಿಸಿ.
- **`developer` ಪಾತ್ರವನ್ನು ಗುರುತಿಸಲಾಗುತ್ತಿಲ್ಲ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; OpenAI ಅಲ್ಲದ ಪೂರೈಕೆದಾರರಿಗಾಗಿ ಇದನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ `system` ಆಗಿ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯೊಂದನ್ನು ದಾಖಲಿಸಿ.
- **Gemini ಜೊತೆಗೆ `json_schema` ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿಲ್ಲ** — v1.x ನಲ್ಲಿ ಪರಿಹರಿಸಲಾಗಿದೆ; `response_format` ಅನ್ನು ಈಗ Gemini ನ `responseMimeType` + `responseSchema`ಗೆ ಪರಿವರ್ತಿಸಲಾಗುತ್ತದೆ. v3.x+ ನಲ್ಲಿಯೂ ನೀವು ಇದನ್ನು ನೋಡುತ್ತಿದ್ದರೆ, ದಯವಿಟ್ಟು ಸಮಸ್ಯೆಯೊಂದನ್ನು ದಾಖಲಿಸಿ.

## ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವದ ಸೆಟ್ಟಿಂಗ್ಗಳು

### ಸ್ವಯಂ ದರ-ಮಿತಿ ಸಕ್ರಿಯವಾಗದಿರುವುದು

- ಸ್ವಯಂ ದರ-ಮಿತಿಯು API ಕೀ ಪೂರೈಕೆದಾರರಿಗೆ ಮಾತ್ರ ಅನ್ವಯಿಸುತ್ತದೆ (OAuth/ಚಂದಾದಾರಿಕೆಗೆ ಅಲ್ಲ)
- **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು** ಎಂಬಲ್ಲಿ ಸ್ವಯಂ ದರ-ಮಿತಿಯನ್ನು ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ
- ಪೂರೈಕೆದಾರರು `429` ಸ್ಥಿತಿ ಕೋಡ್ಗಳನ್ನು ಅಥವಾ `Retry-After` ಹೆಡರ್ಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತಾರೆಯೇ ಎಂದು ಪರಿಶೀಲಿಸಿ

### ಘಾತೀಯ ಬ್ಯಾಕ್ಆಫ್ ಹೊಂದಿಸುವಿಕೆ

ಪೂರೈಕೆದಾರರ ಪ್ರೊಫೈಲ್ಗಳು ಈ ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಬೆಂಬಲಿಸುತ್ತವೆ:

- **ಮೂಲ ವಿಳಂಬ** — ಮೊದಲ ವೈಫಲ್ಯದ ನಂತರದ ಆರಂಭಿಕ ಕಾಯುವಿಕೆ ಸಮಯ (ಡೀಫಾಲ್ಟ್: 1s)
- **ಗರಿಷ್ಠ ವಿಳಂಬ** — ಗರಿಷ್ಠ ಕಾಯುವಿಕೆ ಸಮಯದ ಮಿತಿ (ಡೀಫಾಲ್ಟ್: 30s)
- **ಗುಣಕ** — ಪ್ರತಿ ಸತತ ವೈಫಲ್ಯಕ್ಕೆ ವಿಳಂಬವನ್ನು ಎಷ್ಟು ಹೆಚ್ಚಿಸಬೇಕು (ಡೀಫಾಲ್ಟ್: 2x)

### ಥಂಡರಿಂಗ್ ಹರ್ಡ್ ತಡೆ

ದರ-ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರೈಕೆದಾರರಿಗೆ ಅನೇಕ ಸಮಕಾಲೀನ ವಿನಂತಿಗಳು ಬಂದಾಗ, ವಿನಂತಿಗಳನ್ನು ಅನುಕ್ರಮಗೊಳಿಸಲು ಮತ್ತು ಸರಣಿ ವೈಫಲ್ಯಗಳನ್ನು ತಡೆಯಲು OmniRoute ಮ್ಯೂಟೆಕ್ಸ್ + ಸ್ವಯಂ ದರ-ಮಿತಿಯನ್ನು ಬಳಸುತ್ತದೆ. API ಕೀ ಪೂರೈಕೆದಾರರಿಗೆ ಇದು ಸ್ವಯಂಚಾಲಿತವಾಗಿರುತ್ತದೆ.

### ಚಾಟ್ ವಿನಂತಿಗಳು 503 / chat_admission_busy ಜೊತೆಗೆ ವಿಫಲಗೊಳ್ಳುತ್ತವೆ

**ಲಕ್ಷಣಗಳು:**

- ಚಾಟ್ ಪೂರ್ಣಗೊಳಿಸುವಿಕೆಗಳ ಎಂಡ್ಪಾಯಿಂಟ್, ದೋಷ ಕೋಡ್
  `chat_admission_busy` ಹೊಂದಿರುವ ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
- ಪ್ರತಿಕ್ರಿಯೆಯು `Retry-After` ಅನ್ನು ಒಳಗೊಂಡಿರುತ್ತದೆ. #12135 ರಿಂದ ಇದರ ಮೌಲ್ಯವನ್ನು ಗಮನಿಸಲಾದ
  ಆಕ್ರಮಿತ ಸ್ಥಿತಿಯಿಂದ ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ — ವಿನಂತಿಯು ಈಗಾಗಲೇ ಕಾಯ್ದಿರುವ `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS`
  ವಿಂಡೋ ಮತ್ತು ಪ್ರಸ್ತುತ ಹೆವಿವೇಟ್ ಲೀಸ್ಗಳನ್ನು ಹಿಡಿದಿಟ್ಟಿರುವ ಸಮಯ ಇವೆರಡರಲ್ಲಿ ದೊಡ್ಡದನ್ನು ತೆಗೆದುಕೊಂಡು — ಪೂರ್ಣ
  ಸೆಕೆಂಡ್ಗಳಿಗೆ ಮೇಲ್ಮುಖವಾಗಿ ಪೂರ್ಣಾಂಕಗೊಳಿಸಿ, 60ಕ್ಕೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ. ನಿಷ್ಕ್ರಿಯ ಗೇಟ್ನಲ್ಲಿ ಇದು ಐತಿಹಾಸಿಕ ಕನಿಷ್ಠ ಮಿತಿಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ:
  ಬೈಟ್-ಆಧಾರಿತ ಪಥದಲ್ಲಿ 2 ಸೆಕೆಂಡ್ಗಳು, ರಚನೆ-ಆಧಾರಿತ ಪಥದಲ್ಲಿ 1 ಸೆಕೆಂಡ್ (ಇದು
  `reason: "structure_limit"` ಅನ್ನೂ ಒಳಗೊಂಡಿರುತ್ತದೆ).
- ಮತ್ತೊಂದು ಹೆವಿವೇಟ್ ಚಾಟ್ ಅಥವಾ ದೀರ್ಘಕಾಲ ಚಾಲನೆಯಲ್ಲಿರುವ ಸ್ಟ್ರೀಮಿಂಗ್ ಪ್ರತಿಕ್ರಿಯೆ ಇನ್ನೂ
  ಪ್ರಗತಿಯಲ್ಲಿರುವಾಗ ಇದು ಸಂಭವಿಸಬಹುದು.

ಬೈಟ್-ಆಧಾರಿತ ಪ್ರತಿಕ್ರಿಯೆಯ ಬಾಡಿ ಹೀಗಿದೆ:

```json
{
  "error": {
    "message": "Chat admission capacity is temporarily unavailable. Retry shortly.",
    "type": "server_error",
    "code": "chat_admission_busy"
  }
}
```

ರಚನೆ-ಆಧಾರಿತ ಪ್ರತಿಕ್ರಿಯೆಯು ಅದೇ ಪ್ರಕಾರ ಮತ್ತು ಕೋಡ್ ಅನ್ನು ಬಳಸುತ್ತದೆ; ಅದರ ಸಂದೇಶ
`Local chat admission capacity is busy for this structurally heavy request; upstream provider routing was not attempted. Retry shortly.`
ಮತ್ತು `reason: "structure_limit"` ಆಗಿರುತ್ತದೆ.
ಡೀಫಾಲ್ಟ್ ಮಿತಿಗಳಲ್ಲಿ, ವಿನಂತಿಯು ಕನಿಷ್ಠ `200` ಸಂದೇಶಗಳನ್ನು, ಕನಿಷ್ಠ `64` ಟೂಲ್ಗಳನ್ನು ಅಥವಾ
ಕನಿಷ್ಠ `32,000` ಅಂದಾಜು ಟೋಕನ್ಗಳನ್ನು ಹೊಂದಿದ್ದರೆ, ಅಥವಾ ಮಿತಿಗೊಳಿಸಿದ ರಚನಾ ಅಂದಾಜು ತನ್ನ
`10,000` ಭೇಟಿ ನೀಡಿದ ನೋಡ್ಗಳ ಅಥವಾ `12` ಆಳದ ಮಿತಿಯನ್ನು ತಲುಪಿದರೆ, ಅದನ್ನು ರಚನಾತ್ಮಕವಾಗಿ ಹೆವಿವೇಟ್ ಎಂದು ಪರಿಗಣಿಸಲಾಗುತ್ತದೆ.

**ಕಾರಣ:** ಇದು OmniRoute ಒಳಗಿನ ಉದ್ದೇಶಪೂರ್ವಕ ಲೋಡ್ ಶೆಡ್ಡಿಂಗ್ ಆಗಿದ್ದು, ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ವೈಫಲ್ಯವಲ್ಲ.
ದೊಡ್ಡ ವಿನಂತಿಯ ಬಾಡಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುವ ಮತ್ತು ಪಾರ್ಸ್ ಮಾಡುವ ಮೊದಲು, ಸೀಮಿತ ಹೆವಿವೇಟ್ ಸಾಮರ್ಥ್ಯವನ್ನು ಕಾಯ್ದಿರಿಸಲು
ಪ್ರತಿ ಪ್ರಕ್ರಿಯೆಯು ಪ್ರಕ್ರಿಯೆ-ಸ್ಥಳೀಯ ಗಾರ್ಡ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. SSE ಪ್ರತಿಕ್ರಿಯೆಯ ಸಂಪೂರ್ಣ ಜೀವಿತಾವಧಿಯವರೆಗೆ
ಹೆವಿವೇಟ್ ಲೀಸ್ ಅನ್ನು ಹಿಡಿದಿಡಲಾಗುತ್ತದೆ.

**#503-ಫ್ಯಾನ್-ಔಟ್:** ಈ ತಿದ್ದುಪಡಿಯ ಮೊದಲು, ಹೋಸ್ಟ್ ಮೆಮೊರಿಯನ್ನು ಲೆಕ್ಕಿಸದೆ ಗಾರ್ಡ್ ಸಮಕಾಲೀನತೆಯನ್ನು ಸ್ಥಿರ ವಿನಂತಿ ಸಂಖ್ಯೆಗೆ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`, ಡೀಫಾಲ್ಟ್ `1`) ಮಿತಿಗೊಳಿಸುತ್ತಿತ್ತು; ಆದ್ದರಿಂದ ಕೋಡಿಂಗ್-ಏಜೆಂಟ್
ಫ್ಯಾನ್-ಔಟ್ (ಹಲವಾರು ಉಪ-ಏಜೆಂಟ್ಗಳು/CLIಗಳು, ಸಾಮಾನ್ಯವಾಗಿ > 256 KB ಬಾಡಿಗಳು) ಪರಿಣಾಮಕಾರಿ
ಸಮಕಾಲೀನತೆಯನ್ನು ~1ಕ್ಕೆ ಕುಗ್ಗಿಸಿ, ಸಂಪೂರ್ಣವಾಗಿ ಸಾಮಾನ್ಯವಾದ ಲೋಡ್ನಲ್ಲಿಯೇ 503 ದೋಷಗಳನ್ನು ಉಂಟುಮಾಡುತ್ತಿತ್ತು. ಈಗ ಗಾರ್ಡ್ ಸ್ವಯಂ-ಹೊಂದಾಣಿಕೆ ಮಾಡಿಕೊಳ್ಳುತ್ತದೆ:
ಪ್ರಕ್ರಿಯೆಯ ನೈಜ ಮೆಮೊರಿ ಮಿತಿಯಿಂದ ಗಾತ್ರಗೊಳಿಸಲಾದ, ಸ್ವಯಂ-ನಿರ್ಧಾರಿತ ಇನ್ಜೆಸ್ಟ್ ಬೈಟ್ ಬಜೆಟ್
(`OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES`) ಅದನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ ಮತ್ತು ಅದು ನೇರ ಸಂಪನ್ಮೂಲ-ಒತ್ತಡದ ಸಂಕೇತವನ್ನೂ
ಪರಿಗಣಿಸುತ್ತದೆ — ಹೀಗಾಗಿ ಒಂದಕ್ಕಿಂತ ಹೆಚ್ಚು ಹೆವಿ ವಿನಂತಿಗಳು ಏಕಕಾಲದಲ್ಲಿ ಬಂದವು ಎಂಬ ಕಾರಣಕ್ಕಷ್ಟೇ ಅಲ್ಲದೆ,
ಹೋಸ್ಟ್ ನಿಜವಾಗಿಯೂ ಮೆಮೊರಿ ಒತ್ತಡದಲ್ಲಿರುವಾಗ ಮಾತ್ರ ಅದು ಲೋಡ್ ಅನ್ನು ಕಡಿಮೆ ಮಾಡುತ್ತದೆ. ಹಳೆಯ ಸಂಖ್ಯಾ ಮಿತಿ
(`OMNIROUTE_CHAT_MAX_HEAVY_IN_FLIGHT`) ಇನ್ನೂ ಪಾಲಿಸಲ್ಪಡುತ್ತದೆ, ಆದರೆ ನೀವು ಅದನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಹೊಂದಿಸಿದರೆ ಮಾತ್ರ.

ಸಾಮರ್ಥ್ಯವು ಕಾರ್ಯನಿರತವಾಗಿರುವಾಗ, ಮರುಪ್ರಯತ್ನಿಸಬಹುದಾದ `503` ಅನ್ನು ಉತ್ತರಿಸುವ ಮೊದಲು, ಸ್ಲಾಟ್ ಖಾಲಿಯಾಗುವುದಕ್ಕಾಗಿ
ಹೆವಿವೇಟ್ ವಿನಂತಿಯು ಮೊದಲು `OMNIROUTE_CHAT_ADMISSION_QUEUE_MS` ವರೆಗೆ (ಡೀಫಾಲ್ಟ್ `2000`, `0` ಕಾಯುವಿಕೆಯನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುತ್ತದೆ)
ಕಾಯುತ್ತದೆ. ಫ್ಯಾನ್-ಔಟ್ ಆಗಿ ಹೆವಿ ಉಪ-ವಿನಂತಿಗಳನ್ನು ಸಮಕಾಲೀನವಾಗಿ ಕಳುಹಿಸುವ ಏಜೆಂಟ್-ಶೈಲಿಯ ಕ್ಲೈಂಟ್ಗಳು
(OpenCode, Claude Code, Cursor), ತಕ್ಷಣದ ತಿರಸ್ಕಾರಗಳಿಂದ ತಮ್ಮ ಸಂಪೂರ್ಣ ಮರುಪ್ರಯತ್ನ ಬಜೆಟ್ ಅನ್ನು ವ್ಯರ್ಥಮಾಡಿ
ಕಾರ್ಯದ ಮಧ್ಯದಲ್ಲೇ ವಿಫಲಗೊಳ್ಳುವ ಬದಲು, ವಿನಂತಿಗಳ ಬರ್ಸ್ಟ್ ಅನ್ನು ಅನುಕ್ರಮಗೊಳಿಸುವಂತೆ ಮಾಡಲು ಈ ಮಿತಿಗೊಳಿಸಿದ ಕಾಯುವಿಕೆ ಇದೆ.
ಪ್ರಸ್ತುತ ಹೆವಿವೇಟ್ ಲೀಸ್ ಆಕ್ರಮಿತ ಸ್ಥಿತಿ, ನಿರ್ಧರಿಸಲಾದ ಬೈಟ್ ಬಜೆಟ್ ಮತ್ತು ನೇರ ಒತ್ತಡದ ತೀವ್ರತೆಯನ್ನು
`GET /api/monitoring/health` → `chatAdmission` (`inflightBytes`, `maxInflightBytes`,
`budgetSource`, `pressureSeverity`, `countCapEnabled`) ನಲ್ಲಿ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ — ಯಾವುದೇ env var ಅನ್ನು ಬದಲಾಯಿಸುವ ಮೊದಲು ಇವುಗಳನ್ನು ಪರಿಶೀಲಿಸಿ.
ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ → ವಿನಂತಿ ಕ್ಯೂ → ಸಮಕಾಲೀನ ವಿನಂತಿಗಳು ಇದನ್ನು ನಿಯಂತ್ರಿಸುವುದಿಲ್ಲ; ಆ ಸೆಟ್ಟಿಂಗ್
ಪ್ರತ್ಯೇಕ ಪೂರೈಕೆದಾರರ ವಿನಂತಿ-ಕ್ಯೂ ಕಾರ್ಯವಿಧಾನವನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ.

**ತಿದ್ದುಪಡಿ:**

1. ಮೊದಲು ಮರುಪ್ರಯತ್ನಿಸಿ. ವಿನಂತಿಯನ್ನು ತಕ್ಷಣವೇ
   ಪುನರಾವರ್ತಿಸುವ ಬದಲು ಕ್ಲೈಂಟ್ಗಳು `Retry-After` ಅನ್ನು ಪಾಲಿಸಿ ಬ್ಯಾಕ್ಆಫ್ ಬಳಸಬೇಕು.
2. ಏನನ್ನಾದರೂ ಹೊಂದಿಸುವ ಮೊದಲು `/api/monitoring/health` → `chatAdmission` ಅನ್ನು ಪರಿಶೀಲಿಸಿ. `countCapEnabled:
false` ಮತ್ತು ಸಾಕಷ್ಟು ದೊಡ್ಡ `maxInflightBytes` ಎಂದರೆ ಸ್ವಯಂ-ನಿರ್ಧಾರಿತ ಬಜೆಟ್ ಈಗಾಗಲೇ ತನ್ನ
   ಕೆಲಸವನ್ನು ಮಾಡುತ್ತಿದೆ; `high`/`critical` ಮೌಲ್ಯದ `pressureSeverity` ಎಂದರೆ ಹೋಸ್ಟ್ನಲ್ಲಿ ನಿಜವಾಗಿಯೂ ಮೆಮೊರಿ ಕೊರತೆಯಿದೆ —
   ಅದನ್ನು ಪ್ರವೇಶ env var ಮೂಲಕ ಸರಿಪಡಿಸಲಾಗುವುದಿಲ್ಲ; ಅದಕ್ಕೆ ಹೆಚ್ಚಿನ RAM ಅಥವಾ ಕಡಿಮೆ ಕಾರ್ಯಭಾರ ಅಗತ್ಯವಿದೆ.
3. `/api/monitoring/health` ನಲ್ಲಿ ಸ್ವಯಂ-ನಿರ್ಧಾರಿತ ಬಜೆಟ್ ನಿಮ್ಮ ಹೋಸ್ಟ್ಗೆ ನಿಜವಾಗಿಯೂ ತುಂಬಾ ಚಿಕ್ಕದಾಗಿದೆ ಎಂದು
   ತೋರಿಸಿದರೆ ಮಾತ್ರ (ಇದು ಅಪರೂಪ — ಅದು ಈಗಾಗಲೇ ಕಂಟೇನರ್ನಿಂದ ಬೇರ್-ಮೆಟಲ್ವರೆಗೆ ಸ್ಕೇಲ್ ಆಗುತ್ತದೆ), ಹಳೆಯ ವಿನಂತಿ-ಸಂಖ್ಯಾ ಮಿತಿಗೆ
   ಹಿಂತಿರುಗುವ ಬದಲು `OMNIROUTE_CHAT_MAX_INFLIGHT_BYTES` ಮೂಲಕ ಅದನ್ನು ನೇರವಾಗಿ ಓವರ್ರೈಡ್ ಮಾಡಿ.

ಅಧಿಕೃತ ಪ್ರವೇಶ ಸೆಟ್ಟಿಂಗ್ಗಳಿಗಾಗಿ [ಪರಿಸರ-ವೇರಿಯಬಲ್ ಉಲ್ಲೇಖ](../reference/ENVIRONMENT.md#4-security--authentication)
ನೋಡಿ.

## ಐಚ್ಛಿಕ RAG / LLM ವೈಫಲ್ಯ ವರ್ಗೀಕರಣ (16 ಸಮಸ್ಯೆಗಳು)

ಕೆಲವು OmniRoute ಬಳಕೆದಾರರು ಗೇಟ್ವೇಯನ್ನು RAG ಅಥವಾ ಏಜೆಂಟ್ ಸ್ಟ್ಯಾಕ್ಗಳ ಮುಂಭಾಗದಲ್ಲಿ ಇರಿಸುತ್ತಾರೆ. ಅಂತಹ ಸೆಟಪ್ಗಳಲ್ಲಿ ವಿಚಿತ್ರ ಮಾದರಿಯೊಂದು ಸಾಮಾನ್ಯವಾಗಿ ಕಾಣಿಸುತ್ತದೆ: OmniRoute ಆರೋಗ್ಯಕರವಾಗಿ ಕಾಣುತ್ತದೆ (ಪೂರೈಕೆದಾರರು ಸಕ್ರಿಯವಾಗಿದ್ದಾರೆ, ರೂಟಿಂಗ್ ಪ್ರೊಫೈಲ್ಗಳು ಸರಿಯಾಗಿವೆ, ದರ ಮಿತಿ ಎಚ್ಚರಿಕೆಗಳಿಲ್ಲ), ಆದರೆ ಅಂತಿಮ ಉತ್ತರ ಮಾತ್ರ ಇನ್ನೂ ತಪ್ಪಾಗಿರುತ್ತದೆ.

ಪ್ರಾಯೋಗಿಕವಾಗಿ, ಈ ಘಟನೆಗಳು ಸಾಮಾನ್ಯವಾಗಿ ಗೇಟ್ವೇಯಿಂದಲೇ ಅಲ್ಲ, ಅದರ ನಂತರದ RAG ಪೈಪ್ಲೈನ್ನಿಂದ ಉಂಟಾಗುತ್ತವೆ.

ಆ ವೈಫಲ್ಯಗಳನ್ನು ವಿವರಿಸಲು ಹಂಚಿಕೆಯ ಪದಕೋಶವನ್ನು ಬಳಸಲು ನೀವು ಬಯಸಿದರೆ, WFGY ProblemMap ಅನ್ನು ಬಳಸಬಹುದು. ಇದು ಹದಿನಾರು ಪುನರಾವರ್ತಿತ RAG / LLM ವೈಫಲ್ಯ ಮಾದರಿಗಳನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುವ, MIT ಪರವಾನಗಿಯ ಬಾಹ್ಯ ಪಠ್ಯ ಸಂಪನ್ಮೂಲವಾಗಿದೆ. ಉನ್ನತ ಮಟ್ಟದಲ್ಲಿ ಇದು ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒಳಗೊಂಡಿದೆ:

- ರಿಟ್ರೀವಲ್ ದಿಕ್ಕು ತಪ್ಪುವಿಕೆ ಮತ್ತು ಮುರಿದ ಸಂದರ್ಭ ಗಡಿಗಳು
- ಖಾಲಿ ಅಥವಾ ಹಳೆಯದಾದ ಇಂಡೆಕ್ಸ್ಗಳು ಮತ್ತು ವೆಕ್ಟರ್ ಸ್ಟೋರ್ಗಳು
- ಎಂಬೆಡಿಂಗ್ ಮತ್ತು ಅರ್ಥಾತ್ಮಕ ಹೊಂದಾಣಿಕೆಯ ನಡುವಿನ ವ್ಯತ್ಯಾಸ
- ಪ್ರಾಂಪ್ಟ್ ಜೋಡಣೆ ಮತ್ತು ಸಂದರ್ಭ ವಿಂಡೋ ಸಮಸ್ಯೆಗಳು
- ತರ್ಕ ಕುಸಿತ ಮತ್ತು ಅತಿಯಾದ ಆತ್ಮವಿಶ್ವಾಸದ ಉತ್ತರಗಳು
- ದೀರ್ಘ ಸರಪಳಿ ಮತ್ತು ಏಜೆಂಟ್ ಸಮನ್ವಯ ವೈಫಲ್ಯಗಳು
- ಬಹು-ಏಜೆಂಟ್ ಮೆಮೊರಿ ಮತ್ತು ಪಾತ್ರ ದಿಕ್ಕು ತಪ್ಪುವಿಕೆ
- ನಿಯೋಜನೆ ಮತ್ತು ಬೂಟ್ಸ್ಟ್ರ್ಯಾಪ್ ಕ್ರಮದ ಸಮಸ್ಯೆಗಳು

ಕಲ್ಪನೆ ಸರಳವಾಗಿದೆ:

1. ತಪ್ಪಾದ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ತನಿಖೆ ಮಾಡುವಾಗ, ಇವುಗಳನ್ನು ದಾಖಲಿಸಿ:
   - ಬಳಕೆದಾರರ ಕಾರ್ಯ ಮತ್ತು ವಿನಂತಿ
   - OmniRouteನಲ್ಲಿನ ರೂಟ್ ಅಥವಾ ಪೂರೈಕೆದಾರರ ಸಂಯೋಜನೆ
   - ನಂತರದ ಹಂತದಲ್ಲಿ ಬಳಸಲಾದ ಯಾವುದೇ RAG ಸಂದರ್ಭ (ಪಡೆಯಲಾದ ದಾಖಲೆಗಳು, ಟೂಲ್ ಕರೆಗಳು ಇತ್ಯಾದಿ)
2. ಘಟನೆಯನ್ನು ಒಂದು ಅಥವಾ ಎರಡು WFGY ProblemMap ಸಂಖ್ಯೆಗಳೊಂದಿಗೆ (`No.1` … `No.16`) ಹೊಂದಿಸಿ.
3. OmniRoute ಲಾಗ್ಗಳ ಪಕ್ಕದಲ್ಲಿ, ಆ ಸಂಖ್ಯೆಯನ್ನು ನಿಮ್ಮದೇ ಡ್ಯಾಶ್ಬೋರ್ಡ್, ರನ್ಬುಕ್ ಅಥವಾ ಘಟನೆ ಟ್ರ್ಯಾಕರ್ನಲ್ಲಿ ಸಂಗ್ರಹಿಸಿ.
4. ನಿಮ್ಮ RAG ಸ್ಟ್ಯಾಕ್, ರಿಟ್ರೀವರ್ ಅಥವಾ ರೂಟಿಂಗ್ ಕಾರ್ಯತಂತ್ರವನ್ನು ಬದಲಾಯಿಸಬೇಕೇ ಎಂಬುದನ್ನು ನಿರ್ಧರಿಸಲು ಸಂಬಂಧಿತ WFGY ಪುಟವನ್ನು ಬಳಸಿ.

ಪೂರ್ಣ ಪಠ್ಯ ಮತ್ತು ನಿರ್ದಿಷ್ಟ ವಿಧಾನಗಳು ಇಲ್ಲಿ ಲಭ್ಯವಿವೆ (MIT ಪರವಾನಗಿ, ಪಠ್ಯ ಮಾತ್ರ):

[WFGY ProblemMap README](https://github.com/onestardao/WFGY/blob/main/ProblemMap/README.md)

OmniRouteನ ಹಿಂದೆ ನೀವು RAG ಅಥವಾ ಏಜೆಂಟ್ ಪೈಪ್ಲೈನ್ಗಳನ್ನು ಚಲಾಯಿಸದಿದ್ದರೆ, ಈ ವಿಭಾಗವನ್ನು ನಿರ್ಲಕ್ಷಿಸಬಹುದು.

### Devin CLI ದೃಢೀಕರಣ ವೈಫಲ್ಯಗಳು

**ಲಕ್ಷಣಗಳು:**

- CLI ರನ್ಟೈಮ್ ಪರಿಶೀಲನೆಯು `installed=false` ಎಂದು ವರದಿ ಮಾಡುತ್ತದೆ

**ಕಾರಣಗಳು:**

- `CLI_DEVIN_BIN` ಅಸ್ತಿತ್ವದಲ್ಲಿಲ್ಲದ ಪಥವನ್ನು ಸೂಚಿಸುತ್ತದೆ
- ಹೋಸ್ಟ್ನಲ್ಲಿ Devin CLI ಸ್ಥಾಪಿಸಲಾಗಿಲ್ಲ

**ಪರಿಹಾರ:**

1. ನಿಮ್ಮ ಪ್ಲಾಟ್ಫಾರ್ಮ್ಗಾಗಿ Devin CLI ಅನ್ನು ಸ್ಥಾಪಿಸಿ
2. `.env` ನಲ್ಲಿ `CLI_DEVIN_BIN=/usr/local/bin/devin` (ಅಥವಾ ನಿಜವಾದ ಪಥ) ಅನ್ನು ಹೊಂದಿಸಿ
3. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ ಮತ್ತು **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → CLI ಟೂಲ್ಗಳು** ಮೂಲಕ ಪುನಃ ಪರೀಕ್ಷಿಸಿ

### ಮಾಡೆಲ್ ಕೂಲ್ಡೌನ್ ಸ್ಥಗಿತಗೊಂಡಿದೆ (ಹಸ್ತಚಾಲಿತ ಮರುಹೊಂದಿಕೆ)

**ಲಕ್ಷಣಗಳು:**

- ಮುಕ್ತಾಯದ ಸಮಯ ಕಳೆದ ನಂತರವೂ ಮಾಡೆಲ್ ಅನ್ನು ಕೂಲ್ಡೌನ್ನಲ್ಲಿರುವಂತೆ ಪಟ್ಟಿ ಮಾಡಲಾಗುತ್ತದೆ
- ಟೈಮ್ಸ್ಟ್ಯಾಂಪ್ ಹಿಂದಿನ ಸಮಯದ್ದಾಗಿದ್ದರೂ, ಸಂಯೋಜಿತ ರೂಟಿಂಗ್ನಲ್ಲಿ ವಿನಂತಿಗಳು ಇನ್ನೂ ಆ ಮಾಡೆಲ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತವೆ

**ಹಸ್ತಚಾಲಿತ ಮರುಹೊಂದಿಕೆ:**

- **ಡ್ಯಾಶ್ಬೋರ್ಡ್:** **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಮಾಡೆಲ್ ಕೂಲ್ಡೌನ್ಗಳು** → ಪರಿಣಾಮ ಬೀರಿದ ಕಾರ್ಡ್ನಲ್ಲಿ **ಮರು-ಸಕ್ರಿಯಗೊಳಿಸಿ** ಕ್ಲಿಕ್ ಮಾಡಿ
- **API:** ನಿರ್ವಹಣಾ ದೃಢೀಕರಣ ಹೆಡರ್ಗಳೊಂದಿಗೆ `DELETE /api/resilience/model-cooldowns`

### Command Code ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವು 403 ದೋಷದೊಂದಿಗೆ ವಿಫಲವಾಗುತ್ತದೆ

**ಲಕ್ಷಣಗಳು:**

- Command Code ಪೂರೈಕೆದಾರರ ಸಂಪರ್ಕವನ್ನು ಪರೀಕ್ಷಿಸುವಾಗ 403
- ಹೊಸದಾಗಿ ಸೇರಿಸಿದ ನಂತರ ಪೂರೈಕೆದಾರರ ಕಾರ್ಡ್ "ಅಧಿಕೃತವಾಗಿಲ್ಲ" ಎಂದು ತೋರಿಸುತ್ತದೆ

**ಕಾರಣ:** OAuth ಪ್ರಕ್ರಿಯೆ ಪೂರ್ಣಗೊಂಡಿಲ್ಲ (ಕಾಲ್ಬ್ಯಾಕ್ ಸ್ವೀಕರಿಸಲಾಗಿಲ್ಲ ಅಥವಾ ಟೋಕನ್ ಉಳಿಸಲಾಗಿಲ್ಲ).

**ಪರಿಹಾರ:**

- OAuth ಪ್ರಕ್ರಿಯೆಯನ್ನು ಪುನಃ ಪ್ರಚೋದಿಸಲು CLI ಮೂಲಕ `omniroute providers` ಚಲಾಯಿಸಿ, ಅಥವಾ
- **ಡ್ಯಾಶ್ಬೋರ್ಡ್ → ಪೂರೈಕೆದಾರರು → Command Code → ಮರುಸಂಪರ್ಕಿಸಿ** ಮೂಲಕ OAuth ಅನ್ನು ಪುನಃ ಚಲಾಯಿಸಿ

### ModelScope ತೀವ್ರವಾದ 429 ಕೂಲ್ಡೌನ್ಗಳನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಲಕ್ಷಣಗಳು:**

- ವಿನಂತಿಗಳ ಸಣ್ಣ ಬರ್ಸ್ಟ್ ನಂತರ ModelScopeನಲ್ಲಿ ಬಹಳ ಚಿಕ್ಕ ಅಥವಾ ತಕ್ಷಣದ ಕೂಲ್ಡೌನ್ಗಳು
- ನಿರೀಕ್ಷೆಗಿಂತ ಮುಂಚೆಯೇ ಸಂಯೋಜಿತ ರೂಟಿಂಗ್ ModelScope ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ

**ಕಾರಣ:** ModelScope ಪೂರೈಕೆದಾರ-ನಿರ್ದಿಷ್ಟ `Retry-After` ಹೆಡರ್ಗಳನ್ನು ಹೊರಸೂಸುತ್ತದೆ. v3.8.0 ಆ ಹೆಡರ್ಗಳಿಗಾಗಿ ಮೀಸಲಾದ ನಿರ್ವಹಣೆಯನ್ನು ಒಳಗೊಂಡಿದೆ; ಆದ್ದರಿಂದ ಹಳೆಯ ಆವೃತ್ತಿಗಳು ಅವುಗಳನ್ನು ಸಾಮಾನ್ಯ ದರ-ಮಿತಿ ಸುಳಿವುಗಳೆಂದು ತಪ್ಪಾಗಿ ಅರ್ಥೈಸುತ್ತವೆ.

**ಪರಿಹಾರ:**

- ನೀವು v3.8.0 ಅಥವಾ ನಂತರದ ಆವೃತ್ತಿಯಲ್ಲಿದ್ದೀರಿ ಎಂಬುದನ್ನು ಖಚಿತಪಡಿಸಿಕೊಳ್ಳಿ
- **ಸೆಟ್ಟಿಂಗ್ಗಳು → ಸ್ಥಿತಿಸ್ಥಾಪಕತ್ವ** ಅಡಿಯಲ್ಲಿ `useUpstream429BreakerHints` ಟಾಗಲ್ ಸಕ್ರಿಯವಾಗಿದೆ ಎಂಬುದನ್ನು ಪರಿಶೀಲಿಸಿ

### ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ OMNIROUTE_WS_BRIDGE_SECRET ಕಾಣೆಯಾಗಿದೆ

**ಲಕ್ಷಣಗಳು:**

- ದೂರಸ್ಥ ಉತ್ಪಾದನಾ ಹೋಸ್ಟ್ನಲ್ಲಿ ಚಲಾಯಿಸುವಾಗ ಪ್ರತಿಯೊಂದು Codex/Responses WebSocket ಬ್ರಿಡ್ಜ್ ವಿನಂತಿಗೂ 401
- ಸಂಪರ್ಕಗೊಂಡ ತಕ್ಷಣ WebSocket ಬ್ರಿಡ್ಜ್ ಹ್ಯಾಂಡ್ಶೇಕ್ ಮುಚ್ಚುತ್ತದೆ

**ಕಾರಣ:** ಉತ್ಪಾದನಾ ಪರಿಸರದಲ್ಲಿ `OMNIROUTE_WS_BRIDGE_SECRET` env var ಕಾಣೆಯಾಗಿದೆ.

**ಪರಿಹಾರ:**

1. ಯಾದೃಚ್ಛಿಕ ರಹಸ್ಯವನ್ನು ರಚಿಸಿ: `openssl rand -hex 32`
2. ಉತ್ಪಾದನಾ ಸರ್ವರ್ envನಲ್ಲಿ (ಮತ್ತು ಬ್ರಿಡ್ಜ್ನೊಂದಿಗೆ ಸಂವಹನ ನಡೆಸುವ ಯಾವುದೇ ಕ್ಲೈಂಟ್ನಲ್ಲೂ) `OMNIROUTE_WS_BRIDGE_SECRET=<random-secret>` ಅನ್ನು ಹೊಂದಿಸಿ
3. OmniRoute ಅನ್ನು ಮರುಪ್ರಾರಂಭಿಸಿ

### Responses API: ಹಿನ್ನೆಲೆ ಮೋಡ್ ಸಿಂಕ್ರೊನಸ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಗೆ ಇಳಿಸಲಾಗಿದೆ

**ಲಕ್ಷಣಗಳು:**

- ಲಾಗ್ ಮಾಡಲಾದ ಎಚ್ಚರಿಕೆ: `background mode degraded to synchronous`
- `background: true` ವಿನಂತಿಯು ಹಿನ್ನೆಲೆ ಜಾಬ್ ಹ್ಯಾಂಡಲ್ ಬದಲಿಗೆ ಸಾಮಾನ್ಯ ಸಿಂಕ್ರೊನಸ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ

**ಕಾರಣ:** v3.8.0 ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ Responses API ಯಲ್ಲಿನ `background: true` ಅನ್ನು ಸಿಂಕ್ರೊನಸ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಗೆ ಇಳಿಸುತ್ತದೆ ಮತ್ತು ಎಚ್ಚರಿಕೆಯನ್ನು ಹೊರಸೂಸುತ್ತದೆ. ಪೂರ್ಣ ಅಸಿಂಕ್ ಹಿನ್ನೆಲೆ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆಯು ಭವಿಷ್ಯದ ವಿತರಣೆಯಾಗಿದೆ.

**ಪರಿಹಾರ:**

- `background` ಇಲ್ಲದೆ ಕರೆ ಮಾಡಲು ಕ್ಲೈಂಟ್ ಅನ್ನು ಹೊಂದಿಸಿ, ಅಥವಾ
- ಪೂರ್ಣ ಅಸಿಂಕ್ ಹಿನ್ನೆಲೆ ಮೋಡ್ ಅನ್ನು ಒಳಗೊಂಡಿರುವ ನಂತರದ ಬಿಡುಗಡೆಗಾಗಿ ಕಾಯಿರಿ (ಚೇಂಜ್ಲಾಗ್ ಅನ್ನು ಗಮನಿಸಿ)
